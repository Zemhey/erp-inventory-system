## 1. 契约工作流（强制）

```
① 改 openapi.yaml（唯一入口）
        ↓ 生成
② 服务端接口骨架（springdoc 双向校验，防止实现与契约漂移）
        ↓ 生成
③ 三端 SDK（TypeScript client，Web/小程序/Android 共用）
        ↓ 驱动
④ 契约测试（OpenAPI schema 校验 + Pact）
        ↓ 白捡
⑤ Schemathesis 属性测试（自动生成边界参数）
        ↓ 产出
⑥ index/api-map.md（代码索引）
```

**CI 门禁**：实现导出的 OpenAPI **与**契约源做 diff，**不一致则构建失败**。

## 2. REST 约定

| 项 | 约定 |
|---|---|
| 基础路径 | `/api/v1` |
| 资源命名 | 复数、小写连字符：`/purchase-orders` |
| 动作 | 状态变更用子路径：`POST /purchase-orders/{id}/receive` |
| 分页 | `?page=1&size=20`；响应含 `total`, `page`, `size` |
| 参数避让 | 资源自身也有 `size` 字段时（SKU 尺码），筛选参数必须换名（本项目为 `skuSize`），**禁止与分页 `size` 同名** —— 同名会让 Spring 静默忽略其中一个 |
| 过滤 | `?status=APPROVED&warehouseId=1` |
| 排序 | `?sort=createdAt,desc` |
| 时间格式 | ISO-8601（`2025-06-01T10:00:00+08:00`） |
| 金额 | **JSON 中为整数（分）**，字段名以 `...Amount` 结尾 |
| 字段命名 | 小驼峰：`onHandQty`, `requestId` |
| 版本 | URL 版本；破坏性变更必须升版本 |

## 3. 统一响应结构

```json
// 成功
{ "code": "OK", "message": "success", "data": { ... } }

// 分页
{ "code": "OK", "data": { "items": [...], "total": 137, "page": 1, "size": 20 } }

// 失败
{ "code": "INV_INSUFFICIENT_STOCK", "message": "库存不足：SKU 1001 在 上海仓 可用量 3，需求 5",
  "details": { "skuId": 1001, "available": 3, "required": 5 },
  "traceId": "a1b2c3d4", "timestamp": "2025-06-01T10:00:00+08:00" }
```

**约定**：
- HTTP 状态码表达**类别**（400/401/403/404/409/422/500），**业务码表达具体原因**；
- 业务错误一律用 4xx，**不用 200 包错误**（否则契约测试和监控都失效）；
- `traceId` 贯穿日志 → 测试失败可直接用它捞日志（自动化测试的价值就在这里）；
- 错误消息**必须包含定位信息**（哪个 SKU、哪个仓、差多少）—— 这是"商业系统"与玩具的差别，也让测试断言更容易写。

### 4.1 幂等键分列（已落地的实践，M4/M5 多端必须沿用）

`X-Request-Id` 是**请求级**幂等键（必填 header，见 §5.1 与 §6 的自动边界测试），
而一张单据上往往有**多个**需要幂等的动作。
本项目的做法是：**不同动作的键分列存储，各自有自己的唯一约束** —— 这样
① 同一动作重放一定命中唯一索引；② 同一张单的不同动作用到相同键值也不会被误判成重复提交。

| 动作 | 键 | 唯一约束 | 命中后的行为 |
|---|---|---|---|
| 退货单建单 | `return_orders.request_id` | 部分索引 `uq_ro_request`（`WHERE request_id IS NOT NULL`） | 相同键 → 直接返回首次建成的单据（不报错） |
| 退货单入库 | `return_orders.receive_request_id` | 部分索引 `uq_ro_receive_request` | 已完成 + 同键 → 幂等返回原单；已完成 + **新键** → `RMA_STATUS_ILLEGAL`；并发抢同一键 → 唯一索引拦住后来者并翻译成 `SYS_DUPLICATE_REQUEST`，本事务的库存增量一并回滚 |
| 库存流水 | `inventory_ledger.request_id` | `uq_ledger_request (request_id, biz_type, batch_no)` | 允许一次请求拆多批次（FEFO），**同批次**重放才拒绝。退货入库还按行派生键（`requestId + ":L" + lineNo`），避免多行空批次互相判重 |
| 预占 | `inventory_reservations.request_id` | `uq_reservation_request` | 同一 `request_id` 只能有一条预占记录（不变量 INV-9） |
| 进货 / 出货建单 | `purchase_orders.request_id` / `sales_orders.request_id` | `uq_po_request` / `uq_so_request` | 建单幂等（部分索引） |
| 日清 | **业务维度键** `(biz_date, warehouse_id)` | `uq_daily_settlement` | `INSERT .. ON CONFLICT (biz_date, warehouse_id) DO UPDATE SET .. = EXCLUDED..`，语义是「等于本次重算值」而**不是累加** → 并发日清既不报唯一冲突，也不会把当天的账算成两倍。`daily_settlements.request_id` 只记录最近一次执行的键用于排障，**不参与幂等** |
| 月结 | `settlement_periods.version`（乐观锁）+ `period` 主键 | 首锁用 `ON CONFLICT (period) DO NOTHING` 落行；改已有期间用 `UPDATE .. WHERE period = ? AND status = 'OPEN' AND version = ?` | 并发月结只有 `version` 匹配的一方锁账成功；`DO NOTHING` 返回 0 行 = 干净的"你来晚了"（PG 里语句报错会把事务打成 aborted，所以不用 try/catch），后到者重读同一份已锁账汇总并返回 `duplicate=true`；重算不一致才抛 `SET_ALREADY_SETTLED` |

**三条约定**（多端最容易做错的地方）：

1. **一个动作一个键值，别在同一张单的不同动作间复用同一个 `X-Request-Id`**。
   退货建单键与入库键分列（`request_id` / `receive_request_id`）正是为了让"建单后立刻入库"
   这类连点不会互相判重，而"同一动作重复提交"一定判得中。
2. **幂等靠数据库唯一约束，不靠应用层先查后写**（读后写窗口在并发下必然双写）。
   退货量累加走条件 UPDATE，日清走 `ON CONFLICT DO UPDATE`，月结走 `version` 条件 UPDATE。
3. **日清的键是业务维度而不是请求头** → 多端同时点"日清同一天同一仓"天然收敛成同一行。
   小程序/Android（M4/M5）**不要**给日清造一个"每次点击一个新 requestId"的实现。

> 出处：`V1__init_inventory_slice.sql`（流水/预占）、`V2__mdm_and_documents.sql`（建单）、
> `V4__rma.sql`（退货两键）、`V5__settlement.sql`（日清唯一行 + `version` 乐观锁）、
> `ReturnOrderApplicationService`、`DailySettlementRepository`、`SettlementPeriodRepository`。

### 4.2 与历史文档的命名差异（已核对枚举，别再照旧写法实现）

旧版本节列过这些**代码里根本不存在**的码。它们只出现在文档里，从未出现在枚举、
异常抛出点或契约测试中 —— 按旧写法实现会凭空造码：

| 旧文档写法 | 实际状态 | 应对应 |
|---|---|---|
| `AUTH_INVALID_CREDENTIALS` | 不存在 | `IAM_BAD_CREDENTIALS` |
| `AUTH_TOKEN_EXPIRED` | 不存在（未单独区分"过期"与"无效"） | `IAM_UNAUTHENTICATED` |
| `AUTH_ACCOUNT_LOCKED` | 不存在 | `IAM_ACCOUNT_LOCKED`（423） |
| `PERM_DENIED` | 不存在 | `IAM_FORBIDDEN` |
| `PERM_DATA_SCOPE_DENIED` | 不存在；数据权限本身是 `FR-IAM-03`，尚未实现 | 无对应实现，**不要写进代码或契约** |
| `RMA_ORIGIN_ORDER_REQUIRED` | 不存在。"缺原出货单"属参数校验 | `SYS_VALIDATION_ERROR`（400）；原单不可退另见 `RMA_ORIGIN_NOT_SHIPPED` |
| `SAL_AMOUNT_MISMATCH` | 不存在。金额一律由后端从明细行派生，不接受客户端传入总额，因此没有"金额不一致"这条拒绝路径 | 无对应实现，**不要臆造** |

> 命名口径：**认证与权限统一用 `IAM_` 前缀**（对齐 FR 编号 `FR-IAM-*`），不再有 `AUTH_` / `PERM_` 两套前缀。
> 另有一个**不属于枚举**的码值得注意：兜底分支返回的 `SYS_INTERNAL_ERROR` 是
> `GlobalExceptionHandler` 里的字符串字面量（未预期异常 → 500），枚举中没有它。
> 前端把任何非 `OK` 的码都当字符串展示，因此它不会引起解析问题，但**不要把它当成可断言的业务码**。

### 5.1 契约样例片段（出货：库存不足场景）

```yaml
paths:
  /sales-orders/{id}/ship:
    post:
      summary: 出货确认（预占转出库）
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer, format: int64 }
        - name: X-Request-Id          # ★ 幂等键
          in: header
          required: true
          schema: { type: string, minLength: 8, maxLength: 64 }
      responses:
        '200':
          description: 出货成功
          content:
            application/json:
              schema: { $ref: '#/components/schemas/ApiResponse' }
        '409':
          description: 库存不足
          content:
            application/json:
              schema: { $ref: '#/components/schemas/ApiError' }
              examples:
                insufficientStock:
                  value:
                    code: INV_INSUFFICIENT_STOCK
                    message: "库存不足：SKU 1001 在 上海仓 可用量 3，需求 5"
                    details: { skuId: 1001, warehouseId: 1, available: 3, required: 5 }
```

> 注意 `X-Request-Id` **是一个必填 header** —— 幂等不是可选项，它是契约的一部分。
> 这样 Schemathesis 会自动测缺失/超长/非法 requestId，白捡一批用例。
