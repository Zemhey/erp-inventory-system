# V4 · 自然语言目标级工具（composite intent）与"AI 复核 + 人决定 + 可回溯"计划书

> **术语更正（2026-10-27）**：初稿把这一节叫"双 AI 审核闸门"，容易被读成"两个 AI 各投一票"。
> 实际设计是**三级**：AI 执行 → AI 复核（只出意见）→ **人决定（唯一有权放行的一方）**。
> 所谓"双审核"指的是 **AI 复核 + 人确认** 这两道，不是两个 AI。决定层永远在人。

> 版本：V4-草案（2026-10-26）
> 前置文档：`docs/自然语言操作的两种形态与风险分析.md`（能力边界与风险）
> 状态：**FR-V4-01 已落地并实测通过**；FR-V4-02 ~ 04 为设计，未实现。

---

## 0. 这一版要解决的真问题

上一版的分析得出一个尴尬结论：当前 NL 层"一句话查一件事、一句话起一张草稿"，
**拿不到老师说的"几小时压成几分钟"**。原因不是模型不够强，是三处结构性缺口：

| 缺口 | 后果 |
|---|---|
| 一次只能一个意图（无编排循环） | 用户仍要自己把目标拆成多句话，等于把编排工作还给了人 |
| 写操作止步草稿 | Agent 跑完 90% 却没跑完，人还得回页面点最后几下 |
| 没有目标级工具 | 所有工具都是"原子动作"，没有一个对应"一个目标" |

V4 的定位：**先把"目标级只读工具"做出来（零风险、可立刻演示），
再把"有副作用的操作"在「AI 复核 + 人决定 + 可回溯」的框架下放开到 L2。**
不做通用 Agent 平台，不做开放式问答，不改既有 RBAC 模型。

## 1. 目标与非目标

**目标**

| 编号 | 目标 | 验收口径 |
|---|---|---|
| G1 | 用户说"一个目标"，系统一次给"一个结论 + 依据" | 至少 1 个 composite 意图端到端可用 |
| G2 | composite 意图**不复制业务逻辑** | 与页面同源：同一 ApplicationService、同一公式 |
| G3 | 让"AI 代执行"的错误**可逆** | 任何写操作都有对应的补偿动作，或被限制在可删除的草稿态 |
| G4 | 让 AI 的错**先被另一个 AI 挑出来，再由人拍板** | 复核层只出意见（通过/需人工/否决），放行必须人工点击 |
| G5 | 全过程可回放 | 每次指令留下 actor / intent / 参数 / 结果 |

**非目标（明确不做）**

- 不做"删除 / 作废 / 改历史账"的 NL 通路（见分析文档 §5：意图集合是封闭的，这是设计而非疏漏）。
- 不做多轮会话上下文（"刚才那单再加 10 件"）——属架构级改动，收益低于成本。
- 不让复核 AI 拥有"批准即执行"的权力（原因见 §4.4，这是本方案的安全底线）。
- 不引入工作流引擎（BPMN / Camunda）；用一张审计表 + 状态机足够。

## 2. FR-V4-01 目标级工具：`replenish_advice`（✅ 已落地）

### 2.1 为什么选它做第一个

- **只读**：不建单、不预占、不落表，天然幂等，出错也没有副作用 → 可以先跑起来给老师看。
- **原本是多步**：要查可用量、查在途采购、比上下限、按公式算差额，人要在三个页面之间来回。
- **逻辑已经存在**：页面上早有「补货建议」（`GET /inventory/replenishment`），
  NL 只是给它加了一个入口——这正好证明"NL 层不承载业务规则"这条架构约束是守得住的。

### 2.2 实现（已合入）

| 层 | 改动 | 关键点 |
|---|---|---|
| 意图枚举 | `NlIntent.REPLENISH_ADVICE("replenish_advice", false)` | 放在读意图之后、写意图之前；`write=false` |
| 解析器 | `StubNlCommandParser` 新增分支 | 关键词：补货 / 该补 / 要补 / 需补 / 补什么 / replenish；参数 `warehouseId` |
| 调度器 | `NlCommandDispatcher.replenishAdvice()` | `access.require("inv:read")` → `insights.replenishment(warehouseId)` → 装盘 |
| 权限 | 复用 `inv:read` | 与页面「补货建议」按钮同一权限，不新增权限码 |
| LLM 工具 | `nl/openai-tools.json` 新增 function | 让 `erp.nl.parser=openai` 也能吐出这个意图 |
| 契约 | `openapi.yaml` 意图 enum + 422 示例 | 契约是单一事实源（ADR-0008） |
| 前端 | 示例 chip「补货建议」+ 说明区「能查」+ 列头中文名 | 结果表不再显示 `suggestedQty` 这种字段名 |
| MCP | `tools.ts` 的 `nl_command` 描述 | Agent 侧能看到这个能力 |

### 2.3 返回结构

```json
{
  "intent": "replenish_advice",
  "description": "补货建议（全部仓库）：1 个 SKU 需补，合计建议补货 70 件",
  "write": false,
  "data": {
    "total": 1,
    "totalSuggestedQty": 70,
    "items": [
      { "skuId": 629, "warehouseId": 421, "availableQty": 620,
        "minLevel": 640, "maxLevel": 770, "suggestedQty": 70, "warehousePriority": 10 }
    ]
  }
}
```

`items` 是 `ReplenishmentSuggestion` 记录原样序列化——**不在这里另造 DTO**，
否则"页面算的"和"NL 算的"迟早对不上。

### 2.4 实测（2026-10-26，本机）

| 指令 | 结果 |
|---|---|
| `补货建议` | ✅ 1 个 SKU 需补，合计 70 件 |
| `该补什么货` | ✅ 同上（关键词识别） |
| `补货建议 仓库 421` | ✅ 只返回该仓的建议 |
| `补货建议 仓库 1` | ✅ 0 条（该仓无需补货，属正常空结果） |
| `查询库存` 等原有 8 个意图 | ✅ 无回归 |

### 2.5 已知局限

- 只返回"该补多少"，**不直接生成采购草稿**。要不要一键转草稿属于写操作，见 §4。
- 建议量为 0 的 SKU 不出现（公式返回 null 即跳过），所以"共 1 个 SKU"不代表只有 1 个 SKU 有库存。

## 3. FR-V4-02 后续 composite 候选（按性价比排序）

| 意图 | 一句话 | 内部组合 | 风险 |
|---|---|---|---|
| `stock_aging` 呆滞库存 | "哪些货压了三个月没动" | 库存余额 + 出库流水 + 库龄分档 | 只读 |
| `supplier_scorecard` 供应商表现 | "近半年谁的到货最不准时" | 进货单 + 收货记录 + 质检 | 只读 |
| `customer_receivable` 客户对账 | "A 客户还欠多少，哪几单逾期" | 出货单 + 收款单 + 账期 | 只读 |
| `period_compare` 账期对比 | "这个月比上个月多进了多少" | 两次进销存汇总 | 只读 |
| `replenish_to_draft` 补货转草稿 | "按建议给 421 仓建采购单" | 建议 + 供应商默认值 + 建单 | **写**，需 §4 闸门 |

原则：**先做只读的，把写操作放到闸门完成之后。** 只读 composite 是"AI 替你把账算完"，
写 composite 是"AI 替你签字"，两者的安全要求不是一个量级。

## 4. FR-V4-03 分级审核：AI 执行 → AI 复核 → **人决定**

### 4.1 三级分工，一级都不能省

```
用户一句话
   ↓  ①  执行 AI：听懂 → 选意图 → 填参数 → 生成结构化 Plan
[Plan]  { intent, args, 影响预演, 补偿动作 }
   ↓  ②  AI 复核（第一道审核）：只看 Plan，出意见
[意见]  APPROVE（我不反对） / NEED_HUMAN（我看不懂或风险高） / REJECT（我确定有问题）
   ↓  ③  人决定（第二道审核，唯一有权放行）：看 Plan + 意见 → 确认 / 驳回
[执行]  落库 + 写审计
```

| 层 | 是谁 | 能不能放行 | 作用 |
|---|---|---|---|
| ① 执行 | AI | 不能 | 把人话变成可执行的结构化计划 |
| ② 复核 | **另一个** AI 实例 | **不能** | 挑错、标风险、把"我不确定"显式说出来 |
| ③ 决定 | **人** | **能，且只有人能** | 拍板 |

**为什么复核必须是另一个实例**：同一个模型同时"提方案"和"查方案"，会为自己的错误找理由——
它检查的是"我是不是按我说的做了"，而不是"我说的对不对"。换一个独立实例（不同 prompt、
只喂结构化 Plan、看不到用户原话）能打断这种自我确认。这在工程上等价于"双人复核"，
只是复核者从同事换成了另一个模型。

### 4.2 什么操作需要审核：读不审，有副作用才审

| 操作 | 有没有副作用 | 走审核吗 | 为什么 |
|---|---|---|---|
| 查库存 / 查单据 / 汇总 / 主数据 | 无 | **不走** | 查错了最多是"答案不对"，重问一次就行，挡它只会变慢 |
| **目标级只读**（补货建议、呆滞库存、客户对账） | 无 | **不走** | 同上。这类恰恰是"AI 省时间"最该先做的，不该被审核拖住 |
| 建草稿（进货单 / 出货单） | 有，但可删 | **轻审**：AI 复核 + 人一眼扫过 | 草稿不产生账务、不动库存，删掉即无痕 |
| 提交 / 审核 / 驳回 | 有，且难逆 | **必须**人确认 | 状态流转会推动后续流程 |
| 入库 / 出库 / 预占 | 有，只能红冲 | **必须**人确认 + 影响预演 | 动的是账和货 |
| 删除 / 作废 | 不可逆 | **不开放给 AI** | 见分析文档 §5：意图集合是封闭的 |

> 你说的这一点是对的，而且很重要：**"只是查看"不该有审核成本。**
> 审核闸门只在"会产生副作用"的时候才落下，否则就是把效率又还回去了。

### 4.3 复核 AI 具体看什么、说什么

| 检查项 | 例子 | 输出 |
|---|---|---|
| 参数完整性 | 建单缺供应商 / 明细为空 | REJECT |
| 参数合理性（数量级） | 单价 1 分、数量 999999、金额是上月 100 倍 | NEED_HUMAN |
| 业务前置条件 | 该 SKU 在该仓不可用、客户已停用、账期已锁 | REJECT |
| 影响面 | 涉及 > N 张单据 / 金额 > 阈值 | NEED_HUMAN |
| 越权 | Plan 的动作超出当前账号权限 | REJECT |
| 意图一致性 | 用户说"查"，Plan 里却出现写动作 | REJECT |

这三档输出刻意设计成**不对称**的：`REJECT` 直接挡住，`APPROVE` 什么都不代表，
`NEED_HUMAN` 是人最该看的——它等于 AI 在说"我看不懂，别让我替你决定"。

### 4.4 复核 AI 的权限边界（安全底线）

> **复核 AI 只能"否决"和"降级"，不能"授权"。**

- `APPROVE` 的含义是"我不反对"，**不是通行证**——放行永远要人点那一下。
- 理由：如果 AI 的通过就等于执行，等于把决策权交给了模型；两个模型一起错时，就没人拦得住了。
- 换句话说，复核层是**减速带**，决定层才是**红绿灯**。

### 4.5 审核结果在哪里显示（这一层不能只存在后端）

| 落点 | 显示什么 | 什么时候出现 |
|---|---|---|
| **操作台结果区**（现有 `.nl-result`） | 结果 + 一个审核状态标记：`已执行` / `待人工确认` / `已否决（附理由）` | 每次指令后 |
| **待确认队列**（新页面：`/nl/pending`） | Plan 摘要 + 影响预演 + 复核意见 + 「确认执行 / 驳回」按钮 | 有 NEED_HUMAN 时进入 |
| **工作台待办**（复用现有「待办概况 / 最近的待审批」） | 待确认数量、最久等待时长 | 常驻，有就显示 |
| **审计记录**（`/nl/audit`，或挂在系统工具下） | 谁、什么时候、说了什么、Plan 是什么、谁批的、结果如何 | 事后追查 |

三条显示原则：
1. **不要让"待确认"只活在数据库里**——人看不见就等于没审。
2. 复核意见必须能**点开看理由**，而不是只给一个红色图标。
3. 被 `REJECT` 的指令也要留痕：**"被挡住了什么"本身就是审计价值**。

### 4.6 为什么不让一个更强的模型替代两个普通模型

- 更强 ≠ 不会犯这一类错：参数错位、数量级错误是**结构性**的，不是能力问题。
- 双实例的价值在于**视角独立**，不是能力叠加。
- 成本上，复核只读一段 JSON、输出一个三选一，token 消耗远小于执行侧。

### 4.7 S3 已落地：计划预览 + 人确认（2026-10-27）

**接口** `POST /api/v1/nl/plan`（只生成计划，不执行）。返回 `NlPlan`：

| 字段 | 作用 |
|---|---|
| `requiresReview` | 是否必须人确认。只读恒为 false（读不审），写操作恒为 true |
| `executable` | 参数是否完整到能执行；false 时看 `blockers` |
| `summary` | 一句话摘要，例如"将创建进货单草稿：杭州面料供应商 → 上海主仓，1 行，合计 ¥120.00" |
| `impact` | 影响预演，`{label, value}` 列表，前端直接渲染成两列表格 |
| `warnings` | 不阻止执行但要人注意的点（单价 < 1 元、数量 > 1 万、对象已停用、大额单据…） |
| `blockers` | 阻止执行的原因（缺参数、id 不存在…），一次列全，不用"改一句试一次" |

**前端闭环**：写意图 → 出「待你确认」计划卡（摘要 / 影响 / 步骤 / 警告 / 阻塞）→ 人点「确认执行」才调 `/nl/command`。
只读意图不出卡，直接执行。

**两个顺带做对的细节**

1. **金额不自己算**：预览调用 `PurchaseOrderApplicationService.lineAmount` /
   `SalesOrderApplicationService.lineAmount`（后者本来就是 public static，前者这次从内联乘法抽出来）。
   否则迟早出现"预览 ¥100、建出来 ¥98"。
2. **权限只写一遍**：新增 `NlPolicy` 统一"意图 → 权限码 / 是否需审核"，
   `/nl/plan` 与 `/nl/command` 共用。`NlCommandDispatcher` 也从"每个分支各自 require"改为**入口判一次**
   —— 分散判最容易在加新意图时漏掉，而漏判的后果是越权。

**实测（2026-10-27，admin）**

| 指令 | 结果 |
|---|---|
| `创建进货单 供应商=1 仓库=421 SKU=629 数量=10 单价=1200` | ✅ 计划可执行、需确认；确认后建出 `PO20261027-0001`（DRAFT） |
| `创建进货单` | ✅ `executable=false`，3 条 blockers（缺供应商/仓库/明细） |
| `创建进货单 供应商=9999 …` | ✅ blocker「供应商不存在：id=9999」 |
| `创建进货单 … 数量=20000 单价=50` | ✅ 2 条警告（单价 ¥0.50 偏低、数量 20000 偏大），仍可执行 |
| `补货建议` | ✅ `requiresReview=false`，不出计划卡，直接返回结果 |

**S3 阶段的已知缺口（已在 S4 补上，保留记录）**

> S3 时"人确认"只是前端约定：Agent 绕过 `nl_plan` 直接调 `nl_command` 仍能建草稿。

S4 已把它挪到服务端（见 §4.8）：**写意图缺少合法回执一律 409，不管调用方是页面、豆包还是自研脚本。**
所以从 S4 起，本节的说法才从"预览 + 提示"变成真正的"拦截"。

### 4.8 S4 已落地：复核层 + 服务端确认闸门（2026-10-27）

#### ① 复核层：谁在看，看什么，能做什么

| 层 | 实现 | 能看到什么 | 能做什么 |
|---|---|---|---|
| 规则复核 | `RuleNlReviewer`（无需模型，永远可用） | 计划 + 用户原话（**仅用于数字比对**） | 否决 / 要求人判断 |
| AI 复核 | `AiNlReviewer`（`erp.nl.reviewer=openai`） | **只有结构化计划**，原话在参数里传进来但一次都不读 | 否决 / 要求人判断 |

合并规则写在 `NlReviewService` 一处：**结论永远取更严格的一方**（`APPROVE < NEED_HUMAN < REJECT`）。
于是"模型说通过"永远不能把规则判定的否决抬回去——这就是 §4.4 那条底线的代码形态。

规则复核刻意只做计划做不到的三件事，不重复计划已有的检查：

1. **自洽性**：写操作却标记"无需人工确认" → 直接否决（这种计划本身就是坏的）；
2. **数字一致性**：把原话里的数字与参数逐一对照。"数量 20000 被抽成 2" 是 AI 最现实的错法，
   而计划服务看不到原话，只有这一层能发现；
3. **业务常识**：独立回查 SKU 零售价（出货价低于零售价 40% / 进货价高于零售价）、校对业务日期。

#### ② 确认闸门：把"人点了确认"变成服务端能验的回执

`/nl/plan` 对写意图签发 `NlConfirmation`：

```
token = base64url(payload) + "." + base64url(HMAC-SHA256(payload, secret))
payload = { v, rid, intent, argsHash, actor, verdict, exp }
```

绑定四样东西，因此四种绕过全部失效：

| 绕过方式 | 撞在哪 |
|---|---|
| 不带凭据直接执行 | `NL_CONFIRM_REQUIRED`（409，响应附计划） |
| 预览 10 件、执行 20000 件 | `NL_CONFIRM_INVALID`（参数哈希不符） |
| 预览查库存、执行建单 | `NL_CONFIRM_INVALID`（意图不符） |
| 借别人的回执 | `NL_CONFIRM_INVALID`（账号不符） |
| 拿着被否决的计划去试 | 复核结论为 `REJECT` 时**不签发**凭据 |

**不落库**：凭据是无状态的（签名即真伪），不需要建表、不需要清理过期记录，
也不会因为"清理任务没跑"留下可重放的旧凭据。审计要记的"谁确认了什么"是 S6 的事，不该由凭据兼职。

**密钥**：`erp.nl.confirm.secret`（`ERP_NL_CONFIRM_SECRET`）。留空则进程启动随机生成
——单机开发够用，**多实例部署必须配置同一个值**，否则 A 签的回执在 B 上会被判伪造。

#### ③ 复核结果在哪看

| 落点 | 显示什么 | 状态 |
|---|---|---|
| 计划卡 | 结论徽标（复核不反对 / 需要你判断 / 复核否决）+ 来源（规则 / 规则+AI）+ 逐条意见（带 `规则`/`AI` 标记） | ✅ 已做 |
| 计划卡「确认执行」 | `REJECT` 时禁用，并写明"复核否决了这条计划：先改指令，这里不会放行" | ✅ 已做 |
| 系统说明 | "AI 复核未启用"这类事实单独放脚注，不混进意见列表 | ✅ 已做 |
| 待确认队列 `/nl/pending` | 待人工确认的条目 | 待 S5 |
| 审计 `/nl/audit` | 谁确认了什么、复核结论是什么 | 待 S6 |

#### ④ 实测（2026-10-27）

闸门六条路径（admin）：

| 场景 | 结果 |
|---|---|
| 写操作无凭据 | 409 `NL_CONFIRM_REQUIRED`，`details.plan` 随响应返回 |
| 预览拿凭据 → 带凭据执行 | 201/200，建出 `PO20261027-0005`（DRAFT） |
| 拿 10 件的回执执行 999 件 | 409 `NL_CONFIRM_INVALID`（参数不一致） |
| 篡改签名 | 409 `NL_CONFIRM_INVALID`（签名校验失败） |
| 只读指令无凭据 | 200，正常返回（读不审） |
| 缺参数的写操作 | `review=REJECT`、`confirmation.required=false`、确认按钮禁用 |

合并规则四条（用本地 mock 模型端点验证，非真实模型）：

| 规则结论 | AI 结论 | 合并后 | 是否签发凭据 |
|---|---|---|---|
| APPROVE | APPROVE | APPROVE（并附"这不等于批准"） | 签发 |
| NEED_HUMAN | REJECT | **REJECT** | 不签发 |
| REJECT | APPROVE | **REJECT**（AI 无法翻案） | 不签发 |
| 只读 | 不调用模型 | APPROVE（`source=RULE`） | 不需要 |

> 注意：本机默认 `erp.nl.reviewer=rule`，即**只跑规则复核**。上面第二、三行是用本地 mock
> 端点把 `AiNlReviewer` 这条链路真正跑通后得到的，不是真实模型的判断质量结论。
> 换上真模型只需配 `ERP_NL_REVIEWER=openai` + `ERP_NL_API_KEY`，代码不用改。

#### ⑤ 仍然存在的边界

- **复核不能替代业务校验**：它只判断"这份计划看起来合不合理"，能不能审、账期锁没锁仍由
  ApplicationService 判。复核是减速带，不是红绿灯。
- **回执不能防"人自己点错"**：它只保证"执行的就是你确认的那一份"，不保证"你确认的是对的"。
- **AI 复核的质量未在此环境评估**：链路通、合并规则对，但模型判得准不准要另做评测集。

### 4.9 S5/S6 已落地：待确认队列 + 操作审计（2026-10-27）

#### ① 为什么必须落一张表

S4 的确认回执是**无状态**的（签名即真伪），代价是"有多少条在等人确认"无处可查。
计划只活在前端内存里，用户关掉页面，那条计划就消失了——而它在后端其实什么都没发生。
**看不见的待确认 = 没审。** 这是本步唯一的存在理由。

表 `nl_execution`（V25 迁移），一行 = 一次"打算做什么"：

| 分组 | 列 |
|---|---|
| 谁/何时 | `actor_id` `actor_name` `source`(WEB/MCP/API) `created_at` |
| 说了什么 | `command_text` `intent` `write_op` `request_id` |
| 当时怎么判 | `plan_json` `review_json` `verdict` `review_source` `summary` `status` |
| 最后怎么了 | `doc_type` `doc_id` `doc_no` `result_json` `error_message` |
| 谁拍板 | `decided_at` `decided_by` `decided_by_name` `expires_at` |

**七个状态**（只有 `PENDING` 进队列）：

```
生成即判定：  参数不全 → BLOCKED      复核否决 → VETOED      其余 → PENDING
PENDING 之后：人确认执行 → EXECUTED / FAILED      人驳回 → DISMISSED      超时 → EXPIRED
```

把"参数不全"和"复核否决"分成两个状态，不是为了好看：事后要能回答
"这条到底是 AI 抽错参数，还是被复核挡下的"。混成一个"失败"，这个问题就永远查不清。

**为什么不塞进 `audit_logs`**：那张表是 append-only 的"已发生事实"，
而这件事有生命周期（PENDING → EXECUTED）。塞进去要么改不动，要么把"待确认"
写成一行永不更新的垃圾。所以与 `audit_logs` 并列单开一张有状态表。
`audit_logs` 的仓储仍受"不得有改删方法"的架构规则约束，本表不受——
它本来就要改状态。类名如实写成 `NlExecutionRepository`（不含 Audit），
不是绕过规则，而是规则守的确实是 `audit_logs`。

#### ② 回填靠的是"回执里的 requestId"

执行时浏览器会生成新的 `X-Request-Id`，用它回填**永远找不到那一行**。
所以 S4 的回执里带了**计划那次**的 rid，`/nl/command` 校验通过后拿它回填。
这也是"打算做什么"与"干了什么"能串成一条线的原因。

#### ③ 两条执行路径，一个执行器

| 路径 | 凭据 | 适用 |
|---|---|---|
| 操作台「确认执行」 | `X-Nl-Plan-Token` | 说话的人顺手确认 |
| 队列「确认执行」 | 记录本身（已 PENDING） | 换个人、换个时间回来拍板 |

两条路都调同一个 `NlCommandDispatcher`，业务校验、权限、幂等完全一致。
**队列不是后门**：它只是"人点确认"的另一种入口。

#### ④ 审核结果显示在哪（S5 的四条落点全部就位）

| 落点 | 现在显示什么 |
|---|---|
| 操作台计划卡 | 结论徽标 + 来源（规则 / 规则+AI）+ 逐条意见，`REJECT` 时确认按钮禁用 |
| **待确认队列 `/nl/pending`** | 时间 / 发起人 / 指令 / 复核结论 / 摘要 / 详情·确认·驳回；详情里有影响预演与全部意见 |
| **工作台待办** | 「待确认操作 N」可点进队列；`null`（无 `sys:read`）时这一格不渲染，而不是显示 0 |
| **操作审计 `/nl/audit`** | 七状态全量，可按 状态/意图/来源/读写/时间 筛；详情看当时快照 |

三条原则仍然守住了：待确认不只在数据库里；复核意见能展开看理由；**被 `REJECT` /
`DISMISSED` / `EXPIRED` 的也留痕**。

#### ⑤ 实测（2026-10-27，admin）

| 场景 | 结果 |
|---|---|
| 预览写指令 | 落一行 `PENDING`，`plan` 快照可解析（7 行影响预演） |
| 队列读取 | `total=1 / pendingCount=1`，`source=WEB` |
| 用回执执行 | 该行转 `EXECUTED`，回填 `PO20261027-0007`、`decidedBy=admin` |
| 执行后队列 | `total=0`（不留在队列里） |
| 驳回 | `DISMISSED`；重复驳回 → 409 `NL_EXECUTION_NOT_PENDING` |
| 缺参数的计划 | 落 `BLOCKED`，**不进队列**，审计里可查 |
| 只读查询 | 不落任何档案（前后 total 相等） |
| 界面 | 队列 3 条、审计 6 条（待确认/不可执行/已驳回/已执行齐全）、筛选"已执行"得 1 条、工作台「待确认操作 3」、0 console error |

#### ⑥ 仍然存在的边界

- **队列的可见范围是"同租户 + `sys:read`"**，没有按数据权限再细分。多租户已隔离，
  但同租户内"谁能看谁的指令"目前只到角色级，没到仓库/客户级。
- **可以确认别人发起的指令**（这是队列的意义），因此"能看队列"仍然不等于"能执行"——
  执行时按意图再判一次（建单要 `pur:create`）。
- **没有"审批流"语义**：这里是一人拍板，不是多级会签。多级要接 `aps` 审批模块，属另一件事。
- **回执与队列行可能短暂不一致**：回执有效期内、队列行已被惰性结转成 `EXPIRED` 时，
  执行成功会把状态**改回 `EXECUTED`**——事实优先于账本。

### 4.10 S7 已落地：只开放"提交"，不开放"审核"（2026-10-27）

计划里写的是"提交/审核"，落地时**故意只做了提交**。这不是没做完，是边界。

#### ① 提交与审核不是一回事

| | 提交 | 审核 |
|---|---|---|
| 业务含义 | 把草稿送到它该去的地方 | 决定它过不过 |
| 谁承担后果 | 发起人（还可以撤回重来） | **签字的人** |
| AI 能做吗 | 能——这是跑腿 | **不能**——这是签字 |

同理，入库 / 出库动的是账和货，必须人看着实物做，也没有开放。
所以 S7 的准确表述是：**AI 可以替你跑腿，不能替你签字。**

#### ② 实现（`submit_document`）

- 权限用**页面上的同一个码**：`pur:submit` / `sal:submit` / `rma:submit`。
  刻意不复用 `*:create`——能起草不等于能把单子送进审批流，很多公司这两个动作是不同人做的。
- 计划阶段只校验两件事：单号填了没有、这张单现在是不是 `DRAFT`。
  "能不能提交"的完整判断仍在 `ApplicationService` 里——NL 层只做**预演**，不复制状态机。
- 执行阶段调 `purchaseOrders.submit(id)` / `salesOrders.submit(id)` / `returnOrders.submit(id)`，
  与页面按钮**同一个方法**。
- 仍然要过三道：权限、人工确认（回执或队列）、审计留痕。

#### ③ 实测（2026-10-27）

| 场景 | 结果 |
|---|---|
| `提交进货单 549`（DRAFT） | 计划可执行、需确认；执行后状态 `SUBMITTED` |
| 重复提交同一张 | 计划阶段就挡住：`只有草稿能提交，这张单当前状态是 SUBMITTED`，`review=REJECT`，不签发回执 |
| 带 `submitted` 状态的单直接执行 | 无凭据 → 409 `NL_CONFIRM_REQUIRED`（提交也走闸门，没有后门） |
| `帮助` | 10 个意图，文案改为"写意图只建草稿或提交待审，审核/入库/出货/作废必须人工" |
| 审计 | `intent=submit_document` 可筛，成功记 `docNo`，被挡的记 `BLOCKED` + blocker 原因 |

#### ④ 为什么"审核"留给人，而且不打算开放

- 审核的产物是**责任**，不是数据。AI 无法承担这个责任，签名也签不了。
- 复核层（S4）能发现"这单看起来不对"，但它判断不了"这笔生意该不该做"——
  那是业务判断，只有人手里的信息（客户关系、账期、返利）够。
- 真要提效，正确方向是**把审核要看的材料备齐**（客户历史价、毛利、账龄、库存），
  而不是替人按下那个按钮。这属于报表/工作台的事，不在 NL 的范围内。

## 5. FR-V4-04 可回溯：让错误"可逆"

### 5.1 先承认一件事：不是所有操作都可逆

| 层级 | 动作 | 可逆性 | 逆操作 |
|---|---|---|---|
| L0 只读 | 查询、汇总、补货建议 | **天然可逆** | 无副作用，不需要逆操作 |
| L1 草稿 | 建进货/出货草稿 | **可逆** | 作废草稿（不动账、不动物流） |
| L2 状态流转 | 提交、审核、驳回 | **半可逆** | 反向流转（审核→驳回），需留痕 |
| L3 库存动作 | 入库、出库、预占 | **难逆** | 红冲（反向单据），不能改原单 |
| L4 破坏性 | 删除、改历史账 | **不可逆** | 无——所以本系统不提供 |

结论：**可逆性不是靠"撤销键"，是靠"把操作限制在可逆的层级上" + "不可逆动作必须有红冲单据"。**

### 5.2 三道防线

**第一道 · 事前：把写操作锁在草稿层（现状）**
AI 只能建 `DRAFT`。草稿不产生账务、不移动库存，删掉即可。这是当前系统最有效的"可逆性"设计——
**不是因为有回滚，而是因为它压根没走出可逆的那一步。**

**第二道 · 事中：执行前快照 + 影响预演**
对 L2 及以上的 Plan，执行前记录"将被修改的对象及其当前状态"（快照 JSON），
并在 Plan 里给出"影响预演"：将改哪几张单、金额合计多少、涉及哪些 SKU。
人看到的不是"要不要执行"，而是"执行会发生什么"。

**第三道 · 事后：补偿动作 + 审计回放**
- 每个写意图在代码里必须声明它的补偿动作（`compensate`），没有补偿动作的意图不许开放给 AI。
- 审计表记录完整链路，支持"按 requestId 回放一次执行"。

### 5.3 审计表设计（草案）

```sql
CREATE TABLE nl_execution_audit (
  id              BIGSERIAL PRIMARY KEY,
  request_id      VARCHAR(64)  NOT NULL,      -- 与 X-Request-Id 一致，贯穿幂等
  tenant_id       BIGINT       NOT NULL,
  actor           VARCHAR(64)  NOT NULL,      -- 发起账号
  client          VARCHAR(32)  NOT NULL,      -- web / mcp / api
  agent_name      VARCHAR(64),                -- Agent 自称的名字（可空，不可信，仅供排查）
  intent          VARCHAR(40)  NOT NULL,
  plan            JSONB        NOT NULL,      -- 执行计划（复核 AI 的输入）
  verdict         VARCHAR(16),                -- APPROVE / NEED_HUMAN / REJECT
  verdict_reason  TEXT,
  confirmed_by    VARCHAR(64),                -- 人工确认者（L2+ 必填）
  result          JSONB,
  snapshot        JSONB,                      -- 执行前快照（可逆依据）
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

设计取舍：
- `agent_name` 标注"不可信"——Agent 自报的身份不能作为权限依据，只能作为排查线索。
- `plan` 与 `result` 分开存：**认证的是计划，不是结果**。事后追责看 plan 才追得清"它当时打算干什么"。
- 不建"执行日志流水表"，避免与既有审计重复；只在 NL 入口多记一条。

### 5.4 回滚能力的诚实边界

| 想做 | 能不能 | 说明 |
|---|---|---|
| 撤销一次错误查询 | 不需要 | 只读无副作用 |
| 撤销一张 AI 建的草稿 | 能 | 作废草稿 |
| 撤销一次已审核的单据 | 部分能 | 走反向流转，留痕，不能"当没发生" |
| 撤销一次入库 | 只能红冲 | 生成一张反向单据，账面留两条记录 |
| "把系统恢复到 10 分钟前" | **不能，也不该做** | 数据库时点恢复会连带抹掉别人的正常操作 |

> 这一步很重要：**"可回溯"不等于"可撤销"**。企业系统要的是"每一步都可查、可解释、可补偿"，
> 而不是"一键回到过去"。后者在多人并发下会制造更大的错误。

## 6. AI 到底是怎么"操作系统"的：它不熟悉系统，也不需要熟悉

### 6.1 它读的不是源码，是"说明书"

MCP / function calling 的本质是：**服务端把能力写成人能读、也能机读的清单**。
Agent 启动时拿到的是这样一份东西（本项目 `nl/openai-tools.json` 的真实片段）：

```json
{
  "name": "query_master_data",
  "description": "查询主数据：商品 / SKU / 供应商 / 客户 / 仓库。",
  "parameters": {
    "type": "object",
    "properties": {
      "type": { "enum": ["PRODUCT","SKU","SUPPLIER","CUSTOMER","WAREHOUSE"] },
      "keyword": { "type": "string" },
      "page": { "type": "integer" }
    }
  }
}
```

模型**不需要**知道页面在哪、表叫什么、SQL 怎么写。它只做两件事：**选函数、填参数**。
"查杭州的供应商" → 它输出 `query_master_data(type=SUPPLIER, keyword=杭州)`。
剩下的——权限、SQL、分页、脱敏——全在服务端。

所以"AI 不熟悉系统"这件事，在架构上被转化成了：**系统有没有把说明书写好**。
说明书烂（描述含糊、参数没约束），AI 就会乱填；说明书写清（枚举、必填、示例），
模型填错的空间很小。

### 6.2 它具体会怎么栽，以及各自的兜底

| 栽法 | 真实表现 | 兜底 |
|---|---|---|
| **编造 id** | 直接写 `supplierId: 7`，而 7 号是别的供应商 | system prompt 明令"不要编造 id"；必填 id 缺失→400；**先查后写**（见 6.3） |
| **选错意图** | "补货"被当成"查库存" | 意图白名单（9 个，编译期闭环）+ 关键词表；识别不到→422 并回可用示例 |
| **抽错参数** | "SKU 5" 抽成 `skuId=50` | 类型/范围校验 + 复核层数量级检查 + 影响预演（人一眼看出不对） |
| **想做的事没有接口** | "帮我把这单审核了" | 没有这个意图 → 直接拒绝，**不会硬凑** |
| **幻觉动作** | 编一个不存在的工具名 | `NlIntent.fromCode()` 返回空 → 422 |

注意最后两条：**"做不到"必须是显式的失败，而不是勉强执行。**
宁可让用户觉得"它听不懂"，也不能让它"猜着做"。

### 6.3 关键设计：先查后写

人在界面上建单时，id 是界面给的——点一下客户，隐藏域里带着 `customerId`。
AI 没有界面，**它必须自己先把 id 查出来**：

```
"给杭州那个客户建一张出货单"
   ↓ ① 先查：query_master_data(type=CUSTOMER, keyword=杭州) → 拿到 customerId=3
   ↓ ② 再查：query_master_data(type=WAREHOUSE)  → 仓库 421 / 1 / ...
   ↓ ③ 才建：create_sales_order(customerId=3, warehouseId=421, lines=[...])
```

这就是为什么**读工具要开放得比写工具宽**：读是写的前置条件。
也解释了为什么"补货建议"这类只读 composite 是最该先做的——
它既省时间，又天然是"先查"的一半。

### 6.4 业务规则它不用懂，也不该懂

- "这单能不能审核"、"这个 SKU 该不该补"、"账期锁了没有"——**全部由 ApplicationService 判**。
- AI 的价值在**翻译**（人话 → 结构化参数）和**跑腿**（多次调用、循环重试），不在判断对错。
- 一句话分工：**AI 负责跑腿和翻译，系统负责判断，人负责拍板。**

这也是为什么本项目的 ArchUnit 规则要禁止"NL 层依赖 repository"——
一旦 NL 层开始自己算业务，它就从"翻译官"变成了"第二个业务系统"，两边迟早对不上。

### 6.5 系统要为 AI 准备什么（清单）

| 要素 | 现状 | 缺口 |
|---|---|---|
| 自描述工具清单（名字/描述/schema/示例） | ✅ 9 个工具 + `nl_command` | 描述还可以更细（参数约束、单位、取值范围） |
| 可机读错误码 + 正确示例 | ✅ 422 / 400 都带 `支持的意图…示例…` | 可加"最接近的 3 个可用说法" |
| 幂等键 | ✅ `X-Request-Id` + 数据库唯一索引 | — |
| 只读工具宽口径（先查后写的前提） | ⚠️ 部分（缺 SKU 列表的按名查、仓库关键字） | 需要补 |
| 自检入口 | ✅ `system_status` + `help` | — |

## 7. 实施顺序与工作量

| 阶段 | 内容 | 依赖 | 状态 |
|---|---|---|---|
| S1 | `replenish_advice`（目标级只读，**不走审核**） | 无 | ✅ 已完成 |
| S2 | 再补 2 个只读 composite（`stock_aging` / `customer_receivable`），同样不走审核 | S1 模式复用 | 待做 |
| S3 | `POST /nl/plan`：返回结构化 Plan + 影响预演（不执行）；前端「计划卡 → 确认」闭环 | S1 | ✅ 已完成 |
| S4 | 复核层：`POST /nl/review`（规则 + 可选独立模型，只看 Plan）+ **`/nl/command` 服务端确认凭据**（堵住绕过） | S3 | ✅ 已完成（见 §4.8） |
| S5 | **审核结果的显示**：计划卡状态标记 + `/nl/pending` 待确认队列 + 工作台待办计数 | S4 | ✅ 已完成（见 §4.9） |
| S6 | 审计表 `nl_execution` + `/nl/audit` 查询与详情（含被否决/被驳回的留痕） | S3 | ✅ 已完成（见 §4.9） |
| S7 | 受限 L2：**只开放"提交"**（`submit_document`），"审核"仍归人 | S4/S5/S6 | ✅ 已完成（范围收窄，见 §4.10） |

S3~S6 都不需要放开任何权限，也不改变现有 9 个意图的行为——**是纯增量**。
S5 单列出来，是因为"审核结果只存在后端"等于没审：人要看得见，才叫决定层。

## 8. 验收标准（DoD）

- [x] 一句话"补货建议"返回建议清单 + 依据字段，且与页面「补货建议」数字一致。
- [x] composite 意图不新增业务逻辑（ArchUnit 规则「NL 不得依赖 repository」仍通过）。
- [x] 原有 8 个意图无回归，契约意图 enum 与 `NlIntent` 逐字一致。
- [ ] Plan / Review / Audit 三件套：同一 `request_id` 能串起"打算做什么 → 谁复核 → 谁确认 → 结果"。
- [ ] 待确认队列能显示 Plan、影响预演、复核意见（可展开看理由），并支持「确认执行 / 驳回」。
- [ ] 被 `REJECT` 的指令在审计里可查（被挡住了什么，同样是审计价值）。
- [ ] 任一写意图若没有声明补偿动作，启动时直接失败（fail-fast，而不是运行时才发现不可逆）。

最后一条建议做成**启动期自检**：新增写意图时忘了写 `compensate()`，服务起不来。
把"可逆性"从文档约定变成编译/启动约束——这和项目里已有的 ArchUnit 做法是一致的。

## 9. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 复核 AI 与执行 AI 同源同模型，错误相关 | 闸门形同虚设 | 换模型或至少换 prompt + 只喂结构化 Plan |
| 复核增加一次 LLM 调用延迟 | 交互变慢 | 只对写意图复核；只读意图直通 |
| Plan 的 JSON 结构漂移 | 复核失效 | Plan 用固定 schema + 版本号，变更需改契约 |
| 人养成"看都不看就点确认" | 闸门退化 | 影响预演要给出"差异"而不是"摘要"；超阈值强制二次确认 |
| 审计表膨胀 | 存储与查询变慢 | 按月分区；只存 plan/result 的摘要 + 关键字段 |

## 10. 一句话总结

**V4 不追求"让 AI 更能干"，而是让"AI 干的事可以被检查、被拦住、被补偿"。**
先证明"目标级只读"能省时间（已做到，而且**这类查询不需要审核**），
再证明"有副作用的操作也能安全地交给 AI"（S3~S7，走 AI 复核 + 人决定）。

两条线都不需要放开权限——需要的是把"人点的那串动作"变成"可编排、可审阅、可回放"的服务。

最后记住那条分工，它比任何技术选型都重要：

> **AI 负责跑腿和翻译，系统负责判断对错，人负责拍板。**
