## 0. 一页结论

### 0.1 三句话

1. **规模要对标，但比的是"可用功能面"，不是"表的数量"。**
   参考系统 174 张业务表里，有 40+ 张**没有界面**：它自己在 `_setup/README.md` §七 承认 13 个域"只有数据没有界面"，权限矩阵 61 条资源里有 **22 条无入口**。这种表不产生价值，只产生维护成本。
2. **我们对标它真正强的地方：10 条业务链各自"从起点走到终点"** —— 单据 → 过账 → 流水 → 应收应付 → 核销 → 报表，一条不缺。这才是"像个商业系统"的来源。
3. **我们不抄它弱的地方，并且要比它强一个维度：它没有任何自动化测试框架**（只有 `_probe/` 下的手工探针、无 CI、无 Docker、无单测）。我们是自动化测试项目 —— **同等业务规模 + 全套自动化质量体系**，这才是能写进简历的理由。

### 0.2 规模目标（可验收）

| 维度 | 现在（实测） | 参考系统（实测） | **V2 目标** | 为什么是这个数 |
|---|---|---|---|---|
| 业务表 | 23 | 174（其中 40+ 无界面） | **55~62（推导值 61）** | §4.1 推导：10 条链各补各的表，且**每张表都有界面+端点+测试** |
| 只读视图 | 0 | 121 | **35~45** | 只做有页面消费的报表视图 |
| HTTP 操作 | 50 | 83 | **140~160** | 比它多，因为要服务三端 + 契约先行 + 细粒度动作 |
| 后端模块 | 10 | 14 控制器 | **15** | +`tnt`/`sys`/`prm`/`cst`/`aps` |
| 权限资源 | 28 个码 | 61 资源 × 8 动作 | **50~55 资源 × 6 动作** | 抄它的**矩阵结构**，不抄它的**数量** |
| Web 页面 | 10 | 41 页 / 46 路由 | **36~42 页** | 它 174 表撑 41 页(4.2 表/页)，我们 59 表撑约 40 页(1.5 表/页) —— **每张表都被用起来** |
| 后端用例 | 234 | **0** | **650~780** | 这是我们的主战场 |

### 0.3 不做什么（本文最重要的部分）

> 判定规则见 §3。下面是**已判定"不加"**的清单，理由写在表里，避免以后反复讨论。

| 不加 | 理由（对照参考系统） |
|---|---|
| 174 张表本身 | 它 61 条权限资源里 22 条无入口、13 个域只有表没有界面。**表的数量不是功能** |
| 业务逻辑放存储过程 | 它用 128 个存储过程承载业务规则。我们在 Java 层，单测/集成测试成本低一个数量级。**这是架构优势，不能倒退** |
| GPS 轨迹 / 考勤打卡 / 薪资发放 / 车辆证照 / 离线队列 | 与"进销存 + 自动化测试"无关。它正是有表无界面的反例 |
| 平台订单 / 支付流水认领 / 开放 API 密钥 | 没有真实外部系统可对接，只能造假数据 |
| 复式记账全套（科目/凭证/分录/记账规则/试算平衡/资产负债/利润表） | 那是会计系统，不是进销存。**但"成本与毛利"要** —— 它是经营必需且可测 |
| 报表定义/订阅引擎（元数据驱动报表） | 无底洞。报表用"视图 + 固定页面"就够 |
| 中文表名列名 | 它为 ETL 保真才用中文。我们新建系统，英文 + OpenAPI 契约 |
| 存储过程造一年假数据 | 它用存储过程生成 1.1 万张送气单。我们用种子 + 数据工厂 + 可复现快照 —— **测试要确定性，不是数据量** |
| 多租户的计费/套餐/发票/用量账单 | 只做"隔离"那一半（有测试价值），不做"收钱"那一半（无测试价值），见 §6.9 |

## 2. 关键判断：该抄什么、不该抄什么

### 2.1 要抄的 7 样（"完整"的必要条件）

| # | 抄什么 | 为什么值 | 落到哪个模块 |
|---|---|---|---|
| 1 | **业务链闭环到终点** | 它每条链都走到"凭证/报表"，不是停在"入库成功" | 全部 10 条链，见 §4.2 |
| 2 | **单据通用模式**（主+明细整单提交、单号规则、服务端重算合计） | 一次做好、多类复用 | 已有 `shared/document`，继续复用 |
| 3 | **权限矩阵：资源 × 动作** | 61×8 的粒度比我们 `module:action` 更细，更贴企业 | `iam` + 新增数据权限 |
| 4 | **报表走只读视图** | 报表 SQL 不落在 Java 里，只读聚合天然可测 | `rpt` + PG 视图 |
| 5 | **五维结存**（仓库×SKU×批次×状态×权属） | 真实业务维度，**每个维度都是用例来源** | `inv` 余额表扩展 |
| 6 | **调拨两段式（含在途）** | 两笔流水 + 在途状态，`INV-7 总量守恒` 的天然靶心 | `inv` 调拨 |
| 7 | **单机版交付体验**（一键脚本、端口自动挑、三级回退） | 课程 10% 分值，且它做得很扎实 | M8 已有雏形，V2 复用 |

### 2.2 一条反直觉的结论

参考系统用 **174 张表 + 128 个存储过程** 撑起 41 个页面，平均 **4.2 张表/页**。
我们计划用 **约 58 张表** 撑起约 **40 个页面**，平均 **1.5 张表/页**。

**这不是我们功能少，是我们没有"只建表不建界面"的浪费。** 按"每张表都被用起来"算，58 张全用上的表，功能面不小于 174 张里只有约 130 张被用上的表。

## 3. "不盲目添加"的判定规则（本文的核心）

> 任何功能想进 V2，必须**同时**通过四道闸门。这是硬规则，写进评审。

### 闸门 1：链条闸门 —— 它是否让某条链"从断到通"？

- ✅ 通过：补"应收"让销售链能算出末端的钱；补"调拨"让库存链能跨仓。
- ❌ 不通过：再加一个"商品分类"，商品已有品类字段 —— 它只让某页多一个下拉。

**判定话术**：删掉它，10 条链里哪一条会断？答不出来 = 砍。

### 闸门 2：测试增量闸门 —— 是否带来**新的测试类型或新不变量**？

- ✅ 通过：成本引擎 → `INV-11 成本守恒`；多租户 → 越权矩阵；审批流 → 状态转移穷举。
- ❌ 不通过：再加 5 个档案表 → 只能写 5 组一样的 CRUD 用例。

**判定话术**：它能写的测试，和现有 234 条比，"长得不一样"吗？一样 = 砍。

### 闸门 3：表-界面-测试三件套闸门 —— 新表必须三样齐

> 直接针对参考系统的病：**有表没界面**。

新增一张表时，**同一个 PR 里**必须同时有：
1. 表（Flyway 迁移 + 约束 + 索引）
2. 至少一个端点 + 一个页面（或明确登记"内部表，无端点"并写理由）
3. 至少一条 `@CaseId` 用例

缺一样，PR 不合入。**这条比任何文档都管用。**

### 闸门 4：替代闸门 —— 能不能用已有能力组合出来？

- ✅ 通过：确实需要新的领域概念（如"成本层"）。
- ❌ 不通过：用现有 `customers.discount_rate` + 一条规则就能做"会员等级价"，那不该新建 `price_tiers` 表。

**判定话术**：能不能在已有表上**加列**而不是**加表**？能 = 加列。

### 3.1 一张"被砍掉"的清单（示范判断力）

| 曾想加 | 卡在哪道闸门 | 结论 |
|---|---|---|
| 商品分类树 | 闸门1 ❌ | 现有 `products.category` 够用，砍 |
| 会员积分体系 | 闸门2 ❌ | 只能测"积分增减"，无新不变量，降 P2 |
| 多币种 | 闸门3 ❌ | 让金额断言组合翻倍而无新洞察，砍 |
| 通用工作流引擎（BPMN） | 闸门1+4 ❌ | 只做"单据审批"一种，用 `aps` 轻量实现 |
| 用户自配报表 | 闸门4 ❌ | 视图 + 固定页面已够，砍 |
| 电子签章 | 闸门2 ❌ | 接入即黑盒，无可测收益，砍 |
| 消息中心 / 站内信 | 闸门1 ❌ | 不是任何一条链的断点，砍 |
| 客户 360 视图 | 闸门4 ❌ | 用现有报表拼接即可，不建新模块 |

> **波 A 里刻意"加列不加表"的地方**
> - 采购质检：复用 `purchase_order_lines.qc_status` 列，**不建 `qc_orders` 表**（闸门 4）
> - 客户信用：复用 `customers.credit_limit` + 一张 `customer_credit_snapshots`，不建整套信用模块
> - 批次成本：`inventory_balances` 已有 `batch_no`，成本挂 `cost_layers`，不新建批次主表
> - **补货建议**：只给 SKU 加 `min_level` / `max_level` 两列，**不建 `replenishment_rules` 表**（对标 Odoo 的 reordering rule）
> - **发货选仓**：只给 `warehouses` 加 `priority` 一列，**不建 `allocation_rules` 表**
> - **季节维度**：只给 `skus` 加 `season_code` / `band_code` / `launch_date` 三列，**不建 `seasons` 表**（服装的季节是 SKU 属性；波段 SS/AW 见[竞品对标](竞品对标与业务核实.md) §1.3）

> **61 条不是拍脑袋列的**，来自两处可复核的推导：
> ① 10 条业务链的断点数（上表，59 个功能点）；
> ② [竞品对标](竞品对标与业务核实.md) 找出 10 个差异点，**过四道闸门后只净增 4 项**（其余 6 项并入现有 FR 或判定不加）。
> 第 ② 步恰恰是"不盲目添加"的证据：对标 7 个系统，如果按"别人有就抄"会加 10 个功能，实际只加了 4 个。

### 4.3 与参考系统的逐域对照（哪条链对标哪个域）

| 我们的链 | 它对应域 | 我们刻意不同的地方 |
|---|---|---|
| 主数据 | `md`(9) + `org`(6) | 它 15 条资源；我们约 12 条，砍附件/网点/组织关系 |
| 采购 | `pur`(5) | 对齐，但"质检"做成列而不是单据（少 2 张表） |
| 销售 | `sale`(4) + `dist`(3) | **不抄配送域**（GPS/路线/考核），只做"拣货发货" |
| 库存 | `inv`(5) | 对齐五维结存；"权属"只留自有/客户寄售两种 |
| 逆向 | `sale.return` 单点 | **比它强**：它只有销售退货，我们有换货/退款/质检分流 |
| 成本 | `fin` 一部分 | 对齐移动加权；**不抄复式记账** |
| 结算 | `fin.period` | 对齐月结；加对账差异处置（它有表但无界面） |
| 报表 | `rpt`(4) + 121 视图 | **只做 35~45 个视图**，其余不抄 |
| 平台 | `sys`(7) + `intf`(4) + `mob`(2) | 只抄 `sys`；**不抄集成与移动端设备域** |
| 多端 | 无（单机 Web） | **比它强**：Web+小程序+Android+PDA+单机版 |

## 5. 三期九步路线

> 每期结束都要能答辩、主干全绿。

### 波 A · 把链补全（对齐参考系统的主体功能面）

| 期 | 内容 | 新增表 | 硬性验收 | FR |
|---|---|---|---|---|
| **V2-1** | 库存作业：调拨（在途两段）、盘点、调整、冻结、五维查询、预警、**补货建议** | +6 | **INV-7 调拨守恒**、盘盈亏过账、冻结量不进可用量、补货建议幂等 | INV-07~13 |

### 7.3 三端一致性（设计已有，实现待补）

它的 `_probe/*.mjs` 证明"这些业务值得测"，但每次都要手工跑。
