## 一、项目大纲

### 1.1 项目目标与成功标准

**目标**：一个**真实可用**的服装/鞋帽网店进销存系统 —— 不是演示，一家店真的能用它进货、卖货、查库存。

**成功标准**（按"能不能用"排，不按功能多少排）：

| 维度 | 成功标准 | 当前 |
|---|---|---|
| **数据正确** | 并发下不超卖、重复提交不重复扣减、账实相符 | ✅ 156 条测试守住，含 100 线程抢 50 件的实证 |
| **业务闭环** | 进货→入库→库存→出货→扣减，全链路可跑通 | ✅ 后端完整；Web 端「进货→入库→库存」已用界面跑通，出货页待做 |
| **有人能用** | 运营不用发 JSON，点界面就能完成一件事 | 🚧 M3 已完成 6 / 7 页，剩出货 |
| **能上云** | 有域名、HTTPS、部署脚本，外部可访问 | ⬜ 服务器已有、备案中（M6） |
| **多端** | Web + 小程序 + Android | ⬜ Web 在做，其余 M4/M5 |
| **可交付** | 课程要求的模块全覆盖 | 🚧 见 §2.2 缺口清单 |

> **"大型商业系统"的定义**（沿自 `方向建议与落地路线.md` §0）：
> 不是功能多，而是**订单/库存/金额三者在并发下仍然一致、可对账、可追溯**。
> 这个定义同时就是测试的靶心，也是本项目把工程重心压在这里的原因。

### 1.2 范围边界与非目标

**做什么**（课程要求 + 真实可用）：
采购进货、多仓库存、销售出货、退货入库、日清月结、进销存报表、认证与权限、
Web 端、小程序、Android、云部署、单机版。

**明确不做**（附理由，避免"为什么没做"的反复解释）：

| 不做 | 理由 |
|---|---|
| 微服务拆分 | 单商户规模用不上；`顾客` 数不够，拆了只增加运维负担（ADR-0006） |
| GaussDB | 本地生态差、Testcontainers 镜像缺失，会拖垮自动化测试（ADR-0003） |
| 多租户 SaaS | 本次范围是"一家店能用"；但表结构预留了扩展余地（见 §3.3） |
| 自研前端组件库 | Element Plus 够用，自研是无底洞 |
| 移动端原生重写（除非有余力） | uni-app 一套代码出两端，性价比最高；原生是加分不是必需 |
| H2/内存库做集成测试 | 行为与生产不一致，测试会假绿（ADR-0003 / docs/06） |
| 前端写业务规则 | 规则只在后端一处实现，前端重复实现必然跑偏 |

### 1.3 核心模块与功能分区

```
┌──────────────────────────────────────────────────┐
│  客户端（frontend/）                              │
│  Web(Vue3) · 小程序(uni-app) · Android           │
└───────────────────┬──────────────────────────────┘
                    │ HTTP + OpenAPI 契约（单一事实源）
┌───────────────────▼──────────────────────────────┐
│  服务端（backend/server/）                        │
│  ┌────────┬────────┬────────┬────────┬────────┐  │
│  │  mdm   │  inv   │  pur   │  sal   │  iam   │  │
│  │ 主数据 │ 库存 ★ │ 进货   │ 出货   │ 认证   │  │
│  └────────┴────────┴────────┴────────┴────────┘  │
│              └──── shared（状态机/取号/错误/时钟）│
└───────────────────┬──────────────────────────────┘
                    │
        ┌───────────▼───────────┐
        │  PostgreSQL 16        │
        │  流水=事实源，余额=派生│
        └───────────────────────┘
```

**★ 库存模块是全局枢纽**：所有会改库存的操作（入库、出库、调拨、盘点、退货）
必须经过 `InventoryApplicationService`，禁止任何模块直接写库存表。
这条约束由 ArchUnit 在 CI 强制，不是靠自觉。

### 1.5 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **前端工作量低估** | 7 个页面看似简单，表单+状态机+校验实际很重 | 计划书按 S1~S9 分步，每步可独立提交，避免"全做完才敢提交" |

## 三、项目规划

### 3.1 总体架构与技术路线

| 层 | 选型 | 为什么 |
|---|---|---|
| 后端 | Java 17 + Spring Boot 3.3 | 测试岗 JD 里 Java 出现率最高；事务/锁生态贴"商业系统"（ADR-0002） |
| 数据库 | PostgreSQL 16 | 约束/生成列/行锁语义强；Testcontainers 支持最好（ADR-0003） |
| 前端 | Vue 3 + TS + Element Plus | 国内 ERP 主流；类型检查能在编译期抓契约漂移 |
| 移动端 | uni-app | 一套代码出小程序+H5+APK（ADR-0004） |
| 部署 | Docker + GitHub Actions + 云服务器 | 15% 分值，且 CI 门禁是质量证明的地方 |
| 契约 | OpenAPI 单一事实源 | 驱动服务端/前端 SDK/契约测试/索引（ADR-0008） |

**架构形态**：单体模块化（非微服务）。按业务域分包，域内分层，域间只通过 ApplicationService 调用。

### 3.2 模块划分与边界

| 模块 | 职责 | 边界（谁不能做什么） |
|---|---|---|
| `mdm` | 商品/SKU/供应商/客户/仓库 | 不碰库存 |
| `inv` | 余额/流水/预占/FEFO | **唯一**能改库存的地方 |
| `pur` | 进货单与入库 | 入库必须调 `inv.receiveIn` |
| `sal` | 出货单与出库 | 预占/出货必须调 `inv.reserve` / `shipOut` |
| `iam` | 认证/RBAC | 只管"能不能做"，不管业务 |
| `shared` | 状态机/取号/错误码/时钟 | 无业务依赖，被全体依赖 |

**依赖方向**：`api → application → repository → domain`，反向依赖由 ArchUnit 拦截。

### 3.3 推荐目录结构（已落地）

```
自选/
├── backend/server/          ★ 全部后端
│   ├── src/main/java/com/erp/{mdm,inv,pur,sal,iam,shared}/
│   ├── src/main/resources/db/migration/    Flyway V1~V3
│   └── src/test/java/com/erp/              156 条测试
├── frontend/web/            ★ 全部前端
│   ├── src/{api,views,layouts,router,stores,components,utils}/
│   └── vite.config.ts
├── packages/api-contract/   OpenAPI 单一事实源
├── docs/                    00 索引 / 01~06 设计 / 07 ADR（11 条）
├── index/                   代码索引（脚本生成）
├── scripts/                 环境与索引脚本
├── infra/compose/           PG+Redis+RabbitMQ
└── .plan/                   里程碑计划书（M1、M3）
```

**多租户预留**（当前单商户，但不把路堵死）：
若将来要做 SaaS，需在业务表加 `tenant_id` 并做行级隔离。
**现在不加**是对的 —— 加了会让每条 SQL 多一个维度，而这个项目当前用不上。
但**新增表时不要写死"全世界只有一家店"的假设**（例如不要用全局唯一的单号序号表而不带租户维度）。

### 3.4 迭代计划

**MVP（可给一家店用）** = M1 ✅ + M3 + M6
**增强（完整业务）** = M2（退货/结算/报表）
**完善（多端+加分）** = M4/M5/M7/M8

### 5.4 数据流 / 调用流（出货为例）

```
前端建出货单
  → POST /sales-orders (X-Request-Id 幂等)
    → SalesOrderApplicationService.create
      → 建单据头+明细（DRAFT）
      → ★ inventory.reserveFefo(按效期分段预占)
        → InventoryBalanceRepository.tryReserve（原子 UPDATE，防超卖）
      任一行失败 → 整单回滚（预占全部释放）
审核 → POST /{id}/approve → 状态 APPROVED
出货 → POST /{id}/ship
  → ★ inventory.shipOut（FEFO 拆批次，写多条负向流水）
  → 预占记录标记 CONSUMED
状态 → COMPLETED
对账 → GET /inventory/consistency-check（实存 == 流水净和）
```

### 7.1 三条必读

1. **后端构建必须走 ASCII 联接路径**，否则测试全红（`ClassNotFoundException`，看似"没编译"，实为编码问题）：
   ```powershell
   cd D:\erp-build\backend\server; .\gradlew.bat check
   ```
   初次使用先跑 `.\scripts\build-env.ps1` 建联接。

2. **PostgreSQL 宿主端口是 15432，不是 5432**。
   5432 落在 Windows 保留段 `5358-5457` 内，Docker 绑不上（报 `access forbidden`）。
   用 5432 会**静默连不上**。`application.yml` 默认值已改好，但自己写连接串时要注意。

3. **前端端口是 3000，不是 Vite 默认的 5173**。
   本机 5173/5174 无法绑定（`listen EACCES`）。已在 `vite.config.ts` 固定。
