# 自动化测试入门详解 —— 以「库存页三个数字」为例

> 面向自动化测试新手。目标：读完之后你能看懂本项目里的测试代码，并且知道**每一行为什么这么写**。
> 主线案例：`frontend/web/e2e/05-inventory.spec.ts`（E2E-13，30 行）。
> 辅助对照：后端 `MoneyMathTest.java`（单元测试）。
> 配套策略：`docs/06-测试策略.md`。

---

## 第 0 章 · 先建立直觉：自动化测试到底在做什么

### 0.1 手工测试 vs 自动化测试

假设你要确认「库存页的数字对不对」，手工测试是这样做的：

1. 打开系统，登录；
2. 进后台造一个商品、一个仓库、一个客户；
3. 进一批货（比如 15 件）；
4. 开一张出货单但不出货，把这 4 件「占住」；
5. 打开库存页，用眼睛看三个数字是不是 15 / 4 / 11；
6. 看完把刚才造的数据删掉，别污染下一次测试。

自动化测试就是：**把上面 6 步全部写成代码，让机器每次都替你重做一遍**。人可以下班，机器不会累，也不会忘记第 6 步。

### 0.2 任何一条测试，本质都是三段式

这是最重要的一个心智模型，记住它，后面所有代码都对得上：

| 阶段 | 英文 | 在这条用例里是什么 |
|---|---|---|
| **前置准备**（Arrange） | Arrange | 造商品/仓库/客户、进 15 件货、开一张占 4 件的出货单 |
| **执行操作**（Act） | Act | 打开 `/inventory` 页面 |
| **断言结果**（Assert） | Assert | 断言那一行三个数字是 `15`、`4`、`11` |

外加一个隐形的第四段：**清理（Teardown）**——把本次造的数据删干净（这个项目放在全局的 `global-teardown.ts` 里统一做）。

> 新手常见误区：以为「测试就是跑一遍不报错」。不对。**没有断言的测试不是测试**，它只是把程序运行了一遍而已。测试的价值全在「断言」上。

### 0.3 测试不是「证明程序对」，而是「守住已知的正确」

程序有无数种输入组合，测试不可能穷尽。测试真正的作用是：**把过去确认过的正确行为固化成一道道防线**。以后谁改了代码，如果破坏了这些行为，测试立刻变红。所以测试是「回归防护网」，不是「正确性证明」。

## 第 1 章 · 这个项目的测试全景

### 1.1 四层金字塔（先看全局）

这个项目不是「随便写几条测试」，而是按「测试金字塔」分层组织的：

```
        ▲  L4 E2E（~20-40 条，只覆盖关键路径）
       ╱ ╲       Web：Playwright
      ╱───╲  L3 契约：OpenAPI schema / Pact（三端与后端接口一致）
     ╱─────╲
    ╱ L2 集成 ╲   Spring Boot Test + Testcontainers 起真 PostgreSQL
   ╱───────────╲  测 Repository / SQL / 事务 / 行锁 / MQ 幂等
  ╱   L1 单元    ╲  JUnit5 + AssertJ：金额计算 / 状态机 / 业务规则  ← 最厚
 ╱───────────────╲
```

**为什么要分层？** 因为不同层「性价比」不同：

| 层 | 快不快 | 真不真 | 数量 | 该测什么 |
|---|---|---|---|---|
| L1 单元 | 极快（毫秒） | 只测一小块纯逻辑 | 最多 | 金额、取整、状态机、单个规则 |
| L2 集成 | 中等（秒级，起真数据库） | 真数据库行为 | 中等 | 事务、锁、SQL、幂等 |
| L4 E2E | 慢（分钟级，起后端+前端+浏览器） | 最接近真实用户 | 最少 | 关键业务流「能不能走通」 |

一句话记忆：**便宜又好写的测细节（L1/L2 写厚），昂贵又易碎的只测主干（L4 写精）**。

> 项目策略里有一条硬规则：**禁止用 H2/SQLite 做集成测试**。因为内存数据库和真 PostgreSQL 行为不一致，测出来是「假绿」（看着绿，上线就挂）。这条体现了一个成熟认知：**测试环境要像生产**。

### 1.2 这个项目里测试都在哪

| 层 | 位置 | 例子 |
|---|---|---|
| 后端单元 | `backend/server/src/test/java/com/erp/**/domain/*Test.java` | `MoneyMathTest`、`CostInvariantsTest` |
| 后端集成 | `backend/server/src/test/java/com/erp/**/*IT.java` | `InventoryApiIT`、`SettlementApiIT` |
| Web E2E | `frontend/web/e2e/*.spec.ts` | `05-inventory.spec.ts`、`08-settlement.spec.ts` |
| 小程序 E2E | `app/uniapp/e2e/*.spec.ts` | `02-inventory-balance.spec.ts` |
| 测试地基（配置/工具） | `frontend/web/e2e/helpers/`、`playwright.config.ts` | `api.ts`、`seed.ts`、`run.ts` |
| CI 门禁 | `.github/workflows/ci.yml` | `build-and-test`、`web-e2e` job |

### 1.3 怎么跑

在前端目录 `frontend/web` 下：

```bash
npm run e2e          # 跑全部 E2E（Playwright 会自动起后端 8081 + 前端 3001）
npm run e2e:headed   # 带浏览器界面跑，肉眼能看见它在点
```

跑单个文件 / 单个用例：

```bash
npx playwright test e2e/05-inventory.spec.ts          # 只跑这个文件
npx playwright test -g "E2E-13"                       # 只跑标题含 E2E-13 的用例
```

后端测试在 `backend/server` 下用 Gradle：

```bash
./gradlew test          # 跑 L1 + L2
./gradlew test --tests "com.erp.shared.money.MoneyMathTest"   # 只跑一个类
```

### 1.4 CI 是「什么时候自动跑」

`.github/workflows/ci.yml` 里每次 push / PR 会自动跑：

- `build-and-test`：编译 + 单元/集成测试（Testcontainers 起真 PostgreSQL）+ 覆盖率门禁（JaCoCo）；
- `contract-check`：接口契约一致性；
- `index-check`：扫描 `@CaseId` 注解，校验「测试用例编号 ↔ 追踪矩阵」对得上；
- `web-e2e`：起 PostgreSQL service + 真后端 + Vite，跑 `npm run e2e`。

**门禁（gate）= 不过不许合并。** 这让「测试」从「可选项」变成「硬约束」。

## 第 2 章 · 为什么挑 `05-inventory.spec.ts` 这个案例

它只有 30 行，却是「麻雀虽小五脏俱全」的教科书：

1. **业务含义一眼能懂**：实存 15、预占 4、可用 11。先懂业务再懂代码，适合新手。
2. **覆盖完整链路**：API 造数 → 建真实单据 → 页面查询 → 断言 → 由全局 teardown 清理。
3. **牵出全部基础设施**：能顺带讲清 fixture、登录态、种子数据、API 客户端、配置、清理——这些才是「自动化测试怎么进行」的真相。
4. **断言写法典型**：定位行、取单元格、精确比对文本，是最常用的一套 Playwright 技能。

先看完整代码（这就是全部，没有省略）：

```ts
import { expect, test } from './fixtures'
import { runTag } from './helpers/run'
import { seedBase } from './helpers/seed'

test('E2E-13 库存页三个数字正确（实存 / 预占 / 可用）', async ({ page, api, run }) => {
  const tag = runTag(run, '13')
  const seed = await seedBase(api, tag, { stockQty: 15 })

  // 建一张未出货的出货单，制造 4 件预占：15 / 4 / 11
  const order = await api.createSalesOrder({
    customerId: seed.customer.id,
    warehouseId: seed.warehouse.id,
    lines: [{ skuId: seed.skus[0].id, qty: 4, unitPriceAmount: 12900, discountRate: 9000 }],
  })
  expect(order.status).toBe('DRAFT')

  await page.goto('/inventory')

  const skuText = `${seed.product.name} · 白色-L`
  const row = page.getByRole('row').filter({ hasText: skuText }).first()
  await expect(row).toBeVisible()

  const cells = row.getByRole('cell')
  await expect(cells).toHaveCount(8)
  await expect(cells.nth(0)).toContainText(skuText)
  await expect(cells.nth(1)).toContainText(seed.warehouse.name)
  await expect(cells.nth(4)).toHaveText('15')
  await expect(cells.nth(5)).toHaveText('4')
  await expect(cells.nth(6)).toHaveText('11')
})
```

## 第 3 章 · 逐行精讲 `05-inventory.spec.ts`

### 3.1 前三行：import

```ts
import { expect, test } from './fixtures'
import { runTag } from './helpers/run'
import { seedBase } from './helpers/seed'
```

- `test` 和 `expect` **不是**从 `@playwright/test` 直接拿的，而是从本项目的 `./fixtures` 拿的。
  为什么？因为 `fixtures.ts` 在 Playwright 原生能力上「加了料」——多提供了 `api`、`run` 两个夹具（后面第 4 章细讲）。**用自己封装过的版本，才能拿到项目专属能力**。
- `runTag`：生成「本次运行的唯一前缀」，防止跟别人的测试数据撞车。第 4.4 节细讲。
- `seedBase`：一句话造出一整套主数据（供应商/仓库/客户/商品/SKU/库存）。第 4.5 节细讲。

> 新手要点：**import 的选择本身就是设计**。原生 Playwright 也能测，但每一条用例都得自己写「登录、造数、清理」，会重复到崩溃。所以团队把这些重复动作抽成 helper，测试文件里只留「这一条用例特有的逻辑」。

### 3.2 `test(...)`：用例的定义 + fixture 注入

```ts
test('E2E-13 库存页三个数字正确（实存 / 预占 / 可用）', async ({ page, api, run }) => {
```

- `test(标题, 回调)` 就是在**注册一条测试**。标题是给人看的（失败报告里会显示），本项目约定以 `E2E-13` 这种编号开头，方便跟需求/追踪矩阵对应。
- 回调参数 `{ page, api, run }` 是 **Playwright fixture（夹具）机制——本质是「依赖注入」**。
  你只要在参数里「声明你需要什么」，Playwright 会自动帮你造好再传进来：
  - `page`：一个隔离的浏览器页面对象（Playwright 原生提供）。用它操作页面。
  - `api`：项目自定义的 API 客户端（用来造数据 / 读事实）。
  - `run`：本次运行的上下文（runId、临时账号名等）。
- **为什么用注入而不是 `new`？** 因为框架负责它们的「创建 → 使用 → 销毁」生命周期，还能按需延迟创建。测试只关心「用」，不关心「怎么来、什么时候清理」——这叫**关注点分离**。

### 3.3 `runTag`：给本次数据打上唯一前缀

```ts
const tag = runTag(run, '13')
```

`runTag` 的实现（`helpers/run.ts`）：

```ts
export function runTag(run: RunInfo, caseId: string): string {
  return `${run.runId}-${caseId}`
}
```

假设本次运行的 `runId` 是 `E2E-MF3K2P-AB12`，那 `tag` 就是 `E2E-MF3K2P-AB12-13`。

**为什么要这样？** 这是 E2E 最容易翻车的地方——**数据污染**：

- 如果所有测试都用「商品名叫『测试商品』」，两条用例并行跑就会互相覆盖；
- 如果失败后数据残留，下次运行读到脏数据，断言就随机失败（这叫 flaky，最招人恨）。

用一个包含「本次运行随机串 + 用例号」的前缀，就保证了：**每条用例造的数据都全球唯一；清理时只需按这个前缀删，绝不误伤别人**。这跟你写数据库临时表要带 session id 是同一个道理。

### 3.4 `seedBase`：用「真实业务流」造数据

```ts
const seed = await seedBase(api, tag, { stockQty: 15 })
```

这一行的内部做了很多事（`helpers/seed.ts`），拆开看是这样：

```ts
export async function seedBase(api, tag, options = {}) {
  const supplier  = await api.createSupplier({ code: `${tag}-SUP`, name: `${tag} 供应商` })
  const warehouse = await api.createWarehouse({ code: `${tag}-WH`, name: `${tag} 仓库` })
  const customer  = await api.createCustomer({ code: `${tag}-CUS`, name: `${tag} 客户`, discountRate: 9000 })
  const product   = await api.createProduct({ code: `${tag}-P`, name: `${tag} 商品` })
  // ……再给 product 建 SKU（颜色 白色、尺码 L）
  // 如果 stockQty > 0：走 建进货单 → 提交 → 审核 → 入库，把库存真的做出来
  if (options.stockQty > 0) {
    seed.stockOrder = await stockIn(api, seed, options.stockQty, 8800)
  }
  return seed
}
```

这里有几个非常关键的设计决策，新手一定要理解：

**① 为什么要用 API 造数，而不是用 UI 一步步点？**
E2E 的「昂贵」在于浏览器操作，所以一条用例应该只把**它真正要验收的那个动作**留给 UI（这里是「打开库存页看数字」）。如果连造商品、建进货单都走 UI，一条用例得点几十下，慢且脆（页面一改选择器就崩）。**用 API 快速、稳定地把「前置状态」摆好，再用 UI 验收核心功能**——这是业界的标准做法，叫「API 负责 Arrange，UI 负责 Act + Assert」。

**② 为什么库存要走「真实进货流程」造，而不是直接改数据库把余额写成 15？**
看 `seed.ts` 里的注释：*「库存只能由进货入库产生，所以这里也走真实单据，不直接改余额。」* 这是极其重要的原则——**如果直接把余额改成 15，你就绕过了系统真正的进货逻辑**。万一「进货到底会不会正确增加库存」这件事本身有 bug，直接改库会把 bug 掩盖掉。**造数据要造得和真实用户产生数据的路径一致**，测试才有意义。

**③ `{ stockQty: 15 }` 是什么意思？**
告诉 `seedBase`：「顺便通过真实进货，把这个 SKU 的库存做成 15 件」。于是就有了「实存 = 15」的前提。

> 小提示：`stockIn` 里其实走了四步真实单据：创建 → 提交 → 审核 → 入库。这四步本身就是对后端状态机的隐性冒烟测试。

### 3.5 建出货单：制造「预占 4 件」

```ts
const order = await api.createSalesOrder({
  customerId: seed.customer.id,
  warehouseId: seed.warehouse.id,
  lines: [{ skuId: seed.skus[0].id, qty: 4, unitPriceAmount: 12900, discountRate: 9000 }],
})
expect(order.status).toBe('DRAFT')
```

- `api.createSalesOrder` 通过后端接口建了一张出货单，**数量 4 件**。
- 关键业务知识：这个系统**「建单即预占」**（保存出货单的那一刻，这 4 件就从「可用」里扣走，变成「预占」）。所以建完这张还没出货的单，库存就从「15 可用」变成「15 实存 / 4 预占 / 11 可用」。
- `expect(order.status).toBe('DRAFT')` 是**中间断言 / 前置校验**：确认这张单确实是「草稿、未出货」状态。为什么要多这一句？因为如果建单失败了（接口返回别的状态），后面的数字断言会莫名其妙地错，很难排查。**在前置步骤之后立刻断言它的结果符合预期，能把问题「就近暴露」**，这叫 fail fast。

> 注意 `unitPriceAmount: 12900` 单位是**分**（129.00 元），`discountRate: 9000` 是**万分比**（9000 = 9 折）。这个项目金额全部用整数分存储，是为了避免浮点数误差（第 8 章会展开）。

### 3.6 打开页面

```ts
await page.goto('/inventory')
```

- `page.goto(路径)` 让浏览器导航到某个地址。
- 这里写的是相对路径 `/inventory`，而不是 `http://127.0.0.1:3001/inventory`。因为 `playwright.config.ts` 里配了 `use.baseURL`，Playwright 会自动补全。**好处：换域名/端口时测试代码一行不用改**。
- `await`：几乎所有 Playwright 操作都是异步的，必须 `await` 等它完成，否则会拿着「还没打开」的页面去断言。新手最常见的报错就是漏了 `await`。

### 3.7 定位到「那一行」

```ts
const skuText = `${seed.product.name} · 白色-L`
const row = page.getByRole('row').filter({ hasText: skuText }).first()
await expect(row).toBeVisible()
```

这三行是「怎么在页面里找到目标元素」的典范，逐句拆：

- `seed.product.name` 是造数时生成的商品名（其实带着 runId 前缀，例如 `E2E-MF3K2P-AB12-13 商品`）。页面上的 SKU 列显示成 `商品名 · 颜色-尺码`，所以拼成 `xxx · 白色-L`。
  **为什么用动态生成的名字，而不是硬编码「测试商品」？** 保证了「我找的这行一定是我自己造的那行」，不会撞上别人留下的同名数据。
- `page.getByRole('row')`：按**可访问性角色**找元素。表格里的每一行 `<tr>` 的角色就是 `row`。
  **为什么用 `getByRole` 而不是 CSS class？** 因为角色（row/button/cell）是 HTML 语义，页面换皮、改 class 都不影响；而 `.el-table__row` 这种 class 是 Element Plus 内部实现，升级个版本就可能变。**面向用户语义定位，而不是面向实现细节定位**，测试才稳。
- `.filter({ hasText: skuText })`：从所有行里筛出「文本包含这段字符串」的那一行。
- `.first()`：万一匹配到多行，只取第一行，避免「strict mode violation」（Playwright 默认要求定位器唯一，多个匹配会报错）。
- `await expect(row).toBeVisible()`：断言这一行**可见**。这是「元素找到了」的确认，也为后面读单元格做铺垫。Playwright 的 `expect` 会自动**等待**（最多等到 `expect.timeout`，配置里是 10 秒），直到条件成立——不需要你手写 sleep。

### 3.8 断言三个数字

```ts
const cells = row.getByRole('cell')
await expect(cells).toHaveCount(8)
await expect(cells.nth(0)).toContainText(skuText)
await expect(cells.nth(1)).toContainText(seed.warehouse.name)
await expect(cells.nth(4)).toHaveText('15')
await expect(cells.nth(5)).toHaveText('4')
await expect(cells.nth(6)).toHaveText('11')
```

先交代「这一行到底有几列、每列是什么」。对照页面源码 `InventoryView.vue` 的表头，8 列依次是：

| 索引（0 起） | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 列名 | SKU | 仓库 | 批次 | 效期 | **实存** | **预占** | **可用** | 操作 |

所以：

- `row.getByRole('cell')`：拿到这一行里所有的单元格 `<td>`（角色是 `cell`）。
- `toHaveCount(8)`：先断言「这一行确实是 8 列」。**为什么先断列数？** 万一表结构变了（加了/删了列），`nth(4)` 就会指向别的列，后面数字断言会「莫名其妙」地对不上。先断列数，能在「结构变了」时立刻给出清晰的错误，而不是让你对着数字瞎猜。这叫**用断言描述你对结构的假设**。
- `cells.nth(0)` 用 `toContainText`：因为 SKU 单元格里除了名字，还有一个商品编码小字，所以用「包含」而不是「完全等于」。
- `cells.nth(1)` 同理，仓库列用「包含」。
- `cells.nth(4/5/6)` 用 **`toHaveText`（完全等于）**：因为实存/预占/可用这三个格子里**只有纯数字**，所以要求「精确等于 `15`」。**这里用精确断言，是为了防止模糊通过**——比如显示成 `1,500` 或 `15 件` 都应该算不通过。

> `toContainText`（包含）vs `toHaveText`（完全相等）的区别，是 Playwright 断言最常考的点，务必记牢：
> - 元素里「只有这个值」→ 用 `toHaveText`，严格要求；
> - 元素里「除了这个值还有别的」→ 用 `toContainText`，只要求含这段。

### 3.9 一个隐形的大知识点：为什么全程没有 `sleep`/`wait`？

新手写自动化最爱写 `await page.waitForTimeout(3000)` 来「等页面加载」。这个项目**一处都没有**。原因：

- Playwright 的每个操作（`click`、`fill`、`expect`）都自带**自动等待（auto-waiting）**：它会一直等到元素「可操作 / 条件成立」才继续，超时才失败。
- 手写固定 sleep 有两个毛病：**写短了不稳定（偶发失败），写长了拖慢全量**。而且它只是在「赌」页面够快，并没有真的等对东西。
- 正确姿势是：**断言「我关心的最终状态」**（比如 `expect(cells.nth(4)).toHaveText('15')`），让框架去轮询直到成立。这样既快又稳。

这就是「确定性优先」的测试哲学：**只允许确定性断言，禁止用随机等待掩盖竞态**（策略文档里把这条列为 flaky 治理的核心）。

## 第 4 章 · 支撑这条用例的「地基」（每个文件为什么存在）

一条 30 行的用例能跑起来，背后是一整套基础设施。这一章按「从外到内」的顺序讲清楚每个文件的职责和设计动机。

### 4.1 `playwright.config.ts`：整个 E2E 的总控台

打开这个文件，几条关键配置：

```ts
testDir: './e2e',                 // 测试文件都在 e2e 目录
fullyParallel: false,
workers: 1,                       // 关键：一次只跑一个 worker
globalSetup: './e2e/global-setup.ts',
globalTeardown: './e2e/global-teardown.ts',
use: {
  baseURL,                        // 相对路径的根地址
  trace: 'retain-on-failure',     // 失败时保留 trace（可回放整个操作过程）
  screenshot: 'only-on-failure',  // 失败时截图
  locale: 'zh-CN',
  timezoneId: 'Asia/Shanghai',
},
projects: [
  { name: 'setup',    testMatch: /auth\.setup\.ts/ },
  { name: 'chromium', testIgnore: /auth\.setup\.ts/,
    use: { storageState: adminStorage }, dependencies: ['setup'] },
],
webServer: manageServers ? [ 起后端, 起前端 ] : undefined,
```

逐个讲「为什么」：

- **`workers: 1` + `fullyParallel: false`（串行跑）**：为什么不并行加速？因为这些 E2E **共享同一个真实数据库**，还会操作「保留账期」这种全局资源。并行跑会互相踩数据。**在 E2E 里，确定性 > 速度**。宁可慢一点，也不要随机红。
  （对比：单元测试无共享状态，就应该尽量并行。）
- **`projects: setup + chromium`，且 `chromium` 依赖 `setup`**：这就是「先登录一次，其余用例复用登录态」的机制。`setup` 项目先跑 `auth.setup.ts` 登录并把登录态存盘；`chromium` 项目带着这份 `storageState` 跑所有业务用例。**省掉了每条用例都登录一遍**，也顺带验证了「登录页本身可用」。第 4.2 节细讲。
- **`trace: 'retain-on-failure'` / `screenshot: 'only-on-failure'`**：只在失败时留证据，成功时不占磁盘。失败后看 `trace` 可以像录像一样回放「它到底点了哪、页面当时长什么样」，是排错神器。
- **`webServer`**：声明「跑测试前，先把被测系统起起来」。这里起了两个：
  1. `node e2e/start-backend.mjs`——起后端（等 `/actuator/health` 健康检查通过才继续）；
  2. `npx vite --config e2e/vite.e2e.config.ts`——起前端开发服务器（等 `/login` 可访问）。
  `url` 字段就是「健康检查探针」：探不到就一直等，超时才失败。**好处：开发者什么都不用手动起，`npm run e2e` 一把梭。**
- **端口参数化**（文件顶部那段 `backendPort` 推导）：允许用环境变量 `E2E_BACKEND_PORT` 换端口，这样同一条机器可以并行跑多条「泳道」，各自起一套服务不打架。注释里讲得很清楚：改造前端口写死导致「健康检查探一个端口、代理指另一个端口」的错乱。

> 新手心法：**配置文件决定了「测试在什么环境里跑」**。读一个项目的测试，先读它的 config，你就知道全局约定（要不要真后端、要不要登录态、串行还是并行、失败留什么证据）。

### 4.2 `auth.setup.ts` + `storageState`：登录一次，全站复用

```ts
test('登录并保存 storageState', async ({ page }) => {
  await loginViaUi(page, process.env.E2E_USERNAME ?? 'admin', process.env.E2E_PASSWORD ?? 'Admin@12345')
  await expect(page).toHaveURL(/\/dashboard$/)
  await expect(page.getByText('当前账号权限')).toBeVisible()
  await page.context().storageState({ path: adminStorageFile })
})
```

- 它**真的走了 UI 登录**：填用户名、填密码、点登录；
- 然后断言「确实跳到了 dashboard」「页面上出现了『当前账号权限』」——**登录成功本身也是一条断言**；
- 最后 `storageState({ path })` 把浏览器当前的「登录态快照」（cookie + localStorage 里的 token）**存成文件**。

之后所有业务用例通过配置里的 `storageState: adminStorage` 直接「带着登录态开局」，不用再登录。

**为什么这么设计？**
1. **性能**：登录是慢操作（走一次完整认证），复用快照省几十秒。
2. **安全/整洁**：token 不会出现在每条用例的代码里，凭据集中在一处。
3. **顺带验证**：`setup` 项目本身就是「登录功能」的冒烟测试。

> `readAdminToken()`（`helpers/auth.ts`）就是从这个快照文件里把 `erp.token` 读出来，交给 `ApiClient` 用。所以前面 `api` 夹具能带着管理员身份去造数据。

### 4.3 `fixtures.ts`：给 Playwright 装上「项目专属能力」

```ts
export const test = base.extend<Fixtures>({
  run: async ({}, use) => {
    await use(readRunInfo())           // 提供本次运行上下文
  },
  api: async ({ request }, use) => {
    await use(new ApiClient(request, readAdminToken()))   // 提供 API 客户端
  },
})
export { expect }
```

- Playwright 的 `base.extend` 用来**注册自定义夹具**。这里注册了两个：
  - `run`：读取 `run.json`（本次运行的 runId、临时账号名等），供用例生成数据前缀用。
  - `api`：用 Playwright 的 `request`（一个独立的 API 请求上下文）+ 管理员 token，构造出 `ApiClient`。
- 每个夹具函数形如 `async ({ 依赖 }, use) => { ...; await use(值); ... }`：
  - `use(值)` 之前的代码是「创建」；
  - `use(值)` 之后的代码是「销毁」（这里不需要，所以没有）。
- **为什么用夹具而不是在每个测试里 `new ApiClient(...)`？** 因为夹具能**按需、延迟、复用**：哪条用例声明了 `api`，才为哪条用例创建；不声明就不创建。而且「怎么创建」只写一遍。

> 新手可以这样理解：**fixture = 测试用的「插线板」**。测试只要说「我要电（api）、我要水（run）」，框架负责接好。测试文件里只写业务。

### 4.4 `helpers/run.ts`：runId 与「前缀隔离」的大脑

核心就两个函数：

```ts
export function readRunInfo(): RunInfo {
  // 读 .e2e-artifacts/run.json；读不到就报错提示「请用 npm run e2e 启动」
}

export function runTag(run: RunInfo, caseId: string): string {
  return `${run.runId}-${caseId}`
}
```

还有一个容易被忽略但很见功力的 `normalizeRun`：

```ts
export function normalizeRun(raw) {
  return {
    runId: raw.runId ?? '',
    viewerUsername: typeof raw.viewerUsername === 'string' ? raw.viewerUsername : '',
    financeUsername: typeof raw.financeUsername === 'string' ? raw.financeUsername : '',
    startedAt: raw.startedAt ?? '',
    baseline: raw.baseline ?? {},
  }
}
```

注释解释了它的动机：`financeUsername` 是后来版本才加的字段。如果上一轮运行被强杀，磁盘上留下的是**旧格式**的 `run.json`（没有这个字段）。直接把它喂给清理逻辑，会在 `undefined.replaceAll(...)` 上崩——而且只有「被强杀过的那台机器」才复现，极难排查。`normalizeRun` 把缺字段补成空串，**向前兼容旧数据**。

> 这是「健壮性设计」的典型：**外部文件的内容不可信，先规整成当前 schema 再用**。新手写测试时常常假设「上次留下的文件一定格式正确」，现实里经常不是。

### 4.5 `helpers/seed.ts`：语义化的「数据工厂」

除了 3.4 讲的 `seedBase`，还有三个高频函数：

- `stockIn(api, seed, qty, ...)`：走「创建进货单 → 提交 → 审核 → 入库」把库存做出来；
- `shipOut(api, seed, {...})`：走「创建出货单 → 提交 → 审核 → 出货」把货发出去；
- `completeReturn(...)`：走「创建退货单 → 提交 → 审核 → 退货入库」。

**为什么把它们叫「数据工厂 / 领域构造器」？** 因为它们把「造一个已出货的订单」这种复杂前置，收敛成一个**有业务含义的函数调用**：`await shipOut(api, seed, { qty: 6 })`。用例读起来像业务语言（「发 6 件货」），而不是一堆建单/提交/审核的底层操作堆砌。

注释里还有一句很重要的话：

> *「单价/折扣必须显式传：日清的销售金额按 round(qty × 单价 × 折扣 / 10000) 重算，用例要断的是这个整数公式的结果，不是页面上四舍五入后的字符串。」*

意思是：**造数和断言要用同一套「整数分」的口径**，否则页面显示的是「元」（可能四舍五入），你在数据层断「分」，两边对不上。这是金额类系统测试的经典坑。

### 4.6 `helpers/api.ts`：只做两件事——「安排」和「核对」

打开文件顶部有一句定调注释：

> *「E2E 的 API 客户端：只用于『安排数据』和『读取断言值』，所有被验收的动作仍然走浏览器 UI。」*

这个「**只用于 Arrange 和 Verify，不用于 Act**」的边界非常关键。它保证了 E2E 依然是「真的在测 UI + 后端联动」，而不是「用接口假装测了界面」。

核心是 `call` 方法，它做了几件很专业的事：

```ts
private async call<T>(method, path, options = {}) {
  const headers = { Authorization: `Bearer ${this.token}` }
  if (method !== 'GET') headers['X-Request-Id'] = randomUUID()   // ① 幂等键

  const response = await this.request.fetch(`/api/v1${path}`, {
    method, headers, params, data: options.body,
    failOnStatusCode: false,                                    // ② 不让框架直接抛，自己处理错误
  })
  const payload = JSON.parse(await response.text())             // ③ 解析统一响应信封
  if (!response.ok()) {
    const error = new Error(...)
    Object.assign(error, { status: response.status(), code: payload?.code, details: payload?.details })
    throw error                                                 // ④ 把 HTTP 错误变成带 code 的异常
  }
  return payload.data                                           // ⑤ 只返回业务数据
}
```

- **① `X-Request-Id`**：每次写操作带一个随机 UUID。后端的幂等机制靠它——「同一个 requestId 重复提交只生效一次」。也正因为有它，测试可以安全地重试而不产生重复数据。
- **② `failOnStatusCode: false`**：默认 Playwright 遇到 4xx/5xx 会直接抛一个不好用的错。这里关掉，自己解析响应，**把后端的错误码 `code` 一起抛出来**，用例才能精确断言「是 `SET_PERIOD_CLOSED` 这个错误」（见第 7 章）。
- **③ 统一响应信封**：后端所有接口返回 `{ code, message, data }`，这里统一剥壳，业务方法拿到的直接就是 `data`，清爽。
- **④ 错误对象带 `status/code/message`**：配合 `asApiFailure(error)` 把异常转成结构化对象，用例里就能 `expect(failure).toMatchObject({ status: 409, code: 'SET_PERIOD_CLOSED' })`。
- **⑤ 只返回 `data`**：调用方 `await api.createSalesOrder(...)` 直接拿到订单对象，不用每次 `.data`。

> 新手心法：**客户端 SDK 的职责是「让用例写起来像人话」**。所有 `fetch`、`JSON.parse`、错误处理都应该藏在 SDK 里，用例里不该出现这些底层细节。

### 4.7 `helpers/db.ts`：一条「旁路」，用于造账号/清理/对账

```ts
function psql(sql: string): string {
  // 默认 docker exec erp-postgres psql ...；有 E2E_DATABASE_URL 就用本机 psql
}
export function queryScalar(sql: string): string { ... }
```

为什么测试需要直连数据库？三个正当用途：

1. **造特殊账号**：`global-setup.ts` 要创「只能看的 VIEWER」「能结算不能开单的 FINANCE」这种测试专用账号，走接口不方便，直接 SQL 复制管理员密码哈希最快；
2. **清理数据**：按 runId 前缀删，接口没有「批量删」能力；
3. **做「后端事实」核对**：比如第 7 章结算用例里，页面显示的是「元」，但真正的事实（`46440` 分）直接查库/查接口最可靠。

**注意边界**：`db.ts` 只用于「旁路辅助」，**不用它来伪造被验收的业务结果**。比如库存必须走真实进货产生（3.4 ②），不能直接 `UPDATE` 余额。**「造前置可以抄近路，造结果不行」——这条线要划清楚。**

### 4.8 `global-setup.ts`：整场演出的「开幕准备」

它在所有用例之前**只跑一次**，做四件事：

1. **清理上一轮遗留**：如果 `run.json` 存在且超过 30 分钟，说明上次被强杀，先清掉，避免污染本次基线；
2. **重置「保留账期」并读取基线**：先把测试专用的保留账期清空，再记录「当前各业务表的行数」作为**基线快照**（`baseline`）；
3. **生成 runId 与临时账号**：`runId = E2E-<时间36进制>-<随机hex>`，并据此生成 `viewer-...`、`finance-...` 两个账号名；
4. **先落盘再建账号**：`writeFileSync(runFile, ...)` 在创建账号**之前**执行——注释说得很清楚：*「即使建账号中途失败，teardown 也知道要清理哪些用户名」*。这是「失败也要可收拾」的防御性设计。

**为什么要有「基线」？** 因为 teardown 要能判断「本轮到底把数据库搞脏了没有」。记下开跑前的行数，跑完对比，「计数回到基线」才能证明清理干净（4.9 讲）。

### 4.9 `global-teardown.ts`：清理，并且「硬失败」

```ts
export default async function globalTeardown() {
  if (process.env.E2E_KEEP_DATA === '1') return   // 调试时可保留数据
  const run = JSON.parse(readFileSync(runFile, 'utf8'))
  const { summary, remaining } = cleanupRun(run)  // 按前缀删
  const after = readBaseline()
  // 1) 还有前缀残留 → 报错
  // 2) 业务表计数没回到基线 → 报错
  // 3) 既有预占 e2e-reserve-001 数量变了 → 报错
}
```

这个文件的哲学最值得学：**「测试全绿，但库里一堆垃圾」是不可接受的**。所以清理之后它做了三道硬校验，任何一道不过，**整次 E2E 直接判红**：

1. **前缀残留为 0**：本轮造的数据必须删干净；
2. **业务表计数回到基线**：跟开场快照逐项比对，多一行少一行都算失败；
3. **保护「既有数据」**：连 `e2e-reserve-001` 这种预置数据都不许被碰。

**为什么不「尽力清理、清不掉就算了」？** 因为一旦允许「悄悄留垃圾」，下一轮测试就会读到脏数据、随机失败，最后没人敢信 E2E。**把「干净」变成硬门禁，才能长期保住测试可信度。**

### 4.10 `start-backend.mjs`：把后端「干净地」起起来

两个亮点：

- **用 `bootJar + java -jar` 而不是 `gradlew bootRun`**：注释说，`bootRun` 会多一层 Gradle 守护进程，Playwright 停服时容易留下 Java 子进程占着 8081 端口。直接持有 `java` 进程 pid，停的时候能干净回收。**测试基础设施也要考虑「资源能不能干净释放」**。
- **Windows 中文路径的「联接守卫」**：Windows 下 Gradle 在中文路径会报误导性错误，所以构建要在 ASCII 联接路径（如 `D:\erp-build`）下做。但默认联接可能指向**主工作区**，并行开发时会「跑我的测试、验别人的代码」。所以脚本会核对「这个联接到底指向谁」，不是当前 worktree 就**直接拒绝启动**，而不是默默构建别人的代码。

> 这类代码看着「跟测试没关系」，其实是资深工程师才会想到的点：**测试基础设施本身的正确性，决定了测试结果是否可信**。

## 第 5 章 · 一次 `npm run e2e` 的完整生命周期（时间线）

把上面所有零件串起来，一次运行的顺序是这样的：

```
1. 你敲 npm run e2e  →  实际执行 playwright test（读 playwright.config.ts）
2. Playwright 按 webServer 配置起两个子进程：
     ├─ node e2e/start-backend.mjs   （构建并启动后端 8081，探 /actuator/health）
     └─ vite --config e2e/vite.e2e.config.ts （起前端 3001，探 /login）
3. globalSetup 跑一次：
     ├─ 清理超 30 分钟的遗留 run
     ├─ 重置保留账期 + 读基线快照
     ├─ 生成 runId、viewer/finance 账号名
     └─ 落盘 run.json → 建临时账号
4. setup 项目跑 auth.setup.ts：
     └─ UI 登录 admin → 保存 storageState
5. chromium 项目逐条跑 *.spec.ts（串行 workers=1）：
     ├─ 每条用例拿到 page / api / run 夹具（带 storageState 登录态）
     ├─ runTag 生成唯一前缀 → seedBase 造数 → UI 验收 → 断言
     └─ 失败则保留 trace + 截图
6. globalTeardown 跑一次：
     ├─ 按 runId 前缀删除本轮数据
     ├─ 校验「前缀残留 = 0」「业务表计数回到基线」
     └─ 不达标 → 整次 E2E 判红
7. 生成 HTML 报告（.e2e-artifacts/report）
8. webServer 子进程被 graceful shutdown 回收
```

理解这条时间线，你就能在失败时快速定位「是起服务失败？登录失败？还是某条用例断言失败？还是清理失败？」——这比盲目看日志高效得多。

## 第 6 章 · 断言策略：为什么这样断，而不是那样断

一条测试写得好不好，八成看断言。本项目的几条原则：

### 6.1 断「业务不变量」，不断「页面像素」

`05` 断的是「实存 15 / 预占 4 / 可用 11」这种**业务事实**，而不是「截图长得一样」或「某个 div 的颜色」。业务事实稳定，像素天天变。策略文档把这提到原则高度：*「断言不变量（INV-1~10），而非硬编码期望值。」*

### 6.2 金额一律断「整数分」，避免四舍五入歧义

页面显示「¥ 696.60」，但用例更愿意断后端事实 `69660` 分（第 7 章会看到 `expect(reconciled).toMatchObject({ generalTotal: 46440 })`）。因为「元」是给人看的、经过格式化的；「分」才是系统内部精确值。**断最接近真相的那一层。**

### 6.3 精确 vs 包含，按语义选

- 元素里「只有这个值」→ `toHaveText`（严格相等）；
- 元素里「除了这个值还有别的」→ `toContainText`（包含）。
选错会要么「该松的紧了」（脆），要么「该紧的松了」（漏 bug）。

### 6.4 负向断言 + 副作用检查（进阶但重要）

好测试不只验证「成功的路径」，还验证「失败时什么都没发生」。第 7 章的 `E2E-18` 就是这样：锁账后尝试入库被拒，除了断言「报错了」，还要断言「单据状态还是 `APPROVED`」「库存还是 0」——**证明失败是「干净地失败」，没有留下半截副作用**。这比只断一个错误弹窗难得多，也值钱得多。

### 6.5 少而准：E2E 不追求覆盖所有分支

分支、边界、异常值这些「量大的活」交给 L1/L2 单元/集成测试。E2E 只保证「主干业务流程能走通」。**用最贵的工具干最少的活**，这是金字塔的精髓。

## 第 7 章 · 进阶：同一个项目里更强的案例（`08-settlement.spec.ts`）

`05` 教会你基本套路，`08-settlement` 展示了「成熟测试」的样子。挑几个技巧感受一下（不必逐行，重在理解思想）：

### 7.1 「保留账期」——绕开共享资源的冲突

```ts
const PERIOD_17 = '2031-01'   // 写死一个「保留」的测试账期
const DATE_17 = '2031-01-20'
```

日清/月结是「跨仓库全月」汇总的，天然和别的用例抢数据。解决办法是**约定一个只有测试用的「保留账期」（2031 年）**，并且注释明确警告：*「绝不锁真实当前月 2026-10——那会连带拒掉同一轮里其它用例的建单。」* 这是「测试资源规划」的实战智慧。

### 7.2 「独占性守卫」——先证明环境干净，再断言结果

```ts
function countDocsInPeriod(period) { /* 查这个账期里有几张单据 */ }
...
expect(countDocsInPeriod(PERIOD_17), `保留账期 ${PERIOD_17} 应只有本轮 3 张单`).toBe(3)
```

在断言金额之前，先断言「这个账期里只有我造的 3 张单」。**如果这里不对，说明数据被污染了，而不是结算算错了**——失败信息能直接告诉你是「环境问题」还是「业务 bug」，省下大量排查时间。

### 7.3 「幂等重跑」——验证重复执行不出错

```ts
// 同日重跑结果一致（幂等由 uq_daily_settlement 保证）
await panel.getByRole('button', { name: '执行日清' }).click()
await expect(metric(..., '净销售额')).toHaveText('¥ 464.40')
```

连点两次「执行日清」，结果必须一样。这是对「幂等」的验证——真实系统里用户会手抖点两次，必须保证不出重复账。

### 7.4 「三方核对」——UI / API / DB 交叉验证

```ts
// 页面显示的是「元」
await expect(metric(recon, '差额')).toHaveText('¥ 0.00')
// 后端事实是「分」
const reconciled = await api.reconcile(PERIOD_17)
expect(reconciled).toMatchObject({ generalTotal: 46440, detailTotal: 46440, diff: 0, balanced: true })
```

**UI 断言证「用户看到的对」，API 断言证「后端算的对」，必要时 DB 断言证「存的对」**。三层一起断，才算真的可信。

### 7.5 「错误码断言」——不只断报错文案，还断错误标识

```ts
const failure = await api.createPurchaseOrder({...}).then(() => null, (e) => asApiFailure(e))
expect(failure).toMatchObject({ status: 409, code: 'SET_PERIOD_CLOSED' })
```

页面文案会改，但**错误码是契约**。断错误码比断中文文案稳定得多。

> 这些技巧的共同点：**它们在「证明测试本身可信」**。新手只会断「结果等于某个值」；老手还会断「环境是干净的」「失败没有副作用」「重复执行结果一致」。这才是「非常好的案例」和「一般案例」的差距。

## 第 8 章 · 对照：单元测试长什么样（`MoneyMathTest` 精讲）

E2E 是「从外部走一遍」，单元测试是「把一个小零件捏在手里测」。看后端 `MoneyMathTest.java`：

```java
@DisplayName("金额 · MoneyMath")
class MoneyMathTest {

    @Test
    @CaseId("TC-CST-001")
    @DisplayName("行金额 = 数量 × 单价 × 折扣万分比 ÷ 10000")
    void lineAmount_basic() {
        assertThat(MoneyMath.lineAmount(3, 1000, 10000)).isEqualTo(3000);
        assertThat(MoneyMath.lineAmount(1, 12345, 9000)).isEqualTo(11111);
    }

    @Test
    @CaseId("TC-CST-005")
    @DisplayName("除数为 0 / 非法入参必须拒绝")
    void invalidInputs_rejected() {
        assertThatThrownBy(() -> MoneyMath.mulDivHalfUp(1, 1, 0))
                .isInstanceOf(ArithmeticException.class);
        assertThatThrownBy(() -> MoneyMath.lineAmount(-1, 100, 10000))
                .isInstanceOf(IllegalArgumentException.class);
    }
}
```

逐块讲：

- `@Test`：标记这是一个测试方法，JUnit5 会自动发现并执行。
- `@DisplayName("...")`：给人看的中文说明，报告里显示这句而不是方法名。
- `@CaseId("TC-CST-001")`：**把测试关联到需求/追踪矩阵的编号**。CI 里有个 `index-check` job 专门扫这个注解，保证「需求 ↔ 测试」对得上。这是「可追溯性」——面试常问。
- `assertThat(...).isEqualTo(...)`：AssertJ 的链式断言，可读性极强，失败信息也友好。
- `assertThatThrownBy(() -> ...).isInstanceOf(...)`：**断言「这里必须抛异常」**。测试不只验证「正常路径」，还要验证「非法输入被正确拒绝」。这比 E2E 更容易覆盖边界。

再看它测的 `MoneyMath.java` 里最关键的一段注释：

> *「金额乘法 + 除法 + 舍入只要散落到第二个地方，两处对 HALF_UP 的理解迟早分叉，表现是『行金额之和比合计多一分钱』这类永远调不平的账。」*

这句话解释了「为什么金额运算必须集中到一个类、并被单元测试死死锁住」——**因为这种 bug 一旦漏到线上，是「对不平账」的灾难，而且极难复现定位**。所以在最便宜的地方（L1 单元）把它测厚。

`MoneyMath` 用 `BigInteger` 而不是 `double`：因为金额是整数分，中间乘积（数量×单价×折扣）可能超出 `long`；用 `BigInteger` 做整数乘除，再显式 `HALF_UP` 舍入，**杜绝浮点误差**。

**E2E 和单元测试的分工，一目了然：**
- 单元测试：一条用例只测一个公式/一个规则，毫秒级，能穷举边界（0、负数、非法入参）。
- E2E：一条用例走一整条业务流，分钟级，只测「能不能通」。

> 如果只让你记住一件事：**先把单元测试写厚（又快又稳又便宜），E2E 只留给「跨页面、跨服务、必须真的点一遍才放心」的关键流程。**

## 第 9 章 · 怎么运行、怎么看结果、失败怎么查

### 9.1 常用命令（在 `frontend/web` 下）

```bash
npm run e2e                            # 跑全部（自动起前后端）
npm run e2e:headed                     # 显示浏览器，肉眼看它点
npx playwright test e2e/05-inventory.spec.ts   # 只跑一个文件
npx playwright test -g "E2E-13"        # 只跑标题匹配的用例
npx playwright test --debug            # 单步调试（会停住让你看）
```

后端（在 `backend/server` 下）：

```bash
./gradlew test
./gradlew test --tests "com.erp.shared.money.MoneyMathTest"
```

### 9.2 产物都在 `.e2e-artifacts/`

| 文件/目录 | 是什么 |
|---|---|
| `report/` | Playwright HTML 报告（逐步操作、失败截图、trace 入口） |
| `test-results/` | 失败用例的截图 / trace 原始文件 |
| `admin-storage.json` | 登录态快照（token 在这，别提交） |
| `run.json` | 本次运行的 runId、临时账号、基线 |
| `cleanup.json` | teardown 的清理结果与基线对比 |

看报告：`npx playwright show-report .e2e-artifacts/report`

### 9.3 失败了按这个顺序查

1. **服务起没起来？** 看是不是 `webServer` 健康检查超时（后端 8081 / 前端 3001 没起来）。这是最常见的「一群用例全红」原因。
2. **登录成没成？** 如果 `setup` 项目失败、`admin-storage.json` 没生成，所有业务用例都会红。
3. **单条断言失败？** 打开 HTML 报告的 trace，回放「它当时看到什么、点了哪」，对照 DOM 改选择器或修业务。
4. **teardown 失败？** 说明数据没清干净或污染了基线——**别忽略它**，它保护的是下一轮的可信度。

### 9.4 什么是 flaky，怎么治理

**flaky = 同一条测试，代码没改，这次红下次绿**。它是 E2E 的头号敌人，会让人失去对测试的信任。本项目策略文档给出的标准答案：

**重试（retry）+ 隔离（quarantine）+ 归因（记录原因）+ 只允许确定性断言（禁止乱 sleep）**。

而 `05`、`08` 里那些「先断列数」「独占性守卫」「用动态前缀」「用 `toHaveText` 而非模糊匹配」的写法，本质上都是在**从源头降低 flaky**——**最好的 flaky 治理是「一开始就别写容易 flaky 的测试」**。

## 第 10 章 · 新手学习路径 + 常见坑清单

### 10.1 按这个顺序读代码

1. `MoneyMathTest.java` —— 先懂最简单的单元测试（AAA、边界、异常断言）；
2. `05-inventory.spec.ts` —— 再懂一条完整 E2E 的骨架；
3. `helpers/fixtures.ts` → `run.ts` → `seed.ts` → `api.ts` —— 理解「地基」怎么托住用例；
4. `playwright.config.ts` —— 理解「测试在什么环境跑」；
5. `global-setup.ts` / `global-teardown.ts` —— 理解「为什么测试要自己准备和清理世界」；
6. `08-settlement.spec.ts` —— 看成熟测试如何「证明自己可信」。

### 10.2 新手最容易踩的坑

1. **漏 `await`**：拿着没打开的页面去断言，报一堆莫名其妙的错。
2. **乱用 `waitForTimeout`**：用 sleep 掩盖时序问题，短期「看起来好了」，长期变成 flaky。**永远等「条件」，不等「时间」。**
3. **硬编码数据**：用固定商品名/固定日期，多轮运行互相污染。**用 runId 前缀 + 独立造数。**
4. **只测 happy path**：不测「非法输入被拒」「失败无副作用」。**最好的测试都在测「出错时对不对」。**
5. **用 `toContainText` 该用 `toHaveText` 的地方**：断言太松，漏掉真 bug。
6. **不管清理**：跑完库里一堆垃圾，下一轮随机红。**要么事务回滚，要么按前缀精确清理 + 基线校验。**
7. **依赖执行顺序**：用例 A 产生数据、用例 B 去用。**每条用例必须自给自足、相互独立。**
8. **断页面像素/截图**：页面一改就全红。**断业务事实，不断外观。**

> 结语：自动化测试不是「多写代码」，而是**用工程手段把『已知的正确行为』固化成可重复执行的防线**。一条好的测试，读起来应该像一段业务说明——**前置是什么、做了什么、期望什么**——而所有「造数、登录、清理、定位」的脏活，都被藏进了基础设施里。这也是本项目测试代码值得学的地方：**测试用例本身很短，但地基建得很厚。**
