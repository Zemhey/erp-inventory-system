# 06 · 测试策略（草案）

> 本文件回答"**测试什么时候做、怎么做、做到什么程度算够**"。
> 与 [方向建议与落地路线 §10](planning/方向建议与落地路线.md#10-自动化测试在什么时候做时机问题) 配套。
> 本文状态：🚧 草案（策略已定，测试地基待建）。

---

## 1. 第一原则：测试是并行轨道，不是阶段

| | 谁做 | 什么时候 | 频率 |
|---|---|---|---|
| **写**测试 | 你 | **与功能同一次提交** | 每个功能 |
| **跑**测试 | CI | push/PR 自动 + 每晚全量 | 持续 |

**唯一例外**：E2E 依赖该端 UI+API+DB 就绪，天然晚一点；但"端可用后立刻补 1~3 条"，**不是攒到最后**。

**分层开始时机（关键差异）**：

| 层 | 开始时机 |
|---|---|
| 测试地基（test-kit / CI / Testcontainers） | **M0，早于任何业务功能** |
| L3 契约测试 | **写 OpenAPI 时，早于实现** |
| L1/L2 单元与集成 | 与功能代码同一次提交 |
| L4 E2E | 该端关键路径跑通后，增量补 |
| L5/L6 性能与安全 | 主业务线闭环（M2 后） |

## 2. 四层金字塔

```
        ▲  L4 E2E  (~20-40 条，只覆盖关键路径)
       ╱ ╲       Web(Playwright) / 小程序(automator) / Android(Appium)
      ╱───╲  L3 契约 (OpenAPI schema + Pact) + 属性(Schemathesis)
     ╱─────╲
    ╱ L2 集成╲    Testcontainers 真 PG+Redis：Repository/事务/锁/MQ
   ╱─────────╲
  ╱  L1 单元  ╲   JUnit5+Mockito：业务规则/金额/状态机  ← 最厚
 ╱─────────────╲
```

| 层 | 工具 | 测什么 | 规模目标 |
|---|---|---|---|
| L1 单元 | JUnit5 + Mockito | 金额计算、状态机迁移、业务规则 | line 覆盖率 >80%，branch >70% |
| L2 集成 | Spring Boot Test + **Testcontainers**(PG+Redis) | Repository、SQL、事务、行锁/乐观锁、MQ 幂等 | 核心表 100% |
| L3 契约 | OpenAPI schema 校验 + Pact | 三端与后端契约一致；破坏性变更拦截 | 每接口 |
| L3.5 属性 | Schemathesis | 参数边界/类型/缺失，自动生成 | 白捡 |
| L4 E2E Web | Playwright | 主业务流 | 关键路径 100% |
| L4 E2E 小程序 | miniprogram-automator | 同用例（跨端一致性） | 冒烟子集 |
| L4 E2E Android | Appium(UiAutomator2) | 同用例（跨端一致性） | 冒烟子集 |
| L5 性能 | k6 | 并发下单、库存查询、日清批处理 | 3 个场景 |
| L6 安全 | OWASP ZAP baseline / Trivy | 基础安全门禁 | 每 PR |

**硬规则**：
- ❌ **禁止用 H2/SQLite 做集成测试**（DB 行为不一致 = 假绿）
- ❌ E2E 不超过 40 条（多了必 flaky）
- ✅ L1/L2 写厚，L3/L4 写精

## 3. 可测试性设计（★ 最容易忽略，最能拉开差距）

**在写业务代码时就为测试留门**，且**仅 test profile 生效**：

| 钩子 | 作用 | 让哪些测试成为可能 |
|---|---|---|
| `ClockProvider`（可注入时钟） | 时间可控制 | 日清月结、跨月/跨年、FEFO 效期、预占超时 |
| `POST /__test__/reset` | 重置为标准账套 | 用例间隔离、可复现 |
| `POST /__test__/time-travel` | 跳转时间 | 跨月结算、效期到期 |
| `POST /__test__/seed` | 注入种子数据 | 快速构造前置状态 |
| 幂等键 `requestId` | 重复提交防护 | 幂等测试 |
| 领域事件可断言 | 事件发布可观测 | 断言"事件发布了、发布了几次" |
| 故障注入开关（test profile） | 强制 DB 超时 / MQ 异常 | 补偿与重试逻辑测试 |

**实现要求**：
- 这些 Controller 用 `@Profile("test")` 标注，**生产 profile 不注册**（要有测试验证这一点！）；
- `ClockProvider` 通过 Spring 注入，业务代码**禁止直接调 `LocalDateTime.now()`**（可用 ArchUnit 规则强制检查）。

> 面试话术："我先改造了系统的可测试性——注入时钟、留出 reset/time-travel 后门、让领域事件可断言，之后才有资格谈自动化。"

## 4. 跨端一致性测试（★ 招牌招）

用 **YAML 描述语义化业务用例**（面向业务，不面向元素），每端一个 adapter 映射为具体操作。

**用例格式**：

```yaml
id: TC-E2E-003
title: 出货优先扣减最早效期批次，且三端结果一致
covers: [FR-SAL-02, FR-INV-05, BR-INV-06, INV-1, INV-2]
platforms: [web, miniapp, android]
given:
  - 仓库: 上海仓
  - SKU: T恤/L/白色
  - 批次: [{batchNo: B1, expiry: 2025-06-01, qty: 10}, {batchNo: B2, expiry: 2025-09-01, qty: 10}]
  - 客户: {name: 张三, level: 金卡, discount: 9000}
when:
  - 登录: {role: 仓管员}
  - 出货: {sku: T恤/L/白色, qty: 12, customer: 张三}
then:
  - assert: 批次B1 onHandQty == 0
  - assert: 批次B2 onHandQty == 8
  - assert: 应收金额 == round(单价 * 12 * 0.9)
  - assert: 库存流水条数 == 2
  - assert: INV-2（实存 == 流水净和）
```

**同一份 YAML** 跑 Web（Playwright）/ 小程序（automator）/ Android（Appium），产出**一致性对照报告**。

**这一招证明你懂**：多端治理、用例抽象、数据工厂、断言策略 —— 课程项目里几乎见不到。

## 5. 测试数据与治理

| 项 | 做法 |
|---|---|
| 数据工厂 | 领域构造器 + Faker：`aSoldOrder(...)` 语义化构造，而非硬编码 JSON |
| 标准账套 | 固定种子数据集（pg dump 快照 / Testcontainers template）→ 保证可复现 |
| 隔离策略 | 每用例事务回滚 **或** schema-per-test **或** 每 PR 独立命名空间 |
| 固定时钟 | 时间相关用例**一律走注入时钟**，禁止硬编码断言 |
| 断言原则 | **断言不变量（INV-1~10），而非硬编码期望值** |
| flaky 治理 | 失败重试标记 + 隔离区(quarantine) + 趋势看板 + 归因记录 |

> **flaky 治理是面试必问项**（见 [方向建议 §7.2](planning/方向建议与落地路线.md)）。标准答案：重试 + 隔离 + 归因 + 只允许确定性断言。

## 6. CI 门禁

| 触发 | 做什么 | 门禁 |
|---|---|---|
| 每次 push / PR | 编译 + L1 + L2(Testcontainers) + L3 契约 + Web 冒烟 E2E + Sonar + 索引 `--check` | **不过不许合并** |
| Android E2E | `reactivecircus/android-emulator-runner` | 冒烟子集 |
| 每晚 | 全量三端 E2E + 性能 + 安全 + 覆盖率报告 | 趋势看板 |
| 发布 | 构建镜像 → Trivy → 推送 → 部署 → 线上冒烟 | 失败自动回滚 |

**小程序 E2E 的诚实提醒（重要陷阱）**：
`miniprogram-automator` 依赖微信开发者工具（需扫码登录 + 图形界面），**Linux CI 跑不起来**。
解法：**在你自己 Windows 机器上挂 GitHub Actions self-hosted runner**。
这条本身就是简历亮点："搭建自托管 runner，在 CI 中执行小程序端自动化"。

## 7. Definition of Done（硬规则）

一个功能算完成，缺一条不算完：

- [ ] 代码
- [ ] L1 测试（含**边界值与异常分支**，不只是 happy path）
- [ ] 涉及 DB / 事务 / 锁 / MQ → 补 L2 集成测试
- [ ] 改了接口 → 更新 `openapi.yaml` + 契约测试
- [ ] 新增业务规则 → 检查是否违反 10 条不变量（[02 §4](02-领域模型与术语表.md#4-关键不变量invariants--测试的最终断言对象)）
- [ ] 新加一条主业务流程 → 该端补 1~3 条 E2E（仅当端已就绪）
- [ ] **更新 [00-索引与追踪矩阵](00-索引与追踪矩阵.md) 的状态列与测试用例ID**

> **硬规则：主干永远绿。** 红灯立刻修；来不及就标记进隔离区，**绝不允许带着红灯继续开发**。
> 这一条比任何工具选型都更决定项目能否收尾。

## 8. 测试用例编号规范

`TC-<模块>-<三位序号>`，如 `TC-INV-007`。

| 模块码 | 含义 | 模块码 | 含义 |
|---|---|---|---|
| IAM | 认证权限 | PUR | 采购进货 |
| MDM | 主数据 | SAL | 销售出货 |
| INV | 库存 | RMA | 退货 |
| SET | 结算对账 | RPT | 报表 |
| E2E | 跨端端到端 | PERF | 性能 |
| SEC | 安全 | SYS | 系统能力 |

**规则**：追踪矩阵的"测试用例ID"列只认这个编号。测试代码里用注解关联：

```java
@Test
@CaseId("TC-INV-007")
@DisplayName("出货时可用量不足必须拒绝，且不产生任何流水")
void ship_whenInsufficientAvailable_thenRejectAndNoLedger() { ... }
```
