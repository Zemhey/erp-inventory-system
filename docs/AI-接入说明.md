# AI 接入与模型配置

> 一句话：模型相关的所有配置都在 **系统 → 自然语言 → AI 接入** 页面里，填完保存即刻生效，不用改代码也不用重启。

## 1. 怎么配（三步）

1. 打开左侧菜单 **自然语言 → AI 接入**（`/nl/settings`）。
2. 按下面填：

| 字段 | 填什么 | 说明 |
|---|---|---|
| 解析方式 | **大模型 function calling** | 选它才会真的调模型；不选则走本地关键词匹配 |
| 复核方式 | 规则 + AI 复核（可选） | 只影响**写操作**，查询不会多花一次模型调用 |
| 接口地址 | `https://api.deepseek.com/v1` | DeepSeek 官方地址，已预置 |
| 模型名 | `deepseek-chat` | **不能用 `deepseek-reasoner`**：它不支持 function calling，而工具调用全靠这个 |
| API Key | `sk-...` | 在 https://platform.deepseek.com/api_keys 创建 |

3. 先点 **测试连接**，看到"连接正常"再点 **保存并生效**。

> 顺序很重要：测试连接**不落库**。先测得通再保存，避免拿一个填错的 key 覆盖掉当前能用的配置。

## 2. 怎么判断"到底有没有在用模型"

看页面顶部那条状态带，它说的是**判定结果**，不是配置项：

| 状态带 | 含义 |
|---|---|
| 大模型已启用：deepseek-chat | 真的在调模型 |
| 已选择大模型，但还没有可用的 API Key | 选了 openai 但没 key，**实际仍在跑关键词模式** |
| 当前为关键词模式 | 没选 openai |

判定规则：`parser=openai` **且** 有 key，两个条件同时成立才算启用。只看配置项会误判。

底部还会显示两行事实：复核层是"仅规则"还是"规则 + AI"，实际解析方式是哪一个。

## 3. 密钥是怎么存的

- **落库前加密**：AES-256-GCM，库里形如 `enc:v1:oQ045daDKKll...`，直接查表看不到明文。
- **接口只回显后四位**：`GET /nl/settings` 返回 `keyMasked = ••••••cdef`，后端根本不把明文放进响应体，直接 curl 也拿不到。
- **输入框永远为空**：留空 = 不修改，只有点「清除密钥」才会清空。这样改模型名不必重贴一遍 key。
- **加密口令**来自 `ERP_NL_SECRET` 环境变量。没配时用内置常量派生——这只挡住"翻数据库直接看到"，**不算真安全**。生产部署要显式设置，且多实例必须一致，否则 A 实例存的 key 在 B 实例上解不开（表现为"保存成功但一调用就 401"）。

## 4. 换模型 / 换服务商

任何兼容 OpenAI `POST /chat/completions` + `tools` 的端点都能接：

| 服务商 | 接口地址 | 模型名 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 阿里通义 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 本地 Ollama | `http://127.0.0.1:11434/v1` | `qwen2.5:7b` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |

本地 Ollama 不需要 key，但后端要求 key 非空才算"已启用" —— 填任意非空串（如 `ollama`）即可。

## 5. 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/nl/settings` | `sys:config` | 读配置（密钥掩码） |
| PUT | `/api/v1/nl/settings` | `sys:config` | 保存，即刻生效 |
| POST | `/api/v1/nl/settings/test` | `sys:config` | 真发一次 function calling 请求，不落库 |

`PUT` 的 `apiKey` 是三态：**空 = 不修改**、`__CLEAR__` = 清空、其它 = 替换。

`POST /test` 失败也返回 200 + `ok=false`：这是探测结论，不是服务端故障，失败原因（key 无效 / 地址不通 / 模型不支持工具）本身就该直接展示。

权限用 `sys:config` 而不是 `sys:read`：能改接口地址和 key，等于能决定"系统把业务数据发给谁"。

## 6. 模型能做什么、不能做什么

- **能**：把一句话翻译成结构化意图（查库存、列单据、建草稿单、提交单据、补货建议）。
- **不能**：审核、入库、出库、删除、改库存。这些**接口根本不存在**，不是靠提示词约束的。
- **不论用不用模型**：写操作都要走"计划预览 → 人工确认 → 服务端校验回执"。模型没有执行权，也没有授权权；AI 复核只能否决，不能把否决翻回通过。

## 6. 能听懂哪些说法（单据列表）

模型只负责"把话翻成一次调用"，**能不能做到取决于接口有没有这个参数**。单据列表目前支持：

| 说法 | 落到的参数 |
|---|---|
| 最近一个月 / 上个月 / 本周 / 近7天 | `dateFrom` + `dateTo`（按今天换算） |
| 2026-09-01 到 2026-09-30 | `dateFrom` + `dateTo` |
| 按时间排序 / 按时间顺序 | `orderBy=bizDate` + `sortDir=desc`（最新的在前） |
| 从早到晚 / 最早的在前 | `sortDir=asc` |
| 按金额 / 金额最大的 | `orderBy=totalAmount` |
| 已审核的 / 草稿 / 待审核 | `status` |
| 第2页 / 前50条 | `page` / `size`（默认 20） |

结果摘要会**自证条件**，比如：

```
出货单列表（2026-09-27 ~ 2026-10-27）：第 1 页，共 98 张，按业务日期降序
```

如果摘要里没有出现你给的时间条件，说明它被忽略了 —— 这不是"数据本来就没有"，要当成问题反馈。

> 早期版本的工具定义里**没有** `dateFrom/dateTo/orderBy`，所以模型即使听懂了"一个月内""按时间排"也无处可传，只能回一份全量列表。这是"感觉没在用 AI"的主要来源之一，已修复。

## 6.5 自定义查询（AI 自己写 SQL）

固定工具的参数是写死的，只能表达设计者想到的问法。凡是出现下面这些情况，模型会改用
`sql_query` 自己写一条 SELECT：

- 跨表关联（单据 + 客户 + 商品）
- 分组、排行、占比、同比、平均、最大最小
- 多条件组合筛选
- 问的是"总结 / 分析 / 有什么问题 / 情况怎么样"

然后系统会把结果再交给模型，写成人话回答。例如问「按客户统计近30天的出货金额，给我前5名」：

> 近30天出货金额最高的是海雾直播工作室，出货16单、共56件，金额9336.6元。
> 第二到第五名依次是城南百货7229.7元、季风电商6430.5元……

下面还会附上明细表，但结论已经先说清楚了。

### 安全边界（四道闸，缺一不可）

| 闸 | 做法 | 为什么 |
|---|---|---|
| 只读 | 事务只读 + 语句必须 SELECT/WITH + 禁写关键字 | 前端能绕过，数据库这一层绕不过 |
| 表隔离 | 执行时 `SET LOCAL search_path = ai`，只能查到 `ai` schema 下的**视图** | `sys_config`（Key 密文）、`app_users`（口令哈希）根本不在可见范围 |
| 租户 | `SET LOCAL app.tenant_id`，视图内部按此过滤 | 忘了设 → 返回空，而不是返回全部租户的数据 |
| 成本 | 8 秒超时 + 外层 200 行上限 | 防一条笛卡尔积拖死库 |

可查的表只有 12 个：`sales_orders`、`sales_order_lines`、`purchase_orders`、
`purchase_order_lines`、`return_orders`、`return_order_lines`、`inventory_balances`、
`products`、`skus`、`suppliers`、`customers`、`warehouses`。

写 SQL 时不要自己加 `tenant_id` 条件（系统已隔离），金额单位是分，列名请用中文别名。

### 代价

这类问题要**两次模型调用**（先写 SQL，再组织回答），响应通常 15~25 秒。
标准问法（查库存、列单据）仍走固定工具，1~3 秒返回。

## 7. 排查

| 现象 | 原因 |
|---|---|
| 点了保存，状态还是关键词 | 没填 key，或解析方式没改成"大模型" |
| 测试连接 401 | key 无效/欠费。错误信息里会带 DeepSeek 的原始报错 |
| 测试连接超时 | 地址填错、网络不通，或模型名不存在 |
| 测试通过但指令识别不准 | 换模型（如 `deepseek-chat` → `qwen-plus`）再试；也检查是不是把 `reasoner` 类模型当成了通用模型 |
| 保存后重启又变回关键词 | 多半是 `ERP_NL_SECRET` 变了，旧密文解不开 → 重新填一次 key |
