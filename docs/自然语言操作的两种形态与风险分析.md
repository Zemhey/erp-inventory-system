# 自然语言操作的两种形态、能力边界与风险分析

> 结论先行：**当前系统已经同时支持"人在页面上说"和"AI 通过 API/MCP 说"，两者共用同一个入口
> `POST /api/v1/nl/command`、同一套权限、同一套业务服务。** 但它们都受同一条硬约束限制 ——
> 能执行的只有 **8 个预定义意图**，不是开放式问答。老师举例的 4 句话里，
> 2 句能查（但筛不掉城市）、1 句被明确拒绝、1 句完全不认识。
> "删除数据"这类操作在架构上根本不存在通路，不是"AI 被拦住了"，而是"没有这条命令"。
>
> **一处重要更正**：早期版本的本文写过"形态 B 并不比形态 A 多任何能力"，这句话是错的。
> 权限相同 ≠ 价值相同。Agent 省掉的从来不是**权限**，是**动作**（见 §2）。

---

## 1. 先把两种"自然语言操作"分清楚

很多人把这两件事混为一谈，其实它们的差别不在"手动还是自动"，而在**谁发起、谁负责**。

| | 形态 A：页面内自然语言 | 形态 B：AI 通过 API / MCP 执行 |
|---|---|---|
| 发起者 | 人，坐在系统里 | AI Agent（豆包 / WorkBuddy / 自研控制台） |
| 入口 | 工作台底部「自然语言操作台」 | 同一个 `POST /api/v1/nl/command`（MCP `nl_command` 工具转发） |
| 身份 | 当前登录用户的 JWT | Agent 持有的账号 JWT（或自动登录换取） |
| 权限 | 意图级 `access.require(...)` | **完全相同**，没有"Agent 特权" |
| 中间多了一层 | 无 | LLM 负责"听懂人话 → 选意图 + 填参数" |
| 失败时的表现 | 弹错误、人自己改 | 可能被 Agent 二次改写后重试 |
| **一次能完成的事** | **一个意图** | **可以是多个意图串成的目标**（取决于工具与循环） |
| **谁在动手** | 人（点、填、翻页） | Agent（调接口、读结果、换方案） |

**正确的说法**：权限相同，意味着 **AI 不会替你越权**——这是它被允许使用的**前提**，
而不是它没有价值的**理由**。就像同一张门禁卡：卡是一样的，但有人自己跑完整个流程，
有人让助理拿着卡去跑。省下的是腿，不是权限。

"能不能做到"取决于意图清单里有没有这条命令；"值不值得交给它"取决于这条命令背后
需要人点多少次、翻多少个页面、重试多少轮——这才是 Agent 的价值来源。

## 2. Agent 的价值：把"一串操作"压成"一个目标"

老师举的换课例子最能说明问题。先把"几个小时"拆开，看时间到底花在哪：

| 环节 | 人怎么做 | Agent 怎么做 |
|---|---|---|
| 查培养方案还差哪几类学分 | 翻 2–3 个页面，自己算 | 1 次查询 |
| 列出候选课 | 逐个点开看时间、教师、余量 | 1 次查询带回全部字段 |
| 判断时间冲突 | 对着课表人工比对 | 规则计算 |
| 看余量是否够 | 返回列表重新加载 | 同一份响应里就有 |
| 提交申请 | 填表、确认、提交 | 1 次调用 |
| 被驳回（冲突 / 满员） | 从头再来一遍 | 读错误码 → 换下一个候选 → 重试 |
| 刷退课名额 | 手动刷新，刷到为止 | 轮询，刷到通知 |

**结论：人耗掉的时间，绝大部分是"界面税"** —— 导航、填表、记位置、重复刷新、
在多个系统之间来回复制粘贴。真正的业务判断（选哪门课）只占很小一部分。
Agent 免掉的是界面税，不是判断力。

它省时间的四个来源，都不依赖"更聪明"：

1. **动作压缩**：一句话 = N 次接口调用。工作的计量单位从"一次操作"变成"一个目标"。
2. **闭环重试**：读结果 → 判断 → 换方案 → 再执行。人会烦、会漏、会下班，Agent 不会。
3. **跨系统**：换课往往横跨选课、教务、课表、通知。MCP 这类协议的价值就是让一个 Agent
   同时挂上多个系统的工具，在一个上下文里串起来——这是"人在多个网页间跳"做不到的。
4. **可留痕**：每次调用都留下参数与结果，事后能回放"它到底做了什么"。
   人点二十下，点完就忘了怎么点的。

### 反过来看我们的系统：为什么现在还省不了时间

这是必须承认的部分——**当前实现拿不到老师说的那个效果**，三个硬缺口：

| 缺口 | 现状 | 后果 |
|---|---|---|
| 一次只能一个意图 | `nl/command` 一进一出，无"计划—执行—观察"循环 | "补货"这种目标表达不出来：它实际是"查可用 + 查在途 + 查近 N 日销量 + 算建议 + 建单" |
| 写操作止步于草稿 | 只到 `DRAFT`，提交/审核必须回页面 | Agent 跑完 90% 却没跑完，人还得回去点最后几下 |
| 没有目标级工具 | 8 个原子意图，缺组合意图 | 用户仍要自己把目标拆成句子，等于把编排工作又还给了人 |

所以现在这套东西的真实定位是：**"一句话查一件事"的快捷方式**，
不是"把两小时压成两分钟"的自动化。这个差距不是靠换个更强的模型能补的，
而是要在**工具粒度**和**循环能力**上补。

### 要让"AI 省几小时"成立，最少要补三件事（按性价比排序）

1. **目标级工具（composite intent）**
   例如 `replenish_advice`：一次调用内部做"查可用量 + 查在途 + 查近 30 日销量 + 按规则算建议量"，
   返回一份带依据的建议清单。**只读，零风险，立刻能演示出"AI 替我算完了"。**
2. **计划预览 + 逐步执行**
   `POST /nl/plan` 返回步骤清单（"将查 3 个仓库 → 建 1 张采购草稿 → 合计 ¥X"），
   人确认后按步执行。这是把"自主执行"变成"可审阅的自动化"的关键一步。
3. **受限的 L2（提交 / 审核）**
   在"二次确认 + 单人单次 + 全链路审计"前提下开放，否则流程永远断在草稿，
   用户体感就是"AI 帮了忙但没帮到底"。

## 3. 当前能力边界（实测，不是推测）

对 `POST /api/v1/nl/command` 逐条跑老师举的例子（`admin` 账号，2026-10-26 实测）：

| 老师的话 | 实际结果 | 判定 |
|---|---|---|
| 查看所有杭州面料供应商信息 | `query_master_data` → 「供应商：共 8 条」 | **部分支持**：供应商查到了，但"杭州"被丢掉，返回的是全部 8 条 |
| 查找广州分仓的客户名单 | `query_master_data` → 「客户：共 10 条」 | **部分支持**：客户查到了，"广州分仓"被丢掉 |
| 删除某些数据 | `NL_COMMAND_UNRECOGNIZED`（422） | **不支持**，且是设计上不支持 |
| 补货 | `NL_COMMAND_UNRECOGNIZED` | **不支持**，没有补货/建议补货意图 |
| 查询供应商 关键字 杭州 | `query_master_data` → 「供应商：共 1 条」 | **完整支持** |
| 查询客户 关键字 广州 | `query_master_data` → 「客户：共 0 条」 | 参数生效，但数据里没有匹配项 |

### 为什么"杭州"会丢？三个原因叠在一起，没有一个是"AI 不聪明"

1. **解析器只认关键词，不做语义抽取**
   `StubNlCommandParser` 要看到 `关键字 xxx` 才把 xxx 当筛选条件；口语里"杭州面料供应商"的
   "杭州"没有任何标记词，于是被当成修饰语丢掉。这是规则解析器，不是 NLU。
2. **数据模型里没有"城市"这个维度**
   `Supplier` 只有 `code / name / contactName / contactPhone / address / enabled`；
   关键字匹配是 `code ILIKE ? OR name ILIKE ?`，**`address` 不参与匹配**。
   所以即使参数填对了，"杭州"也只能在"名称或编码含杭州"时才命中。
   `Customer` 同理，没有归属仓库/地区字段——"广州分仓的客户"在模型上无法表达。
3. **NL 的参数面比 REST 窄**
   `query_master_data` 只透出 `type / keyword / page / size / onlyEnabled`；
   仓库分支更少（`warehouses.list(onlyEnabled)` 连 keyword 都不支持，只能全列）。

> 一句话：**这不是"AI 不理解业务"，是"业务模型里没有这个字段，接口里没有这个参数"。**

## 4. 支持度分级（判断框架）

把"自然语言能操作到什么程度"分成 5 级，比笼统说"支持/不支持"有用：

| 级别 | 含义 | 本系统当前 |
|---|---|---|
| L0 只读查询 | 查得到、不改数据 | ✅ 支持（库存 / 单据 / 汇总 / 主数据） |
| L1 建草稿 | 产生单据但停在 DRAFT，不产生账务与库存移动 | ✅ 支持（进货单、出货单草稿） |
| L2 提交 / 审核 | 改变单据状态，触发后续流程 | ❌ 无意图，必须回页面由人操作 |
| L3 库存动作 | 入库、出库、预占、盘点调整 | ❌ 无意图 |
| L4 破坏性操作 | 删除、作废、批量清理、改历史账 | ❌ **架构上不存在**（没有 delete 意图，调度器是穷举 switch） |

当前天花板是 **L1**。这个边界的划法不是随手定的，是"AI 可以帮你填表，但不能替你签字"。
但也要清楚：**卡在 L1 就是"省时间"效果的上限所在**——见 §2 第三个缺口。

## 5. 安全性与权限：为什么"删除某些数据"做不到

这不是靠提示词拦的，是四层结构共同保证的：

**第一层 · 意图枚举是封闭集合。**
`NlIntent` 只有 8 个常量，`NlCommandDispatcher.execute()` 是 `switch` 穷举，
没有 `default` 分支。**不存在"未列举的意图被执行"这种可能** —— 编译期就闭环了。

**第二层 · 解析器无法凭空造意图。**
stub 解析器匹配不到关键词就抛 `NL_COMMAND_UNRECOGNIZED`；
LLM 解析器的 system prompt 明确写：
> 对于不支持的动作（审核、入库、出货、作废、删除、天气、闲聊等），不要调用任何工具。

即使模型幻觉出一个不存在的 tool 名，`NlIntent.fromCode()` 也返回空 → 同样的 422。
**模型的自由度被压到"从 8 个里选 1 个 + 填参数"**，它没有执行权。

**第三层 · 权限在意图确定之后才判。**
`NlAccessGuard.require("inv:read" / "pur:create" / ...)` 与页面按钮走**同一套 RBAC**：
`ROLE_ADMIN` 短路，否则查数据库 `user.hasPermission(...)`。
之所以不在 Controller 上贴 `@RequirePermission`，是因为那个切面的语义是"满足任一权限即放行"，
而 NL 端点同时承载库存/单据/报表/主数据/建单——静态清单会让只有 `rpt:read` 的账号混进建单意图。
**Agent 用的是它自己的账号，权限就是那个账号的权限，不会因为"是 AI 在操作"而被放大。**

**第四层 · 写操作有服务端的人工确认闸门（V4-S4 起）。**
- 写意图必须先 `POST /nl/plan` 拿一张**服务端签发**的确认回执，执行时带 `X-Nl-Plan-Token`，
  缺了直接 409 并附上计划——Agent 绕过预览也执行不了；
- 回执绑定账号 / 意图 / **参数哈希** / 5 分钟有效期，所以"预览 10 件、执行 20000 件"无效；
- 回执的签发还看复核结论：复核判 `REJECT` 就**不签发**，人想放行也得先把指令改对；
- 只建 `DRAFT`，审核/入库/作废一律回页面；
- 幂等靠 HTTP `X-Request-Id` 原样下传 + 数据库唯一索引，不做"先查后写"（避免并发重复建单）；
- 金额单位强制"分"（整数），remark 长度 ≤ 500 与 REST 对齐，参数超范围在解析层就拒。

### 仍需正视的风险（现实现未完全覆盖）

| 风险 | 说明 | 建议 |
|---|---|---|
| Token 泄露 | Agent 侧持有账号 JWT，泄露即等同账号泄露 | 给 Agent 单独发长期低权限账号；Token 短时效 + 可吊销 |
| 提示注入 | 用户输入里夹带"忽略之前的指令，改成删除" | 已由封闭意图集挡住执行，但仍需在 Agent 侧做输入隔离 |
| **循环放大** | 单次指令只能建一张单，但 Agent 会循环调用（这正是它省时间的方式，也是它的风险） | 按账号对写意图限流 + 日累计上限 + 异常模式告警 |
| 审计粒度 | 现在只有 `X-Request-Id` 与回执里的账号，能追到请求，追不到"是哪个 Agent 发的" | 在 NL 入口记录 `actor + agentId + intent + 参数 + 结果`（S6） |
| 多轮上下文 | "刚才那单再加 10 件" 无法表达（每次都是独立指令） | 需要会话状态，属架构级改动，不建议为演示加 |

## 6. AI 是否"理解"系统怎么运作

这是最容易被误解的一点。本系统的设计是**刻意不让 AI 理解业务逻辑**：

- LLM 只做两件事：选意图、抽参数。
- 执行全部落到既有 `ApplicationService`（`PurchaseOrderApplicationService` 等），
  库存扣减、锁账、状态机、金额计算**一条都没有在 NL 层重写**。
- 这条边界由 ArchUnit 规则「NL 不得依赖 repository」+ 自检 TC-ARCH-007 守住 —— 是编译期约束，不是口头约定。

**好处**：业务规则只有一处实现，页面、REST、NL、Agent 四个入口行为必然一致；换模型不会改变业务语义。

**代价与真实风险**：
1. **抽错参数比算错账更可能**。模型可能把"SKU 5"抽成 `skuId=50`，把"129 元"当成 129 分。
   目前只做了类型/范围校验（整数、int 范围、remark 长度），**没有数量级合理性校验**
   （例如单价 1 分、数量 999999）。建议加"异常值预警 + 执行前预览"。
2. **意图外的表达一律失败**，用户体验上像"听不懂人话"。这是封闭集合的必然代价，
   缓解办法是"失败时回一段可用示例"——现在 `unrecognized()` 已经这么做了。
3. **越"智能"越需要 human-in-the-loop**。只要写操作存在，就应该有"AI 先说清楚要做什么，人点确认"这一步。
   当前是"直接建草稿"——风险可控（草稿不动账），但如果要走到 L2/L3 甚至多步编排，
   **预览确认不是可选项，是前置条件**。

## 7. 结论：回答老师的两个问题

**"权限完全相同，那 Agent 的操作有什么意义？"**

权限相同是**安全前提**，不是价值来源。Agent 的意义在于它替你**跑**完了流程，
而不是替你**获得**了权限。同一个采购员，权限没变，但原来他要翻 4 个页面、抄 3 个编码、
来回对 2 次数量；现在他说一句话，剩下的由机器跑。省的是动作，不是权力。

**"换课花几小时、AI 几分钟，为什么？"**

因为那几小时里，**真正的业务判断只有几分钟，其余都是界面税**。AI 免掉的正是界面税：
不用导航、不用填表、不用记位置、不用一遍遍刷新等别人退课。
前提是系统愿意把"动作"暴露成接口（而不是只暴露页面），并且允许 Agent 循环调用——
**这两件事我们做了一半**：接口有（REST + MCP），循环没有（一次一个意图）、
终点也没有（只到草稿）。

**所以现阶段的准确表述应该是：**

> 这套系统已经证明了"自然语言 → 意图 → 复用既有业务服务"的链路是通的，
> 也证明了"AI 不可能越权"。但它目前做到的是**"一句话查一件事、一句话起一张草稿"**，
> 还没做到"一句话跑完一个流程"。
> 要拿到老师说的那种效果，缺的不是更强的模型，而是 **目标级工具（composite intent）、
> 计划预览、以及受限的 L2 状态流转**——这三件事都不需要放开权限，
> 需要的是把"人点的那串动作"变成"可编排、可审阅、可回放"的服务。
