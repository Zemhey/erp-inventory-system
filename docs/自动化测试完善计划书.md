## 1. 背景与现状评估

### 1.1 已有测试资产（以当前代码为准）

| 层 | 位置 | 规模 | 说明 |
|---|---|---|---|
| L1 单元测试 | `backend/server/src/test/**/*Test.java` | 18 个 | 金额、取整、状态机、领域规则 |
| L2 集成测试 | `backend/server/src/test/**/*IT.java` | 73 个 | 真 PostgreSQL（Testcontainers），含事务/锁/幂等/并发 |
| L4 Web E2E | `frontend/web/e2e/*.spec.ts` | 38 条 | 认证、主数据、采购、销售、库存、权限、退货、结算、审计、系统接口 |
| L4 小程序 E2E | `app/uniapp/e2e/*.spec.ts` | 22 条 | 登录、库存、流水、单据、报价、发货、应收、审批 |
| 覆盖率门禁 | `backend/server/build.gradle.kts` | 行 ≥60% / 分支 ≥50% | JaCoCo `jacocoTestCoverageVerification` |
| 契约文档 | `packages/api-contract/openapi.yaml` | 1 份 | 三端与后端接口定义 |
| 静态契约检查 | `scripts/contract-check.py`、`contract-gap-scan.py`、`schema-field-check.py` | 3 个脚本 | 只做源码/文档层的静态比对 |
| CI 门禁 | `.github/workflows/ci.yml` | 4 个 job | `build-and-test` / `contract-check` / `index-check` / `web-e2e` |

**已覆盖的高难场景**（说明系统测试基础不错）：

- 并发防超卖：`InventoryReserveIT` —「100 个请求抢 50 件库存，绝不超卖」；
- 并发幂等：同一 `requestId` 并发只生效一次（数据库唯一约束兜底）；
- 金额整数运算与 HALF_UP 舍入（`MoneyMathTest`）；
- 结算锁账、日清月结、对账（`E2E-17 / E2E-18` + 后端 `SettlementIT`）。

### 1.2 现状结论

系统测试**已覆盖主干业务，且后端细节相当厚**。真正的短板不在“多写几条用例”，而在**四个空白层**：

1. **运行时契约校验缺失**：有 `openapi.yaml` 和静态检查，但接口**实际响应**是否与文档一致，无自动校验；三端与后端易悄悄漂移。
2. **性能/容量测试缺失**：逻辑正确 ≠ 扛得住。并发正确性只在进程内线程验证过，真实 HTTP 负载、连接池、批处理耗时均未测。
3. **测试地基不完整**：无统一 `test-kit` 数据工厂；无 `@Profile("test")` 的 reset / time-travel / seed 后门（代码中 0 处）。
4. **安全与 flaky 治理缺失**：无 OWASP ZAP / Trivy 门禁；无隔离区（quarantine）与覆盖率趋势看板。

### 1.3 核心矛盾

> **Web E2E 已达 38 / 40 条，逼近策略红线。**

因此本计划的基调是：**不再盲目增加 E2E，而是“补空白层 + 补高风险业务缺口”，并把能下沉的覆盖下沉到 API / 集成层。**

## 2. 目标与原则

### 2.1 目标（可衡量）

| 维度 | 现状 | 目标 |
|---|---|---|
| 运行时契约校验覆盖 | 0 | `openapi.yaml` 全部 paths 100% 被校验 |
| 性能测试场景 | 0 | 3 个场景 + 夜间基线趋势 |
| 测试地基 | 无 test-kit / 无 test 后门 | 1 个 `test-kit` 包 + 3 个后门 + 1 条“生产不注册”验证 |
| Web E2E 数量 | 38 | **≤ 40**（结构优化，不破红线） |
| 后端行覆盖率 | ≥60% | ≥70% |
| flaky 率 | 未度量 | < 2% 且全部进隔离区 |
| 安全门禁 | 无 | ZAP baseline + Trivy 每 PR |
| 跨端一致性 | 无 | 1 条 YAML 用例三端（Web/小程序）跑通 |

### 2.2 原则

1. **测试金字塔**：便宜好写的测细节（L1/L2 写厚），昂贵易碎的只测主干（L4 写精）。
2. **E2E 只守关键路径**：新增 UI 验证优先用 API / 组件测试；确需 E2E 的，先淘汰一条低价值老用例。
3. **先补空白层**：契约、性能、地基、安全这类“乘数型”能力优先于再加业务用例。
4. **指标驱动**：每条任务都要有可验收的量化标准。
5. **主干常绿**：红灯立刻修，来不及就进隔离区，绝不带红继续开发。

### 2.3 不在本计划范围（Out of Scope）

- 应用性能调优（本计划只做“测量”，不做“优化”）；
- 大模型 / NL 指令的语义质量评测；
- 生产环境压测与渗透测试（只在测试/预发环境执行）。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Web E2E 触顶（38/40） | 无法直接加 UI 用例 | 新增前先淘汰/降级；能用 API 的不上 E2E |
| 性能环境不稳定、结果不可复现 | 压测结论不可信 | 固定数据量 + 固定环境 + 记录基线与机器规格 |
| 契约测试误报多 | 团队不信、被绕过 | 先只读接口、设白名单；逐步放开写接口 |
| 数据工厂维护成本 | 越写越重 | 只抽高频对象；低频场景仍用 API 直连 |
| 时间紧、排期被压缩 | 计划落空 | 死守阶段一（契约+地基+性能三件）；P2 可顺延 |

## 7. 流程与门禁变更

- **DoD 更新**：新功能合入需满足「L1 + 涉及 DB/事务补 L2 + 改接口更新 `openapi.yaml` 且契约测试通过 + 关键流程补 1~3 条 E2E（仅当端已就绪）」。
- **PR 门禁矩阵**：

| 触发 | 必过门禁 |
|---|---|
| 每次 PR | 编译 + L1 + L2 + 契约（静态+运行时）+ Web 冒烟 E2E + ZAP + Trivy |
| 每晚 | 全量三端 E2E + 性能 + 覆盖率趋势 |
| 发布 | 构建镜像 → Trivy → 部署 → 线上冒烟，失败自动回滚 |

- **主干常绿**：红灯立即修；来不及则进隔离区并登记归因，**绝不允许带红继续开发**。

## 9. 附录

### 9.1 术语

- **契约测试**：校验接口实现是否满足 `openapi.yaml` 约定；
- **属性测试 / fuzz**：自动生成非法输入，验证系统稳健性；
- **flaky**：同代码结果不稳定（时红时绿）；
- **隔离区（quarantine）**：暂时移出主干但仍跟踪的 flaky 用例集合；
- **test 后门**：仅测试环境开放的 reset / time-travel / seed 接口。
