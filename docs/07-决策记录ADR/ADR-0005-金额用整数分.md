# ADR-0005: 金额一律用整数「分」存储

- 状态：已采纳
- 日期：—

## 背景

进销存系统涉及大量金额计算：行金额、折扣、促销叠加、合计、对账。
金额精度问题（浮点误差）是财务类系统最经典、最致命的缺陷来源；同时它是**自动化测试最容易出 bug 的区域**。

## 决策

1. 所有金额字段以 **`BIGINT`，单位「分」** 存储（人民币 1 元 = 100 分）；
2. **禁止 `FLOAT` / `DOUBLE` / `REAL`** 出现在任何金额字段；
3. 折扣用 **整数万分比**（`9000` = 9 折），禁止浮点折扣；
4. 所有舍入**显式**指定 `RoundingMode.HALF_UP`，且**集中在一处工具类**；
5. **先算行金额，再 Σ 汇总**；禁止用单头合计反算行金额。

## 理由

- 整数运算**无精度损失**，结果确定、可复现、可断言 —— 这对自动化测试是决定性的：浮点结果"差不多相等"会让断言变成模糊判断。
- 折扣用整数万分比避免 `0.9` 这类无法精确表示的小数参与乘法。
- 舍入集中在一处：否则"每处各自舍入"会导致行金额之和 ≠ 合计（对账差额非 0，违反不变量 INV-5）。
- "先算行再汇总"保证**单头合计 == 明细合计**这一恒等式在结构上成立。

## 替代方案与放弃原因

- **`DECIMAL(18,2)`**：数据库层可用，但 Java 侧仍需 `BigDecimal`，且 JSON 传输/前端计算容易出现精度与类型转换问题。整数分在 JSON 中无歧义、前端可直接用整数运算。放弃。
- **浮点 + 误差容忍**：绝不可接受。对账要求差额**严格为 0**。放弃。

## 后果

- ✅ 金额运算确定、可断言，适合财产式测试
- ✅ 对账恒等式（INV-5）在结构上成立
- ⚠️ 展示层需做 分→元 转换（集中在一处，禁止各处 `÷100`）
- ⚠️ 对外接口 JSON 中金额是整数分 → **必须在契约文档中显式说明**（已写入 [05 §2](../05-接口契约规范.md)），否则前端/测试会误解
