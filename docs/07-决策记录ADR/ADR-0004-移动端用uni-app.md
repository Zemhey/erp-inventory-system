# ADR-0004: 移动端用 uni-app 一套代码出三端

- 状态：已采纳
- 日期：—

## 背景

课程必选四端：服务端、Web 端、小程序、安卓 APP（可选：苹果、鸿蒙、PC）。
单人项目，时间有限，"每项 5%"的可选端是便宜分，但三端各写一套 = 维护成本爆炸。

## 决策

**Web 端深度自研（Vue3 + TS）；小程序 / Android / 可选端用 uni-app 一套代码出包。**

## 理由

1. **保分效率**：uni-app 一套代码同时出小程序 + H5 + APK，用最低成本拿满必选三端与多数可选端（每项 5%）。
2. **技术栈统一**：uni-app 用 Vue 语法，与 Web 端同语言同思维，切换成本近零。
3. **避免"四端同一层皮"**：Web 端做深（完整 ERP 交互：键盘操作、批量录入、虚拟滚动表格），避免答辩时被质疑"只是一个壳"。

## 深化策略（有余力时）

**Android 可重写为原生 Kotlin** 作为加分亮点。原因：
- uni-app 出的是混合渲染包，**Appium 只能测到 WebView 层**，测试价值有限；
- 原生包的 Appium(UiAutomator2) 测试才是真功夫 → 能写进简历的硬内容。

## 替代方案与放弃原因

- **三端各写原生**：质量最高，但单人时间不可能。放弃。
- **Flutter 一套出全端**：小程序支持不成熟（需额外转译），生态在国内企业系统偏弱。放弃。
- **React Native**：小程序不支持。放弃。

## 后果

- ✅ 低成本拿满多端分数与加分
- ✅ 与 Web 端同栈，认知负担低
- ✅ `packages/api-contract` 生成的 TS SDK 三端共用
- ⚠️ uni-app 对复杂交互（批量录入、大表格）能力有限 → 复杂交互只在 Web 端做
- ⚠️ 小程序自动化依赖微信开发者工具 → 必须用 Windows self-hosted runner（见 ADR-0006 的 CI 部分与 [06-测试策略 §6](../06-测试策略.md#6-ci-门禁)）
