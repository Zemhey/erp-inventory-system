# ADR-0008: OpenAPI 契约为单一事实源

- 状态：已采纳
- 日期：—

## 背景

多端项目（服务端 + Web + 小程序 + Android）最容易出现的失控模式：

- 后端改了字段名，前端不知道，线上炸；
- 三端各自手写接口调用，出现三份不一致的实现；
- 文档（如果有）永远落后于代码。

传统解法是"写文档 + 口头同步"，必然失败。

## 决策

`packages/api-contract/openapi.yaml` 作为**单一事实源（Single Source of Truth）**：

1. **先改契约，再改两侧实现**；
2. 服务端由 springdoc 导出 OpenAPI，**在 CI 中与契约源 diff，不一致则构建失败**；
3. 三端 SDK 由契约**生成**（TypeScript client），Web / 小程序 / Android 共用；
4. 契约测试（schema 校验 + Pact）直接从契约派生；
5. 属性测试（Schemathesis）以契约为输入自动生成请求；
6. `index/api-map.md` 也由契约生成。

## 理由

1. **消灭三端不一致**：三端调用的是同一份生成的客户端，字段名/类型不可能各自漂移。
2. **CI 可拦截破坏性变更**：diff 不一致就失败 —— 这是"接口契约即治理手段"，而不是文档。
3. **测试用例免费增长**：契约一旦成型，Schemathesis 会自动生成大量边界/异常请求，**白捡一批测试**。
4. **它同时是代码索引的输入**：呼应 ADR-0009 —— 索引不必手写。

## 替代方案与放弃原因

- **手写 API 文档（Markdown/Swagger 手改）**：必然腐化。放弃。
- **只看代码、不写契约**：三端不一致无法拦截。放弃。
- **各端手写 HTTP 客户端**：重复劳动 + 必然漂移。放弃。

## 后果

- ✅ 契约变更成为"一件事"，而不是"N 件事"
- ✅ 破坏性变更在 PR 阶段就被拦住
- ✅ 属性测试与契约测试几乎零额外成本
- ⚠️ 引入生成步骤的复杂度（构建脚本）→ 一次投入，长期收益
- ⚠️ 约束了"随手改接口"的自由度 → 这正是目的
