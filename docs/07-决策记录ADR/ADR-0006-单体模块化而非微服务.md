# ADR-0006: 单体模块化，不做微服务

- 状态：已采纳
- 日期：—

## 背景

目标是"大型商业系统"。常见的误解是：大型 = 微服务。于是很多人把单人项目拆成 8 个微服务，然后时间全部消耗在服务发现、分布式事务、链路追踪、跨服务调试上。

## 决策

**单体模块化（Modular Monolith）**：一个 Spring Boot 应用，内部按限界上下文严格分模块（iam/mdm/inv/pur/sal/rma/set/rpt/sys/shared），模块间只允许通过**应用服务接口**调用，**禁止跨模块直接访问对方的表**。

## 理由

1. **复杂度花在正确的地方**：单人项目的真正价值是"库存/金额在并发下的一致性"。微服务会把时间转移到分布式基础设施，而这部分对测试与简历的边际价值低。
2. **事务简单**：库存扣减 + 单据写入 + 流水记录能在**一个本地事务**内完成，不需要 Saga/TCC/最终一致补偿 —— 这直接让"防超卖"这类断言变得干脆。
3. **调试与测试成本低**：一个进程起、一份日志、一个 traceId。E2E 与集成测试搭建成本显著下降。
4. **模块边界仍然存在**：用包结构 + 架构测试（ArchUnit）强制约束，保留未来拆分的可能，属于"微服务的准备工作已做，但不是现在"。

## 替代方案与放弃原因

- **微服务（8 个服务）**：分布式事务、服务发现、跨服务集成测试的成本远超单人承受范围；且会让核心业务的一致性断言变得模糊。放弃。
- **完全不分模块的单体（大泥球）**：无法维护，也不是"大型商业系统"该有的样子。放弃。

## 后果

- ✅ 事务边界清晰，一致性可强断言
- ✅ 起环境简单（一个 compose），CI 快
- ✅ 仍可用 ArchUnit 强制模块依赖规则（`mdm` 不得依赖 `pur`；`inv` 变动唯一入口）
- ⚠️ 需自律维护模块边界，否则会退化成大泥球 → 用 ArchUnit 测试在 CI 中强制执行
- ⚠️ 未来若要拆分，需先抽接口 → 因为已按端口/适配器分层，拆分路径已预留

## 补充：与"大型"的关系

**"大型商业系统"的定义不是服务数量，而是：订单/库存/金额三者在并发下仍然一致、可对账、可追溯、可回滚。**
本 ADR 让项目把资源集中在这一点上。
