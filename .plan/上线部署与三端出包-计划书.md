## 0. 一句话结论

三端代码已经成形，真正的卡点不在代码，而在 **服务器初始化、备案/账号/证书** 这四类外部资源。
建议：**备案审核期间用「服务器 IP + 非标端口」把 API 跑起来供三端联调，域名暂不解析、80/443 不开**；
备案通过后再切 HTTPS、配小程序域名白名单、出正式包。这样既不空等备案，也不碰备案红线。

另有两个必须先处理的事实：

1. **本机 `main` 比 `origin/main` 领先 354 个提交** —— 服务器直接 `git clone` GitHub 会拿到一份很旧的代码。
2. **2C2G 不适合在服务器上编译** Gradle/npm —— 应采用「本机构建镜像 → 导出 → 服务器导入」的方式。

## 3. 关键决策：备案期间怎么部署

### 3.1 "只部署后端、不部署前端"是否影响备案？

**不影响。** 备案审的是**域名对应的网站**，不是服务器上跑了什么端口：

- 备案审核期间，只要 **域名不解析到这台服务器**、**80/443 不提供网站服务**，就不会因为服务器上有个 API 而被驳回；
- 用 `http://<服务器IP>:<非标端口>` 做自己的联调，不进入域名审核链路；
- 但合规上仍要守住：**不公开宣传、不对外提供注册、不做成公开站点**；测试结束关闭该端口。

**不过，建议不要真的"只起后端"** —— 现有 `deploy.sh` 的健康检查依赖 web 容器的 `/readyz`，
拆成 API-only 需要额外 compose override 并绕开部署脚本，收益为零。更省事的做法是：

> **全套 compose 起在 `IP:18080`，三端只使用 `/api`，Web 页面不对外提及。**
> 对 App / 小程序 / PC 来说，这与"只起后端"完全等价（都是 `http://IP:18080/api/v1`）。

### 3.2 三个方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 全套起、只用 API**（推荐） | 现有 compose 原样部署，安全组只开 18080 | 零改动、部署/回滚/备份脚本全部可用 | Web 页面也能被访问（可限制来源 IP） | ✅ 采用 |
| B. 真 API-only | 新增 compose override，只发布 backend 18080 | 暴露面最小 | `deploy.sh` 健康检查失效，回滚脚本也要改 | ❌ 不划算 |
| C. 等备案通过再部署 | 什么都不做 | 最保守 | 白等 1~3 周，App/小程序无法提前联调 | ❌ 浪费时间 |

### 3.3 备案期间三端能测到什么程度

| 端 | 能否连 IP 联调 | 限制 |
|---|---|---|
| Web / H5 | ✅ | 浏览器直接开 `http://IP:18080` |
| 微信开发者工具 | ✅ | 导入 `dist/build/mp-weixin`，勾选"不校验合法域名"；**真机预览依赖开发者工具代理，同样需要该开关** |
| 微信真机正式访问 | ❌ | 必须 HTTPS + 已备案域名进后台白名单；备案前做不到 |
| 安卓演示包 | ✅ | WebView 壳可访问 HTTP；正式 APK 建议等 HTTPS |
| PC 便携包 | ✅ | 打包时把 `apiTarget` 烘成 `http://IP:18080` 即可 |

### 3.4 三条红线（测试期）

1. **域名不解析到这台服务器**，不在任何地方用域名访问；
2. **80/443 不开放**，只用 18080 这类非标端口；
3. 测试期结束（备案通过或演示完成）**关闭 18080**，改走 443。

## 4. 服务器预算与 2C2G 约束

2C2G 跑「PostgreSQL + JVM + nginx」可以，但必须做三件事：

| 项 | 做法 | 理由 |
|---|---|---|
| swap | 增加 2 GB swap | 防止 PG + JVM 峰值把系统 OOM |
| JVM 堆 | `JAVA_OPTS=-Xmx512m` | 默认 `MaxRAMPercentage=75` 在 2 GB 机器上会要 1.5 GB 堆，风险高 |
| 编译位置 | **本机构建镜像后导入** | 服务器上 Gradle 编译峰值 1.5~2 GB，2C2G 会非常慢甚至 OOM |

资源预估：

- 镜像：backend 832 MB + web 672 MB + postgres ≈ 250 MB，导出压缩后约 600~800 MB；
- 运行内存：PG ≈ 200~300 MB，JVM ≈ 512 MB 堆 + 元空间，nginx + OS ≈ 200 MB；
- 磁盘：镜像 + 数据 + 备份，40 GB 足够课程周期。

**升级触发条件**：并发演示 > 10 人、或需要同时跑 E2E / 演示数据重灌时，升 4 GB。

## 7. 关键命令清单

### 7.1 服务器初始化（Alibaba Cloud Linux 4 LTS）

```bash
# 0) 先确认系统与防火墙（Alibaba Cloud Linux 是 RHEL 系，不是 Ubuntu）
cat /etc/os-release
systemctl is-active firewalld
getenforce

# swap（2C2G 必做）
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h

# Docker：Alibaba Cloud Linux 4 官方推荐装内置 Moby 运行时，不用配 Docker CE 外源
sudo dnf install -y moby
sudo dnf install -y docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
docker version
docker compose version

# firewalld 若在运行，放行 22 / 18080（80/443 等备案后再放）
sudo firewall-cmd --permanent --add-port=22/tcp
sudo firewall-cmd --permanent --add-port=18080/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --list-ports

# 目录
sudo mkdir -p /opt/erp
sudo chown "$USER":"$USER" /opt/erp
```

### 7.2 生产 `.env`

```bash
cd /opt/erp
cp infra/deploy/.env.example infra/deploy/.env
chmod 600 infra/deploy/.env

PW=$(openssl rand -base64 32 | tr -d '\n')

sed -i "s|^ERP_JWT_SECRET=.*|ERP_JWT_SECRET=$JWT|" infra/deploy/.env

# 2C2G：显式限制堆，别用默认 75%
sed -i 's|^# JAVA_OPTS=.*|JAVA_OPTS="-Xmx512m -XX:+ExitOnOutOfMemoryError -Duser.timezone=Asia/Shanghai -Dfile.encoding=UTF-8"|' infra/deploy/.env

# 备案前：IP 演示
# WEB_BIND_IP=0.0.0.0
```

### 7.7 备案通过后切 HTTPS（Alibaba Cloud Linux 4）

优先用**阿里云免费 SSL 证书**（控制台申请 → 下载 nginx 格式），不依赖 certbot、也不用开 80 做验证：

```bash
sudo dnf install -y nginx
# 把申请的证书放到 /etc/nginx/cert/，按 infra/deploy/README.md §7.2 的 server 块配置
# proxy_pass http://127.0.0.1:18080;
sudo nginx -t && sudo systemctl enable --now nginx

# .env 改 WEB_BIND_IP=127.0.0.1，重新 up 一次（不重建镜像）
cd /opt/erp
sed -i 's|^WEB_BIND_IP=.*|WEB_BIND_IP=127.0.0.1|' infra/deploy/.env
./scripts/deploy.sh --tag "$(sed -n 's/^CURRENT_TAG=//p' infra/deploy/.deploy-state)" --no-build
```

若要改用 Let's Encrypt：Alibaba Cloud Linux 4 没有 `apt`，需先装 EPEL 或改用 certbot 容器；
课程场景用阿里云免费证书更省事。两种方式都按 `infra/deploy/README.md` §7.2 的 server 块落地。

## 8. 风险与回退

| 风险 | 影响 | 应对 |
|---|---|---|
| 备案驳回 / 延迟 | 无法切域名、小程序不能正式发布 | IP 演示不受影响；按云厂商驳回原因补材料；小程序先用开发者工具联调 |
| 2C2G 内存不足 | 部署后 OOM / 502 | 2 GB swap + `-Xmx512m`；监控 `docker stats`；仍不足升 4 GB |
| `origin/main` 落后 354 提交 | 服务器 clone 到旧代码 | 用 `git bundle` 传当前 `main`；或先 push 并确认 CI |
| 未提交改动 | 移动端包与 `main` 不一致 | P0 先收口；或在交付说明写明包来自哪个工作区状态 |
| 服务器构建镜像 OOM | 部署卡住 | 不在服务器编译，本机 build + save/load |
| Docker Hub 拉取超时 | PG/基础镜像拉不下来 | 配 registry mirror；基础镜像用 `*_BUILD_IMAGE` 覆盖 |
| Android 明文 HTTP 限制 | 正式包连不上 IP | 演示包可用；正式包等 HTTPS；必要时配 network security config |
| 小程序真机域名校验 | 备案前真机全接口失败 | 开发者工具勾"不校验合法域名"；正式发布等备案 |
| 测试期 18080 暴露 | 被扫描 / 弱口令风险 | 强管理员密码、限制来源 IP、不对外宣传、完成后关闭 |
| 演示数据污染 | 上线后数据不干净 | 正式对外前决定保留或清理；清理前先备份 |
| 回滚 | 新版本故障 | `./scripts/rollback.sh`；**镜像回滚 ≠ 数据库回滚**，含迁移的版本先恢复备份 |

## 9. 安全红线

1. 公网只开 22 / 80 / 443；测试期临时 18080，结束后关闭；**绝不开 8080 / 15435**；
2. `.env`、备份、SSH 私钥 600，不进 Git；提交前 `git status` 检查；
3. SSH 仅密钥登录，禁用 root 密码登录；
4. 管理员强密码；`seed-admin.sh` 重置后确认旧密码失效；
5. 备案审核期间域名不解析、不提供 80/443 网站服务；
6. 生产 profile 已关闭 Swagger/OpenAPI，actuator 只暴露 health/info；
7. 测试期的 IP 访问不对外宣传、不开放注册、不做成公开演示站。

## 10. 明确不做（本计划范围外）

| 不做 | 理由 |
|---|---|
| Kubernetes / 多机 / 高可用 | 单商户单机足够；多一层编排只增加故障面 |
| CDN / WAF / 负载均衡 | 课程场景无流量压力；备案后再按需加 |
| iOS / 鸿蒙 | 任务里是可选；没有 Apple 开发者账号 |
| PC 深链注册 / 离线缓存 | 与单机版口径冲突，避免两套离线 |
| 小程序全模块移植 | 财务/报表/系统管理留在 Web/PC；除非课程明确要求 |
| 真实打印套打 | 本机无打印机，等有设备再验 |
| 在服务器上跑全量测试 | 2C2G 资源不够；测试在本机/CI 跑，服务器只跑制品 |
