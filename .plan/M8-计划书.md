## 1. 目标、范围与硬边界

### 1.1 单机版定义

本项目的单机版指：**在一台普通电脑上，不依赖任何云服务、域名或外网，能够一键启动完整系统并长期使用**。具体含义：

| 维度 | 要求 |
|---|---|
| 断网可用 | 启动与运行阶段不拉取镜像、不访问云端；业务数据与文件全部在本机 |
| 一键起 | 一条启动命令拉起 PostgreSQL + 后端 + Web 入口；一条停止命令安全停机 |
| 数据落本地 | 数据保存在 Docker 命名卷；停止/重启/升级不丢数据；备份产物在宿主目录 |
| 功能等价 | 与生产版共用同一套后端/前端镜像与 PostgreSQL，不是"另做一个简化版" |
| 可初始化 | 首次启动可用参数/环境变量传入管理员密码，不写死弱口令 |
| 可运维 | 状态检查、备份、升级、故障排查步骤自足；Windows/Linux 双平台可照做 |

### 1.2 本次交付

| # | 交付 | 判定标准 |
|---|---|---|
| 1 | 单机编排 | `infra/standalone/docker-compose.standalone.yml`，PG + backend + web 三服务，端口 18090 / 15439 |
| 2 | 一键脚本 | 启动/停止/状态检查/备份，PowerShell 5.1 与 POSIX sh 各一份 |
| 3 | 首次管理员 | 密码从参数或环境变量传入；未提供时首次生成随机密码并只打印一次 |
| 4 | 离线能力 | 复用 M6 镜像与离线垫片；文档给出「联网构建一次 → 导出镜像 → 断网导入运行」完整步骤 |
| 5 | 本地实测 | 本机用 standalone 编排走通「登录 → 进货 → 入库 → 出货 → 出货确认 → 库存/流水」，并验证重启持久化与备份 |
| 6 | 文档 | `infra/standalone/README.md`：Windows/Linux、前置 Docker Desktop、离线、备份、升级、排障 |
| 7 | 不碰业务 | 不改后端/前端业务代码、契约、页面；仅新增 `infra/standalone/**` 与 `.plan/M8-计划书.md` |

### 1.3 明确不做

| 不做 | 理由 |
|---|---|
| 公网部署、域名、备案、HTTPS | 属 M6，且需要用户服务器与域名；本泳道不碰 |
| 桌面壳安装包（.exe/.dmg） | 见 §2 方案对比，成本与风险高于收益，且 10% 项不要求 |
| 嵌入式数据库（H2/SQLite）替代 PostgreSQL | 会与生产环境分叉，且无法覆盖并发/约束类缺陷 |
| 自动更新、遥测、云同步 | 与"断网可用"冲突，课程范围外 |
| 多机/高可用/集群 | 单机版定义就是单机；高可用属 M6 之后 |
| 修改 `docs/00`、`README.md`、`docs/planning/**`、`.plan/M1~M3`、`index/` | 合并与计数由协调方统一处理 |

## 2. 方案对比与选择

### 2.1 候选方案

| 维度 | A. Docker 一键包（选中） | B. 桌面壳（Electron/Tauri） | C. 纯 JAR + 嵌入式 H2 |
|---|---|---|---|
| 复用 M6 制品 | 直接复用后端/前端镜像、compose、健康检查、备份脚本 | 需要重新封装启动器，镜像制品用不上 | 需要另一套打包与数据库初始化 |
| 运行时一致性 | 与生产完全相同（Spring Boot + PG 16 + nginx） | 可做到，但需把 JRE、PG、nginx 一并塞进安装包 | 与生产数据库不同，SQL/并发语义分叉 |
| 断网能力 | 镜像预先导入即可，运行期零外网 | 安装包自带依赖，天然离线 | 天然离线 |
| 数据落本地 | Docker 命名卷 + 宿主备份目录 | 用户目录下的 PG 数据目录 | 单文件数据库 |
| 跨平台 | Windows/Linux 同一份 compose（Docker Desktop / Engine） | 每个平台单独打包、签名、测试 | 跨平台容易 |
| 交付体积 | 复用已有镜像；导出 tar 约 2 GB | 安装包通常 300 MB~1 GB，另需 PG | 最小 |
| 首次使用门槛 | 需要 Docker Desktop / Engine | 双击安装，体验最好 | 需要 Java 或自带 JRE |
| 实现与验收成本 | 低：编排 + 脚本 + 文档 | 高：进程管理、端口、崩溃恢复、签名、双平台 | 中：但要重做数据层与测试 |
| 风险 | Docker 未安装时无法启动 | 嵌入 PG 的生命周期/权限/杀软问题多 | 与生产分叉，课程演示价值低 |

### 2.2 选择 A（Docker 一键包）的理由

1. **同一套制品才是真单机版**：M6 已经产出多阶段后端镜像、nginx 前端镜像、生产 compose、健康检查与备份脚本。M8 只换端口、换项目名、加一键脚本，交付物与生产版同源，评审可以直接对照。
2. **PostgreSQL 不能换**：项目的核心价值（原子扣减、唯一约束幂等、FEFO 拆批、流水不变量）都依赖真实 PG；换 H2 等于把最值得证明的部分抽掉。
3. **离线要求可以被工程化证明**：镜像导出/导入 + 启动脚本 `--pull never`，运行期没有任何云端依赖；比"桌面壳里偷偷下载依赖"更容易验收。
4. **成本与风险可控**：桌面壳需要为 Windows/Linux 分别打包 JRE + PG + 前端，处理安装路径、权限、杀软、签名与升级；在课程时间窗内收益低、故障面大。
5. **前置条件可接受**：目标用户是课程评审/单店运维，Docker Desktop 是明确、可安装、可文档化的前置；README 会把安装与验证步骤写全。

### 2.3 代价与缓解

| 代价 | 缓解 |
|---|---|
| 目标机必须先装 Docker | README 给 Windows（Docker Desktop + WSL2）与 Linux（Docker Engine + compose 插件）检查命令 |
| 首次构建需要网络或预置镜像 | 提供「联网机器构建 → `docker save` → 目标机 `docker load`」完整命令；本机另可用 M6 离线垫片构建 |
| Docker 自身可能联网更新 | 明确边界：应用层不依赖云；Docker Desktop 的许可/更新不属于本包控制 |
| 镜像体积较大 | 单机场景可接受；文档给出磁盘空间建议与清理命令 |

## 4. 离线策略

### 4.1 运行期断网

- 启动脚本固定使用 `docker compose up --no-build --pull never`；本机没有镜像时直接失败并提示，不会悄悄联网拉取；
- compose 中不存在任何云服务、对象存储、外部 API；
- 后端只连 compose 内网的 `postgres`，前端只连同源 `/api`；
- Flyway 迁移打包在 jar 内，启动时不下载。

### 4.2 首次准备（二选一）

**方式 A：联网机器构建，导出镜像包（推荐给目标机）**

```bash
# 联网机器（仓库根目录）
docker compose -f infra/standalone/docker-compose.standalone.yml build backend web
docker pull postgres:16-alpine
docker save -o erp-standalone-images.tar \
  erp-backend:standalone erp-web:standalone postgres:16-alpine

# 目标机（断网）
docker load -i erp-standalone-images.tar
./infra/standalone/start-standalone.sh
```

**方式 B：本机已有 M6 离线垫片**

```bash
# 本机 Docker Hub 不可达时，用 M6 的可达 Alpine/npm 镜像源构建
TAG=standalone-local ./scripts/build-local-images.sh
IMAGE_TAG=standalone-local ./infra/standalone/start-standalone.sh
```

> M6 的 `scripts/build-local-images.sh` 原样使用两份生产 Dockerfile，只替换基础镜像与 npm registry；
> 详见 `infra/deploy/offline/README.md`。该垫片只用于网络受限环境，生产服务器仍走官方基础镜像。

### 4.3 边界说明

- 应用层不依赖云；Docker Desktop / Docker Engine 自身的许可校验、更新检查不属于本包控制范围；
- 首次构建需要网络（或预置基础镜像/Gradle/npm 缓存）；一旦镜像导入，后续启动和运行业务不需要外网。
