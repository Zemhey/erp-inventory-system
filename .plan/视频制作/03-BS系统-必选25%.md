这段的**三个记忆点**（评审看到第二个就会记住这个系统不是 CRUD 作业）：
1. **100 个线程抢 50 件，成功数必须恰好是 50**，数据库层还有 `CHECK` 兜底 —— 这是能当场跑出来的数字。
2. **越权返回 404 而不是 403**，因为 403 等于告诉对方"这个 id 存在，只是你没权限"。
3. **我评估后主动放弃了 PostgreSQL RLS**，理由是它会造出"策略已装、用例全绿、隔离零生效"的假绿。这一句是五段视频里最值得讲的工程判断。

## 四、逐字口播文案

**〔00:00 P1〕**
大家好，我是"云裳进销存"的唯一开发者。这是系列第三段，对应评分项第（3）条，**B/S 系统的四个必选端**，25%。这一段最长，因为我要交四份证据：服务端、Web 端、小程序、安卓 App。

**〔00:15 P2〕**
先给你们一张地图。底下是一个后端，上面四个端：浏览器、手机浏览器、微信小程序、安卓 App。
四个端**不是四套业务代码**，它们共用一份接口契约、共用一套权限码。
我这段视频的顺序就按任务里括号那四个词来。

**〔00:55 服务端①：契约〕**
先看服务端。第一个我想让你们看的是**契约**。
〔指 openapi.yaml〕`packages/api-contract/openapi.yaml`，这一个文件是整个项目的接口定义。
〔grep -c〕**202 个路径、260 个操作、194 个组件定义**。
Web 端、H5、小程序、安卓，四个端调的接口都从这一份里出来，不是各自抄一份。
〔跑 contract-check.py〕光有一份文件不够，它会烂。所以我这里有两道门禁：
第一个 `contract-check.py`，验接口对不对得上。〔跑 schema-field-check.py〕
第二个 `schema-field-check.py`，验的是**字段级**：契约里写了这个字段，代码里真的有这个字段吗。
〔指输出〕两个当场都是过的。字段级这件事很细，但四端共用契约最大的风险就是"接口偷偷改了一个字段，另一端还在按老字段读"。

**〔01:50 服务端②：并发防超卖〕**
第二件事，我不想做一个"增删改查作业"，所以我给你们看库存。
〔跑 gradlew test --tests InventoryReserveIT〕
这是一条自动化用例，它的名字叫：**并发预占，100 个请求抢 50 件库存**。
〔指日志里那行 DisplayName〕它做的事情是：起 100 个线程，全部拉到同一条起跑线上，同一个瞬间放出去，抢同样 50 件货。
然后它断言三件事：**成功的数量必须恰好等于 50**，多一个就是超卖；可用量**不能变成负数**；预占记录的数量也要正好是 50。
〔指 rejected〕另外那 50 个必须拿到明确的"库存不足"业务异常，不能悄悄失败。
数据库层还有一道约束兜底。〔指 `V1__init_inventory_slice.sql`〕建表的时候就写了 `on_hand_qty >= 0`、`reserved_qty >= 0`，还有一条 `ck_reserved_le_onhand`：**预占量不能大于实存量**。
就算将来谁加了条新路径漏了校验，脏数据也进不了库。
〔指 Testcontainers 那几行〕还有一个细节我要说一下。这些用例跑之前会先起一个**真的 PostgreSQL**。
我特意不用内存库 H2，因为有些行为只有真库才暴露 —— 比如行锁的等待和释放时机、约束冲突的报错行为。内存库测会一路绿灯到生产才炸，这条我写在决策记录里。

**〔02:40 服务端③：多租户与 RLS〕**
第三件事，多租户。
〔指 PPT〕从 V16 这次迁移开始，**所有业务表都带 `tenant_id`** 这一列。
但"有这一列"不叫隔离。我做的事情是拿用例去撞它：
〔跑 TenantIsolationMatrixIT〕这一条测试的名字是**跨租户矩阵**，9 种资源、5 种读法、3 种身份，**135 个组合**。
〔指输出〕9 种资源是商品、SKU、库存、进货单、出货单、退货单、结算、报表、审计；5 种读法是按 id 直查、列表、导出、关联查询、聚合 —— 因为很多人只堵了"按 id 直查"这一条，列表和导出照样漏。
3 种身份是另一个租户的管理员、本租户的管理员、和匿名。

下面这段是我最想讲的工程判断。〔回 PPT P4〕
PostgreSQL 有一个功能叫 **RLS，行级安全策略**，官方告诉你这是做租户隔离最正统的方法：策略装上，数据库自己会过滤。
**我评估之后主动放弃了它。** 理由是这样的：
如果我装了 RLS，我的测试用例就只会验"查出来对不对"。策略装了、用例全绿、但隔离其实没生效 —— 比如某个连接没带上那句 `SET`，或者某条策略的 `USING` 条件写宽了 —— **数据库安静地返回全部数据，我的测试安静地全绿**。
那种"看起来一切都好"的状态，业内叫**假绿**，比一个会当场报错的 bug 危险得多。
我改成把 135 个组合一个个显式地撞一遍：用 B 租户的身份去读 A 租户的东西，**必须看到拒绝**。测试里是我主动去请求、主动断言被拒，隔离有没有生效，我不会搞错。
这不是 RLS 不好，是**在我一个人做、没有条件去做数据库策略变更审计的情况下，显式断言比声明式策略更可靠**。

〔打 curl〕还有一个我会专门讲的细节：跨租户越权，我返回的是 **404，不是 403**。
因为 403 的意思是"这个资源存在，但你不该看" —— 等于我承认了这个 id 是真的。404 才是不给对方任何信息。

审计查询这个页面本身是有的，我用管理员账号给你们看它长什么样。〔切本机管理员，点 **系统 → 审计查询**〕每一笔写操作都在这。

## 六、常见追问与答法

**Q1：你说你"主动放弃了 RLS"，那不是说明你不会用 RLS 吗？**
我是评估之后选的，不是不会配。判断点在于**风险来自哪一层**。RLS 的失效方式很安静：策略装上之后，如果某条连接的会话变量没设、或者 `USING` 条件写得比预期宽，数据库照样返回数据，接口照样 200，**我的测试如果只验"结果对不对"就永远全绿**。这种"策略已装、用例全绿、隔离零生效"的状态是我这个项目最不能接受的，因为我一个人做，没有条件去做数据库策略层的变更审计。
我的替代方案是把隔离做成**主动撞**：135 个组合里我用自己的身份去请求不属于自己的资源，然后断言它必须被拒（而且是 404，不是 403）。这条路一旦隔离没生效，测试会直接红，不会沉默。
如果这是一个有 DBA 团队的项目，我会重新评估 RLS —— 因为那时策略变更本身有人 review。这个决策依赖的是团队条件，不是技术优劣。

**Q2：防超卖不就是加个锁吗？你这有什么特别的？**
不是加一把全局锁，那样并发就没了。我做的是**两层**：
第一层在应用里，预占走条件更新 + 行级锁，靠"库存不足"业务异常把抢输的那 50 个明确挡回去，并且**要求拿到异常**（断言里写了异常码必须是 `INV_INSUFFICIENT_STOCK`，不许是别的错，也不许悄悄成功）。
第二层在数据库，建表时就写死了约束：`on_hand_qty >= 0`、`reserved_qty >= 0`，以及 `ck_reserved_le_onhand`（预占量不能大于实存量）。万一将来谁加了条新路径漏了校验，脏数据进不了库。
为什么这条值得单独跑给你们看：100 个线程我用 `CountDownLatch` 拉到同一条起跑线上同时放，这才是真竞争。串行跑的并发测试证明不了任何事。
另外同一族里还有一条：20 个线程用**同一个 requestId** 并发打进去，只允许一次生效，靠数据库唯一约束兜 —— 幂等这件事也不能只靠代码记得查一次。

**Q3：你说"库存测试跑的是真 PostgreSQL"，为什么非不用 H2？这不是给自己找麻烦吗？**
是有代价（跑测试要起容器，慢一些），但是换来的东西更值钱。我用 H2 会测不到的东西是具体的：`SELECT ... FOR UPDATE` 的**行锁等待与释放时机**（进货单明细行就是这么锁的），以及约束冲突时**报错的种类和时机** —— 内存库经常把约束错误包成另一种异常，断言就测不出真实行为。
决策记录里我写了这条：用内存库会"一路绿灯到生产才炸"。所以我坚持 Testcontainers —— 代价是构建慢，收益是这类 bug 在 CI 阶段就炸，而不是在客户现场炸。

**Q4：小程序到底能不能用？你只演示了 H5。**
分开答，别含糊：**代码上能编，流程上没上线。**
"能编"的证据是 `app/uniapp/dist/build/mp-weixin` 里的 `app.json`、`pages/`、`project.config.json`，那是完整的小程序包结构；出包前还有一道 `preflight` 会拦接口地址非 https、域名不合规这类"到设备上一定坏"的事。
"没上线"是指：上传体验版要微信开发者工具 + 小程序后台配 request 域名白名单，那两步只能本人操作，我到现在没做。
**所以我不拿 H5 画面说"这是小程序"。** 你要看真小程序，我按现在的代码传一版体验版就行，那一步是纯流程，没有技术障碍 —— 这个说法我能负责。

**Q5：安卓 APK 34 万字节就这么小，是不是里面啥也没有、全靠联网？**
里面是有的：**移动端界面本身打进了包**，`assets/www` 下 68 个文件、约 600 KB，就是 uni-app 的 H5 构建产物。所以断网也能开到登录页 —— 我在视频里真的开了一次飞行模式。
600 KB 是因为它是压缩过的前端资源；不含数据是因为**数据本来就该只有服务器上有**。
另外两处细节：内置包里没有的文件会自动回源、不会白屏，但那是兜底，正常路径应该 100% 命中包内资源，所以每次改完 uni-app 都有同步脚本 `sync-h5.mjs` 会重灌；同步脚本里有一道闸，产物里一旦出现"真实主机 + /api/v1"的绝对地址就报错拒绝 —— 因为那样会变成跨域包，登录直接坏。

**Q6：你说 19 条测试没通过，那这系统是不是坏的？**
不是。我把 19 条拆开说：**4 条是 ArchUnit 架构规则**（架构约束类的漂移，不是业务算错）；**1 条是契约映射**；**14 条是业务断言漂移**，也就是业务行为有意改过、断言里的期望值还停在旧口径。这三类都不是"数据算错"。
**但我不想用这个说法糊过去**，所以我给三个可核查的东西：一，1230 条通过的用例里包含你们刚才看到的并发防超卖、135 格越权矩阵和"实存等于流水净和"这几条硬不变量；二，这 19 条我有一份清单，可以给你看具体是哪几条；三，我把它写进视频的"如实边界"页，不是等你们自己去复现才发现。
顺带一句：README 里有个"1204 全绿"是更早的旧口径，我自己在 README 里也标了它过期 —— 我宁可自己先念出来。

**Q7：Web 端 54 条路由，是不是有很多是空页/占位页？**
不是空页，但我要把口径说准：菜单树上 10 组、路由 54 条，覆盖的是主数据、库存、采购、销售、财务中心、报表、系统、系统工具、自然语言这些业务域，页面都是接后端真接口的。
真正值得说的不是"有多少页"，而是**每一页的数据从哪来**：接口全部出自那一份 OpenAPI 契约，字段级有 `schema-field-check.py` 卡着。页多不代表做得好，但页多还每页都接真接口，就说明这套不是拼皮。
今天这段镜头里我实际点到的：商品与 SKU、进货单、库存查询、出货单、拣货发货、报表中心、数据大屏、用户与角色与审计查询（后者被 403 拒了，那也是一条真实能力）。其余页面我不敢替镜头保证，你们可以拿 `demo / Demo@12345` 自己点。
