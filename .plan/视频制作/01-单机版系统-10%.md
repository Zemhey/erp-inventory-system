## 六、常见追问与答法

**Q1：单机版和云托管版是两套代码吗？维护两份不是很浪费？**
不是两套。同一份后端、同一份前端构建产物，只差编排文件：单机版是 `infra/standalone/docker-compose.standalone.yml`，线上是 `infra/deploy/docker-compose.prod.yml`。功能上唯一的取舍是：单机版把 PostgreSQL 绑在 `127.0.0.1`、后端 8080 不往外发布，因为单机版没有理由把自己暴露到局域网里。要做局域网访问，README §4.4 写了改 `WEB_BIND_IP` 的办法。

**Q2：客户要升版本怎么办？单机版不就没有升级通道？**
升级动作就是"换镜像 + 重启"，脚本化的，不靠人记步骤。数据库那层由 Flyway 迁移负责，起服务时自动往上走版本号 —— 刚才日志里滚的那些行就是它。数据卷不动，所以升级不会把客户的数据洗掉。这个口径和线上是同一套：线上那套我有 `deploy.sh` 和 `rollback.sh`，下一段会当场演一次。

**Q3：备份文件你怎么保证它真的能用？只看到文件生成了。**
两层保证。**第一层在脚本里**：`backup-standalone.ps1` 用 `pg_dump -Fc` 导出之后，会再用 `pg_restore -l` 去解析这个 dump，解析不出来或者里面没有表数据，脚本直接抛错算失败，不会留下一份"看着像成功"的文件。**第二层是一次真实演练**：`infra/standalone/README.md` §6.2 记的那次，把备份恢复到临时库，比对 `purchase_orders=1、sales_orders=1、inventory_ledger=2、app_users=1`，和源库一致。
我另外也在 README 里写了"建议每月做一次恢复演练"——因为它确实不该只做一次，这个动作是流程要求，不是我已经做完的事。

**Q4：为什么要求客户只装 Docker，而不是给他一个 exe 双击就行？**
因为双击的壳还得以容器方式跑起一个数据库和 JVM，客户端资源不可控，出问题也讲不清楚。Docker 这条路的收益是**环境一致性**：我这台机器上验过的镜像，就是他机器上跑的镜像。
顺带说一句，真想要"双击就用"的形态，这个项目有第四个交付：**PC 端便携包**（`04` 段），Electron 起本地静态服务、连的还是同一个后端。两件事是分开的：便携包解决的是"壳双击就能开"，单机版解决的是"整套含数据库在自己机器上跑"。

**Q5：万一 Docker Desktop 商用要收费这个方案不就废了？**
这是真实的部署风险，我认。规避路径是脚本本身不依赖 Docker Desktop，只依赖 `docker compose` v2 命令 —— Linux 上用 Docker Engine 24+ 就走同一份 `start-standalone.sh`，README 第 1 节列了两种系统的前置条件。真要彻底不要 Docker，就得把 Java、Node、PostgreSQL 都装进宿主，那是退回到"我机器好好的、你机器为什么不行"的老问题。

**Q6：这段里为什么没展示用户管理、审计这些功能？**
因为是刻意分工。这段（10%）只看"能不能脱离云跑起来、数据在不在本机"。用户与角色（系统 → 用户与角色）、审计查询、登录日志这些受权限控制的页面，演示账号 `DEMO_VIEWER` 会被拒 403，拿它们当单机版素材只会让画面全是报错。这些能力我放在第三段 B/S 的 25% 里讲，那段有服务端权限和租户的专门镜头。
