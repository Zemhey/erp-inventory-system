## 6. 过程中的两次红灯与自我纠正（都是实测，不是推测）

1. **TC-API-096 首版扫全契约 → 本泳道因 C1 的欠账变红**。
   断言消息：`POST /api/v1/warehouses：契约声明 X-Request-Id，实现未消费它 —— 两边必须一致`。
   这正是任务书红线禁止我处理的内容（「不得为了让 contract-check 归零而去动 MDM 契约声明」）。
   处理：把 JVM 侧门禁的比对范围收到 `V23_OPERATIONS` 的 15 个写操作上（13 POST + 2 PUT），
   并在测试里注释掉「为什么不是全契约」。全契约方向的核对仍由 `contract-check.py` 负责（残留 8 条 = C1）。
2. **`assertThat(map.get("tags")).isNotEmpty()` 编译失败**（`ObjectAssert<Object>` 没有 `isNotEmpty`）：
   `:compileTestJava FAILED` 2 个错误。YAML 解析出来的是 `Object`，必须显式转成
   `List<String>` / `Map<String,Object>` 再断言。
   教训：`gradlew ... | tail -40` 在管道下会把后台任务的退出码显示成 0，
   第一时间的「通过」是我误读 —— 之后所有运行都在命令里显式回打 `GRADLE_EXIT=`。

### 7.1 申请稿 ↔ 实现

| # | 申请稿的说法 | 实现的实际行为 | 契约写法 |
|---|---|---|---|
| A | 通则「所有写操作必须携带 X-Request-Id」 | **7 个** V2-3 写端点不消费：报价单 `submit/approve/reject/void`、`POST /product-bundles`、`POST /product-bundles/{id}/disable`、`POST /shipments/{id}/scan` | 这 7 条不声明 `RequestId`，在 description 写明幂等由状态机/唯一约束/累加上限保证 |
| B | `POST /sales-quotes` 幂等键复用到另一张报价单 → 409 `SYS_DUPLICATE_REQUEST` | `create()` 先 `findByRequestId` 命中即**返回首次报价单**，无错误码，也不判别内容/客户 | 声明 201 + 幂等重放语义，409 只留 `SET_PERIOD_CLOSED` |
| C | `auto-split` 响应 `lines[].allocations = [{warehouseId, qty, reservations:[…]}]` | 每个分配只有 `{warehouseId, qty}` 两个键；预占 id 在兄弟字段 `reservationIds` | 按实现定义 `SalesOrderAllocation{warehouseId, qty}`，`reservationIds` 沿用 `SalesOrderLine` 既有字段 |
| D | `SAL_RECEIVABLE_NOT_FOUND` 记在 409 | `ErrorCode.SAL_RECEIVABLE_NOT_FOUND(404)` | 404 |
