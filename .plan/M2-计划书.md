## 2. M2 范围（做什么 / 不做什么）

### 2.1 做什么

| FR | 功能 | M2 的具体交付 | 验收要点 |
|---|---|---|---|
| **FR-RMA-01** | 客户退货入库 | 退货单建单/提交/审核/入库/作废；关联原出货单；累计退货不超已出货；回补库存；金额冲销 | 超退拒绝且库存不变；入库产生 `RETURN_IN` 流水；`returned_qty` 原子累加 |
| **FR-SET-01** | 日清 | 按业务日期汇总采购入库、销售出库、退货入库的数量与金额；可指定仓库；同日重复执行幂等 | 同日重复执行结果一致；不产生重复行 |
| **FR-SET-02** | 月结/锁账 | 汇总账期、写入 `settlement_periods` 并置 `CLOSED`；锁账后该期间单据不可新增/执行/作废 | 锁账后建单/入库/出货/退货均返回 `SET_PERIOD_CLOSED` |
| **FR-SET-03** | 对账 | 总账（期间汇总）与明细（单据/流水聚合）比对；差额必须 0 | 差额非 0 返回 `SET_RECONCILE_MISMATCH` 且带 details |
| **FR-RPT-01** | 进货统计 | 按供应商/商品/SKU/日/月分组，期间内**已入库**数量与金额 | 与进货单累计入库口径一致 |
| **FR-RPT-02** | 出货统计 | 按客户/商品/SKU/日/月分组，期间内**已出货**数量与金额 | 折扣金额按行公式计算，与出货单一致 |
| **FR-RPT-03** | 进销存汇总 | 期初 + 本期入 − 本期出 = 期末；可按仓库 | 恒等式成立，且与流水净和一致 |
| **BR-INV-05** | 预占超时释放 | 后台任务 + 可注入时钟；到期 ACTIVE 预占自动释放 | 过期后可用量恢复；未到期不动；重复执行幂等 |
| **FR-SYS-01** | 幂等（复用） | 退货建单/入库、日清/月结都带 `X-Request-Id` | 重复提交不重复生效 |

**M2 的一条主线**（也是端到端验收路径）：

```
建出货单 → 出货（库存减少） → 建退货单 → 审核 → 退货入库（库存回补）

```

## 3. 技术方案（关键设计决策）

### 3.1 模块与依赖

新增三个包：

```
com.erp.rma   api / application / domain / repository
com.erp.set   api / application / domain / repository
com.erp.rpt   api / application / repository（只读，无写服务）
```

依赖方向：

```
PUR / SAL / RMA ──▶ INV（库存唯一入口）
RMA ─────────────▶ SAL（只读：可退明细；由 SAL 提供查询/登记服务，RMA 不直接写 SAL 表）
SET ─────────────▶ 只读查询单据/流水（自己的 JdbcTemplate 查询，不直接改业务表）
RPT ─────────────▶ 只读跨域查询（自己的 JdbcTemplate，不写任何表）
PUR / SAL / RMA ──▶ shared.period.PeriodGuard（接口，SET 提供实现）
```

**为什么 `PeriodGuard` 放 `shared`**：锁账后 PUR/SAL/RMA 都要拒绝写入，但若它们直接依赖
`com.erp.set`，会形成 `SET → 单据 → SET` 的包依赖环。用一个接口做依赖倒置：
接口在 `shared.period`，实现 `SettlementPeriodGuard` 在 `set.application`。

**SAL 对 RMA 的只读服务**（避免 RMA 直连 `sales_order_*` 表）：

- `ReturnableSalesOrderService.requireShippedOrder(orderId)`：返回原单 + 可退明细
  （`shippedQty`、累计 `returnedQty`、剩余可退）；
- `SalesOrderReturnService.registerReturn(lineId, qty)`：原子校验并累加 `returned_qty`；
- RMA 只通过这两个服务与 SAL 交互，不注入 SAL 的 Repository。

**ArchUnit 同步**（S2/S3 必须做，否则新包不在门禁里）：

- 把 `com.erp.rma..`、`com.erp.set..`、`com.erp.rpt..` 加入"禁止直接依赖系统时间"两条规则；
- 把 `com.erp.rma.application..` 加入"单据模块必须复用统一状态机"；
- 新增规则：`pur/sal/rma` 不得直接依赖 `com.erp.set..`（只能依赖 `shared.period`）；
- 新增规则：`rpt` 包不得依赖 `..application..` 的写服务（只允许自己的查询仓储）。

#### V4：退货

```sql
ALTER TABLE sales_order_lines
    ADD COLUMN returned_qty INTEGER NOT NULL DEFAULT 0 CHECK (returned_qty >= 0);
ALTER TABLE sales_order_lines
    ADD CONSTRAINT ck_so_line_return_le_shipped CHECK (returned_qty <= shipped_qty);

CREATE TABLE return_orders (
    id                    BIGSERIAL PRIMARY KEY,
    order_no              VARCHAR(64)  NOT NULL,
    status                VARCHAR(32)  NOT NULL DEFAULT 'DRAFT',
    origin_sales_order_id BIGINT       NOT NULL REFERENCES sales_orders (id),
    customer_id           BIGINT       NOT NULL REFERENCES customers (id),
    warehouse_id          BIGINT       NOT NULL REFERENCES warehouses (id),
    biz_date              DATE         NOT NULL,
    total_amount          BIGINT       NOT NULL DEFAULT 0 CHECK (total_amount >= 0),
    total_qty             INTEGER      NOT NULL DEFAULT 0 CHECK (total_qty >= 0),
    period                VARCHAR(7),
    remark                VARCHAR(500),
    request_id            VARCHAR(64),
    receive_request_id    VARCHAR(64),
    created_by            BIGINT,
    version               INTEGER      NOT NULL DEFAULT 0,
    created_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT uq_return_order_no UNIQUE (order_no),
    CONSTRAINT ck_return_order_status CHECK (status IN
        ('DRAFT','SUBMITTED','APPROVED','COMPLETED','VOIDED','REJECTED'))
);
-- request_id / receive_request_id 各建部分唯一索引（幂等）

CREATE TABLE return_order_lines (
    id                BIGSERIAL PRIMARY KEY,
    order_id          BIGINT      NOT NULL REFERENCES return_orders (id) ON DELETE CASCADE,
    line_no           INTEGER     NOT NULL CHECK (line_no > 0),
    origin_line_id    BIGINT      NOT NULL REFERENCES sales_order_lines (id),
    sku_id            BIGINT      NOT NULL REFERENCES skus (id),
    qty               INTEGER     NOT NULL CHECK (qty > 0),
    unit_price_amount BIGINT      NOT NULL CHECK (unit_price_amount >= 0),
    discount_rate     INTEGER     NOT NULL CHECK (discount_rate > 0 AND discount_rate <= 10000),
    amount            BIGINT      NOT NULL CHECK (amount >= 0),
    batch_no          VARCHAR(64) NOT NULL DEFAULT '',
    production_date   DATE,
    expiry_date       DATE,
    CONSTRAINT uq_return_line_no UNIQUE (order_id, line_no),
    CONSTRAINT uq_return_origin_line UNIQUE (order_id, origin_line_id)
);
```

要点：

- **金额不信任前端**：建单只收 `originLineId + qty`，单价/折扣从原出货行读取；
  `amount = round(unitPrice × qty × discountRate / 10000)`，与 SAL 行金额同一公式；
- **累计退货上限**：`returned_qty` 在入库时原子累加，条件 `returned_qty + qty <= shipped_qty`；
  并发超退由 SQL 更新 0 行 → `RMA_QTY_EXCEED_ORIGIN`；
- **批次**：退货入库允许操作员指定 `batchNo` / 生产日期 / 有效期（默认空批次），
  M2 不做"自动追溯原出货批次"——那需要逐笔出货批次留存，属 M2.5；
- **状态**：退货单只走 `DRAFT → SUBMITTED → APPROVED → COMPLETED`，
  入库为整单一次性回补（不分批）；`PARTIAL` 不使用。

#### V5：结算

```sql
CREATE TABLE settlement_periods (
    period          VARCHAR(7) PRIMARY KEY,       -- yyyy-MM
    status          VARCHAR(16) NOT NULL DEFAULT 'OPEN'
                        CHECK (status IN ('OPEN','CLOSED')),
    purchase_qty    BIGINT NOT NULL DEFAULT 0,
    purchase_amount BIGINT NOT NULL DEFAULT 0,
    sales_qty       BIGINT NOT NULL DEFAULT 0,
    sales_amount    BIGINT NOT NULL DEFAULT 0,
    return_qty      BIGINT NOT NULL DEFAULT 0,
    return_amount   BIGINT NOT NULL DEFAULT 0,
    net_amount      BIGINT NOT NULL DEFAULT 0,
    closed_at       TIMESTAMPTZ,
    closed_by       BIGINT,
    version         INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE daily_settlements (
    id              BIGSERIAL PRIMARY KEY,
    biz_date        DATE    NOT NULL,
    warehouse_id    BIGINT  NOT NULL REFERENCES warehouses (id),
    purchase_qty    BIGINT  NOT NULL DEFAULT 0,
    purchase_amount BIGINT  NOT NULL DEFAULT 0,
    sales_qty       BIGINT  NOT NULL DEFAULT 0,
    sales_amount    BIGINT  NOT NULL DEFAULT 0,
    return_qty      BIGINT  NOT NULL DEFAULT 0,
    return_amount   BIGINT  NOT NULL DEFAULT 0,
    net_amount      BIGINT  NOT NULL DEFAULT 0,
    request_id      VARCHAR(64),
    settled_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_daily_settlement UNIQUE (biz_date, warehouse_id)
);
```

> **口径决策（重要，见 §7 决策 1）**：M2 的日清/月结/报表统一按**单据业务日期 `biz_date`**
> 归属，不按 `inventory_ledger.occurred_at` 的实际执行时刻归属。理由：
> 契约的日清请求本来就带 `bizDate`；期间锁账也以 `biz_date` 为准；
> 若两者混用，跨天分批执行会让历史日清行不断变化，锁账后无法解释。
>
> 代价：一张单的多次分批入库/出货都归到单据 `biz_date` 那一天（不是每次执行日）。
> 这是**明确接受的简化**；若将来要按实际执行日归属，需新增 `receipts` 表并重做日清，
> 属 M2.5，不在本次偷换概念。

| GET | `/return-orders` | `rma:read` | 列表：status / customerId / originSalesOrderId / page / size |
| GET | `/return-orders/{id}` | `rma:read` | 详情（含明细与可退信息） |
| GET | `/return-orders/returnable-orders` | `rma:read` | **可退货的出货单列表**（建单"选原出货单"用；只返回还有可退数量的单，含可退明细与客户/SKU 名称。S5a 补口新增，解 §6 坑 13/14） |
| POST | `/return-orders/{id}/submit` | `rma:submit` | 提交 |
| POST | `/return-orders/{id}/approve` | `rma:approve` | 审核 |
| POST | `/return-orders/{id}/reject` | `rma:reject` | 驳回 |
| POST | `/return-orders/{id}/receive` | `rma:receive` | **回补库存**，整单完成 |
| POST | `/return-orders/{id}/void` | `rma:void` | 作废（仅入库前） |

`POST /return-orders` 请求体：

```json
{
  "originSalesOrderId": 123,
  "bizDate": "2026-10-22",
  "remark": "客户尺码不合",
  "lines": [
    { "originLineId": 456, "qty": 2, "batchNo": "RET-001",
      "productionDate": "2026-10-01", "expiryDate": "2027-10-01" }
  ]
}
```

不传客户/仓库/单价/折扣——**全部从原出货单派生**，避免篡改。

#### 建单校验

1. 原单必须存在，且状态为 `PARTIAL` / `COMPLETED`，至少有一行 `shipped_qty > 0`；
2. 每行 `originLineId` 必须属于原单；`qty > 0`；
3. `qty <= shipped_qty - returned_qty`（预检；最终以入库时原子更新为准）；
4. 同一原单可开多张退货单，但同一张退货单内同一原行只能出现一次；
5. `bizDate` 缺省用 `clock.today()`；`period = yyyy-MM`；
6. `requestId` 命中已有退货单 → 直接返回首次结果（幂等）。

#### 入库（唯一库存入口）

```java
// RMA 只调用 INV，不直接写库存
inventory.receiveIn(skuId, warehouseId, batchNo, productionDate, expiryDate,
        qty, "RETURN_IN", returnOrderNo, returnOrderId, null, perLineRequestId);
```

顺序：

1. `SAL.registerReturn(originLineId, qty)` 原子累加 `returned_qty`（超出 → `RMA_QTY_EXCEED_ORIGIN`）；
2. `inventory.receiveIn(... RETURN_IN ...)` 增加实存并写正向流水；
3. 整单所有行完成后，状态推进 `APPROVED → COMPLETED`；
4. 任一行失败 → 整个事务回滚（`returned_qty`、库存、流水都不留痕迹）。

**入库幂等**：`receive_request_id` 唯一；同 `requestId` 重复调用且单已 `COMPLETED` → 直接返回原单，不重复加库存。
同单不同 `requestId` 再次入库 → `RMA_STATUS_ILLEGAL`。

#### 作废

- `DRAFT/SUBMITTED/APPROVED` → `VOIDED`（不产生库存变动）；
- `COMPLETED` 作废 → 拒绝（需要红冲，M2.5）；
- 作废同样受账期锁约束（S7 接 `PeriodGuard`）。

#### 错误码

`RMA_ORDER_NOT_FOUND(404)`、`RMA_STATUS_ILLEGAL(409)`、
`RMA_ORIGIN_NOT_SHIPPED(409)`、`RMA_QTY_EXCEED_ORIGIN(409)`。

### 3.4 SET（结算）设计

#### 日清 `POST /settlements/daily`

请求：`{ "bizDate": "2026-10-22", "warehouseId": 1 }`（`warehouseId` 省略 = 全部仓库）。

对每个目标仓库，按 `biz_date = D` 汇总：

| 字段 | 来源 | 公式 |
|---|---|---|
| `purchaseQty` | 进货单明细（`status IN ('PARTIAL','COMPLETED')`） | `Σ received_qty` |
| `purchaseAmount` | 同上 | `Σ unit_price_amount × received_qty` |
| `salesQty` | 出货单明细（`status IN ('PARTIAL','COMPLETED')`） | `Σ shipped_qty` |
| `salesAmount` | 同上 | `Σ round(unit_price_amount × shipped_qty × discount_rate / 10000)` |
| `returnQty` | 退货单（`status = 'COMPLETED'`） | `Σ qty` |
| `returnAmount` | 同上 | `Σ amount` |
| `netAmount` | 计算 | `salesAmount − returnAmount` |

写入 `daily_settlements (biz_date, warehouse_id)` 的 upsert 行；**同日重复执行结果一致**，
不新增行。返回按仓库的 `items` + 全部仓库的 `totals`。

- 账期已 `CLOSED` → `SET_PERIOD_CLOSED`；
- 同一天并发执行 → 唯一索引 + upsert 保证只有一行；测试覆盖。

#### 月结 `POST /settlements/monthly`

请求：`{ "period": "2026-10" }`。

1. 按单据重算该账期每一天的汇总，**补齐缺失的日清行**（按 `(biz_date, warehouse_id)` upsert；
   已有行若与重算不一致 → 先报 `SET_ALREADY_SETTLED`，不静默覆盖）；
2. 汇总该账期内所有 `daily_settlements` 得到期间总额；
3. 写入/更新 `settlement_periods`：`status='CLOSED'`、`closed_at=clock.now()`、汇总字段；
4. 返回期间汇总 + `closedAt` + `duplicate`。

> 月结自动补齐缺失日清行，是为了避免"某天忘了点日清就永远关不了账"。
> 但已有行与重算不一致时**必须报错**，不能悄悄覆盖 —— 那会把数据问题埋掉。

幂等：

- 已 `CLOSED` 且重算结果与已存汇总一致 → 返回原结果（`duplicate=true`），不报错；
- 已 `CLOSED` 但重算结果不同 → `SET_ALREADY_SETTLED`（说明锁账后仍有数据变动，属严重异常）。

#### 对账 `GET /settlements/reconcile?period=yyyy-MM`

- 账期未结算 → `SET_PERIOD_NOT_CLOSED`；
- `generalTotal` = `settlement_periods` 存的汇总；`detailTotal` = 按单据/明细实时重算；
- `diff = generalTotal − detailTotal`；`diff != 0` → `SET_RECONCILE_MISMATCH`，details 含
  `period`、`generalTotal`、`detailTotal`、`diff`；
- `diff == 0` → `{ period, generalTotal, detailTotal, diff: 0, balanced: true }`。

#### 锁账（`PeriodGuard`）

`SettlementPeriodGuard.requireOpen(LocalDate bizDate)` 查询该 `period` 的 `settlement_periods`：
`CLOSED` 则抛 `SET_PERIOD_CLOSED`，消息包含账期与动作。

接入点（S2 + S7）：

- PUR：建单、提交、审核、入库、作废；
- SAL：建单（预占）、提交、审核、出货、作废；
- RMA：建单、提交、审核、入库、作废（S7 集成时补）；
- 日清/月结自身按账期状态判断，不走 guard。

**只拦写操作**；查询、报表不受影响。锁账不可逆（`allow-unlock-closed-period` 默认 false，不提供解锁接口）。

#### 错误码

已有：`SET_PERIOD_CLOSED(409)`、`SET_RECONCILE_MISMATCH(409)`、`SET_ALREADY_SETTLED(409)`；
新增：`SET_PERIOD_NOT_CLOSED(409)`（对账时账期未结算）。

### 3.5 RPT（报表）设计

统一响应：`ListResponse` 的 `data.items` 为报表行数组。

#### 行结构

```json
// 进货/出货统计
{ "key": "SUP-001", "label": "杭州面料供应商", "qty": 30, "amount": 264000, "orderCount": 2 }

// 进销存汇总
{ "skuId": 1, "warehouseId": 1, "openingQty": 10, "inboundQty": 20,
  "outboundQty": 15, "closingQty": 15 }
```

#### 三个接口

| 接口 | 参数 | 口径 |
|---|---|---|
| `GET /reports/purchase` | `from`、`to` 必填；`groupBy` = supplier/product/sku/day/month，默认 supplier | 只统计 `received_qty > 0` 的进货单；数量按累计入库，金额按单价 × 入库量 |
| `GET /reports/sales` | 同上，`groupBy` = customer/product/sku/day/month，默认 customer | 只统计 `shipped_qty > 0` 的出货单；金额按行折扣公式；**不含退货**（退货在结算/报表页单独显示） |
| `GET /reports/inventory-summary` | `period` 必填；`warehouseId` 可选 | 按 `inventory_ledger` 的实际发生日期归属：期初 = 期间前净和，入/出 = 期间内正/负变动，期末 = 期初 + 入 − 出 |

日期范围**闭区间** `[from, to]`；`from > to` → 400。
`groupBy` 非法 → 400（Spring enum 校验）。

#### 不变量

- `RPT-03`：`openingQty + inboundQty − outboundQty == closingQty`；
- `RPT-03` 的 `closingQty` 必须等于该 SKU+仓库截至期末的流水净和；
- 对当前期间（无后续流水）时，必须等于 `inventory_balances.on_hand_qty`；
- 报表只读，不产生任何单据/流水/结算行。

> 为什么 `RPT-03` 用流水日期而不是单据 `biz_date`：报表要回答"货什么时候真的动了"，
> 流水是事实源；进货/出货统计回答"业务单据口径"，用单据日期。两种口径在页面上要写清楚，
> 不要混在同一张表的合计里。

### 3.7 金额、时间、幂等、并发（统一约定）

| 主题 | 约定 |
|---|---|
| 金额 | 全程 `long` 分；除法只出现在折扣，统一 `Math.round((double)?)` 不可用，必须用 `BigDecimal` + `HALF_UP` 或整数公式；复用 SAL 的 `lineAmount` 实现，不复制一份 |
| 折扣 | 整数万分比 1~10000；退货沿用原行折扣 |
| 时间 | 只用 `ClockProvider`；日清/月结的 `bizDate` 来自请求；`closed_at` 用 `clock.now()` |
| 幂等 | 建单用唯一 `request_id`；退货入库用 `receive_request_id`；日清用唯一 `(biz_date, warehouse_id)` upsert；月结用期间状态 + 重算比对 |
| 并发 | 退货累计用条件 UPDATE；日清 upsert 依赖唯一约束；月结用 `settlement_periods.version` 乐观锁；失败给稳定业务码，不抛裸异常 |
| 事务 | 退货入库 = 累计退货 + 库存 + 流水 + 状态，一个事务；日清/月结一个事务 |
