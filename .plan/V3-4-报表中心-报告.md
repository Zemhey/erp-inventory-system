## 2. grep 出来的 rpt 真实端点清单（这是本报告最有用的部分）

全部在 `backend/server/src/main/java/com/erp/rpt/api/` 与 `cst/api/MarginController.java`。
权限统一 `@RequirePermission("rpt:read")`；响应包络统一 `{ code, message, data }`（`shared/web/ApiResponses`）。
**金额字段一律整数分（ADR-0005）**，`*RateBp` 是万分比。

### 2.1 `ReportController`（3 个）

| 路径 | 参数 | `data` 结构 |
|---|---|---|
| `GET /api/v1/reports/purchase` | `from`(date,必填) `to`(date,必填) `groupBy`(选填，`supplier`\|`product`\|`sku`\|`day`\|`month`，默认 `supplier`) `warehouseId`(选填) | `{ items: [{ key, label, qty, amount, orderCount }] }` |
| `GET /api/v1/reports/sales` | 同上，但 `groupBy` 允许 `customer`\|`product`\|`sku`\|`day`\|`month`，默认 `customer` | 同上 |
| `GET /api/v1/reports/inventory-summary` | `period`(必填，`yyyy-MM`，非法即 400) `warehouseId`(选填) | `{ items: [{ skuId, warehouseId, openingQty, inboundQty, outboundQty, closingQty }] }`（**没有名称、没有金额**） |

> `groupBy` 白名单来自 `ReportRequestParams.PURCHASE_DIMS / SALES_DIMS`；传错时 400 的 message 里会列出本报表允许的值。

### 2.2 `ReportAdvancedController`（4 个）

| 路径 | 参数 | `data` 结构 |
|---|---|---|
| `GET /api/v1/reports/operating` | `from` `to`(date,必填) `dimension`(选填 `day`\|`month`，默认 `day`) `warehouseId` | `{ items: [{ period, openingQty, inboundQty, outboundQty, closingQty, purchaseQty, purchaseAmount, salesQty, salesAmount }] }` |
| `GET /api/v1/reports/inventory-turnover` | `from` `to`(必填) `deadDays`(默认 **30**) `warehouseId` | `{ items: [{ skuId, skuCode, skuName, warehouseId, warehouseName, openingQty, closingQty, outboundQty, turnoverDays(可 null), idleDays, stale }] }` |
| `GET /api/v1/reports/customer-contribution` | `from` `to`(必填) `limit`(默认 **20**) `warehouseId` | `{ items: [{ customerId, customerCode, customerName, orderCount, qty, amount, repurchase, newCustomer }], summary: { customerCount, repurchaseCount, repurchaseRateBp, newCustomerCount, returningCustomerCount, totalQty, totalAmount, orderCount } }` |
| `GET /api/v1/reports/aging` | `type`(**必填，取值 `AR`\|`AP`**) `asOf`(必填，单日 date，无默认) | `{ items: [{ partnerId, partnerCode, partnerName, balanceAmount, bucket0, bucket1, bucket2, bucket3 }], summary: { partnerCount, totalBalance, bucket0..bucket3 } }` |

### 2.3 `ReportExportController`（7 个 CSV，与查询同名同参）

`GET /api/v1/reports/{purchase,sales,inventory-summary,operating,inventory-turnover,customer-contribution,aging}/export`
参数与对应 JSON 端点**完全一致**（同一个 `ApplicationService`），响应 `text/csv;charset=UTF-8` + **UTF-8 BOM** + `Content-Disposition`。
前端消费入口已有：`src/api/report.ts#downloadReportCsv(path, params, fallbackName)`（不能用 axios，响应拦截器会把 CSV 剥成 undefined）。

### 2.4 `cst/api/MarginController`（毛利，第 8 个报表端点）

`GET /api/v1/reports/profit` — 参数 `from`、`to` 是 **账期 `yyyy-MM`**（`MarginApplicationService.analyze` 内部 `parsePeriod`），**不是** ISO 日期；`groupBy` = `product`\|`customer`\|`period`。
返回 `{ items: [{ key, label, qty, revenueAmount, costAmount, grossProfitAmount, grossMarginRateBp, orderCount }] }`。
**没有对应的 `/profit/export`。**

### 2.5 简报与代码不一致的三处（以代码为准，已按代码实现）

1. 简报写 `/reports/aging?type=RECEIVABLE|PAYABLE` → 真实取值是 **`AR`|`AP`**（`ReportRequestParams.parseAgingType`），照简报写必 400。
2. 简报说呆滞分析「需新增后端」→ **不需要**：`inventory-turnover` 已回 `idleDays` / `stale` / `deadDays`，前端过滤即可（选了「不新增后端」这一支）。
3. 简报把 `/reports/profit` 归到 `/cst/...` → 真实路径就是 `/api/v1/reports/profit`，且参数口径与别的报表不同（账期不是日期）。

**纯前端拼出来的 3 张**：
- `slow-moving`：周转端点 + `closingQty > 0 && idleDays >= minIdle` 过滤 + 按 idleDays 降序。阈值语义与后端 `deadDays` 一致，不新造口径。
- `sales-top`：`groupBy=sku` 全量取回 → 前端按 amount 排序取前 N → 追加名次列与「占比」列（分数量除以榜内合计，万分比）。`limit` 类参数后端没有，所以是前端切片。
- `ap-aging` 的供应商筛选：端点不收 `partnerId`，只能按名称/编码在前端包含过滤。

**每页都有的东西**（框架统一给，不在各页重复实现）：加载遮罩、三态空状态（未查询 / 查询无结果并提示换期间 / 失败保留后端 message + 「重试」+「重载主数据字典」）、`el-table` 表尾合计行（`show-summary` + `summary-method`，只对 money/qty/int 求和，rate/days/bool 按口径不参与）、千分位（`Intl.NumberFormat('zh-CN')`）、负数标红（恒等式差额 / 四桶差额列）、汇总 chip、手绘 SVG 图、导出 CSV、打印。

**期间与维度联动**（框架层 `syncPeriodAndRange` + 报表层 `linkage` 两层纯函数）：
- 预设 chips（今天/近7天/近30天/本月/上月/本季/本年）一次写入 from+to 并立即查询；手工改任一端则回到「自定义」。
- `period`(yyyy-MM) 与 from/to 互相跟随：改账期时若原区间正好是一个整月，把新区间铺成该月首末日；改日期时账期跟着走。
- `operating`：`dimension` 切「按月」把区间对齐到整月，避免半个自然月。
- `profit`：`groupBy` 切「按账期」自动把区间放开到全年。
- `slow-moving`：改 `deadDays` 时把「空闲天数下限」一起带走，两个条件不打架。
- select / warehouse / period / date 类条件改完即查；日期区间要两头填完，交给「查询」按钮。

## 5. 缺失端点清单（交给主控 / 后端泳道）

按「有了能让前端删掉多少 hack」排序：

1. **`GET /api/v1/reports/profit/export`** —— 毛利分析是 8 张表里唯一没有服务端 CSV 的。其余 7 个导出端点参数与 JSON 端点一一对应，这个补上就整齐了。
2. **`GET /api/v1/reports/slow-moving?from=&to=&days=&warehouseId=`** —— 简报点名的呆滞端点。前端已用 `inventory-turnover` 的 `stale`/`idleDays` 兜住，但代价是：① 只能前端 CSV（无「导出 == 页面」）；② 呆滞表把全量周转行拉回浏览器再过滤，SKU×仓 大目录时是白白的传输。**若后端补，注意 `rpt` 模块的 `ArchitectureTest` 禁止依赖其它模块的应用服务**，应复用 `ReportAdvancedRepository` 而不是跨域调 inv 的服务。
3. **`/reports/aging` 缺筛选参数** —— 现在只有 `type` + `asOf`，没有 `partnerId` / `warehouseId` / `groupBy`。结果：应付账龄的「按供应商筛选」只能前端包含匹配；想看单一客户的全额账龄也得整表拉回。建议加 `partnerId`（可选）与 `limit`。
4. **`/reports/inventory-summary` 不回名称也不回金额** —— 只有 `skuId`/`warehouseId` 与四个数量。前端被迫：① 用 `/skus`+`/products`+`/warehouses` 拼名称，而 `/skus` 每页上限 200，超出就退化成 `SKU#id`（页面已显式提示）；② 受 `mdm:read` 权限牵制——只有 `rpt:read` 的账号能看报表却看不到名称。建议左连接返回 `skuCode`/`skuName`/`warehouseName`（`inventory-turnover` 已经这么做了，两个端点口径不一致）。
5. **库存金额（库存总值）没有报表端点** —— `/reports/inventory-summary` 只有数量。最接近的现成数据是 `GET /api/v1/cost/monthly?period=yyyy-MM`（`cst` 模块，返回 `closingCostAmount` 按 sku×仓），但它属 W2 的成本域且权限码是 `cst:*`，**本泳道没有擅自消费**。若产品要「库存金额 / 库存总值」这张表，建议由后端在 `rpt` 命名空间下开一个 `rpt:read` 的端点，而不是让前端跨权限码取数。大屏的「期末库存」因此只能放**件数**而不是金额。
6. **没有单据行级的「进货明细 / 销售明细」** —— 简报表格里的 #2「进货明细·按单据展开」、#3「销售明细·按单据展开」，现有 `/reports/purchase`、`/reports/sales` 都是**聚合**端点（`key/label/qty/amount/orderCount`），拿不到单号、业务日期行、经手人。要真正做到「按单据展开」需要新的 `/reports/purchase-detail`、`/reports/sales-detail`。本泳道按现有能力做成了「按供应商 / 按客户…聚合」，页面口径说明里写清了。
7. **`/reports/{purchase,sales}` 无分页与 limit** —— 按 `sku`/`day` 聚合时返回全量，前端「TOP N」只能全拉再切。建议加 `limit`（`customer-contribution` 已经有，风格可对齐）。

## 7. 踩的坑（都是真实报错，不是推测）

1. **`aging` 的 `type` 是 `AR`/`AP`**，简报写 `RECEIVABLE`/`PAYABLE`。照简报写 → 400。
2. **`/reports/profit` 的 from/to 是 `yyyy-MM`**（`MarginApplicationService.analyze` 里 `parsePeriod`），跟同页其它报表的 `LocalDate` 不同口径。混用会 400 或查空。
3. **`NavItem.icon` 在本基线是必填**（`icon: unknown`），11 条子菜单不写 icon 直接 `TS2741`。而且 `MainLayout` 用 `<component :is="m.icon" />` 渲染，写 `undefined` 虽然过类型检查但会画个空图标 —— 所以逐条给了 `@element-plus/icons-vue` 里**已确认存在**的图标名。
4. **`<script setup>` 旁边再放一个 `<script>` 写 helper 是错的**（两个 default export，vue-tsc `TS2300 Duplicate identifier`）；helper 和类型都收进 `<script setup>`。
5. **行对象别用 `Record<string, unknown>`**：TS 的 interface 没有隐式索引签名，后端 DTO 类型赋不进去（几十个 `TS2322`）。改成 `Row = Record<string, any>` + 只在 loader 出口做一次 cast，格式化函数收 `unknown` 入参再自己判数值。
6. **`el-table` 的 `summary-method` 返回数组必须与列一一对应**：所以框架刻意不插 index/selection 列，`total: 'count'` 的列（如「期间」「维度名称」）占住数组槽位。
7. **`rptApi` 返回的是 `{ items: [...] }` 不是数组**：大屏 `Promise.all` 里想统一成数组，结果 `TS2339/TS2488` 一片。定成 `guard(promise, { items: [] })` + 下游 `.data.items` 才对齐。
8. **CSV 不能用 axios 实例下载**：`client.ts` 的响应拦截器会把包络剥成 `data`，对 `text/csv` 得到 `undefined`。已有的 `downloadReportCsv` 用原生 `fetch` + 手动带 token，本次直接复用（`/screen` 不涉及导出）。
9. **前端本地 CSV 必须补 UTF-8 BOM**（`\uFEFF`）才不被 Excel 按 GBK 猜；同时把单元格里的逗号在导出前摘掉，避免没有引号包裹时错列。
10. **SKU 没有 `name`/`code` 字段**（`Sku` 接口只有 `productId/color/size/barcode`）：业务上的「SKU 名称」= `商品名 · 颜色-尺码`，且 `/skus` 每页 200 条封顶，装不下要显式提示，否则用户以为报表算错了。
11. **没有 `meta.fullscreen` 支持**，而 `router/index.ts` / `MainLayout.vue` 不归本泳道改（三条泳道并行必冲突）。`/screen` 用 `position: fixed; inset: 0; z-index: 2000` 覆盖整视口 + 原生 Fullscreen API 按钮，效果等同。**合并后建议主控给路由加 `meta.fullscreen`，把 `/screen` 提成顶层路由**（届时只需改 `75-screen.ts` 一处）。
12. **构建要先把 TEMP/TMP 指进 ASCII 工作树**：`export TEMP="$PWD/.tmp" TMP="$PWD/.tmp"`，否则 esbuild/vite 往中文路径或系统临时目录写。`.tmp/` 已被 `.gitignore` 的 `*.tmp` 规则覆盖（`git check-ignore` 验过），构建产物没进版本库。
13. `node_modules` 是 junction —— 全程没跑 `npm install`，也没动 `package.json`，所以共享目录没被破坏。
