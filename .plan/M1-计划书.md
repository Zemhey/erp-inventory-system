## 2. M1 范围（做什么 / 不做什么）

### 2.1 做什么 —— 17 个未完成的 MVP 项

按依赖顺序分四批。**每批做完都要 `./gradlew check` 全绿 + 更新追踪矩阵**。

#### 批次 A：主数据（地基，必须先做）

| FR | 功能 | 关键点 |
|---|---|---|
| FR-MDM-01 | 商品与 SKU（颜色×尺码）管理 | SKU 矩阵批量生成；`(product_id,color,size)` 唯一已有约束 |
| FR-MDM-02 | 供应商管理 | 编码唯一 |
| FR-MDM-03 | 客户/会员管理 | 含折扣等级（影响售价，M2 促销会用到） |
| FR-MDM-04 | 仓库管理 | 已有表，补 CRUD |

**产出**：`mdm` 模块的实体 + Repository + ApplicationService + Controller + 测试。
**注意**：这些是纯 CRUD，但**不要写成贫血 CRUD**——编码唯一性、SKU 停用不删（`enabled` 字段已有）等规则要有测试。

#### 批次 B：进货闭环（第一次真正调用库存）

| FR | 功能 | 关键点 |
|---|---|---|
| FR-PUR-01 | 进货单创建 / 提交 / 审核 | 状态机：DRAFT → SUBMITTED → APPROVED |
| FR-PUR-02 | 入库确认 | ★ **必须调用 `InventoryApplicationService.receiveIn`**，不得自己写库存 |

**这一批的价值**：打通"单据 → 库存"的第一次真实联动，是 M1 的核心。

#### 批次 C：出货闭环（对称于进货，但更复杂）

| FR | 功能 | 关键点 |
|---|---|---|
| FR-SAL-01 | 出货单创建（同时预占库存） | 建单即调 `reserve`，库存不足要回滚整单 |
| FR-SAL-02 | 出货确认（预占转出库） | ★ 调 `shipOut`，按 FEFO 拆批次 |

**难点**：建单预占 + 审核 + 出货，是**多步骤、多事务**的流程。
要明确：预占失败整单回滚；单据作废要释放预占（M1 可先不做作废，FR-SAL-04 是 P1）。

#### 批次 D：认证与权限（横切，可最后做但必须做）

| FR | 功能 | 关键点 |
|---|---|---|
| FR-IAM-01 | 登录 / 登出（JWT） | 密码错误锁定 |
| FR-IAM-02 | RBAC 角色与菜单权限 | 无权限接口返回 403 |

**说明**：IAM 放最后不影响前三个批次开发（可先用固定用户），但**必须做**——它是 MVP 项，也是面试高频考点。

### 2.2 不做什么（M1 明确不做，别手痒）

| 项 | 为什么不做 |
|---|---|
| FR-RMA-01 退货 | 属 M2（逆向流程，依赖出货先稳定） |
| FR-SET-01~03 日清月结 | 属 M2（需要 MQ 与批处理） |
| FR-RPT-01~03 报表 | 属 M2（依赖数据先流动起来） |
| FR-INV-04 调拨、FR-INV-06 盘点 | P1/P2，非 MVP |
| 任何 Web / 小程序 / Android 前端 | 属 M3~M5 |
| 促销 / 优惠券 | P1，M2 再说 |
| 多级审核（金额阈值） | 待你拍板（见 §7） |

## 3. 技术方案（关键设计决策）

### 3.1 单据状态机（复用，不要每个单据写一套）

M0 已在契约里定义了统一七态：`DRAFT / SUBMITTED / APPROVED / PARTIAL / COMPLETED / VOIDED / REJECTED`。

**实现建议**：在 `shared` 里建一个 `DocumentStatus` 枚举 + 一个 `StatusTransitionValidator`，
把合法转移写成一张表（`Map<DocumentStatus, Set<DocumentStatus>>`），所有单据共用。

```java
// 示意
DRAFT      -> {SUBMITTED, VOIDED}
SUBMITTED  -> {APPROVED, REJECTED, VOIDED}
APPROVED   -> {PARTIAL, COMPLETED, VOIDED}
PARTIAL    -> {PARTIAL, COMPLETED, VOIDED}
COMPLETED  -> {}          // 终态
VOIDED     -> {}
REJECTED   -> {DRAFT, VOIDED}
```

**测试价值**：7 个状态 × 若干目标态 = 一张转移矩阵，**非法转移必须全部被拒绝**。
这是"状态机测试"的标准靶子，值得写成参数化测试（`@ParameterizedTest` + `@MethodSource`）。

### 3.2 单据表设计（进货单为例）

M0 已在 `docs/04-数据模型.md` 定了通用字段。M1 落地为 Flyway `V2__purchase_sales.sql`：

```sql
CREATE TABLE purchase_orders (
  id BIGSERIAL PRIMARY KEY,
  order_no       VARCHAR(64) NOT NULL UNIQUE,   -- PO20250601-0001
  status         VARCHAR(32) NOT NULL,
  supplier_id    BIGINT NOT NULL REFERENCES suppliers(id),
  warehouse_id   BIGINT NOT NULL REFERENCES warehouses(id),
  biz_date       DATE NOT NULL,                 -- 业务日期（ClockProvider 注入）
  total_amount   BIGINT NOT NULL DEFAULT 0,     -- 分
  total_qty      INTEGER NOT NULL DEFAULT 0,
  period         VARCHAR(7),                    -- yyyy-MM，月结锁账用
  remark         VARCHAR(500),
  created_by     BIGINT,
  version        INTEGER NOT NULL DEFAULT 0,    -- 乐观锁
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**三个必须注意的点**：

1. **单号生成**：不要用 `SELECT max(no)+1`（并发下会重号）。建议用 PostgreSQL 序列 + 日期前缀，
   或建 `document_sequences` 表用 `UPDATE ... RETURNING` 原子取号。**这条要写测试**。
2. **金额一律 `BIGINT` 分**（ADR-0005），`total_amount` 由明细汇总得出，**不允许反算**。
3. **`period` 字段预留**：M2 的月结锁账会用它校验"该期间已锁，禁止改单"。现在建好省一次迁移。

### 3.3 跨模块调用规则（最容易违规的地方）

```
PUR 模块                          INV 模块
─────────                        ─────────
PurchaseOrderService  ──调用──▶  InventoryApplicationService.receiveIn(...)
                                  ↑
                                  唯一库存入口
```

**绝对禁止**（违反就是架构破防）：

```java
// ❌ 严禁：PUR 模块自己写库存
jdbc.update("UPDATE inventory_balances SET on_hand_qty = on_hand_qty + ?", qty);

// ✅ 正确
inventoryApplicationService.receiveIn(skuId, warehouseId, batchNo, ..., qty, "PURCHASE_IN", orderNo, ...);
```

**M1 建议加一条 ArchUnit 测试**把它固化成 CI 门禁：

```java
@ArchTest
static final ArchRule 库存变动只能经由INV模块 =
    noClasses().that().resideOutsideOfPackage("com.erp.inv..")
        .should().dependOnClassesThat().areAssignableTo(InventoryBalanceRepository.class);
```

> 这就是"用架构测试守住架构决策"——比写文档提醒自己有效得多，也是简历亮点。

### 3.4 幂等键（重试与重复提交）

M0 已在预占上验证过。M1 的单据创建同样要带 `X-Request-Id`：

- **入库确认 / 出货确认**：这两个会写库存流水，天然需要幂等
- 现成的护栏：`inventory_ledger` 唯一索引 `(request_id, biz_type, batch_no)`
- **单据创建**：需要额外的 `idempotency_keys` 表（表已建，但还没用起来）

### 3.5 时间处理

**禁止** `LocalDateTime.now()`。业务日期一律：

```java
LocalDate bizDate = clock.today();   // 可注入 → 测试可穿越时间
```

M1 的测试大概率还不需要时间穿越，但**现在就用对**，M2 做日清月结时就不用回头改。

## 4. 测试策略（M1 的重点，别只写 happy path）

### 4.1 每个 FR 的最低测试要求（DoD）

| 层 | 要求 |
|---|---|
| L1 单元 | 状态机转移合法性、金额计算、编码唯一性校验 |
| L2 集成 | 每个 Repository 的 SQL；单据创建→审核→执行的完整链路 |
| 契约 | 实现与 `openapi.yaml` 一致（CI 已有 contract-check） |
| 不变量 | 进货入库后 INV-2 成立；出货后 INV-1/INV-3 成立 |

### 4.2 M1 必须新增的测试用例（预估编号）

| 编号段 | 覆盖 |
|---|---|
| TC-MDM-001~010 | 商品/SKU 唯一性、SKU 矩阵生成、停用不删 |
| TC-PUR-001~012 | 进货单状态机（含**非法转移**）、分批入库、超量入库拒绝 |
| TC-SAL-001~015 | 出货单预占、库存不足整单回滚、FEFO 拆批次、出货后不变量 |
| TC-IAM-001~008 | 登录、token 过期、无权限 403 |
| TC-DOC-001~008 | 单号生成并发唯一性、幂等重复提交 |

**特别强调三个高价值用例**（面试可讲）：

1. **并发建单不重号**：50 线程同时创建进货单，单号必须全不重复
2. **库存不足时整单回滚**：出货单 3 行明细，第 3 行库存不足 → 前 2 行的预占必须一起回滚
3. **状态机非法转移**：参数化覆盖全部 7×7 组合，只允许合法转移

### 4.3 覆盖率目标

M1 完成后：**行覆盖 ≥ 60%，分支 ≥ 50%**。同步修改 `build.gradle.kts` 的 `jacocoTestCoverageVerification` 阈值。

## 6. 已知坑与规避（M0 踩过的，别重踩）

| 坑 | 症状 | 规避 |
|---|---|---|
| 中文路径 | 测试全红 `ClassNotFoundException` | 走 `D:\erp-build` |
| Docker 未启动 | `Could not find a valid Docker environment` | 先启 Docker Desktop |
| `set -e` + `find` 失败 | 脚本静默退出、无报错 | `find ... \|\| true` |
| 时间戳进产物 | `index-check` 永远失败 | 已改为确定性输出，勿再写时间戳 |
| 用 H2 测 | 假绿，生产才炸 | 只用 Testcontainers 真 PG |
| 唯一索引设计过窄 | 合法操作被误判重复 | M0 踩过（`batch_no` 漏了），设计索引时想清业务语义 |
| PowerShell 传 JSON | `\` 转义导致请求体损坏 | 用文件 `--data-binary @file` |
| 提交信息含引号 | git 报 pathspec 错误 | 用 `.msg.txt` 文件 + `git commit -F` |
