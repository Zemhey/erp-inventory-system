> 基线：`main @ 97c094c`，本泳道分支 `feat/m25-reversal`，工作区 `../erp-m25-reversal`，

## 0. 一分钟交接

M2 只做了"未执行作废"：出货单/进货单一旦有 `shippedQty > 0` / `receivedQty > 0`，
作废就被明确拒绝，库存不会被静默丢弃，但也无法纠正"发错货/入错库"。
M2.5 把这条断头路补成闭环：

1. 已出货（`PARTIAL/COMPLETED`）的出货单作废时，按原 `SALES_OUT` 流水**逐批次回补实存**，
   写 `SALES_REVERSAL` 正向流水，状态到 `VOIDED`；
2. 已入库（`PARTIAL/COMPLETED`）的进货单作废时，按原 `PURCHASE_IN` 流水**逐批次回退实存**，
   写 `PURCHASE_REVERSAL` 负向流水，状态到 `VOIDED`；
3. 库存变动仍只经 `InventoryApplicationService`；`COMPLETED` 对常规状态机仍是终态，
   红冲走**显式补偿转移白名单**（不把 `COMPLETED` 改成可常规流转，否则月结 `isOpen()` 会误算未结）；
4. 契约继续用现有 `POST /{id}/void`（只追加描述与 409 示例），补上契约早就声明、实现却没收的
   `X-Request-Id`，同键重放幂等、异键重复作废 409；
5. 有退货的出货单**不允许红冲**；红冲后原单上未入库的退货单也不能再入库（否则会二次回补库存）。

## 2. 口径决策（本泳道的关键，先定死再写代码）

### 2.1 有退货的出货单能否红冲？——**不能**

判定口径：只要原出货单任一明细 `returnedQty > 0`，红冲直接拒绝，返回
`SAL_STATUS_ILLEGAL`，消息包含"已退货 N 件，不能红冲；请先处理退货单"。

理由：

1. 已完成退货的库存已经通过 `RETURN_IN` 回补；此时再按原 `SALES_OUT` 全额红冲，
   会把同一批货回补两次；
2. 若要支持"扣掉已退数量后红冲剩余"，必须同时定义退货金额/成本的冲销顺序，
   而退货单本身又不支持红冲（M2 明确不做），口径会变成半截；
3. 保守拒绝是**可解释、可测试、不会写脏库存**的；将来 RMA 支持红冲后，
   再放开为"剩余净出货量红冲"。

> 实测补充（写 TC-SAL-020 时暴露）：退货入库的批次由**操作员指定**（M2 口径），
> 因此 `RETURN_IN` 常常落在与原 `SALES_OUT` **不同的批次**上。
> 这意味着"扣掉已退数量后按原批次红冲"在批次维度根本无法对齐 ——
> 拒绝红冲不只是金额口径问题，也是批次守恒问题。

配套守卫（必须一起做，否则"红冲 + 待入库退货"仍会双补库存）：

- 红冲后原出货单变为 `VOIDED`；
- 退货入库的 `SalesOrderReturnService#registerReturn` 先对原出货单头行加锁
  （`SELECT ... FOR UPDATE`），要求状态仍为 `PARTIAL/COMPLETED`；
- 因此红冲前已建、但还没入库的退货单，红冲后入库会被拒（`RMA_ORIGIN_NOT_SHIPPED`），
  用户需先作废该退货单。该行为由 `TC-SAL-021` 钉住。

### 2.2 红冲写哪种流水？——**新增两个方向明确的 biz_type**

| 动作 | 流水方向 | 新 `biz_type` | 批次与数量 |
|---|---|---|---|
| 出货红冲 | 实存增加 | `SALES_REVERSAL` | 按原 `SALES_OUT` 每条流水**逐条**反向，同批次、同数量 |
| 进货红冲 | 实存减少 | `PURCHASE_REVERSAL` | 按原 `PURCHASE_IN` 每条流水**逐条**反向，同批次、同数量 |

不选 `ADJUST_IN/ADJUST_OUT` 的原因：调整类流水语义是"盘点/人工调账"，
与"单据红冲"在报表、对账和追责上是两类事实；混用会让"这笔库存为什么变"永远说不清。
`biz_ref_no` 仍写原单号，`biz_ref_id` 写原单 id，`request_id` 由
`X-Request-Id + ":REV:" + 原流水 id` 派生，保证同一请求多批次不撞
`uq_ledger_request (request_id, biz_type, batch_no)`。

### 2.3 是否新增 `biz_type` 需要迁移？——**需要，新增 V8（追加式）**

- V1 的 `inventory_ledger.biz_type` 有内联 CHECK，枚举写死 7 个值；
- V8 用 `DO $$` 按约束定义找到并删除该 CHECK（不依赖 PostgreSQL 自动生成的约束名），
  再新增命名约束 `ck_ledger_biz_type`，值 = 原 7 个 + 2 个红冲类型；
- 同迁移增加 `sales_orders.void_request_id` / `purchase_orders.void_request_id`
  与各自的部分唯一索引，作为作废动作的幂等键；
- V1~V7 一行不改，符合"已合并迁移只增不改"。

### 2.4 锁账期如何拒绝？——**动库存前先过 `PeriodGuard`**

`voidOrder` 在读取单据后、任何状态/库存变更前调用
`periodGuard.requireOpen(order.bizDate())`；账期 `CLOSED` 时抛
`SET_PERIOD_CLOSED`（409），消息带账期与业务日期。

- 普通作废与红冲同一口径：锁账后都不允许改该期间单据；
- 已 `VOIDED` 的同键重放放在锁账检查**之前**：首次成功后账期才被锁的极端场景下，
  重放仍应幂等返回首次结果，而不是 409。

### 2.5 幂等语义——**一单一键，状态更新先行**

| 场景 | 行为 |
|---|---|
| 首次作废（普通或红冲） | 执行；把 `X-Request-Id` 写入 `void_request_id` |
| 同一 `X-Request-Id` 重放 | 200，返回同一张 `VOIDED` 单；**不**再写流水/改库存 |
| 作废成功后再用**新**键 | 409 `SAL_STATUS_ILLEGAL` / `PUR_STATUS_ILLEGAL`（已作废） |
| 并发同键 | 行锁 + 条件 UPDATE 串行化；后到者更新 0 行后重读，发现同键 → 幂等返回 |
| 并发异键 | 只有一个状态 UPDATE 成功；另一个重读后报状态非法；库存只回补一次 |
| 同一键被用于另一张单 | `void_request_id` 唯一索引拦住，翻译为 `SYS_DUPLICATE_REQUEST` |

实现顺序（关键）：**先做状态条件 UPDATE（`WHERE id=? AND status=? AND version=?`，
红冲另加 `NOT EXISTS returned_qty > 0`），再做库存反向流水**。
状态 UPDATE 是并发串行化点；若库存回退失败（如进货已被卖出），事务整体回滚状态。

### 2.6 状态机口径——**COMPLETED 仍是常规终态，红冲是补偿性转移**

不把 `COMPLETED -> VOIDED` 加进 `DocumentStatus.TRANSITIONS`：

- `isTerminal()` 被 `isOpen()` 复用，而 `isOpen()` 参与月结"未结单据"口径；
  把 `COMPLETED` 改成非终态会让已完成单据被当成未结；
- 常规 7×7 转移表与前端镜像（86 项门禁）保持不动；
- 在 `DocumentStatusMachine` 增加显式 `requireRedReversal(from, ...)`：
  只允许 `PARTIAL/COMPLETED -> VOIDED`，只由 PUR/SAL 的"已有执行量"作废路径调用。

### 2.7 契约与前端

**契约：扩展现有 `POST /{id}/void`，不新增 operation。**

理由：契约从一开始就把 `/void` 描述为"作废/红冲"并已声明 `X-Request-Id` 必填；
新增 `/reverse` 会让同一个业务结果有两条路径、两套权限码和两份客户端方法，
却没有带来任何新语义。本期只做追加式修改：

- 补全两个 void 的 description（普通作废 vs 红冲、退货限制、锁账、幂等）；
- 补 409 示例（`SAL_STATUS_ILLEGAL` / `PUR_STATUS_ILLEGAL` / `SET_PERIOD_CLOSED` /
  `INV_NEGATIVE_NOT_ALLOWED`）；
- 不删路径、不改已有 schema 字段。

**前端：本期不改行为。** 状态机通用转移表未变，镜像不需要同步；
`npm run check` 保持 86 项。`frontend/web/src/api/client.ts` 里两条"已出货/已入库作废会被拒绝"
的注释改为指向 M2.5 红冲（纯注释，不影响类型与门禁）。
红冲按钮的 UI 暴露留给后续前端泳道：它需要把"补偿性转移"正式纳入镜像与 86 项门禁的设计，
不适合在本次后端泳道里用旁路绕过门禁。

### 2.8 进货红冲与后续出货/退货的交互

- 红冲只回退**原入库批次**，不做跨批次挪用；
- 每个批次回退前用条件 UPDATE 检查
  `on_hand_qty >= 回退量 AND reserved_qty <= on_hand_qty - 回退量`：
  - 货已被出货 → 实存不足 → `INV_NEGATIVE_NOT_ALLOWED`；
  - 货已被出货单预占 → 回退后预占会超过实存 → 同样 `INV_NEGATIVE_NOT_ALLOWED`；
- 错误消息带 sku/仓库/批次/当前实存/当前预占/需要回退量；
- 后续退货回补的是**退货单指定批次**，不会自动补回原进货批次；因此"先卖后退"后
  原进货批次仍可能不足，红冲依旧拒绝——这是"不跨批次挪用"的必然结果，见
  `TC-PUR-021`（退货入库到另一批次后仍拒绝原批次红冲）。

## 3. 数据与代码改动

### 3.1 V8（`backend/server/src/main/resources/db/migration/V8__document_reversal.sql`）

```
① inventory_ledger.biz_type CHECK：原 7 值 + SALES_REVERSAL + PURCHASE_REVERSAL
② sales_orders.void_request_id VARCHAR(64) + uq_so_void_request（部分唯一）
③ purchase_orders.void_request_id VARCHAR(64) + uq_po_void_request（部分唯一）
```

### 3.2 INV（库存唯一入口）

- `InventoryLedgerRepository#findByBizRefAndBizType(bizRefNo, bizType)`；
- `InventoryBalanceRepository#decreaseOnHand(...)`（条件 UPDATE，防负/防低于预占）；
- `InventoryApplicationService`：
  - `reverseSalesOut(orderNo, orderId, requestId)`：读 `SALES_OUT` → 逐条 `increaseOnHand`
    + 写 `SALES_REVERSAL`；
  - `reversePurchaseIn(orderNo, orderId, requestId)`：读 `PURCHASE_IN` → 逐条
    `decreaseOnHand` + 写 `PURCHASE_REVERSAL`；
  - `releaseIfActive(reservationId)`：`PARTIAL` 红冲时释放未出货行仍 `ACTIVE` 的预占。

### 3.3 状态机

- `DocumentStatusMachine.requireRedReversal(from, errorCode, ref)`：
  白名单 `{PARTIAL, COMPLETED}`，目标 `VOIDED`；非法状态抛单据自己的状态码。
- `DocumentStatus.TRANSITIONS` 不动，`TC-DOC-001~006` 语义不动；
  新增 `TC-DOC-011~012` 覆盖补偿转移的允许/拒绝边界。

### 3.4 SAL

`SalesOrderApplicationService#voidOrder(long id, String requestId)`：

1. 幂等短路（`VOIDED` + 同 `void_request_id` → 返回）；
2. `PeriodGuard`；
3. `anyShipped()`：
   - `anyReturned()` → `SAL_STATUS_ILLEGAL`；
   - `requireRedReversal`；
   - 校验 `Σ shippedQty == Σ(-SALES_OUT.change_qty)`，不一致拒绝（防流水漂移下红冲）；
   - `markVoidedWithNoReturns`（含 `NOT EXISTS returned_qty > 0` 与版本条件）；
   - `inventory.reverseSalesOut(...)`；
   - 对未出货行的 `ACTIVE` 预占逐段 `releaseIfActive`（`PARTIAL` 防御性处理）；
4. 未出货：原逻辑（释放预占）但状态更新改为带 `void_request_id` 的 `markVoided`。

`SalesOrderReturnService#registerReturn`：先 `SELECT ... FOR UPDATE` 锁原出货单头，
状态非 `PARTIAL/COMPLETED` → `RMA_ORIGIN_NOT_SHIPPED`（消息含"已作废"），
再走原条件 UPDATE。锁顺序与红冲一致（先单头、后明细/库存），避免红冲与退货入库并发双补。

### 3.5 PUR

`PurchaseOrderApplicationService#voidOrder(long id, String requestId)`：

1. 幂等短路；
2. `PeriodGuard`；
3. `anyReceived()`：
   - `requireRedReversal`；
   - 校验 `Σ receivedQty == Σ(PURCHASE_IN.change_qty)`；
   - `markVoided`（版本条件）；
   - `inventory.reversePurchaseIn(...)`；
4. 未入库：原逻辑 + 带 `void_request_id` 的 `markVoided`。

### 3.6 Controller / 契约

- `SalesOrderController#voidOrder`、`PurchaseOrderController#voidOrder`
  增加 `@RequestHeader("X-Request-Id") @NotBlank String requestId`；
- 错误码不新增：`SAL_STATUS_ILLEGAL` / `PUR_STATUS_ILLEGAL` / `SET_PERIOD_CLOSED` /
  `INV_NEGATIVE_NOT_ALLOWED` / `SYS_DUPLICATE_REQUEST` 全部复用；
- `INV_NEGATIVE_NOT_ALLOWED` 从"无名枚举"变成真实抛出点（docs/05 同步）。

## 7. 已知风险与规避

| 风险 | 规避 |
|---|---|
| 红冲与退货入库并发导致双补库存 | 红冲先锁单头（状态 UPDATE），退货入库先 `SELECT ... FOR UPDATE` 单头；锁顺序一致 |
| 红冲与入库/出货并发 | 状态 UPDATE 带 `version` 条件；失败方整事务回滚 |
| 进货红冲把库存减成负数 | 应用层条件 UPDATE 提前拒绝 + DB `CHECK (on_hand_qty >= 0)` 兜底 |
| 进货红冲使 `reserved_qty > on_hand_qty` | 条件 UPDATE 同时检查 `reserved_qty <= on_hand_qty - qty` |
| 重复红冲写两套流水 | `void_request_id` 幂等短路 + `uq_ledger_request` 最后一道 |
| 红冲把 `COMPLETED` 当常规可流转，污染月结 | 补偿转移白名单，`TRANSITIONS` 不动 |
| 前端 86 项门禁因镜像改动变红 | 本期不改镜像；红冲 UI 交后续前端泳道 |
| `INV_NEGATIVE_NOT_ALLOWED` 原来没有抛出点 | 本期作为进货红冲的稳定业务码，docs/05 同步 |

**过程中真实纠正的一处（写进坑表）**

`TC-SAL-020` 第一版把"退货已回补 2 件"断言成原批次 `''` 从 5 变 7，实测 `onHand('')` 仍是 5：
退货入库的批次由**操作员指定**（M2 口径），`RETURN_IN` 落在 `BACK-01` 这个新批次上。
断言改成"原批次 5 + 退货批次 2"，并顺手把这条写进 §2.1 的拒绝理由 ——
它让"有退货就不能按原 `SALES_OUT` 批次红冲"从金额口径上升级到批次守恒口径。
