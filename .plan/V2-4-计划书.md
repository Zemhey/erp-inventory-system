## 2. 口径（先定口径，再落表）

### 2.1 成本对象

- **成本池 = (sku_id, warehouse_id)**，跨批次统一移动加权。
  理由：批次是库存可追溯维度，不是财务核算维度；销售 FEFO 拆批次时，毛利仍应按 SKU 级均价结转。
- 每次库存流水按 `occurred_at ASC, id ASC` 顺序回放，得到该条流水的成本层。
- 金额一律 `BIGINT` 分；数量为 `INTEGER`（流水原值），池数量用 `BIGINT` 累加。
- 除法只允许出现在 `com.erp.shared.money.MoneyMath`，显式 HALF_UP；
  新代码禁止 `BigDecimal` / `double` / `float` 做金额中间运算，ArchUnit 追加规则拦截。

### 2.2 各类流水的单位成本来源

| biz_type | 方向 | 成本来源 |
|---|---|---|
| `PURCHASE_IN` | 正 | 流水的 `unit_cost_amount`（进货行单价） |
| `PURCHASE_REVERSAL` | 负 | 流水的 `unit_cost_amount`（原进货成本） |
| `SALES_OUT` | 负 | 当前移动均价；整池清空时取剩余全部成本，避免零数量残留分值 |
| `SALES_REVERSAL` | 正 | 配对原 `SALES_OUT` 成本（同单号 + SKU + 仓库 + 批次 + 数量，按流水 id 顺序）；配不上时退回当前均价 |
| `RETURN_IN` | 正 | 配对原出货单的 `SALES_OUT` 成本（通过 `return_orders.origin_sales_order_id` 解析）；配不上时退回当前均价 |
| `TRANSFER_IN` | 正 | **优先配对同一调拨单号 + SKU + 批次的 `TRANSFER_OUT` 出库总成本**；配不上再显式成本；最后当前均价 |
| `ADJUST_IN` | 正 | 显式成本（若有）否则当前均价；池空时为 0 |
| `TRANSFER_OUT` | 负 | 当前移动均价（或显式成本），并把该笔成本登记到调拨配对队列，供稍后到货的 `TRANSFER_IN` 使用 |
| `ADJUST_OUT` | 负 | 当前移动均价 |

**红冲配对**：正流水 + 反向流水在无其他流水插入时，成本净效果严格为 0。
配对按数量精确匹配；同一批次多次出货时按 id 顺序先进先出配对。

**退货配对**：退货按原出库成本回补，使 `SALES_OUT` 与 `RETURN_IN` 的成本净额等于 0；
毛利按「已出货 − 已退货」净额口径计算。

**调拨配对（V2-1 补丁）**：调拨是两段式的仓间移动，建单时只写 `TRANSFER_OUT`，
到货时才写 `TRANSFER_IN`，两者可能相隔数天；调拨行的 `unitCostAmount` 允许为空。
因此成本引擎按 `biz_ref_no + sku_id + batch_no` 维护跨事件队列：
调入优先消费调出成本，配不上才用显式成本，最后才用目的仓当前均价。
否则源仓按成本出、目的仓按自己的均价入，两仓合计成本会凭空增减。

### 2.3 结转与舍入

- 出库成本 `total = mulDivHalfUp(poolCost, qty, poolQty)`；
- 当 `qty == poolQty` 时 `total = poolCost`（最后一批全额结转，杜绝零库存残留成本）；
- 入库成本 `total = qty × unitCost`（整数乘法，无除法）；
- 入库均价不单独持久化为一个小数，而是由 `poolCost / poolQty` 在每次出库时显式舍入一次。
- 金额溢出：乘法用 `BigInteger` 中转（整数运算），最后 `longValueExact()`；不得用 `BigDecimal`。

### 2.4 期间归属

| 对象 | 归属依据 |
|---|---|
| `cost_layers` | 流水 `occurred_at`（业务时间，ClockProvider 注入） |
| `cost_monthly` | 流水 `occurred_at` 所在 `yyyy-MM` |
| `margin_records` | 出货单 `biz_date` 所在 `yyyy-MM`（与结算/出货报表口径一致） |

成本月结只允许在账期未锁时执行：复用 `PeriodGuard`（实现为 `SettlementPeriodGuard`），
`requireOpen(period.atEndOfMonth())`。月结锁账后成本数据冻结，重跑报 `SET_PERIOD_CLOSED`。
因此执行顺序为：先成本月结，再结算月结锁账。

## 3. 数据模型（V12）

### 3.1 `cost_layers`

一条库存流水对应一条成本层，保存该流水的成本与回放后的池状态。

```sql
CREATE TABLE cost_layers (
    id               BIGSERIAL PRIMARY KEY,
    ledger_id        BIGINT      NOT NULL,
    sku_id           BIGINT      NOT NULL,
    warehouse_id     BIGINT      NOT NULL,
    batch_no         VARCHAR(64) NOT NULL DEFAULT '',
    biz_type         VARCHAR(32) NOT NULL,
    biz_ref_no       VARCHAR(64) NOT NULL,
    direction        VARCHAR(8)  NOT NULL CHECK (direction IN ('IN','OUT')),
    qty              INTEGER     NOT NULL CHECK (qty > 0),
    unit_cost_amount BIGINT      NOT NULL CHECK (unit_cost_amount >= 0),
    total_cost_amount BIGINT     NOT NULL CHECK (total_cost_amount >= 0),
    pool_qty_after   BIGINT      NOT NULL,
    pool_cost_after  BIGINT      NOT NULL,
    occurred_at      TIMESTAMPTZ NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_cost_layer_ledger UNIQUE (ledger_id),
    CONSTRAINT ck_cost_layer_direction CHECK (
        (direction = 'IN'  AND biz_type IN ('PURCHASE_IN','RETURN_IN','SALES_REVERSAL','ADJUST_IN','TRANSFER_IN'))
     OR (direction = 'OUT' AND biz_type IN ('SALES_OUT','PURCHASE_REVERSAL','ADJUST_OUT','TRANSFER_OUT'))
    )
);
```

- 不建 `inventory_ledger` 外键：流水是不可变事实源，成本层是派生表；重建时先删后插，
  外键会拖慢且不增加正确性。`uq_cost_layer_ledger` 保证一条流水最多一个成本层。
- 派生表可整表重建：`POST /cost/recalculate` 与月结都会重建；
  `pool_qty_after` / `pool_cost_after` 让「当前结存成本」可直接查询，不必每次全量回放。

### 3.2 `cost_monthly`

```sql
CREATE TABLE cost_monthly (
    id                   BIGSERIAL PRIMARY KEY,
    period               VARCHAR(7) NOT NULL,
    sku_id               BIGINT     NOT NULL,
    warehouse_id         BIGINT     NOT NULL,
    opening_qty          BIGINT     NOT NULL DEFAULT 0,
    opening_cost_amount  BIGINT     NOT NULL DEFAULT 0,
    inbound_qty          BIGINT     NOT NULL DEFAULT 0,
    inbound_cost_amount  BIGINT     NOT NULL DEFAULT 0,
    outbound_qty         BIGINT     NOT NULL DEFAULT 0,
    outbound_cost_amount BIGINT     NOT NULL DEFAULT 0,
    closing_qty          BIGINT     NOT NULL DEFAULT 0,
    closing_cost_amount  BIGINT     NOT NULL DEFAULT 0,
    request_id           VARCHAR(64),
    computed_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    version              INTEGER     NOT NULL DEFAULT 0,
    CONSTRAINT uq_cost_monthly UNIQUE (period, sku_id, warehouse_id),
    CONSTRAINT ck_cost_monthly_period CHECK (period ~ '^[0-9]{4}-[0-9]{2}$'),
    CONSTRAINT ck_cost_monthly_qty CHECK (
        closing_qty = opening_qty + inbound_qty - outbound_qty),
    CONSTRAINT ck_cost_monthly_cost CHECK (
        closing_cost_amount = opening_cost_amount + inbound_cost_amount - outbound_cost_amount)
);
```

- 幂等键是 `(period, sku_id, warehouse_id)` 唯一约束；应用层先读后比，完全一致则
  `duplicate=true` 且不改 `computed_at`/`version`；有差异才更新并 `version+1`。
- 结存恒等式写成数据库 CHECK：即使应用层算错，也进不了表。

### 3.3 `margin_records`

```sql
CREATE TABLE margin_records (
    id                    BIGSERIAL PRIMARY KEY,
    period                VARCHAR(7)  NOT NULL,
    sales_order_id        BIGINT      NOT NULL,
    sales_order_no        VARCHAR(64) NOT NULL,
    customer_id           BIGINT      NOT NULL,
    sku_id                BIGINT      NOT NULL,
    warehouse_id          BIGINT      NOT NULL,
    biz_date              DATE        NOT NULL,
    qty                   INTEGER     NOT NULL CHECK (qty > 0),
    revenue_amount        BIGINT      NOT NULL CHECK (revenue_amount >= 0),
    cost_amount           BIGINT      NOT NULL CHECK (cost_amount >= 0),
    gross_profit_amount   BIGINT      NOT NULL,
    gross_margin_rate_bp  BIGINT      NOT NULL,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_margin_order_sku UNIQUE (sales_order_id, sku_id),
    CONSTRAINT ck_margin_period CHECK (period ~ '^[0-9]{4}-[0-9]{2}$'),
    CONSTRAINT ck_margin_profit CHECK (gross_profit_amount = revenue_amount - cost_amount)
);
```

- 粒度：**出货单 × SKU**。同单同 SKU 多行合并（避免行间分摊误差）；
  商品/客户/期间维度的分析在此表上聚合。
- 净额口径：`qty = shipped_qty − returned_qty`；`revenue = 已出货行金额 − 退货行金额`；
  `cost = SALES_OUT 成本 − RETURN_IN 成本`；完全退货（qty=0）不落行。
- `gross_margin_rate_bp = revenue == 0 ? 0 : mulDivHalfUp(grossProfit, 10000, revenue)`，万分比。
- 毛利记录在成本月结时重建；查询只读 `margin_records`，不在 GET 里写表。

### 4.1 回放算法

```
pools: Map<(sku, warehouse), (qty, cost)>
salesOutQueue: Map<(bizRefNo, sku, warehouse, batch), Deque<(qty, totalCost)>>
originOutStats: Map<(originOrderNo, sku, warehouse, batch), (qty, totalCost)>
transferOutQueue: Map<(transferNo, sku, batch), Deque<(qty, totalCost)>>
for event in events sorted by (occurredAt, id):
    key = (sku, warehouse)
    if event is inbound:
        unit = paired transfer cost (TRANSFER_IN)
               ?? explicitCost
               ?? current avg (or 0 when pool empty)
        // SALES_REVERSAL / RETURN_IN 沿用原配对优先级
        total = qty * unit
        pool.qty += qty; pool.cost += total
    else:
        unit/total = explicitCost (PURCHASE_REVERSAL)
                     ?? current avg (SALES_OUT / TRANSFER_OUT etc.)
        if qty == pool.qty: total = pool.cost
        pool.qty -= qty; pool.cost -= total
        if SALES_OUT: salesOutQueue.add(...); originOutStats.add(...)
        if TRANSFER_OUT: transferOutQueue.add(...)
    emit CostLayer(..., unit, total, pool.qty, pool.cost)
```

校验：出库后池数量不得为负（库存约束本应保证）；否则抛 `IllegalArgumentException`
（领域层只表达程序性错误，业务错误由应用层翻译）。

### 4.2 重算与并发（硬验收 3、5）

- `POST /cost/recalculate`：全局 advisory lock（`pg_advisory_xact_lock`）→ 读全部流水 →
  全量回放 → 删 `cost_layers` → 批量插入。同一份流水重复执行结果逐字节一致。
- `CostApplicationService.rebuildPool(sku, warehouse)`：按池 advisory lock → 只回放该池流水 →
  删该池成本层 → 重插。并发入库时，后到事务必须等前一个事务提交后再读流水，
  因此第二笔入库的均价包含第一笔，不会「后写赢」。
- 为什么不把增量状态放在内存：成本是派生数据，重算永远以流水为准；
  锁的粒度是池，重算范围也是池，逻辑只有一份。
- 测试用两个线程并发调用 `rebuildPool`，断言最终均价 = 两笔入库金额 / 总数量。

### 4.3 月结幂等（硬验收 4）

`closeMonthly(period, requestId)`：

1. `periodGuard.requireOpen(period 月末)`；
2. 获取期间 advisory lock；
3. 重建该期间涉及的成本层（保证与流水一致）；
4. 计算 `cost_monthly` 行：期初取期间前最后一条成本层的池状态，期内按方向汇总，期末 = 期初 + 入 − 出；
5. 与库中同键行逐字段比较：完全一致不动；缺失插入；不一致更新并 `version+1`；多余行删除；
6. 重建 `margin_records`（同期间）：先算后比，相同不动、不同更新、多余删除；
7. 返回 `duplicate = 无任何插入/更新/删除`。

同账期无数据变化时连跑两次：第二次 `duplicate=true`，业务字段与 `computed_at` 均不变。

### 4.4 毛利分析

`GET /reports/profit?from=yyyy-MM&to=yyyy-MM&groupBy=product|customer|period`

- 从 `margin_records` 聚合，只读；
- `product`：按 `sku_id`，标签由 SKU/商品字典补齐（SQL join）；
- `customer`：按 `customer_id`，标签取客户名；
- `period`：按 `period`；
- 返回 `items`，每行 `key/label/qty/revenueAmount/costAmount/grossProfitAmount/grossMarginRateBp/orderCount`；
- 汇总毛利率 = `mulDivHalfUp(ΣgrossProfit, 10000, Σrevenue)`，不按行平均（避免小金额行权重失真）。

### 6.1 关于 `unit_cost_amount` 的明确决策

施工指挥台模板写的是"把它填上"；本泳道按下发提示词中更严格的约束执行：

- `inventory_ledger` 是**不可变事实源**（ADR-0007，V1 结构上无 `updated_at`/`deleted`），
  阶段 0 清场也明确要求"不改现有库存写入语义"；
- 出库成本完全可以从流水 + 配对规则**确定性重算**，不需要回写；
- 因此本泳道**不回写** `inventory_ledger.unit_cost_amount`，而是把每条流水的成本
  （含出库成本、红冲/退货配对成本）持久化在 `cost_layers`；
- 若后续确有"从流水表直接看成本"的需求，只能在 cst 新增的、仅 cst 调用的方法里回填，
  且必须先与 V2-1 对齐流水不可变语义，不能在本泳道顺手做。

这条决策由 TC-CST-029/037 直接断言：重算后出库流水的 `unit_cost_amount` 仍为 null。

## 10. 补充补丁 · 调拨成本配对（2026-10-24）

### 10.1 缺口

V2-1 的仓间调拨是两段式：建单写 `TRANSFER_OUT`（源仓，负数量），到货写
`TRANSFER_IN`（目的仓，正数量），`biz_ref_no` 相同，调拨行 `unitCostAmount` 可空。
修复前，`TRANSFER_IN` 在没有显式成本时回退到目的仓当前均价，而 `TRANSFER_OUT`
按源仓成本结转；跨仓移动会让两仓合计成本凭空增减。

### 10.2 修复

`MovingAverageCostCalculator` 新增 `transferOutQueue`：

- 处理 `TRANSFER_OUT` 时，按 `(biz_ref_no, sku_id, batch_no)` 登记该笔出库总成本；
- 处理 `TRANSFER_IN` 时优先消费配对队列（支持部分/多段），配不上再使用
  `unitCostAmount`，最后才使用目的仓当前均价；
- `SALES_REVERSAL` 与 `RETURN_IN` 的既有配对逻辑保持不变；
- 键不含仓库：调拨单号唯一，单号已隐含源/目的仓；批次保证多批次不串成本。
