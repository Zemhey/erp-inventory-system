## 1. 目标、范围与硬边界

### 1.1 本次要证明什么

课程把「云与 DevOps」单独计 15% 分值。本次不追求"点一下真的上线"，而是交付一套**另一个运维照着做就能部署**的制品与手册：

| # | 交付 | 判定标准 |
|---|---|---|
| 1 | 可部署制品 | 后端多阶段 Dockerfile、前端 nginx 镜像、生产 compose、`.env.example`、健康检查 |
| 2 | 本地全栈验证 | 用**生产 compose** 在本机起 PG + backend + nginx，入口 18080 / PG 15435；走通「登录 → 库存查询 → 建进货单」 |
| 3 | 可重建 | 镜像能重新构建并记录耗时；不是"手工改容器"得到的 |
| 4 | 可回滚 | 镜像带 tag，脚本保留上一版并按 tag 回退；数据库有备份脚本与恢复步骤 |
| 5 | 可运维 | `infra/deploy/README.md` 自足：初始化、部署、HTTPS、备案后切域名、日志/监控/备份/回滚、常见故障 |
| 6 | 不碰业务 | 后端只加生产 profile / 端口可配置；不改业务逻辑、契约、前端页面 |

### 1.2 明确不做

| 不做 | 理由 |
|---|---|
| **真实部署到公网服务器** | 服务器 SSH 凭据不在仓库；真实部署需用户提供凭据并单独授权 |
| **申请/配置域名与备案** | 备案进行中；本次只准备「备案通过后如何切」的步骤 |
| **申请 Let's Encrypt 证书** | 需要一个已解析的公网域名且 80/443 可达；步骤写进 Runbook，本地无法验证 |
| **Kubernetes / 多机 / 高可用** | 单商户单机足够；多一层编排只会增加故障面（与 ADR-0006 的取舍一致） |
| **Redis / RabbitMQ** | **已核实后端零引用**（`grep -rniE "redis|rabbit|amqp"` 只命中测试数据源），不进生产 compose |
| **Prometheus / Grafana** | 后端未暴露 Prometheus 端点，单机 2C4G 也没有余量；本次用 actuator + Docker 日志 + 外部拨测 |
| **CI 部署 job 进门禁** | 未在真实 runner 验证过的部署 job 不能拿 main 的红绿作赌注；只给 `workflow_dispatch` 草案 |

### 1.3 与既有文档的关系

- `docs/03` §5 的部署图是 M0 期**愿景**（含 miniapp、Redis、RabbitMQ、Prometheus、Grafana）。本次按实际技术栈落地，并在 `docs/03` **追加**"M6 实施注记"，不改写原图。
- `docs/00`、`README.md`、`docs/planning/**`、`.plan/M1~M3` 不在本泳道写入范围；计数与状态由主工作区合并后统一刷新。

## 2. 部署架构

### 2.1 形态：单机 Docker Compose + nginx 反代

```
                         Internet / 校园网 / 本机
                                   │
                    ┌──────────────▼──────────────┐
                    │  云服务器（Ubuntu 22.04/24.04）│
                    │                              │
                    │  ① 宿主 nginx :80/:443        │  ← 备案后 + Let's Encrypt 在这一层
                    │      └─ proxy_pass 127.0.0.1:18080
                    │                              │
                    │  ② compose: erp-prod         │
                    │  ┌────────────────────────┐  │
                    │  │ web (nginx:1.27-alpine)│  │  ← 静态资源 + SPA fallback + /api 反代
                    │  │   :80 → 宿主 18080      │  │
                    │  └───────────┬────────────┘  │
                    │              │ /api/          │
                    │  ┌───────────▼────────────┐  │
                    │  │ backend (Spring Boot)  │  │  ← 仅内网，不 publish 端口
                    │  │   :8080                │  │
                    │  └───────────┬────────────┘  │
                    │              │ JDBC           │
                    │  ┌───────────▼────────────┐  │
                    │  │ postgres:16-alpine     │  │  ← 宿主 127.0.0.1:15435（便于运维/备份）
                    │  │   :5432                │  │
                    │  └────────────────────────┘  │
                    └──────────────────────────────┘
```

**为什么两层 nginx**：

- 容器内 nginx 负责**应用交付**（静态文件缓存、SPA history fallback、`/api` 反代、gzip），镜像在本地/CI 可复现；
- 宿主 nginx 负责**TLS 与域名**（Let's Encrypt 证书、HTTP→HTTPS、备案后切域名）。证书不进镜像，续期不重建镜像。
- 未备案阶段：不装宿主 nginx，直接 `http://<IP>:18080`；备案通过后再把 `WEB_BIND_IP` 改为 `127.0.0.1` 并启用宿主 nginx。

### 2.2 服务与端口

| 服务 | 镜像 | 容器端口 | 宿主端口 | 暴露范围 | 健康检查 |
|---|---|---|---|---|---|
| `postgres` | `postgres:16-alpine` | 5432 | `127.0.0.1:15435` | 仅本机 | `pg_isready` |
| `backend` | `erp-backend:<tag>` | 8080 | 不发布 | compose 内网 | `GET /actuator/health` |
| `web` | `erp-web:<tag>` | 80 | `${WEB_BIND_IP}:${WEB_PORT}`（默认 `0.0.0.0:18080`） | 按需 | `GET /healthz`（静态） |
| 宿主 nginx（可选） | 系统包 | 80/443 | — | 公网 | systemd + 外部拨测 |

**健康检查的三种语义**（不要混用）：

- `/healthz`（web）：**web 进程活着**。只返回 `ok`，不依赖后端；后端挂了不应把 web 反复重启。
- `/readyz`（web → backend actuator）：**整套是否可服务**。部署脚本与外部拨测用它；backend 未就绪时返回 503。
- `/actuator/health`（backend）：DB 连通性等组件状态。生产只暴露 `status`，不泄露细节。

### 2.3 请求路径

```
浏览器 → GET /                    → web nginx → /usr/share/nginx/html/index.html
浏览器 → GET /assets/xxx.js       → web nginx → 静态文件（30d immutable）
浏览器 → GET /purchase-orders     → web nginx → try_files 失败 → index.html（history 模式）
浏览器 → POST /api/v1/auth/login  → web nginx → http://backend:8080/api/v1/auth/login
```

**为什么 `/api` 前缀在开发与生产都成立**：Vite dev 用 `server.proxy` 把 `/api` 转发到 8080（`vite.config.ts`），生产用 nginx 转发到 `backend:8080`。前端 `baseURL` 始终是 `/api/v1`，两种环境没有分支。

### 2.4 数据与卷

| 卷 | 内容 | 备份 |
|---|---|---|
| `erp-pgdata`（compose 命名卷） | PostgreSQL 数据目录 | `scripts/backup-db.sh` 每日 `pg_dump -Fc`，保留 14 天 |
| 宿主 `/opt/erp/backups`（建议） | 备份文件 | 由运维决定是否再同步到对象存储；**不放在容器卷里** |

**迁移策略**：Flyway 在 backend 启动时自动执行。生产只允许**向前迁移**；回滚应用版本不自动回滚数据库。因此部署前必须备份，破坏性迁移必须走「先扩展、后收缩」两步（本次不新增迁移）。

## 3. 环境变量与密钥清单

**原则：所有环境相关值走 env；仓库里只有 `.env.example` 的占位值。** `.env` 已被 `.gitignore` 的 `.env` / `.env.*` 规则忽略（`!.env.example` 例外）。

### 3.1 必填（缺失则拒绝启动/拒绝部署）

| 变量 | 用途 | 生成/取值 | 泄漏影响 |
|---|---|---|---|
| `POSTGRES_PASSWORD` | PG 账号密码 | `openssl rand -base64 32` | 直接读全库 |
| `ERP_JWT_SECRET` | JWT HS256 签名密钥 | `openssl rand -base64 48`（≥32 字节） | 可伪造任意用户 token |
| `POSTGRES_DB` | 数据库名 | 默认 `erp` | — |
| `POSTGRES_USER` | 数据库用户 | 默认 `erp` | — |

**失败关闭**：

- compose 用 `${POSTGRES_PASSWORD:?}` / `${ERP_JWT_SECRET:?}`，未设置直接拒绝启动；
- `application-prod.yml` 对 `DB_URL` / `DB_USER` / `DB_PASSWORD` / `ERP_JWT_SECRET` **不写默认值**（占位符无法解析 → 启动失败），避免生产误用 `application.yml` 里的开发默认值；
- `scripts/deploy.sh` / `deploy.ps1` 额外拒绝 `change-me`、`erp`、`dev-only` 等占位/弱值。

### 3.2 可调（有安全默认值）

| 变量 | 默认 | 说明 |
|---|---|---|
| `WEB_PORT` | `18080` | 容器 web 的宿主端口；备案/宿主 nginx 后可改 `18080` 保持不变 |
| `WEB_BIND_IP` | `0.0.0.0` | 有宿主 nginx 时改 `127.0.0.1`，不要直接暴露容器 |
| `PG_HOST_PORT` | `15435` | 只绑 `127.0.0.1`，用于本机 psql/备份排障 |
| `TZ` | `Asia/Shanghai` | 业务日期与日志时区 |
| `IMAGE_TAG` | `latest` | 部署脚本每次生成 `<git短SHA>-<UTC时间>` |
| `BACKUP_RETENTION_DAYS` | `14` | 备份保留天数 |
| `JAVA_OPTS` | `-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError -Duser.timezone=Asia/Shanghai -Dfile.encoding=UTF-8` | 堆上限按容器内存比例，OOM 退出交给 restart 策略 |
| `BACKEND_BUILD_IMAGE` / `BACKEND_RUNTIME_IMAGE` | `eclipse-temurin:17-jdk-alpine` / `eclipse-temurin:17-jre-alpine` | 换镜像仓库/内网镜像时用 |
| `WEB_BUILD_IMAGE` / `WEB_RUNTIME_IMAGE` | `node:22-alpine` / `nginx:1.27-alpine` | 同上 |

### 3.3 密钥不进 Git 的三道保险

1. `.gitignore`：`.env`、`.env.*`、`*.pem`、`secrets/`、`application-local.yml`、`application-prod.local.yml`；
2. `.env.example` 只含占位值，Runbook 明确写"复制后必须改"；
3. 部署脚本在构建前做占位值检查；Git 提交前用 `git grep -nE 'ERP_JWT_SECRET=.{16,}'` 自查（真实值长度通常超过占位值）。

> `application-prod.yml` 会入库，但它**只有** `${ENV}` 占位符，没有任何真实凭据；这也是它可以从 `.gitignore` 的 `application-prod.yml` 规则中例外的原因。

## 4. 镜像、版本与回滚

### 4.1 镜像命名与 tag

| 镜像 | tag 格式 | 示例 |
|---|---|---|
| `erp-backend` | `<git短SHA>-<yyyyMMdd-HHmmss>` | `5e8a74d-20261023-163012` |
| `erp-web` | 同上（同一次部署共用 tag） | `5e8a74d-20261023-163012` |

同一 tag 同时标记 backend 与 web，保证"前端与后端是同一次构建"；回滚也以 tag 为单位。

### 4.2 部署状态文件

`infra/deploy/.deploy-state`（**不入库**）：

```
CURRENT_TAG=5e8a74d-20261023-163012
PREVIOUS_TAG=5e8a74d-20261022-101500
DEPLOYED_AT=2026-10-23T16:30:12+08:00
```

- 部署成功后写入；`PREVIOUS_TAG` 保留上一版，回滚默认回到它；
- 文件由脚本维护，不要手改；损坏时按 `docker image ls` 人工指定 tag。

### 4.3 回滚策略

| 场景 | 动作 |
|---|---|
| 新版本启动失败/健康检查不过 | `deploy` 默认**自动回滚**到 `PREVIOUS_TAG`（`--no-auto-rollback` 可关）；失败日志保留 |
| 新版本运行一段时间后发现业务问题 | `./scripts/rollback.sh`（不带参数 = 上一版）；也可 `./scripts/rollback.sh <tag>` |
| 数据库迁移不兼容 | **不要只回滚镜像**。停服 → 用部署前备份 `pg_restore --clean --if-exists` → 再回滚镜像。Runbook §8 有步骤 |
| 镜像被误删 | 保留上一版镜像；若两个都没了，用同一 commit 重新 `build`（tag 会变，但代码等价） |

**不做的事**：不自动删除旧镜像（磁盘满由运维按 Runbook 的保留策略清理），避免"回滚时发现镜像已被 prune"。

### 4.4 备份策略

- 每日 03:00 `pg_dump -Fc`（自定义格式，已压缩），文件名带时间戳；
- 保留 `BACKUP_RETENTION_DAYS` 天（默认 14）；
- 备份文件落在宿主 `infra/deploy/backups/`（不入库）；
- 每月至少做一次**恢复演练**：`pg_restore --list` 验证可读 + 恢复到临时库抽查表计数；
- 备份不等于高可用：单机 PG 仍是单点，课程范围内接受。

## 5. 验收标准（DoD）

| ID | 验收项 | 判定方式 |
|---|---|---|
| AC-M6-01 | 生产 compose 能在本机起整套 | `docker compose ... up -d` 后三个服务 `healthy` |
| AC-M6-02 | 前端入口可访问 | `GET http://127.0.0.1:18080/` 返回 200 且是 Vue 应用 HTML |
| AC-M6-03 | SPA history fallback 生效 | `GET /purchase-orders` 返回 200 + `index.html`（不是 404） |
| AC-M6-04 | `/api` 反代生效 | 经 18080 调 `POST /api/v1/auth/login` 成功拿到 token |
| AC-M6-05 | 业务链路走通 | 经 18080：登录 → `GET /inventory` → 建供应商/仓库/商品/SKU → `POST /purchase-orders` 成功 |
| AC-M6-06 | 健康检查分层正确 | `/healthz` 200；`/readyz` 200；停 backend 后 `/readyz` **非 2xx（502/503/504）** 而 `/healthz` 仍 200，恢复后 `/readyz` 200 |
| AC-M6-07 | 镜像可重建 | backend/web 从**生产 Dockerfile** 重新构建成功（本地离线基础镜像替换），记录耗时 |
| AC-M6-08 | 回滚可执行 | `rollback.sh` 能按 tag 切回上一版并通过健康检查（本地演练） |
| AC-M6-09 | 备份可恢复 | `backup-db.sh` 产出非空 dump；`pg_restore --list` 可读 |
| AC-M6-10 | 密钥不进库 | `.env` 未入库；`git grep` 无真实密钥；prod profile 无默认密钥 |
| AC-M6-11 | 不回归 | 后端 `gradlew check` 仍 **221 全绿**；前端 `npm run build` 通过 |
| AC-M6-12 | 手册自足 | 另一个人只看 `infra/deploy/README.md` 能完成部署/回滚/备份 |

## 7. 执行记录

> 环境：Windows 10.0.26200（Git Bash）· Docker 29.5.2 / API 1.54 · Docker Compose v5.1.4 ·
> Node v24.18.0（宿主）· JDK 17 · worktree `D:\MajorCacheFolder\Company system\erp-m6-deploy` ·
> ASCII 联接 `D:\erp-build-m6`（PowerShell 建，避免 Git Bash 路径转换）。
>
> **本机网络实测**：Docker Hub、GitHub、nginx.org、registry.npmjs.org 均连接超时；
> Maven Aliyun、Alpine 镜像站、registry.npmmirror.com 可达。因此镜像采用 §7.4 的离线方案，

### 7.1 制品构建（生产 Dockerfile）

**后端**（`backend/server/Dockerfile`，多阶段）：

```bash
docker build -t erp-backend:local \
  --build-arg BUILD_IMAGE=erp-offline-jdk:local \
  --build-arg RUNTIME_IMAGE=erp-offline-base:local \
  backend/server
```

实测：**106s**（构建阶段 Gradle `bootJar` 32s；4 个 task 全部 executed；导出 4.6s），
镜像 ID `sha256:d9b23595cde7f...`，本地基础镜像下 818 MB。
构建阶段使用的是本机 Gradle 缓存（wrapper dist + modules-2，约 518 MB），运行阶段使用
`erp-offline-base:local`（Alpine + JRE 17.0.20 + nginx，见 §7.4）。

**前端**（`frontend/web/Dockerfile`，多阶段）：

```bash
docker build -t erp-web:local \
  --build-arg NODE_IMAGE=erp-offline-node:local \
  --build-arg NGINX_IMAGE=erp-offline-nginx:local \
  --build-arg NPM_REGISTRY=https://registry.npmmirror.com \
  frontend/web
```

实测：首次 **39s**（`npm ci` 走 npmmirror；`vue-tsc + vite build` 在 Linux 内完成，
`✓ built in 10.15s`）；补 `CMD ["nginx","-g","daemon off;"]` 后重建 62s；纯缓存 2~3s。
镜像 ID `sha256:2b7352ccb4864...`，671 MB。

**一键重建脚本**（`scripts/build-local-images.sh`，复用缓存）：总耗时 **9s**；
最终 `erp-backend:local` / `erp-web:local` 均重新产出并通过 compose 启动。

> **没有验证到的**：`eclipse-temurin` / `node:22-alpine` / `nginx:1.27-alpine`
> 官方基础镜像的真实拉取。生产服务器/CI 有网络时执行 `scripts/deploy.sh` 即走官方基础镜像；
> 本机只能证明 Dockerfile 逻辑、Gradle/npm 构建、nginx 配置与整套 compose 是通的。

### 7.2 Compose 启动与健康检查

```bash
IMAGE_TAG=local docker compose --env-file infra/deploy/.env \
  -f infra/deploy/docker-compose.prod.yml up -d --no-build --wait --wait-timeout 180
```

- 第一次启动时 web 反复重启，日志为：
  `nginx: [emerg] "map" directive is not allowed here in /etc/nginx/conf.d/default.conf:19`
  与随后的 `"server" directive is not allowed here`。
  根因：本机 Alpine 包版 nginx 把 `conf.d` include 在顶层，而官方 nginx 镜像在 `http{}` 内。
- 修正：`infra/deploy/offline` 的 nginx 垫片改用一份与官方镜像等价的最小主配置
  （把 `conf.d` 放进 `http{}`）；同时 `frontend/web/nginx.conf` 去掉 `map`，
  改为 location 内 `set/if`，两种布局都能加载。**生产配置本身没有放宽**。
- 修正后最终状态（`docker compose ps`）：


## 8. 已知约束与移交

### 8.1 环境约束（本机实测，非代码缺陷）

1. **Docker Hub / GitHub / npmjs / nginx.org 不可达**：生产镜像的官方基础镜像未在本机拉取；
   已在本地用 Alpine 包 + 生产 Dockerfile 验证构建逻辑。生产服务器请用 `scripts/deploy.sh`
   走官方基础镜像；国内网络可配 registry mirror 或 `*_BUILD_IMAGE` / `*_RUNTIME_IMAGE`。
2. **Windows 宿主 esbuild `Access is denied`**：`vite:esbuild-transpile` 删除临时文件失败
   （主 worktree 与 M6 worktree 均复现）。已改用 Linux 容器内的生产 Dockerfile 构建；
   宿主 `npm run check` 不受影响。若后续要在 Windows 宿主直接 `npm run build`，
   可尝试把 `TEMP/TMP` 指到短路径、关闭安全软件对该目录的实时扫描，或升级/降级 esbuild；
   本次未改前端依赖。
3. **Alpine 包版 nginx 的 `conf.d` 位置与官方镜像不同**：本机垫片已用最小主配置对齐官方布局；
   生产 `nginx.conf` 用 `set/if` 代替 `map`，两种布局都能加载。若以后换基础镜像，
   先跑 `nginx -t`（在 compose 网络内，`backend` 主机名可解析）。
4. **Git Bash 会把内联中文 `curl -d` 转码**：中文 JSON 用 UTF-8 文件或 Python 发送；
   这不是服务端 bug。
5. **备份文件名用 UTC（`...Z`）**：Git Bash 的 `date` 与 Windows 本地时区不一致；
   UTC 命名避免歧义。`.deploy-state` 的 `DEPLOYED_AT` 在 shell 下是 UTC、PS 下是本地时区，
   脚本只读取 tag，不受影响。
