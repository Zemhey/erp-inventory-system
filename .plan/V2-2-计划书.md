## 2. 关键设计决策

### 2.1 请购单复用 `purchase_orders`，不新增第 6 张表

迁移只允许 5 张新表，因此请购单落在 `purchase_orders`：

- `doc_type`：`PURCHASE`（进货单）/ `REQUISITION`（请购单），默认 `PURCHASE`；
- 请购单明细仍用 `purchase_order_lines`（`qty` = 申请数量，`received_qty` 恒为 0）；
- `source_requisition_id` 落在转化生成的订单上；`converted_order_id` / `conversion_request_id`
  落在请购单上，唯一索引保证"一张请购单最多转出一张订单、一个幂等键只生效一次"；
- 现有 `/purchase-orders` 的查询与状态推进全部加 `doc_type='PURCHASE'` 过滤，
  请购单不会混入进货单列表，也不能走入库/红冲接口。

转化规则：

1. 只有 `APPROVED` 请购单可转；转化后状态置 `COMPLETED`（终态），不能再提交/审核/转化；
2. 请求必须**逐行覆盖**请购单全部明细（行不丢），每行 `1 <= 转化数量 <= 申请数量`（数量不超）；
3. 单价、供应商、仓库从请购单派生，不接受前端改价；
4. 同 `X-Request-Id` 重放返回首次生成的订单；换键再次转化 → `PUR_REQ_STATUS_ILLEGAL`。

### 2.2 质检发生在入库确认时，合格量才入库存

`POST /purchase-orders/{id}/receive` 的每一行新增可选字段：

- `qcQty`：本次到货中的合格数量，缺省 = `qty`（兼容既有调用）；
- `qcNote`：质检备注。

约束与口径：

- `0 <= qcQty <= qty`，否则 400；
- `received_qty += qty`（到货量，含不合格），`qc_qty += qcQty`（累计合格量）；
- 只有 `qcQty` 调 `InventoryApplicationService.receiveIn(...)`，不合格量**没有流水、没有余额行**；
- 行级 `qc_status` 由累计值推导：`qc_qty=0 → FAILED`；`qc_qty<received_qty → PARTIAL`；否则 `PASSED`；
- 应付金额 = `Σ qcQty × 单价`，不合格量不生成应付；
- 分批到货时 `qc_status` 按累计口径刷新，`qc_note` 保留最近一次非空备注。

### 2.3 应付按收货单生成，余额为生成列

- 一收货单（`po_receipts`）最多一张应付单（`receipt_id` 唯一）；
- `balance_amount = original_amount - returned_amount - paid_amount` 是 **PostgreSQL 生成列**，
  应用层无法写错，且 `returned_amount + paid_amount <= original_amount` 有 CHECK 兜底；
- 供应商维度恒等式：`Σbalance = Σoriginal − Σreturned − Σpaid`，由
  `GET /supplier-payables/reconcile` 每次实时聚合，可重复调用；测试连续调用两次断言一致。

### 2.4 付款核销明细逐行落库，付款单号分组守恒

迁移没有付款单头表，因此 `payable_allocations` 每行是一条核销明细，并重复保存：

- `payment_no`：付款单号（`PY...`）；
- `payment_amount`：付款单总额（同组相同）；
- `amount`：本行核销金额；
- `request_id`：付款幂等键（同组相同）。

守恒检查：

```sql
SELECT payment_no
  FROM payable_allocations
 GROUP BY payment_no
HAVING MIN(payment_amount) <> MAX(payment_amount)
    OR SUM(amount) <> MIN(payment_amount);
```

应用层在写库前校验 `Σ amount == 请求付款总额`（400 `PUR_PAYMENT_AMOUNT_MISMATCH`），
并对每张应付做条件 UPDATE `余额 >= 本次核销`；0 行 → 409 `PUR_PAYMENT_EXCEED_PAYABLE`。
`uq_payable_alloc_request (request_id, payable_id)` 保证并发重放不会重复核销。

### 2.5 采购退货按收货批次冲减

- 退货行引用 `po_receipt_lines.id`（原收货批次），数量上限 = 合格量 − 已退货量；
- 执行时先锁 `purchase_order_lines` 行，再聚合 `purchase_returns.lines` 的已退数量，
  防并发超退；
- 库存走 `InventoryApplicationService.purchaseReturnOut`（新增，`decreaseOnHand` +
  `PURCHASE_RETURN` 负流水），不允许 PUR 直接写余额表（ArchUnit 强制）；
- 应付按 `receipt_id` 减少 `returned_amount`，若会超过"原值 − 已付"则拒绝，余额不为负；
- 迁移把 `PURCHASE_RETURN` 追加进 `ck_ledger_biz_type`。

### 2.6 时间与幂等

- 所有业务日期/时间走注入的 `ClockProvider`，迁移与代码里不用 `LocalDateTime.now()`；
- 收货、请购建单/转单、退货执行、付款各自独立幂等键，不复用同一 `X-Request-Id`；
- 账期锁：请购建单/审核/转单、收货、退货执行、付款均调用 `PeriodGuard.requireOpen`；
  同键重放先短路再校验账期，保证锁账后重复请求仍返回首次结果。

## 3. V10 迁移

文件：`backend/server/src/main/resources/db/migration/V10__purchase_loop.sql`

### 3.1 新表（恰好 5 张）

| 表 | 作用 | 关键约束 |
|---|---|---|
| `po_receipts` | 到货单头（一次入库确认一张） | `request_id` 唯一；`accepted_qty + rejected_qty = total_qty` |
| `po_receipt_lines` | 到货行（含质检与批次） | `qc_qty + rejected_qty = received_qty`；`accepted_amount = qc_qty × unit_price_amount` |
| `supplier_payables` | 应付单（一收货单一张） | `receipt_id` 唯一；`balance_amount` 生成列；`returned + paid <= original` |
| `payable_allocations` | 付款核销明细 | `(payment_no, payable_id)` 唯一；`(request_id, payable_id)` 唯一 |
| `purchase_returns` | 采购退货单（明细 JSONB） | `return_no` / `request_id` / `approve_request_id` 唯一；`jsonb_array_length(lines) > 0` |

### 3.2 加列

- `purchase_order_lines`：`qc_status`（NONE/PASSED/PARTIAL/FAILED）、`qc_qty`、`qc_note`；
  存量已入库行回填 `qc_qty = received_qty`、`qc_status = PASSED`（保持"历史已入库即可用"）。
- `purchase_orders`：`doc_type`、`source_requisition_id`、`converted_order_id`、`conversion_request_id`。
- `inventory_ledger` 的业务类型 CHECK 追加 `PURCHASE_RETURN`。

### 3.3 历史数据回填

- 对 V10 之前已入库的进货单生成 `-LEGACY` 收货单与应付单（批次记空），
  使 `Σ应付原值 == Σ已收货合格金额`，避免新功能上线后应付恒等式从第一天就不平；
- 回填不写库存流水、不改库存余额。

### 3.4 权限

新增 `pur:payable`（读应付/余额核对）与 `pur:pay`（付款核销），授予 `FINANCE`；
`PURCHASER`/`VIEWER` 只授予 `pur:payable`。ADMIN 的 `pur:*` 自动覆盖。

## 5. 错误码（新增，均为可编程判断）

| 码 | HTTP | 场景 |
|---|---|---|
| `PUR_REQ_NOT_FOUND` | 404 | 请购单不存在 |
| `PUR_REQ_STATUS_ILLEGAL` | 409 | 请购单状态不允许提交/审核/转化（含重复转化） |
| `PUR_REQ_CONVERT_EXCEED` | 409 | 转化数量超过申请数量 |
| `PUR_RECEIPT_NOT_FOUND` | 404 | 到货单不存在 |
| `PUR_QC_QTY_INVALID` | 400 | 合格数量越界（<0 或 >本次到货量） |
| `PUR_RETURN_NOT_FOUND` | 404 | 退货单/收货行不存在 |
| `PUR_RETURN_STATUS_ILLEGAL` | 409 | 退货单状态不允许执行/作废 |
| `PUR_RETURN_QTY_EXCEED` | 409 | 退货数量超过可退量 |
| `PUR_RETURN_EXCEED_PAYABLE` | 409 | 退货金额超过该到货单应付余额（已付款部分不能被退货冲掉） |
| `PUR_PAYABLE_NOT_FOUND` | 404 | 应付单不存在 |
| `PUR_PAYMENT_AMOUNT_MISMATCH` | 400 | 核销明细合计 ≠ 付款单金额 / 金额非正 / 重复应付行 |
| `PUR_PAYMENT_SUPPLIER_MISMATCH` | 400 | 核销的应付不属于该供应商 |
| `PUR_PAYMENT_EXCEED_PAYABLE` | 409 | 核销额超过应付余额（**不是 401**） |

权限失败仍由 IAM 返回 401（未登录）/403（无权限），与业务错误码互不混用。
