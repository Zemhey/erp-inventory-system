因此在 `JdbcTemplate` 外包一层**唯一出口**是这里唯一能做到"新增仓储自动安全"的做法。

## 2. 关键设计决策（写清"为什么"，评审与后续泳道都靠这段）

### 2.1 为什么加列是"可空 + 无默认"而不是"带默认 + NOT NULL"

需求原文要求"先加列带 DEFAULT 到默认租户"。**这里刻意偏离**，理由是实测语义：

- PostgreSQL 11+ 的 `ADD COLUMN ... DEFAULT <const>` 是 O(1)（只写默认值到 catalog），
  所以"带默认值"本身不锁表；但**一旦带默认值，新写入的行如果不显式给租户，就会静默落到默认租户** ——
  这正好是"漏写租户"这个最危险缺陷的**掩盖机制**：漏了不报错，数据悄悄进错租户。
- 因此本实现分两层：
  1. **加列时**：`ADD COLUMN IF NOT EXISTS tenant_id BIGINT`（可空、无默认）→ 存量行是 NULL → 立刻可区分"历史行"与"新行漏写"；
  2. **回填**：`UPDATE ... SET tenant_id = 1 WHERE tenant_id IS NULL`（`audit_logs` 除外）→ 历史行归默认租户；
  3. **收尾**：`SET NOT NULL` + `SET DEFAULT 1` —— 此时"没写租户"仍然有兜底（应用层若漏传，DB 给默认值），
     但因为第 2 步已经把所有 NULL 消掉，`SET NOT NULL` 不会失败；且**任何时刻都没有"NOT NULL 打碎存量库"的窗口**。
- "三步式不碎库"的实质要求（加列 → 建索引 → 最后才 NOT NULL）被完整保留，
  只是第 1 步的默认值从"加列时"移到"收尾时"，换来"漏写租户可被发现"这个更强的性质。
  **这一点会在报告里点名说明偏离与理由**，供指挥侧裁决。

### 2.2 复合索引与复合唯一（顺序不可颠倒）

每张表：`CREATE INDEX IF NOT EXISTS idx_<表>_tenant ON <表> (tenant_id, <原主查询列>)`，
唯一约束则"先建新复合唯一索引 → 再 `DROP CONSTRAINT` 旧单列唯一"。
若反过来先删旧约束，中间窗口里"同编码两行"是合法的，并发写入可能塞进真重复；
若先建新约束再删旧的，旧约束仍在时新插入必须同时满足两者（更严），不会产生脏数据。

### 2.3 `audit_logs` 的特殊处理（与下发包原文的差异，明确记录）

下发包要求"只 `ADD COLUMN ... NULL`、不回填、不 NOT NULL、不动触发器与既有索引"。
但 V13 已经给 `audit_logs` 建了 `tenant_id BIGINT NOT NULL DEFAULT 1`（历史遗留的"预留列"）。
现状下：
- **不能**回填（UPDATE 会被 `audit_logs_append_only()` 拒绝）；
- **不能**改 `NOT NULL`/默认值（那是 `ALTER COLUMN`，PostgreSQL 允许，但语义上等于"改既有列定义"，
  且下发包要求"不动"）；
- 但**必须**能区分"这条审计属于哪个租户"，否则审计查询无法隔离。

因此本实现的做法：
1. `audit_logs.tenant_id` **原样不动**（保留 `NOT NULL DEFAULT 1`，既有行全部是 1 —— 它们本来就是单租户历史数据）；
2. 新写入时**显式传** `tenant_id`（`AuditLogRepository.insert` 增加该参数，取当前 `TenantContext`）；
3. **查询侧**统一加 `AND tenant_id = ?`（`TenantSql` 自动注入），于是租户 2 看到的审计 = 租户 2 写入的行，
   租户 1 看到的是历史行 + 自己新写的行；
4. 触发器与 V13 的三条既有索引一行不动（只用 `CREATE INDEX IF NOT EXISTS` 追加 `(tenant_id, occurred_at DESC)`）。
   —— 追加索引不违反"不动既有索引"，而"审计查询按租户+时间倒序"是本泳道新增的真实查法。

**遗留风险（写进报告 §风险）**：租户 2 的审计行 `tenant_id` 来自应用层显式传值，
数据库层没有"必须等于当前租户"的强约束（触发器不能改，且 append-only 表不宜加复杂 CHECK）。
防线是 `TenantSql` 的唯一出口 + 矩阵用例（跨租户读审计必须 404/空）。

### 2.4 SQL 注入层为什么能覆盖所有形态

`TenantAwareJdbcTemplate` 覆写的是 `JdbcTemplate` 的**四个入口**：
`query(...)`、`update(...)`、`execute(...)`、`batchUpdate(...)`，以及 `queryForObject/queryForList` 的委托版本。
这四类最终都收敛到 `query(String sql, ...)` / `update(String sql, ...)` 两个重载簇，
因此"改写 SQL 文本"这一个动作能覆盖 366 个调用点。改写规则（`TenantSql.rewrite`）：
- `INSERT INTO <表> (cols...)` → 追加 `tenant_id` 列与占位符（值取当前租户）；
- `SELECT ... FROM <表>` / `UPDATE <表>` / `DELETE FROM <表>` → 在 `WHERE`（无则新建）追加 `AND <表>.tenant_id = ?`；
- `JOIN <表>` → 在 `ON` 之后追加 `AND <表>.tenant_id = ?`（保证联表两侧同租户）；
- **白名单**：`tenants`（租户表本身）、`flyway_schema_history`、`information_schema` 等系统表不改写；
- **显式豁免**：`TenantScope.system()`（仅迁移/运维脚本用，且**不能**从 HTTP 路径到达）。

不在 SQL 文本上做正则"猜表名"是危险的，因此 `TenantSql` 只认**本项目已知的表清单**
（V16 里同一份清单以 Java 常量 `TenantTables.ALL` 存在，矩阵用例断言"清单里的表都已加列、
清单外的表都不需要"），正则只用于定位 `FROM/JOIN/UPDATE/INSERT INTO` 之后紧邻的第一个标识符。

## 4. 坑（本泳道实测/预判，按出现顺序）

1. **Gradle 必须走 ASCII 联接**：`D:\erp-build-v27\backend\server` + `powershell -NoProfile`。
   中文路径下测试全 `ClassNotFoundException`（ADR-0010）。
2. **乱序迁移**：任何 V2-3/V2-6 之前建的持久库缺 V11/V14/V15 → Flyway validate 拒起。
   一次性 `--spring.flyway.out-of-order=true`，**不改仓库默认配置**。
3. **`audit_logs` 回填 = UPDATE = 触发器报错**：任何 `UPDATE audit_logs ...` 都会
   `restrict_violation`。V16 里绝不能出现对它的 UPDATE。
4. **`ON CONFLICT (col)` 依赖的约束一旦改成复合**，不更新 `ON CONFLICT` 目标就会报
   `there is no unique or exclusion constraint matching the ON CONFLICT specification`。
   → 所有 `ON CONFLICT` 目标必须同步加 `tenant_id`（本泳道逐处改，并用用例覆盖）。
5. **`TRUNCATE ... CASCADE` 与租户表**：`tenants` 不能被 `truncateAll` 清掉（它是配置）；
   反过来 `TRUNCATE tenants CASCADE` 会清空所有业务表 —— 造数里必须显式排除。
6. **`ThreadLocal` 泄漏**：`TenantContext` 必须在 `finally` 清理；
   Spring 的 `TaskExecutor` 复用线程，漏清 = 下一个任务继承上一个租户。
   本实现同时提供 `TenantContext.runIn(tenantId, runnable)` + `wrap(...)` 两种正确写法。
7. **矩阵用例最容易的假绿**：404 断言若用"不存在的 id"，测的只是"接口会 404"。
   矩阵每一格都必须用**真实存在但属于另一租户**的 id（与 V2-6 的 `DataScopeMatrixIT` 同一条纪律）。
8. **`check` 是 UP-TO-DATE 时不给覆盖率的"新"数字**：报告里必须贴**强制重跑**那一次的输出
   （`--rerun-tasks` 或先 `clean`），否则计数器原值是上一轮的。

## 5. 回滚

| 层次 | 手段 |
|---|---|
| 代码 | `git revert` 单个提交（本泳道全部提交按步分离）；**不**用 `reset --hard`/`clean -fd` |
| 迁移 | V16 是**纯追加**（加列 + 加索引 + 加约束），不删任何既有列/表；回滚 = `git revert` 掉 V16 文件 + 手工 `DROP` 新增索引。**生产不回滚到 V15**（Flyway 不允许版本回退，且已写入的 `tenant_id` 值无害） |
| 运行期 | `erp.tenant.enforce=false`（本泳道提供开关）：`TenantAwareJdbcTemplate` 退化为原 `JdbcTemplate`，租户过滤全关，等价于 V15 行为。**默认 true**，且关闭时启动日志打 WARN |
