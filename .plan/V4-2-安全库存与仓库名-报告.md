## 一、实测到的 `skus` 真实列（`\d skus`，不假设）

```
 id                  | bigint                   | not null | nextval('skus_id_seq')
 product_id          | bigint                   | not null |
 color               | character varying(32)    | not null |
 size                | character varying(16)    | not null |
 barcode             | character varying(64)    |          |
 retail_price_amount | bigint                   | not null | 0          ← 单位：分
 enabled             | boolean                  | not null | true
 created_at          | timestamptz              | not null | now()
 updated_at          | timestamptz              | not null | now()
 min_level           | integer                  | not null | 0          ← 单位：件
 max_level           | integer                  | not null | 0          ← 单位：件
 season_code         | character varying(32)    |          |
 band_code           | character varying(32)    |          |
 launch_date         | date                     |          |
 create_request_id   | character varying(64)    |          |
 tenant_id           | bigint                   | not null |
```

CHECK 约束（决定了我采用的校验口径）：

```
"ck_sku_level_order"      CHECK (max_level = 0 OR max_level >= min_level)
"skus_max_level_check"    CHECK (max_level >= 0)
"skus_min_level_check"    CHECK (min_level >= 0)
"skus_retail_price_amount_check" CHECK (retail_price_amount >= 0)
```

**关键发现**：`ck_sku_level_order` 不是 `max >= min`，而是 **`max = 0` 或 `max >= min`**。
`max_level = 0` 是"未设上限"的哨兵值（`InventoryInsightRepository.replenishmentCandidates`
就靠 `AND s.max_level > 0` 过滤）。如果按字面"必须 `min <= max`"实现校验，用户就没法只设预警下限
而不被界面拦住。因此后端、前端和契约三处都统一成库里这条口径，避免界面放行、库里翻 CHECK 变 500。

其它既有列（`enabled`、`barcode`、`retail_price_amount`、维度三列、`create_request_id`）在更新时都不能被冲掉——
见下面的 PUT 语义处理。

`warehouses` 也实测过（第二个任务要用）：`name varchar(64) NOT NULL`、`enabled`、`priority`、`tenant_id`，
FK 列名是 `inventory_balances.warehouse_id`。

阈值落库走**独立的 `updateLevels()`**，没有塞进既有的 `update()`——理由和文件里既有的
`updateDimensions()` 一样：`update()` 只覆盖 `barcode / retail_price_amount / enabled` 三列，
把阈值并进去会让"只想改价"的调用把阈值清零。

### PUT 的缺省语义（原样保留，前端适配）

`enabled == null || enabled()`、`trimToNull(barcode)` 是 V1 起的全量覆盖语义：
省略 `enabled` 会把已停用的 SKU **静默重新启用**，省略 `barcode` 会清空条码。
本期不改这个语义（改了会影响其它调用方），但**前端两个入口都先把整行 SKU 读回来、带上原值再提交**，
运行期已验证：改 SKU 1 的阈值后 `barcode=6901000001 / enabled=true / price=12900` 原样保留。

新字段本身用的是"省略 = 保持原值"（`Integer`，与 `retailPriceAmount` 一致），
所以只调阈值不会被要求同时填回别的字段。

### 前端（第一件事）

- `api/client.ts`：`Sku` / `SkuCreate` / `SkuUpdate` 加 `minLevel` / `maxLevel`（注释写明单位是**件**不是分）
- `views/mdm/ProductView.vue`：SKU 编辑对话框加两个 `el-input-number` + 跨字段校验；SKU 列表加"安全库存"列
  （未设显示"未设"，让用户看见"这行永远进不了预警"）
- `views/inv/InventoryAlertView.vue`：SAFETY 每行加「调阈值」抽屉式对话框（沿用同目录既有 `el-dialog + el-form + rules` 写法），
  保存后立刻重载预警列表；阈值列同时显示补货上限
- 没做：`SkuMatrixDialog`（矩阵批量生成）的阈值入参——矩阵一次生成几十个 SKU，
  给整矩阵统一阈值不是本期要求，且该组件是共享组件，改它影响面大。**记为遗留**。

### 契约

`packages/api-contract/openapi.yaml`：只在 `SkuCreate` / `SkuUpdate` / `Sku` 三个 schema 节点内追加字段，
未重排、未动其它 tag。另在 `/dashboard/summary` 的 `description` 里补记 `charts` 各数据集的字段口径
（该端点响应体本来就是 `additionalProperties: true`，没新造 schema 节点）。

### 非法输入 → 400

```
PUT /skus/629 {"minLevel":-5}                 -> 400  code=MDM_SKU_LEVEL_INVALID
       message=安全库存下限不能为负：-5（单位是件，0 表示未设）
PUT /skus/629 {"maxLevel":-1}                 -> 400  code=MDM_SKU_LEVEL_INVALID
       message=补货上限不能为负：-1（单位是件，0 表示未设）
PUT /skus/629 {"minLevel":600,"maxLevel":500} -> 400  code=MDM_SKU_LEVEL_INVALID
       message=补货上限不能小于安全库存下限：minLevel=600、maxLevel=500（上限留空/0 表示只预警）
GET /skus/629 -> min=400 max=500    ← 被拒的 PUT 没有留下半更新
```

（前两条在 `a058a07` 之后的收尾提交里才拿到 `MDM_SKU_LEVEL_INVALID`：
原先 DTO 上有 `@Min(0)`，负数会先被 bean validation 拦成 `SYS_VALIDATION_ERROR`——
状态码同样是 400，但错误码不是那个"专门给阈值"的码，前端定位不到输入框。
去掉 `@Min` 让三种非法统一由应用层给码。）

### 新建 SKU 一条 POST 直接带阈值

```
POST /skus (X-Request-Id: v42-lane-create-*) {productId, color:"V42验证色", size:"XXL",
     retailPriceAmount:9900, minLevel:7, maxLevel:21} -> 201  id=635 min=7 max=21
GET  /skus/635 -> 200 {barcode:null, enabled:true, minLevel:7, maxLevel:21}
```

### 预警 / 补货建议：改前 vs 改后

```
改前：SAFETY=0   replenishment=0
改后：SAFETY=3   replenishment=1
  ALERT sku=1   wh=1   avail=16  threshold=50
  ALERT sku=629 wh=421 avail=348 threshold=400
  ALERT sku=630 wh=422 avail=314 threshold=500
  REPL  sku=1   wh=1   avail=16  min=50  max=120  suggested=104
```

`104 = 120 − 16`，与 `ReplenishmentFormula`（补到 max）一致。
629/630 **有意不出现**在补货建议里：实测这两行分别有在途 14 / 15 件
（`purchase_order_lines` 的 `qty - received_qty`，SQL 直查确认），
`replenishmentCandidates` 的 `pending_purchase_qty > 0` 分支由应用层跳过，避免重复建议——
这是既有设计，不是本期缺陷。tenant 1 里"有库存且无在途"的行只有 SKU 1 一条，
所以补货建议只有 1 条；克隆库里 627（仓 419）属于 tenant 2，`admin` 取它是 404（实测），属正常租户隔离。
