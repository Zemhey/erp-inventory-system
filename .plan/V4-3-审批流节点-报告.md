## 1. `approval_*` 真实表结构（`\d` 实测，非推断）

### `approval_flows`

| 列 | 类型 | 约束 |
|---|---|---|
| id | bigint | PK, `nextval` |
| code | varchar(32) | NOT NULL |
| name | varchar(64) | NOT NULL |
| biz_type | varchar(32) | NOT NULL |
| description | varchar(200) | NULL |
| enabled | boolean | NOT NULL, DEFAULT true |
| created_at / updated_at | timestamptz | NOT NULL, DEFAULT now() |
| tenant_id | bigint | NOT NULL |

- CHECK `biz_type IN ('PURCHASE_ORDER','SALES_ORDER','RETURN_ORDER')`
- UNIQUE `(tenant_id, code)` ← **不是** V14 源文件里写的 `UNIQUE (code)`，V16 改成了带租户的复合唯一。
  只看迁移文件会写错，这是必须 `\d` 的第一个理由。
- UNIQUE `(tenant_id, biz_type) WHERE enabled`（每种单据只允许一条启用流）
- TRIGGER `trg_approval_flows_tenant_fill BEFORE INSERT` → `erp_tenant_fill()`
- 被引用：`approval_instances.flow_id`、`approval_steps.flow_id`

### `approval_steps`（一张表两种角色）

| 列 | 类型 | 约束 |
|---|---|---|
| id | bigint | PK |
| flow_id | bigint | NOT NULL → `approval_flows` ON DELETE CASCADE |
| instance_id | bigint | NULL → `approval_instances` ON DELETE CASCADE |
| step_no | integer | NOT NULL, CHECK `> 0` |
| name | varchar(64) | NOT NULL |
| approver_permission | varchar(64) | NOT NULL |
| approve_mode | varchar(16) | NOT NULL |
| required_approvals | integer | NOT NULL DEFAULT 1, CHECK `> 0` |
| threshold_amount | bigint | NOT NULL DEFAULT 0, CHECK `>= 0` |
| status | varchar(16) | NOT NULL DEFAULT `'DEFINED'` |
| approved_by | **bigint[]** | NOT NULL DEFAULT `'{}'`（数组列，不是 JSON） |
| decided_at | timestamptz | NULL |
| decision_by | bigint | NULL |
| remark | varchar(200) | NULL |
| created_at / updated_at | timestamptz | NOT NULL |
| tenant_id | bigint | NOT NULL |

- CHECK `approve_mode IN ('SINGLE','ALL_SIGN','ANY_SIGN')`
- CHECK `status IN ('DEFINED','PENDING','APPROVED','REJECTED','SKIPPED')`
- **`ck_approval_step_form`**（最关键）：
  `instance_id IS NULL AND status='DEFINED' AND decided_at IS NULL AND decision_by IS NULL AND approved_by='{}'`
  **OR** `instance_id IS NOT NULL AND status <> 'DEFINED'`
  → 定义行只能是 DEFINED/空票数；实例行只能不是 DEFINED。
- UNIQUE `(flow_id, step_no) WHERE instance_id IS NULL` ← **幂等的天然键**
- UNIQUE `(instance_id, step_no) WHERE instance_id IS NOT NULL`
- INDEX `(flow_id) WHERE instance_id IS NULL`
- **没有** `(flow_id, name)` 之类的唯一键 → 幂等只能按 `(flow_id, step_no)`，按名字判重会插出第二份。

| tenant_id | bigint | NOT NULL |

- CHECK `biz_type IN (PURCHASE_ORDER, SALES_ORDER, RETURN_ORDER)`
- CHECK `status IN (DRAFT, PENDING, TRANSFERRED, APPROVED, REJECTED, WITHDRAWN, CANCELLED)`
- UNIQUE `(biz_type, biz_id) WHERE status IN (DRAFT, PENDING, TRANSFERRED)` → 一单只能有一个未结实例
- UNIQUE `(tenant_id, request_id) WHERE request_id IS NOT NULL` → 幂等键

### 现状实测

- `approval_flows` 6 行：`PO-STD/SO-STD/RO-STD` × `tenant_id 1,2`，全部 `enabled=false`。
  （V16 给演示租户整体复制了一份，所以修复必须覆盖 6 条而不是 3 条。）
- `approval_steps` **0 行**（定义与实例都是 0）→ 缺陷在克隆库上同样复现。
- `app_users` 只有 1 个账号：`admin`（tenant 1，ADMIN）。

### 为什么 V14 有 INSERT 却是 0 行（根因）

`V14__iam_deepening_and_approval.sql:244` 确实写了 `INSERT INTO approval_steps ... SELECT ...`，
`flyway_schema_history` 里 V14 是 `success=t`。**Flyway 记录为成功的迁移永远不会重跑**，
所以不管那 6 行是当初没插进去、还是被 `TRUNCATE ... CASCADE` 连带清掉
（`TestDataFactory.java:207` 的注释就记着这件事故），唯一能修的地方是追加 V23。
改 V14 会让 checksum 变化、直接撞 Flyway 校验。

## 2. 三条流的节点设计与权限码依据

```
PO-STD  1 采购主管审批            pur:approve   SINGLE 1 阈值 0
        2 财务审批（金额超阈值）   set:monthly   SINGLE 1 阈值 500000
SO-STD  1 销售主管审批            sal:approve   SINGLE 1 阈值 0
        2 财务审批（金额超阈值）   set:monthly   SINGLE 1 阈值 500000
RO-STD  1 客服主管审批            rma:approve   SINGLE 1 阈值 0
        2 财务审批（金额超阈值）   set:monthly   SINGLE 1 阈值 500000
```

### 权限码依据（实测 `app_role_permissions`，列名是 `permission`，**不是 `permission_code`**）

| 码 | 真实持有者 | admin 能不能签 |
|---|---|---|
| `pur:approve` | PURCHASER | ✅ `pur:*` |
| `sal:approve` | （无角色，V3 漏授） | ✅ `sal:*` |
| `rma:approve` | （无角色） | ✅ `rma:*` |
| `set:monthly` | FINANCE | ✅ `set:*` |

admin 实测登录返回的权限码里有 `aps:* pur:* sal:* rma:* set:*`，而
`ActorContext.Actor#hasPermission()`（`shared/security/ActorContext.java:63`）支持
`模块:*` 前缀通配 —— 所以每一级 admin 都签得动。**运行期已证**：两级节点的
`decisionBy` 都是 1（admin 的 user id）。

`sal:approve` / `rma:approve` 虽然是"没有任何角色被授予"的码，但它们**不是编的**：
正是 `SalesOrderController:116` / `ReturnOrderController:159` 上 `@RequirePermission`
用的那一个。选它们=与"能不能审这张单据"同一个门槛。

### 为什么最终取值和 V14/测试夹具逐字一致（重要，中途返工过一次）

我第一版把节点名改成「仓管确认数量→财务复核金额」、三级阈值全取 0，读代码看不出问题，
跑 `ApprovalIT` 才发现两处会**静默改测**：

1. `TC-APS-012` 断言"5 万分小额单只有 1 个 PENDING + 1 个 SKIPPED 快照"，
   靠的正是第二节点 `threshold_amount=500000`。全取 0 后两级都 PENDING，断言直接反了。
2. `TestDataFactory#ensureApprovalSeed`（`src/test/.../support/TestDataFactory.java:255`）
   的补种守卫是 `WHERE NOT EXISTS (flow_id, step_no)` —— 迁移一旦把节点种上，
   夹具就永远不会再插它自己那份，测试于是改测迁移里的流程。

所以 V23 与夹具/ V14 保持 `(step_no, 名称, 权限码, 阈值)` 逐字一致，把"业务语义更好听"
的改名留给单独一次带测试改动的提交。这一条已写进迁移文件注释。

### 幂等与多租户

- 幂等键 `(flow_id, step_no) WHERE instance_id IS NULL`；实测第二次执行 `INSERT 0 0`。
- 按 `approval_flows` **JOIN 展开**而不是写死 flow_id：写死只会补齐 tenant 1。
- `tenant_id` 显式取 `f.tenant_id`：触发器 `erp_tenant_fill()` 只在 NULL 时填，
  而 `erp_tenant_current()` 实测在裸 psql / Flyway 会话里返回 NULL（无 `erp.tenant_id` GUC），
  不显式写就撞 `tenant_id NOT NULL`。
- 收尾 `DO $$ ... $$` 断言：任何一条流若"定义节点为 0"或"没有 step_no=1 且阈值 0 的必经首节点"
  就 RAISE，让这类流程不能静默存在。**失败路径单独验过**：
  `format()` 里没有 `%d`（只有 `%s/%I/%L/%p`），这个错一切正常时根本不会求值
  （`string_agg` 只对不合格行调用 `format`），正向跑一遍发现不了 —— 只有把失败路径
  真造出来才暴露。造出来时的原文：
  ```
  ERROR:  V23 收尾自检失败：[RO-STD/tenant1：节点 0 个，必经首节点 0 个]。零节点流程一旦被启用，
          submit() 会空转回滚、单据卡死在 SUBMITTED —— 这条断言就是为了让这种流程无法静默存在。
  ```

## 3. 闸门：启用态零节点必须响亮失败（第 2 件事）

### 改了什么

`ApprovalApplicationService.submit()`：把节点检查提到 **`instances.insert()` 之前**。
原来是"插实例 → 遍历 `flow.steps()` 快照 → 循环 0 次 → `firstActive==null` → 抛错 → 整体回滚"，
对外表现为"提交审批但一个实例也没生成"。

新增 `ErrorCode.APS_FLOW_NO_STEPS(409)`，**只在枚举末尾追加**，并把原最后一条
`FIN_VOUCHER_DELETE_FORBIDDEN(409);` 的分号改成逗号。取 409 而不是 400：
请求体完全合法，400 会让人去查自己的入参，冲突的是服务端流程配置态。

顺带把**从来没有任何调用方**的 `ApprovalFlow#validate()` 接进提交路径
（序号断裂、首节点阈值>0 也在提交前拒掉，转成 `APS_FLOW_INVALID`）。

### 运行期原文（克隆库 8114）

人为把 `SO-STD` 的定义节点删到 0 行、保持 `enabled=true`，然后提交审批：

```
### POST /approvals
    --> body: {"bizType":"SALES_ORDER","bizId":384,"bizRefNo":"SO20261023-0006","amount":11610}
    <-- 409 {"code":"APS_FLOW_NO_STEPS",
             "message":"审批流 SO-STD（单据类型 SALES_ORDER）已启用但没有任何审批节点，无法提交审批。
              请在迁移里补齐该流程的 approval_steps 定义节点，或把这条流程关掉
              （POST /approvals/flows/2/enabled?enabled=false）。",
             "traceId":"61328b4f19b643af"}
    >>> 反向用例 http=409 code=APS_FLOW_NO_STEPS

### GET /approvals?bizType=SALES_ORDER&page=1&size=5
    <-- 200 {"data":{"items":[],"total":0}}
    >>> SALES_ORDER 实例数=0        ← 明确失败，且没有留下半截实例
```

**没改的部分（记录现状）**：零节点流下 `POST /sales-orders/384/approve` 仍然是那句误导文案
`APS_APPROVAL_REQUIRED「单据 SO20261023-0006 需要审批但尚未提交…请先提交审批」`。
现在用户会在 submit 那一步就先撞上 `APS_FLOW_NO_STEPS`，所以这句话不再是唯一出口；
把文案本身也修正是另一件事，不在本次范围。

## 4. ★ 给 seeder 用的操作序列（第 3 件事，全部实测）

### 4.1 四个问题的确切答案

**Q1 审批实例全部通过后，单据是自动推进到 APPROVED，还是要再打一次 `POST /purchase-orders/{id}/approve`？**
→ **要再打一次。审批绝不改单据表。**
实测（克隆库，PO20261023-0007，实例已 `status=APPROVED`、两级节点都签过之后，只 GET 不 POST）：
```
### GET /purchase-orders/526        ← 审批已 APPROVED，此时还没有调用单据 approve
    <-- 200 {"data":{"id":526,"orderNo":"PO20261023-0007","status":"SUBMITTED", ...}}
    >>> 关键证据：审批已 APPROVED，单据状态 = SUBMITTED（自动推进=false）
```
下一条用例立刻放行：
```
### POST /purchase-orders/526/approve
    <-- 200 {"data":{"status":"APPROVED", ...}}
    >>> 单据状态 = APPROVED
```
**旁证（不是我读代码猜的）**：`ApprovalIT` 里本来就有一条用例，名字就是这个结论 ——
`★ 审批不改单据表：审批走完后单据状态纹丝不动，仍由单据侧自己推进 PASSED`。
代码依据：`PurchaseOrderApplicationService.approve()` 第 221 行只
`approvalGate.requireApproved(...)`"问一句"，状态推进仍由它自己 `transition(...)`。

**Q2 再打一次时闸门会不会拦？**
→ **不拦。** `ApprovalGateService.stateOf()` 见最近实例 `APPROVED` → `ApprovalState.APPROVED`
→ `requireApproved()` 走 `case APPROVED -> 放行`。上面 `POST /purchase-orders/526/approve → 200 APPROVED` 即证。
反之，审批**还在途中**时会被拦，而且是另一个正确的码（不是"尚未提交"那句）：
```
### POST /purchase-orders/526/approve（实例 status=PENDING）
    <-- 409 {"code":"APS_APPROVAL_PENDING",
             "message":"单据 PO20261023-0007 的审批仍在进行中，请先完成审批再审核单据"}
```

**Q3 `POST /approvals` 与"提交单据时自动生成实例"是什么关系？**
→ **没有任何关系：提交单据不生成实例。`POST /approvals` 是唯一能创建审批实例的入口。**
`POST /purchase-orders/{id}/submit` 只做单据状态机 DRAFT→SUBMITTED（服务里第 206-214 行，
不调用 aps）。实测：
```
POST /purchase-orders/526/submit        → 200 status=SUBMITTED
GET  /approvals?page=1&size=5           → total 相比提交前没有增加（0 个该单实例）
POST /approvals {bizType,bizId,bizRefNo,amount} + X-Request-Id → 201 生成实例，status=PENDING
```
这也解释了缺陷的传导路径：`approval_instances` 只能由 `POST /approvals` 产生，
所以"没节点 → submit 空转回滚"直接导致"零实例"，闸门于是认为"从未提交审批"。

**Q4 审批人判定走哪个权限码？admin 通不通过？**
→ **两道门都要过**：
1. 接口级 `POST /approvals/{id}/approve` 的 `@RequirePermission("aps:approve")`（实测只授予 FINANCE）；
2. 节点级 `ApprovalApplicationService:175` `actor.hasPermission(current.approverPermission())`，
   取值即 `approval_steps.approver_permission`。
admin **两道都过**：`aps:*` 覆盖 ①，`pur:*/sal:*/set:*` 覆盖 ②。实测两级 `decisionBy=1`。
⚠️ 需要主控知道的现实：因为 ① 只给了 FINANCE，PURCHASER/SALESPERSON（有 `aps:submit`、
有节点权限码）**连接口都进不来**，当前库里又只有 admin 一个账号 → 演示链路只能用 admin 驱动。
要让采购员自己签第一级，得单独处理 `aps:approve` 的授予，不在本次范围。

### 4.2 操作序列（照抄可用；`X-Request-Id` 每个写操作都要带，缺失会被拦成 400）

```
# 0) 登录，拿 Bearer token
POST /api/v1/auth/login        body {"username":"admin","password":"Admin@12345"}
                                → data.token

# 1) 启用流程前先确认它有节点（这一步就是原缺陷的防线，seeder 里那段跳过逻辑现在会自动放行）
GET  /api/v1/approvals/flows
     → data.items[]: {id, code, bizType, enabled, steps:[{stepNo,name,approverPermission,thresholdAmount}]}
     对 steps.length > 0 且 !enabled 的那条：
POST /api/v1/approvals/flows/{flowId}/enabled?enabled=true

# 2) 建单据
POST /api/v1/purchase-orders   body {supplierId, warehouseId, bizDate, remark,
                                     lines:[{skuId, qty, unitPriceAmount}]}
     → data.id(=bizId), data.orderNo(=bizRefNo), data.totalAmount(=amount), data.status=DRAFT

# 3) 提交单据（只动单据状态机，不生成审批实例）
POST /api/v1/purchase-orders/{poId}/submit      → data.status=SUBMITTED

# 4) 提交审批 —— 这一步才生成实例，必须带 X-Request-Id（幂等键）
POST /api/v1/approvals         body {bizType:"PURCHASE_ORDER", bizId:{poId},
                                     bizRefNo:"{orderNo}", amount:{totalAmount}}
     → 201 data.id(=instanceId), data.status=PENDING,
            data.steps[]: {stepNo, status, approverPermission, thresholdAmount}

# 5) ★ 按实例实际生成的 PENDING 节点逐级签，不要硬写"签两次"
#    第二级 threshold_amount=500000（5000 元）：小额单的这一级是 SKIPPED，
#    对它调用 approve 会撞上"节点权限/状态非法"，必须跳过。
loop: GET /api/v1/approvals/{instanceId}
        while (data.status === "PENDING"):
            POST /api/v1/approvals/{instanceId}/approve   body {"remark":"..."}
        until data.status !== "PENDING"
     期望终态 data.status=APPROVED
     小额单（<50万分）实测：1 次调用；steps=[[1,"APPROVED"],[2,"SKIPPED"]]
     大额单（≥50万分）实测：2 次调用；steps=[[1,"APPROVED"],[2,"APPROVED"]]

# 6) ★ 必须再打一次单据侧 approve —— 审批不会替单据改状态
POST /api/v1/purchase-orders/{poId}/approve     → data.status=APPROVED

# 7) 入库（写库存流水并自动生成 PUR_IN 凭证）
POST /api/v1/purchase-orders/{poId}/receive     body {"lines":[{"lineId":{单据行的 id},"qty":{qty}}]}
     → data.status=COMPLETED, lines[].receivedQty=qty, qcStatus=PASSED
```

出货单同构：`bizType:"SALES_ORDER"`、`/sales-orders/{id}/{submit|approve|ship}`。
退货单同构：`bizType:"RETURN_ORDER"`、`/return-orders/...`。
幂等提示：同一个 `X-Request-Id` 重放 `POST /approvals` 返回首次实例而不报错；
换键重复提交同一张单会被 `APS_INSTANCE_ALREADY_OPEN` 拦掉。

**如果 seeder 想继续保留"不启用零节点流"的防御**，现在的正确读法是
`GET /approvals/flows` 的 `steps.length`（V23 之后三条流都是 2），
`seed-demo.mjs:160-170` 那段判断不用改就能自然放行 —— 我没有动那个文件。

## 7. 没做完 / 留给主控的

1. **`APS_APPROVAL_REQUIRED` 的文案本身没改**。它现在只在"用户从未调用 `POST /approvals`"时出现，
   这个场景下"请先提交审批"是对的；零节点场景已被 §3 的新码提前拦住。
2. **`POST /approvals/flows/{id}/enabled?enabled=true` 仍然允许启用一条零节点流**。
   `setFlowEnabled()` 没接 `validate()`。按最小改动原则只做了 submit 侧（主控要求的位置）。
   若要更早失败，在 `setFlowEnabled(id, true)` 里加一次 `flow.validate()` 即可，
   但那是第二条错误路径、需要配套用例，我没顺手加。
3. **审批人只可能是 admin 或 FINANCE**（接口级 `aps:approve` 只给了 FINANCE，V14:213 有意为之），
   而库里只有 admin 一个账号。PURCHASER 有节点权限码却进不了接口 —— 这是角色模型的问题，
   不是节点数据的问题，我没有擅自改授权。
4. **节点名称/权限码的"更好听"版本**（仓管确认数量 → 财务复核金额）留在 V23 注释里没落地，
   因为那会同时改 `ApprovalIT` 的断言前提。要做就是"迁移 + 夹具 + 用例"一起改。
5. **前端审批工作台/待办中心没有验证过渲染**。V23 之后 `GET /approvals/flows` 的 `steps`
   有值、`GET /approvals` 会有 PENDING 实例，数据侧通了；界面我没动也没截图。
6. **`erp` 主库没应用 V23**（按硬约束只读）。V23 会在主库下次正常启动时由 Flyway 自动应用；
   启用主库上的流程仍是运维动作。
