1. **H5 构建告警**：`startScan()` 里用 `// #ifdef H5 ... return` 提前返回，

### 3.4 E2E 期间真实拦到的四个问题（都已修，非绕过）

1. `JAVA_TOOL_OPTIONS` 全局导出 → `bcrypt-hash.ps1` 里 javac 往 stderr 打一行提示被判失败，
   `globalSetup` 在 `ensureAdmin` 处直接红。**修法**：只注入到后端 webServer（`playwright.config.ts`）。
2. `seed.setup.ts` 的 storageState `origin` 写死 `127.0.0.1:3005` → 实跑 3020 时
   app project 全部静默「没登录」。**修法**：跟随 `E2E_BASE_URL` 取 origin。
3. 给出货单详情加「生成发货计划」后，既有用例的裸 `.action-btn` 撞 strict mode violation
   （该页现在**确实**有两个动作）。**修法**：给原按钮补 `data-action="ship"` 并按它定位，
   不削弱原断言语义。
4. 取 hash 路由里的 `?id=` 用 `new URL(page.url()).searchParams` → 永远拿到 null
   （uni-app H5 是 hash 路由，query 在 `#` 之后）。**修法**：直接匹配 `[?&]id=(\d+)`。

★ 另有一处**断言口径错误**是我自己写的：TC-MOB-008 最初把客户汇总卡断成「= 本轮那一张应收的金额」，
实测拿到 `¥1990.00` 而不是 `¥398.00` —— 因为 `/receivables/summary` 是**整个客户**的聚合，
而同客户在本轮已被三张单出货（2+4+4=10 件 × 19900 分）。改成断言两条恒等式
（汇总 = 明细之和；出货 − 退货 − 回款 = 余额），既真实又不依赖别的用例跑没跑。

## 7. 清理外键顺序（本批补的部分）

V2-3 的销售闭环 11 张表 main 已排好；本批只补审批与账号，顺序如下：

```
approval_steps (instance_id ∈ e2e_approvals)      ← 显式删，让计数能如实报出节点行数
  → approval_instances (id ∈ e2e_approvals)       ← initiator_id 是指向 app_users 的**非级联**外键
  → …（销售闭环 / 采购闭环 / 库存）…
  → app_users (id ∈ e2e_users, username LIKE 'E2B-<runId>%')
      ↑ app_user_roles / data_scopes 是 ON DELETE CASCADE，随账号走
```

`e2e_approvals` 的识别口径是三选一：`initiator_id ∈ 本轮临时账号` ∪
`biz_ref_no ∈ 本轮单据号` ∪ `request_id LIKE 前缀%`。三条同时给是因为
`X-Request-Id` 由 `api/client.ts` / `e2e/helpers/api.ts` 自动生成（`e2e-<uuid>`），
**不带 E2B 前缀** —— 只靠 request_id 会漏，只靠 biz_ref_no 又覆盖不到「审批挂的是别的单据」的情况。

★ `audit_logs` 一行没删（DB 有 append-only 触发器，删它会直接把 teardown 弄红）。
本轮登录、审批决策都会往 `audit_logs` 追加行 —— 它**不在** BASELINE_TABLES 里，
这是既有纪律（日志表自然增长），不是本批的豁免。

## 8. 偏离与取舍（三条显式偏离）

1. **报价单不做建单页**。任务书范围原文是「列表 + 详情 + 提交/审核/驳回/作废 + 转出货单」，
   没有建单；且既有 `purApi` / `salApi` 的口径就是「建单留 Web」。
   → 移动端只能流转别人建好的单，报告如实标注，不假装完成。
2. **收款登记只核销当前这一张应收**。后端 `allocations` 支持跨多张核销（合计必须精确等于收款额），
   移动端一次一张已能覆盖「部分核销可用、超额逐字报错」这两条硬验收；
   多张勾选核销是桌面场景的表单，留 Web。
3. **超额核销不在前端拦**。页面上线内提示，但请求照发（见 §3.4 第 4 条与 TC-MOB-009）。
   前端一旦自己截断，就再造了一套口径，也就永远看不到后端那句带 id/余额/本次核销额的消息。

## 10. 给指挥会话的两处后端观察（本泳道无权改，仅登记）

**A. 转办的目标资格与节点资格用了两套权限码。**
`ApprovalController.java:161-164` 判的是目标有没有 **`aps:approve`**，
而 `ApprovalApplicationService.java:175`（以及 `acceptTransfer` :355）判的是当前节点的
**`approverPermission`**（SO-STD 第一节点是 `sal:approve`）。
后果：可以把审批转办给一个「能接、但接了也审不了」的账号 —— 不是越权
（接办和同意都还有节点这道门），但转办会**看起来成功、后续卡死**。
实测证据：`grep -rn "'sal:approve'" db/migration/*.sql` 只命中一处，
即 `V14__iam_deepening_and_approval.sql:252` 里 SO-STD 第一节点的 `approver_permission` ——
**没有任何角色被授予过 `sal:approve`**。所以当前配置下，除 ADMIN（`PermissionAspect`
的 ROLE_ADMIN 短路）之外没有账号能真正审 SO-STD 的第一节点，
「金额阈值触发上级」这条链路在非管理员身上是走不通的。建议：把转办的目标检查改成
节点权限（与接办一致），并给主管角色补上节点权限码。

**B. 转办被拒的消息与实际判据不一致。**
`ApprovalApplicationService.java:317-320` 的消息模板里填的是 `current.approverPermission()`
（`sal:approve`），但真正测的是 `aps:approve`。排障时会把人往错的方向带。
（TC-MOB-014 因此只断言「转办目标账号」「不能接收该审批」这两段稳定文本，不锁权限码那半句。）
