## 2. 修改密码流程

### 真实契约（`iam/api/AuthController.java`）

```
POST /api/v1/auth/change-password
  body: ChangePasswordRequest(@NotBlank @Size(max=128) oldPassword, @NotBlank @Size(max=128) newPassword)
  200 → data { "changed": true, "mustChangePassword": false }
  旧密码不对 → 401 IAM_BAD_CREDENTIALS「旧密码不正确」
  与旧密码相同 / 不合策略 → 400 IAM_PASSWORD_WEAK（message 带具体缺哪条）
```
登录响应与 `GET /auth/me` 都下发 `mustChangePassword` / `passwordExpiresAt` / `passwordRules`。
`passwordRules` 来自 `PasswordPolicy.describe()`，逐字是：

```
"密码长度至少 %d 位" / "至少包含 %d 类字符（大写/小写/数字/符号）" / "密码每 %d 天过期" | "密码不按时间过期"
```

### ★ 关键发现：`iam/security/PasswordExpiryFilter.java`

该状态下后端**只放行 3 个路径**：`/auth/change-password`、`/auth/me`、`/auth/login`；其它业务接口一律
`403 IAM_PASSWORD_EXPIRED`（httpStatus 取 `ErrorCode.IAM_PASSWORD_EXPIRED` = 403，body 里 `code` 逐字是这个枚举名）。
这就是"必须给强制引导、不给跳过"的技术依据 —— 不锁住的话用户点哪儿都是 403，看起来像系统坏了。
`views/iam/UserRoleView.vue:117` 那句"首次登录将被强制修改密码"到此才真正成立（管理员 `POST /iam/users/{id}/reset-password` 确实会写 `must_change_password`，见 `AppUserRepository.java:223`）。

### 改动

- `api/client.ts`：新增 `authApi.changePassword()`；403 `IAM_PASSWORD_EXPIRED` 不再刷 toast（同一条错误弹十条没意义），改为 `onAuthEvent('password-expired', cb)` 广播 —— 用模块级 `Set` 而不是 pinia store，因为 `stores/session` 已引用 `client.ts`，反向引用会循环依赖。
- `stores/session.ts`：落 `mustChangePassword` / `passwordExpiresAt` / `passwordRules` 三字段，并持久化到 `erp.password`。存本地的唯一目的是让过期态刷新页面**首屏**就是强制改密，不等 `/auth/me` 往返那几百毫秒；真实判定仍在服务端。
- 新增 `components/ChangePasswordDialog.vue`：规则**原文显示**后端 `passwordRules`；从文案里正则解析"长度至少 N"「N 类字符」做前置校验，**解析不出来就不拦**，交后端 400 的具体理由（避免管理员调策略后界面仍按老阈值提示）。前端没有自带一套阈值。
- `layouts/MainLayout.vue`：顶栏常驻「修改密码」入口（强制态变黄色「改密」并带 tooltip）；`watch(pwdForced, …, { immediate: true })` 把强制态顶开对话框。对话框 `:show-close="false"`、禁遮罩/ESC，唯一逃生口是"退出登录"；用单向 `:model-value` + 接管 `update:model-value` 而非 `v-model`，否则 X 一按就真关、强制态等于没锁。

## 3. 审批：详情 / 提交 / 转办 / 接受转办

### 真实契约（`aps/api/ApprovalController.java`，逐字核对后使用）

```
POST /api/v1/approvals            X-Request-Id 必填, aps:submit
  SubmitRequest(@NotBlank bizType, @NotNull Long bizId, @NotBlank @Size(max=64) bizRefNo, @NotNull Long amount)
  → 201 CREATED, data = 实例 map
POST /api/v1/approvals/{id}/transfer   aps:approve
  TransferRequest(@NotNull Long targetUserId, @Size(max=200) String remark)
POST /api/v1/approvals/{id}/accept-transfer   aps:approve   ← 无请求体
GET  /api/v1/approvals/{id}       aps:read
```
响应字段（`toMap(ApprovalInstance)`）：`id flowId bizType bizId bizRefNo amount currentStep status initiatorId steps[]`；
step（`toMap(ApprovalStep)`）：`stepNo name approverPermission approveMode requiredApprovals thresholdAmount status approvedBy decidedAt decisionBy remark`。
与 `api/client.ts` 里的 `ApprovalInstanceView` / `ApprovalStepView` 逐字段一致，所以封装没改，只补了调用。

后端两道转办校验（决定界面文案与选人方式）：
- 发起人必须有**当前节点**的 `approverPermission`，否则 `APS_NOT_APPROVER`；
- 目标账号必须有 `aps:approve`（控制器用 `ActorContext.actorOf(...).hasPermission` 判），否则同样拒绝 —— 防"转给没审批权的人绕开 RBAC"。
- `acceptTransfer` 仅当实例 `status == TRANSFERRED`，否则 `APS_STATUS_ILLEGAL`。

`amount` 是**分**（列表原本就按 `amount / 100` 显示元），`bizType` 只允许 `PURCHASE_ORDER | SALES_ORDER | RETURN_ORDER`。

### 改动（`views/iam/ApprovalView.vue`）

- **详情抽屉**：`approvalApi.detail(id)` 重新取而非复用列表行 —— 审批是多人动作，看着旧快照点按钮最容易出事。抽屉含节点决定人/时间/已同意人数/意见/阈值，并有「同意 / 驳回 / 转办 / 接办 / 刷新」；`TRANSFERRED` 时不给同意驳回（只给接办），与后端状态机一致。
- **转办对话框**：有 `iam:read` 时用 `iamApi.users(keyword)` 远程选人（后端 `GET /iam/users` 要求 `iam:read`）；**没有该权限则退回手填用户 id** —— 审批人不必然有 iam 读权限，不能因此把功能做没。
- **接办按钮**：列表行与抽屉都可发起，仅 `TRANSFERRED` 显示。
- **发起审批**：★ 这条不是可选装饰 —— 单据侧只在 `approve()` 前调 `ApprovalGate.requireApproved(...)` 做**校验**，不会自建审批实例（`pur/…PurchaseOrderApplicationService.java:221`、`sal/…SalesOrderApplicationService.java:244`、`rma/…:223`）。缺这个入口，需要审批的单据走不到"有实例可批"。表单按**元**录入、提交时 `Math.round(元 × 100)` 换算为分并写注释（漏乘 100 会让小额单据跳过审批阈值，是越权路径）。
- 单据类型列改用中文标签。

## 4. 凭证 DELETE（后端补 + 前端入口）

### 新增端点

```
DELETE /api/v1/fin/vouchers/{id}
  @RequestHeader("X-Request-Id") @NotBlank        ← 与其它 fin 写接口同口径
  @RequirePermission("fin:voucher:write")         ← 沿用既有权限码，未新增
  200 → data { "deleted": true, "id": <long> }
  404 FIN_VOUCHER_NOT_FOUND
  409 FIN_VOUCHER_DELETE_FORBIDDEN（新增）        ← 非 DRAFT，或并发下状态已变
  409 FIN_PERIOD_CLOSED（账期已月结锁定，既有码）
```

### 新增错误码（`shared/error/ErrorCode.java`，**只往末尾追加**）

```java
FIN_VOUCHER_DELETE_FORBIDDEN(409);
```
前一条 `PRM_PROMOTION_CODE_DUPLICATED(409)` 的分号改为逗号，其它条目一字未动。
为什么不复用 `FIN_VOUCHER_STATUS_ILLEGAL`：后者同时覆盖"非草稿不可改 / 不可重复审核"等多种非法转移，前端按它做通用提示；而"删除被拒"要给的是**另一套**指引（去作废/红冲，不是"改成草稿再删"）。

### 语义与隔离（三层各司其职）

- `FinVoucherApplicationService.delete(id)`：`require(id)` → 非 DRAFT 直接 409，消息里区分手工单（"如需冲销请走作废/红冲"）与自动生成单（"请改为冲销来源单据"，因为 `sourceType != MANUAL` 落库即 POSTED，天然删不掉）→ `periodGuard.requireOpen(voucherDate)`（与 create/update/post 同口径）→ 条件删除失败再给并发错误。
- `FinVoucherRepository.deleteDraft(id)`：先 `DELETE FROM fin_voucher_line WHERE voucher_id = ?`，再 `DELETE FROM fin_voucher WHERE id = ? AND status = 'DRAFT'`。
  - 状态闸门写进 SQL 而不是只在外层判断：「读到 DRAFT → 别人刚好审核 → 我删除」这个竞态只有让条件更新自己原子失败才防得住，0 行时回查给准确错误。
  - 显式删分录不依赖 `ON DELETE CASCADE`（V20 里确实有），理由是 ① 不赌某句迁移长期存在 ② 与既有 `replaceLines` 的"先删后插"口径一致。
  - 两条 SQL 都走 `TenantJdbc` → `TenantAwareJdbcTemplate` 改写；`fin_voucher` 与 `fin_voucher_line` 都在 `shared/tenant/TenantTables.java:82` 注册，`TenantSql` 对 `delete` 分支会追加 `tenant_id` 谓词 —— 跨租户 id 的结果是"0 行/未删除"，不会删别人的凭证。
- 契约：`packages/api-contract/openapi.yaml` 在既有 `/fin/vouchers/{id}` 路径项下**追加** `delete:`（`operationId: deleteFinVoucher`），未重排、未改他人节点。
- 前端：`finApi.deleteVoucher(id)` + 凭证页删除按钮**只在 `row.status === 'DRAFT'` 渲染**，带确认框；按钮隐藏只是礼貌，真正的拒绝在 409。

**没有新建迁移**：本次没引入任何新权限码（`fin:voucher:write` 是既有码，自动生成的 ADMIN 通配已覆盖），按约束"不需要新表新权限就别建迁移"。

## 5. 库存预留 / 收货 / 发货端点 —— **结论：不接，放弃本条**

这不是"没做完"，是调研后的正确结果。证据如下。

### 这四个端点的真实形状（`inv/api/InventoryController.java`）

| 端点 | 行 | 请求体 | 内部实际调用 |
|---|---|---|---|
| `POST /inventory/reserve` | :88 | `{skuId, warehouseId, batchNo, qty}` | `inventory.reserve(new ReserveCommand(..., requestId))` |
| `POST /inventory/reservations/{id}/release` | :107 | 无体（仅 X-Request-Id） | `inventory.release(id)` |
| `POST /inventory/receipts` | :124 | `{skuId, warehouseId, batchNo, productionDate, expiryDate, qty, bizRefNo, unitCostAmount}` | `inventory.receiveIn(..., "PURCHASE_IN", req.bizRefNo(), null, ...)` |
| `POST /inventory/shipments` | :150 | `{skuId, warehouseId, qty, bizRefNo}` | `inventory.shipOut(..., "SALES_OUT", req.bizRefNo(), null, requestId)` |

控制器自己的注释就写着它们的定位：「入库：**M0 阶段先作为内部能力暴露，M1 由进货单 /receive 调用**」「出库（FEFO）：**M1 由出货单 /ship 调用**」。

### 证据 A：同一批应用服务方法已经被业务链路在 Java 层调用

```
pur/application/PurchaseOrderApplicationService.java:41   ← 类注释：PurchaseOrderApplicationService ──调用──▶ InventoryApplicationService.receiveIn(...)
pur/application/PurchaseOrderApplicationService.java:351  ← 方法注释直接指向 receiveIn
pur/api/PurchaseOrderController.java:144                     purchaseOrders.receive(id, ...)
sal/application/ShipmentApplicationService.java:38        ← 「确认发货才真正扣库存：按仓调 InventoryApplicationService.shipOut」
rma/application/ReturnOrderApplicationService.java:43     ← 「──▶ InventoryApplicationService.receiveIn(RETURN_IN)（**唯一库存入口**）」
pur/application/PurchaseReturnService.java:45 / sal/application/ProductBundleService.java:29  同样注入 InventoryApplicationService
```
即：**入库/出库在 Java 层已经有唯一入口**。前端若再直接打 `/inventory/receipts`、`/inventory/shipments`，等于绕过单据状态机开第二个库存入口。

### 证据 B：这两个方法**没有任何幂等/去重保护**

```java
// InventoryApplicationService.java:373-380
public void receiveIn(...) {
    balances.increaseOnHand(...);
    ledger.insert(..., requestId, clock.now());   // requestId 只是落进流水，没有"先查再插"
}
```
`shipOut`（:394 起）同理，只有 FEFO 可用量校验，没有按 `requestId` 或 `bizRefNo` 去重。
对比 `reserve`（:128-132）**有**幂等：`reservations.findByRequestId(cmd.requestId())` 命中就直接返回首次结果、`duplicate=true`。

而前端的幂等键是**每个请求新生成**的（`api/client.ts:122-124`，`crypto.randomUUID()`），两次用户点击必然两个不同 `X-Request-Id`。结论：**HTTP 层的幂等机制救不了重复调用**，"进货页点一次收货 + 库存页再点一次收货" = 两次 `increaseOnHand` + 两条 `PURCHASE_IN` 流水，实存与账实一致校验（`/inventory/consistency-check`，不变量 INV-2）当场被打破。这是数据正确性事故，比"没有入口"严重。

### 证据 C：`/reserve` 与 `/release` 单独接也有问题

- `reserve` 生成的预占 `biz_ref_no` 只是 **requestId 占位**（`InventoryApplicationService.java:175-178` 注释：「biz_ref_no 在 M0 用 requestId 占位，M1 接单据号」）——预占不挂任何单据，变成无人负责的库存锁定。
- `InventoryController` 里**没有** `GET /inventory/reservations`：前端拿不到"现有哪些预占、各归属谁、什么时候过期"，只能让用户盲填一个 `id` 去 release。
- 真实预占是销售单在应用层按 FEFO 分段建的：`sal/application/SalesOrderApplicationService.java:214 inventory.reserveFefo(...)`，并在 :297 `inventory.release(reservationId)` 自行释放。暴露一个"按任意 id 释放"的裸接口，等于允许把别人销售单锁定的库存解开 → 超卖。

### 处置

第 5 项**整条放弃**，不改前端、不改后端。若将来要给出入库/预留做界面，正解是：
1. 后端先补 `GET /inventory/reservations`（带归属单据、过期时间）与按单据的 `receiveIn/shipOut` 幂等（`uk (biz_type, biz_ref_no)` 或 requestId 去重）；
2. 前端入口挂在**单据页**（有单据上下文、有状态机把关），而不是库存页放四个裸动作按钮。

## 给主控的运行期验证清单（按风险排序）

> 我只做了静态验证。以下每一条都可能"编译绿但跑不对"。

**A. 强制改密（最高风险，我改了 axios 拦截器）**
1. 造一个强制态账号：管理员在「用户与角色」对某账号点重置密码（`AppUserRepository:223` 会写 `must_change_password=true`）。
2. 该账号登录 → 首屏**立即**是不可关闭的改密对话框；尝试 ESC / 点遮罩 / 点右上角都应无效；只有"退出登录"能走。
3. 故意输错旧密码 → 应弹后端那句「旧密码不正确」，**且不能把用户踢回登录页**。
   我按这个改了拦截器（见下"顺带修的坑"），但仍请实测确认会话没被清。
   - 回归点：登录页输错用户名/密码（同为 401 `IAM_BAD_CREDENTIALS`）必须仍然在原页显示错误、不跳转。
   - 回归点：token 过期（401 `IAM_UNAUTHENTICATED`）必须仍然清 token 跳登录。
3.1 改密成功后 → 对话框自动关闭、菜单可点、`erp.password` 里 `mustChangePassword` 转 false。

#### 顺带修的坑（`api/client.ts` 401 分支）

原拦截器**只看 status**：401 一律 `clearToken()` + 跳 `/login`。
而 `AuthController.changePassword` 对"旧密码不对"抛的是 `IAM_BAD_CREDENTIALS(401)` ——
不特判的话，接上改密入口后会得到「打错一次旧密码就被登出」这种荒谬行为。
现按业务码分流：`IAM_BAD_CREDENTIALS` → 只提示、保留会话；其余 401（`IAM_UNAUTHENTICATED`）→ 仍清 token 跳登录。
（这是既有注释「状态码表达类别，具体原因在业务码里」在本泳道的又一次落地。）
