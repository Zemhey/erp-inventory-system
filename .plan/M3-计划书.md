## 2. M3 范围（做什么 / 不做什么）

### 2.1 做什么 —— 7 个业务页面 + 工程保障

按依赖顺序分四批。**每批做完 `npm run build` 必须通过，且手工点通主流程**。

#### 批次 A：主数据四件套（先做，因为其他页面都依赖它们的数据）

| 页面 | 关键点 |
|---|---|
| **商品与 SKU** | 列表（搜索/分页）+ 新建编辑 + **颜色×尺码矩阵生成**（服装行业核心能力） |
| **供应商** | 列表 + 新建编辑 + 停用 |
| **客户/会员** | 列表 + 新建编辑 + **折扣等级**（整数万分比，9000 = 9 折） |
| **仓库** | 列表（不分页，返回数组）+ 新建编辑 + 停用 + `onlyEnabled` 过滤 |

**这一批的价值**：做完之后，进货单/出货单才有供应商、客户、仓库、SKU 可选。
**顺序不能颠倒** —— 先做进货单会卡在"没有供应商可选"。

#### 批次 B：库存查询

| 页面 | 关键点 |
|---|---|
| **库存查询** | 按 SKU/仓库/批次筛选；**区分展示实存/预占/可用**；流水追溯 |

**难点**：三个数字的语义必须让用户一眼分清。实存是"仓库里有多少"，
可用是"还能卖多少"。把它们混为一谈是库存系统最常见的误用。

#### 批次 C：进货单（第一个有状态机的页面）

| 页面 | 关键点 |
|---|---|
| **进货单** | 列表（按状态筛选）+ 建单 + 提交/审核 + **分批入库** |

**难点**：
1. **状态机驱动的按钮显隐**：DRAFT 只能提交/作废；SUBMITTED 才能审核；
   APPROVED/PAIRIAL 才能入库；COMPLETED/VOIDED 什么都不能做。
   写死按钮状态是最常见的 bug —— 用户点了会收到 409。
2. **分批入库**：每行显示"单据数量 / 已入库 / 未入库"，用户填本次入库量。
   超量必须在前端先提示，但**最终由后端判断**。

#### 批次 D：出货单（最难，因为建单即预占）

| 页面 | 关键点 |
|---|---|
| **出货单** | 列表 + 建单（选客户/折扣）+ 审核 + 出货 + 作废 |

**难点**：
1. **建单即预占**：用户点"保存"的瞬间库存就被锁了。因此
   **失败提示必须清楚**（哪一行、差多少），否则用户不知道改哪里。
2. **折扣实时计算**：明细里改数量/单价/折扣，行金额与小计要立刻更新，
   且必须按整数万分比算（见 §3.4）。
3. **作废要确认**：作废会释放预占，但已出货的作废会被拒绝（需红冲）。

## 3. 技术方案（关键设计决策）

### 3.1 页面结构约定（统一，不要每页自己发明）

每个业务页面统一三段式：

```
┌─────────────────────────────────────────┐
│ page-header：标题 + 主操作按钮（新建）    │
├─────────────────────────────────────────┤
│ 筛选区：搜索框 + 下拉筛选 + 查询/重置     │
├─────────────────────────────────────────┤
│ 数据表格（el-table）+ 分页（el-pagination）│
└─────────────────────────────────────────┘
```

弹窗表单统一用 `el-dialog` + `el-form`，`label-width="100px"`，
必填项标红星，提交前 `formRef.validate()`。

**为什么要统一**：ERP 有十几个列表页。如果每页布局不同，
用户每换一页都要重新找"新建按钮在哪"。

### 3.2 状态机与按钮显隐（进货单/出货单专用）

后端状态（`DocumentStatus` 七态）与允许动作的映射，**前端照抄这张表**：

| 状态 | 进货单可做 | 出货单可做 |
|---|---|---|
| `DRAFT` | 提交、作废 | 提交、作废 |
| `SUBMITTED` | 审核、驳回、作废 | 审核、驳回、作废 |
| `APPROVED` | **入库**、作废 | **出货**、作废 |
| `PARTIAL` | **继续入库** | **继续出货** |
| `COMPLETED` | （终态，无动作） | （终态，无动作） |
| `VOIDED` | （终态，无动作） | （终态，无动作） |
| `REJECTED` | 作废 | 作废 |

> **上表已按后端实际能力校正过两处（S1 执行时发现，原文是错的）**：
>
> 1. `REJECTED` 原本写"退回草稿、作废"，但**后端没有那个接口** ——
>    `DocumentStatus` 允许 REJECTED → DRAFT 的转移，却没有暴露成 HTTP 动作
>    （两个 Controller 都没有 `/{id}/reopen`）。照原文做出来的按钮点了必然 405。
>    现在只给"作废"；若要支持退回草稿，得先补后端接口（见 §5.2 缺口 G2）。
> 2. `PARTIAL` 原本在"可做"列没写作废，这是对的；但反过来说，
>    即便是 APPROVED/PARTIAL 的"作废"，后端对**已有入库/出货**的单据也会拒绝
>    （要求先红冲，FR-PUR-03 / FR-SAL-04 属 M2）。所以作废按钮的确认框里
>    必须写清"已有入库/出货的会被拒绝"，否则用户会以为按钮坏了。

**这两处校正不是笔误修正，而是"计划书与代码不一致"的实例。**
为避免再次发生，S1 一并交付了可执行校验：
`npm run check:status-parity` 现场解析 `DocumentStatus.java` 与两个 Controller，
逐项比对前端这张镜像表（当前 64 项检查），并反向校验豁免清单是否过期。


**实现建议**：写一个 `src/utils/documentStatus.ts`，把这套映射集中定义，
两个单据页共用。**不要在模板里写 `v-if="status === 'DRAFT'"` 散落各处** ——
七种状态 × 两个单据 = 十几处判断，必然有人漏改。

### 3.3 错误处理约定

- 后端返回的业务错误消息**必须原样展示**（它含定位信息：哪个 SKU、差多少）
- `api/client.ts` 已经在拦截器里统一弹 `ElMessage`，**页面不要再重复弹**
- 只有需要用户"做决定"的场景（如确认作废）才用 `ElMessageBox.confirm`
- 提交按钮必须加 `:loading`，防止用户连点造成重复提交
  （虽然后端有幂等键兜底，但重复请求仍会浪费一次往返）

### 3.4 金额与折扣（最容易算错的地方）

**铁律：前后端之间一律传「整数分」，只在显示时转元。**

```typescript
import { fenToYuan, yuanToFen, discountLabel } from '@/api/client'

fenToYuan(12900)        // "129.00"
yuanToFen("129.00")     // 12900
discountLabel(9000)     // "9 折"
discountLabel(10000)    // "不打折"
```

**行金额计算**（出货单明细，前端实时预览用）：

```typescript
// 折扣率是整数万分比：9000 表示 9 折
// 必须四舍五入到分，且用 Math.round 而不是浮点比较
function lineAmount(qty: number, unitPriceFen: number, discountRate: number): number {
  return Math.round(qty * unitPriceFen * discountRate / 10000)
}
```

> ⚠️ 这个前端函数**只用于界面实时预览**。提交后以后端返回的 `amount` 为准 ——
> 后端用 BigDecimal HALF_UP，与 JS 的 `Math.round` 在 .5 边界上行为一致，
> 但仍以服务端为唯一真相（ADR-0005）。

### 3.5 SKU 矩阵生成（服装行业的特色交互）

这是本系统区别于通用进销存的地方，交互必须好用：

```
商品：圆领T恤 (P-TS-001)
┌──────────────────────────────────────┐
│ 颜色： [白色 ×] [黑色 ×] [+ 添加]     │
│ 尺码： [S ×] [M ×] [L ×] [XL ×]      │
│ 统一零售价： [129.00] 元              │
│                                      │
│ 预览：将生成 2 × 4 = 8 个 SKU         │
│   白色-S 白色-M 白色-L 白色-XL        │
│   黑色-S 黑色-M 黑色-L 黑色-XL        │
│                          [生成]      │
└──────────────────────────────────────┘
```

**三个必须处理的返回值**：
- `createdCount`：本次新建了几个
- `skipped`：**已存在被跳过的个数** —— 不是错误，是正常情况（补色重放）。
  必须提示"已跳过 N 个已存在的组合"，否则用户以为没生效
- 请求自身重复（如颜色里写了两次"白色"）→ 后端 409 `MDM_SKU_DUPLICATED`，
  前端应在**提交前就拦住**（输入时去重）

### 3.6 目录与文件约定

```
frontend/web/src/
├── api/client.ts          ★ 接口封装（已有，新增接口加在这里）
├── views/
│   ├── mdm/               主数据：Product / Supplier / Customer / Warehouse
│   ├── inv/               库存：Inventory
│   ├── pur/               进货：PurchaseOrder
│   └── sal/               出货：SalesOrder
├── components/            ★ 本阶段新增：跨页面复用的组件
│   ├── PageTable.vue      列表页骨架（筛选 + 表格 + 分页）
│   ├── SkuMatrixDialog.vue SKU 矩阵生成弹窗

├── utils/
```

**新增 `components/` 与 `utils/` 的理由**：7 个页面会重复同样的列表骨架、
状态标签、状态判断。抽出来之后改一处即全部生效，
否则改个状态颜色要改 7 个文件。

## 4. 测试策略

### 4.1 前端测试的取舍（明确说清）

**M3 阶段不写单元测试**。理由：

- 业务规则的测试已经在后端做了（156 条，覆盖状态机、库存、金额）
- 前端如果重复测一遍业务逻辑，等于把规则实现两遍 —— 正是 §0 要避免的
- 前端真正的风险是**"页面能不能用"**，这只能靠 E2E 或人工点，单测测不出来

**M3 的验收靠三样**：
1. `npm run build` 通过（含 `vue-tsc` 类型检查 —— 它已经抓过真实 bug，见 §6）
2. 每个页面能完成主流程（人工验收，验收清单见 §5）
3. 错误路径能正确提示（故意制造失败，看提示是否可读）

### 4.2 E2E（Playwright）的时机

**放在 M3 全部页面做完之后，作为 M3 的收尾**，理由：
- 页面还在变的时候写 E2E，等于给流水线装了个会频繁报错的警报
- E2E 依赖"选择器稳定"，而选择器要等页面结构定稿

计划写 10~15 条（计划书 §5.6 明确"E2E 只覆盖关键路径，多了必 flaky"）：

| 用例 | 覆盖 |
|---|---|
| E2E-01 | 登录成功 → 进工作台 |
| E2E-02 | 登录失败 → 提示密码错误（不区分用户不存在） |
| E2E-03 | 无 token 访问业务页 → 跳登录 |
| E2E-04 | 建商品 → SKU 矩阵生成 6 个 |
| E2E-05 | 建供应商/客户/仓库 |
| E2E-06 | 建进货单 → 提交 → 审核 → 入库 → 状态变 COMPLETED |
| E2E-07 | 分批入库（先 4 再 6） |
| E2E-08 | 超量入库被拒，库存不变 |
| E2E-09 | 建出货单（预占成功）→ 库存可用量减少 |
| E2E-10 | 出货单库存不足 → 整单失败，库存不变 |
| E2E-11 | 出货确认 → 库存扣减，状态 COMPLETED |
| E2E-12 | 作废未出货单据 → 预占释放 |
| E2E-13 | 库存页三个数字正确（实存/预占/可用） |
| E2E-14 | 权限：VIEWER 登录看不到写按钮 |

> 注意 E2E-08 / E2E-10 / E2E-12 是**反向用例**，价值高于 happy path。
> 它们验证"系统拒绝做错事"，而后端对应的 TC-PUR-009 / TC-SAL-003 / TC-SAL-011 已经证明逻辑对，
> E2E 只是确认**界面把这个真相正确传达给了用户**。
