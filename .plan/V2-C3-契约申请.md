## 申请 1（必落）：**新写操作的响应一律用 `ApiResponse` 包裹**

### 1.1 现状：两种形状并存，且各自与自己的实现相符

| 操作 | 200 的契约写法（本批修复后） | 实现 | 形状 |
|---|---|---|---|
| `POST /purchase-requisitions/{id}/convert` | `allOf: [ApiResponse, {data: PurchaseOrder}]` | `PurchaseRequisitionController.java:131` `ApiResponses.ok(orderMap(order))` | `{code,message,data}` 包裹 |
| `POST /sales-quotes/{id}/convert` | `allOf: [ApiResponse, {data: SalesOrder}]` | `SalesQuoteController.java:125` `ApiResponses.ok(SalesOrderController.toMap(order))` | `{code,message,data}` 包裹 |
| ~~`POST /purchase-requisitions/{id}/convert`（**修复前**）~~ | ~~裸 `$ref: PurchaseOrder`~~（且该 schema 不存在 → 悬空引用） | 同上 | 契约写的裸对象，实现返回包裹 —— **两边不符** |

**关键事实**：任务书 §1 表里的 N 描述为「一个裸对象、一个包裹」，那是**修复前**的状态。
本批修 M 时把 `POST /purchase-requisitions/{id}/convert` 的 200 补成了 `ApiResponse` 包裹
（因为实现本来就是包裹的，且裸对象指向的 `PurchaseOrder` schema 根本不存在）。
所以**现在两边其实已经统一成 `ApiResponse` 包裹了**，N 的「形状不一致」在当前契约里
只剩历史意义 —— 这一点必须如实登记，否则 `docs/05` 会写进一条已不存在的情状。

> 复跑验证：`python scripts/schema-field-check.py` 对这两个操作都不再报红；
> `grep -n "PurchaseOrder" packages/api-contract/openapi.yaml` 只剩
> `PurchaseOrder` / `PurchaseOrderLine` / `PurchaseOrderCreate` 三个真实定义，
> 以及 `POST /purchase-requisitions/{id}/convert` 里那处 `data: $ref` 。

### 1.2 请求写进 `docs/05-接口契约规范.md` 的规矩（建议措辞）

> **响应信封（强制）**
>
> 所有 HTTP 200/201 的业务响应一律是 `ApiResponse`：`{ code, message, data, traceId?, timestamp? }`，
> 分页是 `ApiPageResponse`：`data = { items, total, page, size }`。
>
> - **新写操作不得返回裸对象**（形如 `{ id, orderNo, … }` 直接挂在顶层）。
>   裸对象没有 `code`，前端无法在不看 HTTP 状态码的情况下判定业务结果，
>   也与全局错误处理（`ApiError`）不对称。
> - 契约里对应的写法是：
>   ```yaml
>   responses:
>     '200':
>       content:
>         application/json:
>           schema:
>             allOf:
>               - $ref: '#/components/schemas/ApiResponse'
>               - type: object
>                 properties:
>                   data: { $ref: '#/components/schemas/YourPayload' }
>   ```
>   已有可复用的 `#/components/responses/SingleResponse`（`data` 不定型）与
>   `PageResponse`；`data` 已定型时按上面的 `allOf` 写。
> - **例外只允许存量**：目前没有任何一处业务 200 是裸对象（v2c3 修复后）；
>   若将来发现，应视为缺陷登记，而不是"风格差异"。
> - `POST /purchase-requisitions/{id}/convert` 与 `POST /sales-quotes/{id}/convert`
>   这两个转化型操作**现在都在规矩内**（都是 `ApiResponse` 包裹），
>   但它们的历史形状不一致曾是真实的契约缺陷（前者一度声明裸对象且 schema 悬空），
>   这一点作为教训保留：**"两边各自与实现相符"不等于"契约自洽"**。

### 1.3 需要指挥会话做的

1. 把 §1.2 的规矩落进 `docs/05-接口契约规范.md`（本泳道不动 docs）。
2. 若 §1.1 的「修复前状态」在其它文档里被写成现状（例如 `.plan/V2-C2-报告.md` §7.3 的 N 行），
   建议加一句「V2-C3 已按实现改为 `ApiResponse` 包裹，N 的形状差异已消除」；
   **C2 报告本泳道不改**（历史证据保留原样）。

## 申请 2（请裁决）：`GET /skus` 与 `GET /products` 的分页元素在契约里是裸 `{}`

### 2.1 事实

`#/components/schemas/ApiPageResponse` 的 `data.items` 写的是 `items: {}`（裸对象数组），
所以**任何走 `$ref: PageResponse` 的列表端点，其元素字段在契约里都是没定义的**：

```
GET /suppliers  GET /customers  GET /products  GET /skus  GET /inventory/transfers
GET /inventory/stocktakes  GET /inventory/adjustments  GET /inventory/freezes
GET /purchase-orders  GET /sales-orders  GET /return-orders  GET /purchase-requisitions
GET /purchase-returns  GET /iam/users  GET /approvals  GET /sales-quotes
GET /product-bundles  GET /shipments  GET /receivables  GET /customer-receipts
```

共 **20 个列表端点**。部分端点（`/reports/*`、`/audits`、`/skus`）在操作条目里用
`allOf: [ApiPageResponse, {data: {items: {$ref: X}}}]` 补了元素类型，其余没有。

### 2.2 为什么不归本泳道

给这 20 处补元素 `$ref` 是**操作级**的结构扩展（每处都要选定元素 schema 并核对实现），
而本泳道的范围是「字段级债」；而且它不影响 H/L/M 三条的清偿。
新脚本已把它们记成「未比对缺口」并逐条打印（`--show-gaps`），不会被静默当成通过。

### 2.3 请裁决

- 方案 A：后续泳道逐端点补 `allOf` 元素 `$ref`（推荐，纯增量、无回退风险）；
- 方案 B：维持裸 `{}`，把「列表元素字段不在契约保证范围内」写进 `docs/05`。

在裁决前，`schema-field-check.py` 对这 20 处**只比分页四键**（`items/total/page/size`），
元素字段进「未比对缺口」清单，不算绿。

## 申请 3（请裁决）：`NlCommandResult` 的 data 是 record 载荷，静态形状不可得

`POST /nl/command` 的 200 `data` 是 `NlCommandResult`（应用层 record），
Controller 只写 `ApiResponses.ok(result)`，不拼 Map。
新脚本对 record 载荷的字段不做比对（它只读 Controller 的 `put` 键与请求体 record），
于是该操作进「未比对缺口」清单。

这不是缺陷，只是门禁的覆盖边界。若希望覆盖，需要让脚本读 `record` 组件 ——
属于下一轮脚本演进，不建议塞进本批。
