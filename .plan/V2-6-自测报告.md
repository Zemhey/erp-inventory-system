## 5. ★ 越权矩阵实际条数

**120 条 = 8 资源 × 5 越权方式 × 3 身份**（参数化生成，逐格断言；硬验收下限是 40）。

| 维度 | 取值 |
|---|---|
| **资源（8）** | 商品 / SKU / 库存 / 进货单 / 出货单 / 退货单 / 结算 / 报表 |
| **越权方式（5）** | 跨仓直查 id（`DIRECT_ID`）/ 列表注入（`LIST_INJECTION`）/ 导出（`EXPORT`）/ 关联查询（`ASSOCIATION`）/ 统计聚合（`AGGREGATE`） |
| **身份（3）** | 他仓仓管（`OTHER_WAREHOUSE_KEEPER`，限定 A 仓）/ 本仓只读（`OWN_WAREHOUSE_VIEWER`，限定 A 仓）/ 无 token（`ANONYMOUS`） |

### 5.1 期望形态（★ 不是"统统 404"，这里刻意更严格也更诚实）

| 形态 | 格数 | 断言 | 为什么 |
|---|---|---|---|
| **404**（单据按 id 直查/关联） | 6 | 必须 404 且业务码是不存在语义，**且响应不得出现 `IAM_FORBIDDEN`** | 403 会泄露"这个 id 存在"，攻击者按 id 遍历即可枚举整个 id 空间 |
| **200 + 只见本仓**（列表/导出/聚合） | 24 | 必须 200，**且响应正文不得出现 B 仓的 `warehouseId`** | 这是硬验收第 3 条的形态：跨仓查询得到"空结果"而不是 403 |
| **200 + 有内容**（主数据 商品/SKU） | 10 | 必须 200 且**非空** | 主数据无仓库维度，不该被过滤；**同时是防假绿的对照组** |
| **401**（匿名） | 40 | 必须 401 + `IAM_UNAUTHENTICATED` | 无身份时"该去登录"，与资源是否存在无关 |

> ★ **为什么必须逐格写期望，而不是"统统 404"**：
> 第一版我确实写成了"一律 404"，结果它把**正确实现**判成红的（列表接口本来就返回 200），
> 也掩盖了真缺陷。更危险的是反面：如果一个系统把所有接口都收成空，
> "统统断言空结果"的矩阵会**全绿**，却什么也没证明。
> 因此矩阵里同时存在 404 / 200空 / 200有内容 / 401 四种期望，并由
> `TC-IAM-043` 反向校验这三类（另一类）格子数固定为 **6 / 24 / 10**。

### 5.2 防假绿的两道保险

1. **主数据 10 格要求"非空"** —— 若数据权限误把所有查询收空，这 10 格立刻红。
2. **`TC-IAM-026` 本仓对照组** —— 同一个 token、同一个接口，本仓 id 必须 200 且有内容，
   换 B 仓 id 必须 404。**没有这条，120 格里所有 404 都可能是"接口全坏"造成的。**

## 6. ★ 审批状态机穷举数

**49 = 7 × 7**，与硬验收完全一致。

| 项 | 数值 | 用例 |
|---|---|---|
| 状态数 | 7（DRAFT / PENDING / TRANSFERRED / APPROVED / REJECTED / WITHDRAWN / CANCELLED） | `TC-APS-011` 断言恰好七个 |
| 合法转移 | **13** | `TC-APS-001` 断言 `legal == EXPECTED_LEGAL.size() == 13` |
| 非法转移 | **36** | `TC-APS-001` 断言 `illegal == 36` |
| **合计** | **49** | `TC-APS-001` 断言 `legal + illegal == 49` |
| 参数化逐条 | 49 条 | `TC-APS-002`：合法返回目标态；非法抛 `APS_STATUS_ILLEGAL` 且消息含当前态/目标态/实例标识 |

合法转移的 13 条：`DRAFT→PENDING/WITHDRAWN/CANCELLED`（3）、
`PENDING→APPROVED/REJECTED/TRANSFERRED/WITHDRAWN/CANCELLED`（5）、
`TRANSFERRED→PENDING/APPROVED/REJECTED/WITHDRAWN/CANCELLED`（5）。

> ★ **两套状态机各自穷举**：单据侧仍走 `DocumentStatusMachine` 的 7×7（`TC-DOC-001/002`，
> 既有用例保持不变），审批侧是本期的 49 条。`TC-APS-011` 额外断言"审批的四个特有状态
> （PENDING/TRANSFERRED/WITHDRAWN/CANCELLED）不得被单据状态机吸收" —— 这条守的就是任务书坑 3。

## 8. 偏离与取舍（★ 三条显式偏离，都有理由）

| # | 任务书要求 | 实际做法 | 理由 |
|---|---|---|---|
| 1 | 架构自检从 `TC-ARCH-009` 起 | 用 **`TC-ARCH-015/016`** | 并行泳道已占用 `TC-ARCH-008~014`（V2-4 成本 3 条、V2-5 审计 4 条）。编号唯一是纪律，顺延比抢号安全。 |
| 2 | "`data_scopes` 加列到 `app_users`：`failed_count` / `locked_until` …" | **不动** `failed_attempts` / `locked_until`，只**新增** `password_expires_at` / `must_change_password` | 任务书自己也提示"先查 V3 已有哪些列"。V3 已有 `failed_attempts` 与 `locked_until`，重复加列会破坏既有锁定逻辑（`TC-IAM-002` 直接依赖它们）。 |
| 3 | 种子审批流"开发/测试用" | 种子**默认 `enabled = FALSE`** | 若默认启用，存量 775 条用例第一次 `approve()` 就撞 `APS_APPROVAL_REQUIRED`（实测红过）；生产上升级当天所有单据突然都要审批、而没人配过审批人。启用是显式运维动作。 |

### 8.1 另外两处"看起来像偷懒、其实必须如此"

- **内部回读不走数据权限**：`DataScopeResolver` 在**没有身份上下文**时返回全量。
  这不是漏洞 —— `SecurityConfig` 是 `anyRequest().authenticated()`，无 token 的 HTTP 请求
  在过滤器层就 401，到不了控制器。空上下文只出现在"服务内部 create 后回读 / 后台任务 /
  直接调应用服务的集成测试"。给异常路径一个"全空"默认值反而会让 `create()` 之后
  `require(id)` 抛 404（实测红过 200+ 条存量用例）。
  ⚠️ 前提写进了代码注释：**新增匿名可达的业务路径时必须重新审视这条**。

- **主数据（商品/SKU）不被数据权限过滤**：它们没有仓库维度。强行收窄会让选品下拉全空、
  报表明细只剩 id。矩阵里那 10 格"必须是 200 且非空"就是把这个决定钉住。
