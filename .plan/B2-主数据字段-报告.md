**关键实现决策**
1. **默认地址唯一**：应用层"先锁客户行（`FOR UPDATE`）→ 清旧默认 → 置新默认"，DB 部分唯一索引做最终兜底（并发下第二个事务会撞唯一键而不是产生两个默认）。
2. **停用默认自动提升**：停用的若是默认地址，同事务把 id 最小的启用地址提升为默认；无其它启用地址时该客户暂无默认（合法）。历史单据不受影响 —— `sales_orders.customer_id` 只指向客户。

## 3. 守恒口径（写死）

`SUM(启用库位 capacity_qty) == warehouses.capacity_qty`

| 情形 | 行为 |
|---|---|
| 仓库容量 = 0（未设定） | 不设上限；核对端点报 `consistent=false` + 实际差额，**不特判成绿** |
| 建/改/启用库位将超限 | `409 MDM_LOCATION_CAPACITY_EXCEEDED` |
| 分配不足（合计 < 仓库容量） | 允许存在，核对报差额 —— 这是补齐库位前的真实运营状态 |
| 停用库位 | 不参与合计（"停用"的自然语义），核对因此会暴露容量缺口 |
| 下调仓库容量至低于已分配 | **不阻断**（缩库是运营决策），核对暴露 `consistent=false` |
| 库存余额维度 | 仍是 `(SKU, 仓库, 批次)`，**不引入库位维度**；停用库位不动 `inventory_balances` / `inventory_ledger` |

### 7.1 施工中遇到的一个真实仓库级故障（必须交接）

**现象**：本 worktree 的 `HEAD` 无法解析（`fatal: your current branch 'feat/mdm-fields' does not have any commits yet`），
`git add -A` 把整仓 736 个文件当成新增；连主工作区的 `main` 也报 "No commits yet。"

**根因**：`feat/mdm-fields` 分支引用从未真正建立，且 **`.git/packed-refs` 的排序被破坏**。
该文件首行声明 `# pack-refs with: peeled fully-peeled sorted`，git 依赖这个 `sorted` 断言做二分查找。
新增分支若被追加到文件末尾（`refs/heads/feat/mdm-fields` 排在 `refs/heads/main` 之后），
整个引用库的解析就会失效 —— 表现是"分支明明在 `show-ref` 里，`rev-parse` 却说不存在"。
唯一能解析的 `feat/v2c1-mdm-idem` 是因为它在 `refs/heads/` 下有 loose 文件，走的是另一条查找路径，掩盖了问题。

**修复**：把 `packed-refs` 按 ref 名字典序整体重排后，`main` 与 `feat/mdm-fields` 立即恢复正常。
**影响面**：零文件丢失；提交对象 `af166de` 在故障期间就已正确生成（reflog 有记录），修复后直接指向它。

**给后来者的三条**：
1. 新建分支一律用 `git switch -c` / `git branch`，**不要手改 `.git/packed-refs`**；非改不可时，改完必须整体重排并对 `main` 做一次 `rev-parse` 自检。
2. 看到 "does not have any commits yet" 而 `git show-ref` 又能列出该分支 → 先怀疑 `packed-refs` 排序，不要 `reset`、不要 `checkout .`。
3. `git add -A` 前先 `git rev-parse HEAD` 确认基线可解析；解析不了时 `add -A` 会把整仓当成新增。
