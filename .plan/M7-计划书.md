## 2. 关键设计决策

### 2.1 NL 层只做「解析 + 调度」，不碰业务规则

```
POST /api/v1/nl/command { "command": "查询 SKU 12 的库存" }
  → NlCommandController        （只做 HTTP 绑定、X-Request-Id、统一响应）
    → NlCommandParser.parse    （自然语言 → NlCommand{intent, arguments}）
      → NlCommandDispatcher    （按 intent 校验参数形状 + 校验权限 + 调用既有 ApplicationService）
        → InventoryApplicationService / PurchaseOrderApplicationService / SalesOrderApplicationService /
          ReturnOrderApplicationService / ReportApplicationService / *ApplicationService（mdm）
  → NlCommandResult{intent, description, write, data}
```

**为什么必须这样切**：如果 NL 里出现「库存够不够」「能不能审核」这类判断，它就成了第二套业务规则；
一旦规则变化，两条路径必然分叉。ArchUnit 新增规则 9（`nl` 不得依赖 repository）+ 自检 `TC-ARCH-007` 把这条钉成门禁。

### 2.2 解析器可注入：接口 + 两个实现

| 实现 | 触发条件 | 用途 | 是否依赖外网/key |
|---|---|---|---|
| `StubNlCommandParser` | `erp.nl.parser=stub`（**默认，缺省即 stub**） | 确定性规则解析；CI、单测、离线演示 | 否 |
| `OpenAiNlCommandParser` | `erp.nl.parser=openai` | 真实 LLM function calling（OpenAI 兼容 `/chat/completions`） | 是，key 走 `ERP_NL_API_KEY` |

配置（只追加 `erp.nl` 段，不动其它段）：

```yaml
erp:
  nl:
    parser: ${ERP_NL_PARSER:stub}          # stub | openai
    openai:
      base-url: ${ERP_NL_BASE_URL:https://api.openai.com/v1}
      api-key: ${ERP_NL_API_KEY:}          # 只从环境变量读取，绝不写进仓库
      model: ${ERP_NL_MODEL:gpt-4o-mini}
      timeout-seconds: 30
```

**为什么默认 stub**：测试和 CI 不能因为外网抖动、额度耗尽、key 泄露而红；演示也必须可离线复现。
真实 LLM 只需改一个环境变量 `ERP_NL_PARSER=openai`，业务调度一行不用动 —— 这就是「解析器可注入」的意义。
OpenAI 实现用 JDK 自带 `java.net.http.HttpClient`，不引第三方 SDK；请求体带 `tools` + `tool_choice:auto`，
取 `choices[0].message.tool_calls[0]` 的 `function.name/arguments`；无 tool call → `NL_COMMAND_UNRECOGNIZED`；
key 缺失/网络失败/上游返回非法 JSON → `NL_PARSER_UNAVAILABLE`（503），**不把基础设施故障伪装成用户指令错误**。

### 2.3 权限：按意图映射既有权限码，不新增权限

NL 是「入口」，不是「越权通道」。控制器只要求登录（`SecurityConfig` 默认拒绝匿名），
**每个意图执行前用 `NlAccessGuard` 做一次精确权限判断**，语义与 `PermissionAspect` 完全一致
（ROLE_ADMIN 短路；否则从数据库读 `AppUser#hasPermission`）。

| 意图 | 所需权限 |
|---|---|
| `help` | 无（登录即可） |
| `query_inventory` | `inv:read` |
| `list_documents` / `get_document`（进货） | `pur:read` |
| `list_documents` / `get_document`（出货） | `sal:read` |
| `list_documents` / `get_document`（退货） | `rma:read` |
| `inventory_summary` | `rpt:read` |
| `query_master_data` | `mdm:read` |
| `create_purchase_order` | `pur:create` |
| `create_sales_order` | `sal:create` |

**为什么不在 Controller 上贴一个 `@RequirePermission`**：切面语义是「满足任一声明的权限即放行」，
一个 `rpt:read` 账号会因此被放进写意图。精确判断必须发生在知道 intent 之后。
`NlAccessGuard` 复用 `AuthenticationService` 与 `AppUser`，没有另造权限模型。

### 2.4 幂等：NL 端点统一要求 `X-Request-Id`

- 契约里 `/nl/command` 是 POST，按项目硬规则必须声明 `X-Request-Id`（CI 的 `contract-check` 会检查）。
- 读意图也要求该头：**一条规则比「先解析再决定要不要键」简单**，且 NL 入口无法在 HTTP 层预知意图。
- 写意图把同一个 `X-Request-Id` 原样传给 `PurchaseOrderApplicationService.create` / `SalesOrderApplicationService.create`
  作为建单幂等键；同键重放返回首次建单结果，不会产生第二张单（INV-9）。

### 2.5 意图清单与参数形状

| intent | arguments | 说明 |
|---|---|---|
| `help` | — | 返回支持的意图与示例 |
| `query_inventory` | `skuId? warehouseId? batchNo? onlyAvailable?` | 调 `InventoryApplicationService.query` |
| `list_documents` | `docType`（PURCHASE/SALES/RETURN）、`status?`、`partyId?`、`page?`、`size?` | PUR 传 supplierId，SAL/RMA 传 customerId |
| `get_document` | `docType`、`id` | 调对应 `require(id)` |
| `inventory_summary` | `period`（yyyy-MM，缺省=当前月）、`warehouseId?` | 调 `ReportApplicationService.inventorySummaryReport` |
| `query_master_data` | `type`（WAREHOUSE/PRODUCT/SKU/SUPPLIER/CUSTOMER）、`keyword?`、`productId?`、`page?`、`size?` | 调对应 mdm ApplicationService |
| `create_purchase_order` | `supplierId`、`warehouseId`、`lines[{skuId,qty,unitPriceAmount}]`、`bizDate?`、`remark?` | 只建草稿；金额/单号/状态由后端算 |
| `create_sales_order` | `customerId`、`warehouseId`、`lines[{skuId,qty,unitPriceAmount,discountRate?}]`、`bizDate?`、`remark?` | 建单即预占由既有服务完成 |

**注意**：NL 不接受「审核/入库/出货/作废」等状态推进意图。原因：这些动作一旦由一句话触发，
既无法在 UI 上二次确认，也不适合无人值守的 MCP 默认暴露；本期刻意只到「建草稿」。
`create_*` 的参数形状与对应 REST 接口一致，NL 不额外发明金额字段。

### 2.6 错误码（追加到 `ErrorCode`）

| 码 | HTTP | 何时抛出 |
|---|---|---|
| `NL_COMMAND_UNRECOGNIZED` | 422 | 解析器无法把文本映射为已支持意图（含模型未返回 tool call） |
| `NL_COMMAND_INVALID_ARGUMENT` | 400 | 意图已识别，但参数缺失/类型非法/枚举取值非法 |
| `NL_PARSER_UNAVAILABLE` | 503 | 配置为真实 LLM 但 key 缺失、网络/超时、上游返回非法响应 |

空指令是 Bean Validation → 既有 `SYS_VALIDATION_ERROR`（400）；未登录仍是 `IAM_UNAUTHENTICATED`（401）；
缺权限仍是 `IAM_FORBIDDEN`（403）。**不新增兜底 500 路径**。

### 2.7 stub 解析文法（离线可复现）

stub 是「演示与测试的确定性解析器」，不是通用 NLU。支持：

- 意图关键词：
  - `帮助` / `help` / `能做什么` → `help`
  - `查询库存` / `查库存` / `库存查询` → `query_inventory`
  - `进货单` / `出货单` / `退货单`（不含「创建/新建」）→ `list_documents`
  - `汇总` / `进销存` → `inventory_summary`
  - `商品` / `SKU` / `供应商` / `客户` / `仓库`（查询语境）→ `query_master_data`
  - `创建/新建/建单` + `进货` → `create_purchase_order`
  - `创建/新建/建单` + `出货` → `create_sales_order`
- 参数：`key=value` 形式（如 `skuId=12 warehouseId=3`）与常用中文形式
  （`SKU 12`、`仓库 3`、`第 2 页`、`每页 10`、`状态 已审核`、`账期 2026-10`、`本月`/`上月`）。
- 建单行的紧凑写法：`SKU=5 数量=10 单价=1000`，多行用 `；` 或 `;` 分隔。
- 机器可读兜底：`query_inventory skuId=12 warehouseId=3`（意图代码 + 键值对）。
- 识别不到 → `NL_COMMAND_UNRECOGNIZED`，消息里带支持的意图清单与示例。

stub 的限制会写进 MCP 接入文档与前端示例：**它不解析相对时间、别名、同义词**；真实自然语言请切 `openai`。

## 4. 后端模块结构（`com.erp.nl`）

```
backend/server/src/main/java/com/erp/nl/
├── api/
│   └── NlCommandController.java        POST /api/v1/nl/command
├── application/
│   ├── NlCommandParser.java            接口：String → NlCommand
│   ├── StubNlCommandParser.java        默认；确定性文法
│   ├── OpenAiNlCommandParser.java      OpenAI 兼容端点 + function calling
│   ├── NlCommandDispatcher.java        意图 → 既有 ApplicationService
│   ├── NlAccessGuard.java              复用 AuthenticationService/AppUser 做意图级权限
│   └── NlArguments.java                参数形状校验（缺失/类型 → NL_COMMAND_INVALID_ARGUMENT）

    ├── NlIntent.java                   8 个意图 + code + write 标记
```

`ArchitectureTest` 同时把 `com.erp.nl..` 纳入「禁止系统时间」两条规则（stub 的 `本月/上月` 走 `ClockProvider`）。

**不改 PUR/SAL/RMA/SET/RPT/MDM/IAM 的任何业务代码**。

## 5. MCP Server（`packages/mcp-server`）

### 5.1 形态与配置

- TypeScript + 官方 `@modelcontextprotocol/sdk`，**stdio** transport。
- 配置（环境变量）：`ERP_BASE_URL`（默认 `http://127.0.0.1:8080/api/v1`）、`ERP_TOKEN`（JWT，必填）。
- 每个工具都是「HTTP 薄适配器」：不实现业务、不缓存数据、不做写操作以外的本地状态。
- 错误统一返回 MCP `isError: true` + 后端 `code/message`（HTTP 非 2xx 时原样透出）。

### 5.2 工具清单（6 个）

| 工具 | 参数 | 后端接口 | 权限 |
|---|---|---|---|
| `query_inventory` | `skuId? warehouseId? batchNo? onlyAvailable?` | `GET /inventory` | `inv:read` |
| `list_documents` | `type: purchase\|sales\|return`、`status? page? size?` | `GET /purchase-orders` / `/sales-orders` / `/return-orders` | 对应 `*:read` |
| `get_document` | `type`、`id` | `GET /{type}/{id}` | 对应 `*:read` |
| `inventory_summary` | `period`（yyyy-MM）、`warehouseId?` | `GET /reports/inventory-summary` | `rpt:read` |
| `query_master_data` | `type: product\|sku\|supplier\|customer\|warehouse`、`keyword? page? size?` | `GET /products` / `/skus` / `/suppliers` / `/customers` / `/warehouses` | `mdm:read` |
| `nl_command` | `command` | `POST /nl/command`（自动生成 `X-Request-Id`） | 意图对应权限 |

### 5.3 接入演示与实证

- `packages/mcp-server/README.md`：两种接法（Claude Desktop / 任意 MCP 客户端）+ 环境变量 + 工具清单 + 安全说明。
- `packages/mcp-server/scripts/smoke.mjs`：用 SDK 的 `Client` + `StdioClientTransport` 启动 server，
  `listTools` 后依次调用 `query_inventory`、`inventory_summary`、`nl_command`，打印结果并以退出码表达成败。
- 实证记录写进 §9：命令、输入、输出摘要（token 已在命令里，不写入文档）。

> 安全：MCP Server 只持有调用者给的 JWT，不保存口令；`nl_command` 与直接调 REST 的权限完全一致。
> 不默认暴露审核/入库/作废这类不可逆动作。

## 10. 已知限制与后续

1. **stub 不是通用 NLU**：只认关键词与键值对，不做相对时间、别名、同义词与多轮上下文；真实自然语言需切 `openai`。
2. **写意图只到草稿**：不支持「审核/入库/出货/作废」的自然语言触发（不可逆动作需要 UI 二次确认与更明确的授权模型）。
3. **按 ID 而非名称**：NL 参数里客户/供应商/SKU/仓库用 id；按名称解析要么新增只读解析接口、要么让模型先查主数据再组合调用，属后续增强。
4. **OpenAI 实现只用本地假服务器验证**：本机没有真实 LLM key，真实端点联调需要用户提供 key；调用链（请求构造、tool_call 解析、错误映射）已由单测覆盖。
5. **MCP 工具是 REST 的薄适配器**：没有为 Agent 设计专门的批量/事务工具；`nl_command` 的写操作仍受同一套权限与幂等约束。
6. **索引与计数**：`index/`、`docs/00`、`README`、`总纲` 的计数由主工作区在批次合并后统一刷新（本泳道不改）。
