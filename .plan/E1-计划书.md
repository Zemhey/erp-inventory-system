## 3. 关键设计决定

### 3.1 API 层单独成文件

`src/api/auditDict.ts`（对齐 V2-3 的 `salesV23.ts` 做法）：只追加自己的端点与类型，减少多泳道在 `client.ts` 同一区域撞车。该文件**一个写方法都没有** —— 页面上的"只读"不是文案，是这层调不出写接口。

### 3.2 diff 用纯函数、不引组件库

`src/utils/auditSnapshot.ts`：`diffSnapshots(beforeJson, afterJson)` 把快照摊平成 `路径 → 文本`，返回 `fields / counts / beforeMissing / afterMissing / rawText / hasDiff`。

三条口径：
- **解析失败不静默**：不是合法 JSON 时给原文并单独告警，绝不显示成"无变化"；
- **缺失不说死**：`before` 为空既可能是首次创建，也可能是动作路径不带资源 id（`/submit`、`/approve`），界面只说"无变更前快照"（详见契约申请 §3）；
- **值只转字符串**：前端不参与业务判断（金额、状态、数量都不在这里算）。

### 3.3 为什么筛选里要有"资源类型 / 资源 ID"

后端刻意不把主数据编码当 `bizRefNo`（`AuditAspect.BIZ_REF_KEYS` 不含 `code`），所以**供应商/商品/SKU 的审计查不到单据号**。只给"操作人 + 时间"的话，主数据变更历史只能按人翻页。补上契约已有的 `resourceType`/`resourceId` 两个维度后，一条主数据的所有变更才能精确定位。

### 3.4 菜单与路由只追加

两条路由追加在 `children` 数组末尾（通配兜底仍在最后），两条菜单追加在 `allMenus` 末尾。上批合并已在 `MainLayout.vue`/`router/index.ts` 撞过两次，只追加是最小冲突面。

## 5. 数据隔离与清理口径（审计表不删）

- `audit_logs` 有 append-only 触发器（`audit_logs_append_only()`），**清理脚本不碰审计表**；审计自然增长是设计行为，不是残留。
- teardown 的硬校验只覆盖业务表计数与 `e2e-reserve-001`；`audit_logs` 不在基线里。
- 断言隔离用三种不变量（清理会回收当日取号序列，同一 PO 号会跨轮复现）：
  1. **resourceId**（BIGSERIAL，不复用）收窄列表；
  2. **造数前时间戳** `from` 收窄接口列表（TC-API-118）；
  3. **traceId** 全局唯一（TC-API-119 / TC-SYS-093）。
- 轨迹接口无时间参数（契约如此）→ 断言钉"正序末尾四条"，历史轮同号记录允许排在前面（截图与报告均说明）。
- TC-SYS-095 的临时 PURCHASER 账号由用例 `finally` 删除，保证 teardown 的 `users` 计数回到基线。

## 7. 风险与已知缺口

1. **动作枚举是前端镜像**（`AUDIT_ACTIONS` ↔ `AuditAction.java`）：后端已把枚举做成闭合集合，但没有机器可读的导出；前端下拉只能镜像。缓解：列表与详情按**原始字符串**显示，漂移时显示新动作码而不是空白。诉求见契约申请 §2。
2. **单据工作流的 before_json 恒为 null**：`AuditAspect` 只按"路径末段是纯数字"取上一次快照，`/submit`、`/approve` 这类动作取不到。审计页对单据流程只能展示"变更后"，看不到状态迁移的前后对照。见契约申请 §3。
3. **数据权限未收窄**：`AuditQueryService` 明说不做过滤（V2-6 数据权限只落在单据侧），页面已用警示条明示"有 `sys:read` 就能看全公司"。
4. **`audit_logs` 只增不减**：长时间跑 E2E 的库会积累同号历史；本泳道已把所有断言改用 resourceId / 时间戳 / traceId 隔离，**不删审计行**。
5. **字典值尚未成为 SKU 录入的下拉约束**：字典页只是"可读取值清单"，`ProductView` 的颜色/尺码仍是自由输入。页面已写明，避免把"有字典"误读成"已被约束"。
