# E1 契约申请 · 审计查询 / 数据字典界面暴露的缺口

- 提出泳道：E1（`feat/e1-dict-ui`）
- 事实源：`backend/server/src/main/java/com/erp/sys/**`、`V13__sys_audit_and_dict.sql`、`packages/api-contract/openapi.yaml`
- 本泳道按约定**未改后端与契约**；以下缺口以界面实跑证据提出，由指挥侧排期。

---

## 1. 字典没有写端点 → 维护界面无法交付（阻塞项）

**现象**：`DictController` 只有两个 GET；`/dicts`、`/dicts/{typeCode}/items` 在契约里也只有 GET。
`V13` 的种子只覆盖 COLOR / SIZE / SEASON / UNIT 四类 14 项，运营无法新增或停用任何字典项。

**影响**：字典页只能是"只读浏览"。已按实情交付并在页面上写明原因（见 `TC-SYS-094`），
**没有**做"看起来能改、点下去 405"的假表单 —— 那比没入口更糟。

**需要的最小契约**（建议 V2-7「参数/字典期」）：

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| POST | `/dicts` | 新建类型（code 唯一、enabled 默认 true） |
| PUT | `/dicts/{code}` | 改名/说明/启停 |
| POST | `/dicts/{typeCode}/items` | 新建字典项（`(type_id, code)` 唯一） |
| PUT | `/dicts/{typeCode}/items/{itemCode}` | 改 label / sortNo / enabled |
| DELETE 或 POST | `/dicts/{typeCode}/items/{itemCode}/disable` | 停用（推荐停用而非物理删，历史单据仍要能解释旧值） |

同时需要：权限码（建议 `sys:dict:write`，与 `sys:read` 分离）+ 写操作的审计动作（`CREATE/UPDATE/DISABLE` 已有，可直接复用）。

**前端就绪度**：API 层已按"只追加"组织（`src/api/auditDict.ts`），后端补端点后只需加 5 个方法与维护弹窗；页面骨架与只读说明不用重写。

## 2. `GET /dicts/ACTIONS` 被后端文案引用，但种子里不存在（一致性缺陷）

**现象**：`AuditController.parseAction()` 的 400 文案是
`非法 action 取值：%s（可选值见 GET /dicts/ACTIONS）`，
但 `V13__sys_audit_and_dict.sql` 只种了 COLOR / SIZE / SEASON / UNIT，没有 `ACTIONS` 类型；
访问 `/dicts/ACTIONS/items` 返回 404 `SYS_DICT_TYPE_NOT_FOUND`。

**影响**：① 错误文案把用户引到一个 404；② 审计页的"操作类型"下拉**没有后端可读的枚举来源**，
只能在 `src/api/auditDict.ts` 里镜像 `AuditAction.java` 的 17 个值 —— 这正是
`check:status-parity` 当初要消灭的那类"前端照抄、以后漂移"的问题。

**建议二选一**（推荐 A）：

- **A**：种子补一个 `ACTIONS` 字典类型，项 = `AuditAction` 全部枚举（label 用中文动作名，sortNo 按枚举顺序）。
  前端下拉改成读 `/dicts/ACTIONS/items`，枚举漂移由数据自己兜住；同时把契约 §audits 的 `action` 描述指向该字典。
- **B**：把 400 文案改成不再引用字典；前端镜像保留，但需补一条"前端清单 ↔ `AuditAction.java`"的 parity 门禁
  （现成的 `scripts/check-status-parity.mjs` 只覆盖单据状态机，**本泳道未擅自扩它的规则**）。

无论选哪条，"描述里承诺的查询入口必须真的存在"是这单的底线。

## 3. 单据工作流的 `before_json` 恒为 null → 审计最有价值的对照在单据上缺失

**现象**：`AuditAspect` 这样取变更前快照：

```java
String pathResourceId = pathVariablePathId(request);   // 仅当路径末段是纯数字
String beforeJson = pathResourceId == null ? null
        : recorder.beforeSnapshot(resourceType, pathResourceId);
```

- `PUT /suppliers/{id}` → 末段是 id → 有 before ✅
- `POST /purchase-orders/{id}/submit`、`/approve`、`/receive` → 末段是动作词 → **before 永远 null** ❌

**影响**：审计页对单据只能展示"变更后"（例如审核后的整单 DTO），看不到
"DRAFT → SUBMITTED"的状态迁移对照。而"这张单谁审核的、状态从什么变成什么"正是 FR-SYS-07 的核心诉求。
前端已如实标注"无变更前快照（两种成因）"，没有把缺失粉饰成"首次创建"。

**建议**：在 `proceed()` 之后、写审计之前，若 `pathResourceId == null` 且响应 `data.id` 存在，
用 `beforeSnapshot(resourceType, String.valueOf(data.id))` 补取一次（此时业务事务已提交，
上一次成功审计仍是"本次之前"的那条，语义不变）。注意：这会让单据动作也带 before_json，
需要同步更新契约 `AuditLog.beforeJson` 的描述（当前写的是"取自该资源上一次成功审计的 after_json"，仍成立）。

**回归影响**：`before_json` 从 null 变为有值，属**增量**；现有 `TC-SYS-*` 断言的是"链路可回溯"，
需检查是否有"首次动作为 null"的强断言（本泳道未改这些测试）。

## 4. 轨迹接口没有时间过滤，长历史下"同一单号"会被多轮数据稀释（低优先）

**现象**：`GET /audits/timeline?bizRefNo=` 只有单号一个参数，返回该号**全部**历史。

**背景**：E2E 清理会回收当日的取号序列（当天已无单据时删 `document_sequences` 行），
于是同一个 `PO20261024-0001` 会在后续轮次复用；而 `audit_logs` append-only、不清理。
结果是同一单号的轨迹会混入历史轮记录（本泳道截图 `TC-SYS-093-audit-timeline` 可见）。

**影响**：生产上单号不会复用，问题不大；但"按单号追溯"在多租户/多环境合并库时同样会撞号。
前端已把断言改成"正序末尾 N 条"，页面不加过滤以避免掩盖后端行为。

**建议**（可选）：`/audits/timeline` 增加可选 `from`/`to`（半开区间，与 `/audits` 同口径），
或返回分页。优先级低，可并入 V2-7。

## 5. 观察项（不申请变更，已在页面明示）

1. **审计不做数据权限过滤**：`AuditQueryService` 注释明确"本期只要求按人/单据/时间/操作类型能查"。
   `sys:read` 的身份可看全公司操作记录。审计页用警示条明示了这一点，避免验收时被误读成已按仓/本人收窄。
2. **字典值尚未成为录入约束**：`ProductView` 的颜色/尺码仍是自由输入，字典页只是可读取值清单。页面已写明。
