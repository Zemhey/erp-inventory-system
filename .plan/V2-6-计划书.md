## 0. 一分钟交接

V1~V8 的权限只解决了 **RBAC 的一半**：

| 已有 | 缺口 |
|---|---|
| 角色 → 权限码（`app_role_permissions`） | 没有"数据权限"：采购员能看**所有仓**的进货单 |
| `@RequirePermission` 逐接口声明 | 没有用户/角色管理界面，改权限要手工写 SQL |
| 登录失败锁定（M1） | 没有密码复杂度、没有过期、没有在线改密 |
| `DRAFT→SUBMITTED→APPROVED` 三态推进 | **没有审批流**：任何有 `pur:approve` 的人一步就能审完，金额再大也是 |

本期把这三块补成闭环，并**只补这三块**（蓝图 §0.3：不做通用 BPMN）。

## 1. 范围（做什么 / 不做什么）

### 1.1 做什么

| FR | 功能 | 具体交付 | 验收要点 |
|---|---|---|---|
| **FR-IAM-04** | 数据权限（按仓/本人） | `data_scopes` 表 + 解析器 + **注入 6 个模块的 12 条查询** | 越权矩阵 120 条；A 仓查 B 仓 → **空结果**（不是 403） |
| **FR-IAM-05** | 用户与角色管理 | 8 个接口 + 2 个前端页面（用户/角色/数据权限） | **授权即时生效**：改完下一个请求即可见 |
| **FR-IAM-06** | 登录安全策略 | 复杂度 + 过期 + 强制改密 + 在线改密（均可配置） | 不合规拒 / 过期拦截 / 锁定生效 |
| **FR-IAM-07** | 多级审批授权 | 金额阈值触发上级节点 | 小额 1 级、超阈值 2 级 |
| **FR-APS-01** | 审批流定义 | `approval_flows` + `approval_steps`（节点/阈值/会签/或签） | 定义校验（首节点阈值必 0） |
| **FR-APS-02** | 审批实例流转 | 提交/同意/驳回/撤回/转办/接办 | 状态机 **7×7=49 穷举** |
| **TC-ARCH-009/010** | 新架构门禁 | `aps` 不得依赖单据仓储 / 单据领域类型 | 规则自检用例证明会红 |

### 1.2 不做什么（明确划掉）

| 项 | 原因 | 去向 |
|---|---|---|
| 通用 BPMN / 流程设计器 | 蓝图 §0.3 明确砍掉；本项目只有"单据审批"一种流程 | 永久不做 |

| 修改 `packages/api-contract/openapi.yaml` | **本泳道不是契约 owner** | 见交付报告「契约变更申请单」 |
| 租户隔离 | 属 V2-7 | 不做（本期 404 语义已为它铺好路） |

## 2. 架构与分层

### 2.1 新增模块 `com.erp.aps`

分层照抄 `mdm`：

```
aps
├── api/          ApprovalController            （HTTP 绑定 + DTO）
├── application/  ApprovalApplicationService    （流转编排）
│                 ApprovalGateService           （shared.approval.ApprovalGate 的实现）
├── domain/       ApprovalStatus                （七态状态机，独立于 DocumentStatus）
│                 ApprovalStatusMachine         （唯一执行点）
│                 ApprovalInstance / ApprovalStep / ApprovalFlow
└── repository/   ApprovalInstanceRepository / ApprovalStepRepository / ApprovalFlowRepository
```

### 2.2 依赖方向（这是本期最关键的一条）

```
pur / sal / rma ──依赖──▶ shared.approval.ApprovalGate（接口）
                                  ▲
                                  │ 实现
                            aps.application.ApprovalGateService

pur / sal / rma / inv / rpt ──依赖──▶ shared.scope.DataScopeProvider（接口）
                                            ▲
                                            │ 实现
                                    iam.application.DataScopeResolver
```

**为什么必须接口在 `shared`、实现在业务模块**：与 M2 的 `PeriodGuard` 完全同一个理由。
若 `aps` 直接依赖 `pur.repository`，而 `pur` 又要问 `aps`"批准了没有"，就是包依赖环；
编译能过、模块拆不开、单测只能整块起容器。

### 2.3 两条状态机边界（任务书坑 3）

| | 单据状态机 | 审批状态机 |
|---|---|---|
| 枚举 | `shared.document.DocumentStatus` | `aps.domain.ApprovalStatus` |
| 七态 | DRAFT/SUBMITTED/APPROVED/PARTIAL/COMPLETED/VOIDED/REJECTED | DRAFT/PENDING/TRANSFERRED/APPROVED/REJECTED/WITHDRAWN/CANCELLED |
| 谁推进 | 单据自己的 ApplicationService（含红冲的补偿转移） | 审批自己的 ApplicationService |
| 是否碰库存/账期 | 是（`PeriodGuard` + `InventoryApplicationService`） | **否**，完全不知道它们 |

**硬约束：`aps` 不写单据表、不 import 单据领域类型。** 单据侧在 `approve()` 之前调
`ApprovalGate.requireApproved(...)` 问一句，然后**自己**调 `DocumentStatusMachine`。

## 3. 数据模型（V14 迁移）

| 表 | 作用 | 关键约束 |
|---|---|---|
| `data_scopes` | 数据权限（主体 = 用户或角色） | `ck_data_scope_subject`（二选一）、`ck_data_scope_value`（WAREHOUSE 必须有 id）、表达式唯一索引把 NULL 折成 0 |
| `approval_flows` | 流程定义头 | `uq_approval_flow_code`；**部分唯一** `uq_approval_flow_enabled_biz`（同类型最多一条启用） |
| `approval_steps` | 节点（定义 + 实例快照同表） | `ck_approval_step_form`（定义态/实例态字段组合自洽） |
| `approval_instances` | 审批实例 | 部分唯一 `uq_approval_instance_open`（同单据最多一个未结） |
| `app_users` 加列 | `password_expires_at` / `must_change_password` | ★ V3 已有 `failed_attempts` / `locked_until`，**不重复加** |

### 3.1 两条"默认值"决定（都很容易被做反）

1. **数据权限默认放开**（未配置 = 全量）。收紧的默认值会让 251 条存量用例全红，
   且"新功能把老系统锁死"在生产里就是事故。
2. **种子审批流默认停用**（`enabled = FALSE`）。同一个理由：引入审批不能改变存量行为，
   否则升级当天所有单据突然都要审批、而没人配过审批人。
   启用是显式运维动作（`POST /approvals/flows/{id}/enabled`）。

> 这两条都在代码注释里写明了"为什么"，并由
> `TC-IAM-038`（未配置=全量）与 `TC-APS-026`（无流程则照旧）钉死。

## 4. 硬验收怎么做到

| # | 验收 | 做法 | 用例 |
|---|---|---|---|
| 1 | **越权矩阵 ≥ 40** | 8 资源 × 5 方式 × 3 身份 = **120** 参数化 | `TC-IAM-024`（120 格）+ `TC-IAM-025`（规模自检）+ `TC-IAM-026`（**防假绿对照组**） |
| 2 | **审批状态机 7×7** | 期望表独立书写，断言 `legal + illegal == 49` | `TC-APS-001/002`（13 合法 / 36 非法） |
| 3 | 数据权限真生效 | 谓词注入 SQL；A 仓查 B 仓得**空结果** | `TC-IAM-026`、`TC-IAM-034` |
| 4 | 授权即时生效 | 每请求回库重读；改完同一 token 下一请求即变 | `TC-IAM-033`（权限）、`TC-IAM-034`（数据范围） |
| 5 | 登录策略可配置且拦住 | 策略对象化 + `PasswordExpiryFilter` | `TC-IAM-012`~`TC-IAM-023`（L1）、`TC-IAM-027`~`TC-IAM-032` |
| 6 | 新增用例 ≥ 55 | `TC-IAM-012`~`TC-IAM-042`（31）+ `TC-APS-001`~`TC-APS-030`（30）+ `TC-ARCH-009/010`（2） | **63 条** |
| 7 | 覆盖率不倒退 | 见自测报告 | jacoco |

### 4.1 ★ "404 而非 403"的实现位置

数据权限不是"查出来再判权限"，而是**把谓词拼进 SQL**：

```java
// PurchaseOrderRepository#findHeaderById
args.add(id);
String predicate = scope.predicates("warehouse_id", "created_by", args);
return jdbc.query("... WHERE id = ?" + predicate, MAPPER, args.toArray()).stream().findFirst();
```

于是越权的 id 根本查不出行 → 上层照常抛 `PUR_ORDER_NOT_FOUND`（404）。
**403 会泄露资源存在性**：攻击者按 id 遍历、用响应码就能枚举出整个 id 空间。

### 4.2 ★ 为什么必须有对照组

如果接口本身全坏了，矩阵的 120 条会**全部** 404 —— 而 404 正是"通过"的期望值。
一个永远 404 的系统能把矩阵跑绿却什么都没证明。
`TC-IAM-026` 断言"本仓数据必须 200 且有内容"，让 404 真正意味着"被收窄"。

## 6. 踩过的坑（给后来者）

| # | 坑 | 症状 | 正确做法 |
|---|---|---|---|
| 1 | **TRUNCATE CASCADE 清掉配置表** | `TC-APS-019` 报"在金额 10000 下没有任何可执行节点" | `TRUNCATE approval_instances` 会级联清空 `approval_steps`（含定义节点）。改用 `DELETE` |
| 2 | **测试辅助方法把身份上下文提前恢复** | 16 条用例同一句"未登录或登录已过期" | `asUser(id, () -> { body.run(); return null; })` 会在 body **之前**恢复上下文；必须在 try 内执行 body |
| 3 | **角色是配置、不在 truncate 清单里** | 第二条用例撞 `uq_app_role_code` | 用"取出或新建"，不要裸 `insert` |
| 4 | **种子流程若默认启用** | 251 条存量用例第一次 `approve` 就红 | 种子 `enabled = FALSE`，显式启用 |
| 5 | **内部回读也被数据权限过滤** | `create()` 之后 `require(id)` 抛 404 | 无身份上下文时返回全量（前提：`anyRequest().authenticated()`，无匿名业务路径） |
| 6 | **Controller 直接 import 仓储类型** | ArchUnit「控制器不得直连仓储」红 | 应用层返回自己的 `RoleView` / `ScopeView` 记录 |
| 7 | **审计时间戳用 `now()`** | ArchUnit「禁止系统时间」红 | 一律走 `ClockProvider`；"审计时间例外"会被后来者越用越宽 |
