### 0.3 ★ 一次"编号撞车"的误判与纠正（值得记住）

我一度用 `git grep -o 'TC-[A-Z]+-[0-9]{3}'` 统计，得到"67 处重复、RPT-013 重复 7 次"的结论，并据此判断"追踪矩阵会指错文件"。

**这个结论是错的。** 原因：那条正则把**注释、`@DisplayName`、类级 Javadoc 里提到的编号**都算了进去，例如：

```java
* 采购闭环的 HTTP 契约测试（TC-API-030~039）。   ← 注释里的范围描述
@DisplayName("采购闭环 · HTTP 契约（TC-API-030~039）")  ← 显示名
```

**正确做法**：只匹配注解本体 `@CaseId("TC-XXX-NNN")`。
按此重算：**400 个 `@CaseId` 实例，400 个唯一编号，真实重复 0 个。**

> **教训**：统计"编号是否唯一"时，正则必须锚定到**注解**，不能锚定到"编号字符串出现"。
>
> **★ 同一天第二次犯同族错误（2026-10-24 13:10，由契约清偿会话抓出）**：
> 我用 `git grep -c '@(Get|Post|...)Mapping'` 数实现侧端点，得 134、缺口 44，并把 44 写进了本文。
> 契约清偿会话指出：`AuditAspect.java:102` 的 javadoc 里有一句 `* 只写 {@code @GetMapping}` ——
> **那是注释文本**。真实端点是 **133**，缺口是 **43**（且与 `UNDOCUMENTED_DEBT` 的 43 条三向一致）。
>
> 两次错误同一个根因：**用"字符串出现次数"代替"语法结构计数"**。
> 正确做法：编号锚定 `@CaseId\("(TC-...)"\)`；端点用行首 `^\s*@(Get|Post|...)Mapping`，
> 或直接问 Spring 的 `RequestMappingHandlerMapping`（运行时注册表是唯一权威）。
> **这条已记入坑表 24。**
> 否则会把"文档引用"误判成"撞号"，进而在错误的方向上浪费排查时间。
> 这条与我 M2 批次那次"把两泳道都用了 TC-API-016"的真实事故不同 —— 那次是真撞，
> 这次是**统计方法的假阳性**。两者都要防，但防法不同。

### 0.3.1 ★ INV-15 的"自动扩展"——门禁价值的实证（值得写进答辩）

**现象**：V2-5 交付时，写接口是 **42 个**、审计覆盖 42/42。
V2-5 合并进 main 后（此时 V2-1/V2-2/V2-4 也已在主线上），写接口变成 **59 个**（采购闭环带来了 17 个）。
**INV-15 仍是 59/59 全绿，V2-5 没有改一行代码、没补一条用例。**

**为什么这不是巧合**：

INV-15 的实现方式是 —— 从 Spring 的 `RequestMappingHandlerMapping` 取**运行时真正注册**的写接口，
逐个发**真实请求**，断言 `audit_logs` 里出现对应记录。

```java
// 不是解析源码文本（会漏掉组合路径、条件映射），而是问 Spring：你到底注册了哪些？
var endpoints = mapping.getHandlerMethods().entrySet().stream()
    .filter(e -> WRITE_METHODS.contains(method) && !isTestBackdoor(path))
    ...
```

于是它**自动具备了两个方向的价值**：
- **正向**：任何人新增写接口 → 枚举器自动把它纳入 → 审计没覆盖就红；
- **负向**：枚举器自己被改坏（漏掉写接口 / 把 GET 算成写接口 / 把后门算进来）→ `TC-SYS-030` 抓住它。

> **答辩话术**：这条门禁不是"我写了 42 个断言"，而是"**我写了一条会随系统增长自动变强的断言**"。
> 加 17 个接口不用改测试，它自己就跟上了 —— 这才是"用测试守架构"，而不是"用手工清单守架构"。

**对照参考系统**（`瓶装气进销存系统`）：它有 83 个端点、零自动化测试，
所以"某个写接口忘了留痕"这类问题只能靠人肉发现。**这正是我们的质量面领先的地方。**

### 0.3.2 V2-5 修掉的那个空断言（一次真实的"假绿"捕获）

我指出 `TC-SYS-031` 是空断言后，V2-5 的修法与验证过程本身值得记录：

### 0.3.3 ★ 契约欠账正在累积（架构级退步，必须优先处理）

**实测（`71e8937`，V2-6 合并后；2026-10-24 13:10 三向交叉复核）**：

| 项 | 阶段 0 前 | 现在 |
|---|---|---|
| 实现侧接口映射 | 68 | **133** |
| 契约操作 | 50 | **90** |
| **缺口（实现有、契约无）** | 18 | **43** |
| 契约覆盖率 | 73.5% | **67.2%** |

**这不是数字问题，是架构原则在失效**：

`ADR-0008` 说 **OpenAPI 是单一事实源**，它驱动四样东西：
① 服务端接口骨架 ② 三端 SDK ③ 契约测试 ④ Schemathesis 属性测试。

现在 43 个接口不在契约里 → 这四样**全都覆盖不到它们**：
- 前端 TS 类型无法从契约生成（只能手写，必然漂移）；
- 契约测试（`ApiContractMappingIT` 的 `CONTRACT_ONLY` 方向）看不见；
- Schemathesis 属性测试只测契约里的 90 个操作，另外 43 个**零模糊测试**。

**根因**：并行泳道为了"不抢契约 owner"，把新接口登记进 `UNDOCUMENTED_DEBT` 就往下走。
一次登记是合理的妥协，**但 5 条泳道 × 各自登记 = 欠账复利**。

**欠账构成**：

| 来源 | 条数 |
|---|---|
| 历史（M0~M3 期） | 17 |
| V2-6 权限/审批 | 26 |
| 合计 | **43** |

**处置（必须做，不能继续欠）**：
1. **开一条专门的"契约清偿"泳道**（`feat/v2-contract-payoff`），把 43 个接口一次性写进 `openapi.yaml`；
2. 清偿后 `UNDOCUMENTED_DEBT` 必须**清零**，`ApiContractMappingIT` 双向全绿；
3. **从此规则**：新接口**必须在同一个 PR 里进契约**，不许只登记债务。
   理由：债务登记机制原本是为"历史遗留"设计的，不是为"新开发"开的后门。

> **这条比再加一个功能重要得多**。答辩时"契约是单一事实源"是要被追问的；
> 如果那时有 43 个接口不在契约里，这句话就站不住。

### 1.5.4 合并顺序（并行会带来新的合并顺序问题）

并行会话交付**时间不一**，合并不再是固定顺序，改为**按风险动态排序**：

| 优先级 | 情形 | 处理 |
|---|---|---|
| 1 | 交付的分支**只新增目录/文件**（如 `infra/standalone`、`com/erp/sys`） | 随时可合，先合它 |
| 2 | 交付分支**改契约** | 等其它分支合完再合（契约是唯一事实源，最后落） |
| 3 | 交付分支**改共享文件**（`ArchitectureTest`、`application.yml`、`InventoryApplicationService`） | 逐个合、每合一个跑全量 |
| 4 | 两个分支都改了同一文件 | **合一个、跑全量、再合另一个**，不许连合两个再跑 |

> ★ **铁律**：任何时候只有**一个会话**在跑 `gradlew check`（它们各用各的 ASCII 联接与 build 目录，
> 所以技术上可并行，但**合并后的全量验收必须串行**，否则 build 目录互踩 —— M2 批次记录过这次事故）。

### 1.5.5 首批并行实测：三个共享热点（★ 合并前必须知道）

> 2026-10-23 23:34 六泳道同时开工后，我扫了全部 worktree 的改动文件，得到这张**共享文件表**。
> 它决定了合并顺序与"能不能自动合"。

| 共享文件 | 谁在改 | 合并难度 |
|---|---|---|
| `com/erp/inv/application/InventoryApplicationService.java` | **V2-1 / V2-2 / V2-3** | ★★★ 最危险（三家同时改核心库存入口） |
| `com/erp/shared/document/DocumentNumberGenerator.java` | V2-1 / V2-2 / V2-3 | ★★ 中（都是"加单号前缀") |
| `com/erp/shared/error/ErrorCode.java` | V2-1 / V2-2 / V2-3 / V2-6 | ★★ 中（都是追加枚举） |

**由此定下的写法约束（已下发给全部泳道）**：
1. `ErrorCode.java` **只追加**，追加到自己模块分组末尾，**禁止重排现有行**；
2. `DocumentNumberGenerator` 只在**自己的前缀常量区**追加，不改既有逻辑；
3. `InventoryApplicationService` 是**唯一允许三家都改**的文件，但必须遵守：
   - 每人只**新增方法**，不改既有方法签名与实现；
   - 新方法追加在类末尾，不插在中间；
   - 若要改既有方法 → **必须先报指挥台**，由指挥台决定谁拿到这次修改权。

**为什么这条比"写好代码"更重要**：合并顺序不可控（谁先交付谁先合），
只有"纯追加、不动既有行"的部分 git 才能自动合；任何重排都会让后面所有人手工解冲突，
而手工解冲突时最容易发生的事故是**丢掉一侧的改动**（M2 批次记录过）。

## 5.5 并行协作的实战教训（2026-10-23 首批并行）

> 首批三会话并行开工当天就出了一次事故，记在这里，后面每一批都要防。

### 5.5.1 事故：指挥侧的文件被清场会话"收拾工作区"时冲掉

**经过**：
- 指挥会话在主工作区改了 4 个文档（`README` / `docs/00` / `docs/01` / `总纲`），尚未提交；
- 清场会话在同一工作区执行合并，为保持工作区干净，把这些改动 `git stash` 了，并 `git reset`；
- 幸而它**正确地 stash 了**（`stash@{0}`，4 文件 / +90 行），没有直接 `checkout .` 丢弃。

**如果它当时用 `git checkout .` 或 `git reset --hard`**，一天的规划文档就没了。

### 5.5.2 由此定下的两条硬规矩

1. **指挥侧改完文档，立刻单独提交**，不要留未提交的工作区改动。
   > 指挥会话的提交只含 `docs/`、`.plan/`、`README`，**不碰代码**，因此不会与任何泳道冲突。
2. **派发"清场/合并"类会话时，提示词必须写明**：
   ```
   不要执行 git checkout . / git reset --hard / git clean -fd。
   若工作区有未提交改动，用 git stash push -m "<说明>" 保存，并在报告里告知。
   未跟踪的 .plan/ 与 docs/planning/ 新文件不要删除、不要提交。
   ```
   本次漏了这条，靠对方自觉才没出事 —— 下次写进模板。

### 5.5.3 并行泳道的"健康信号"

| 信号 | 含义 | 本次实测 |
|---|---|---|
| 该泳道自己的 PG 容器已起（`erp-v25-pg` / `erp-v26-pg`） | 已进入开发 | V2-5 ✅ 已起 |
| worktree `git status` 出现新文件 | 正在写代码 | 启动初期为 0 属正常 |
| 长时间 `git status` 为空 **且** 无 PG 容器 | 可能卡在阅读/环境，需询问 | — |

### 5.5.4 合并会话与开发会话的隔离边界

| 会做 | 不会做 |
|---|---|
| 合并会话：`git merge` / 跑全量 `check` / 改 `docs/00` 与 `README` | ❌ 改任何业务源码 |
| 开发会话：写自己模块的代码 + 测试 + 迁移 | ❌ 碰主工作区、碰别人的 worktree、改 `docs/00` |

> **唯一例外**：契约 owner（本批是 V2-5）可以改 `openapi.yaml`，但只在**自己的 worktree** 里改，
> 由合并会话在合并时统一落盘。

### 11.2 契约操作数的"游标"机制

> 契约不是"谁都能追加"就安全 —— main 前进后，**后合的分支会拿着旧基线的 paths 去合，必然冲突**。
