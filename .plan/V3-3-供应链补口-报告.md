## 2. 四个"后端已有"控制器的真实接口签名（grep 实测）

**PurchaseReturnController** `/api/v1/purchase-returns`（pur:read/create/approve/void）
- `GET ?status=&supplierId=&purchaseOrderId=&page=&size=` → ApiResponses.page
- `GET /{id}`；`POST`（头 X-Request-Id，体 `{purchaseOrderId, bizDate?, remark?, lines:[{receiptLineId, qty≥1}]}`）——批次/单价/金额全部后端从到货记录派生
- `POST /{id}/approve`（扣库存+冲应付）、`POST /{id}/void`；状态机 DRAFT→COMPLETED/VOIDED
- 退货行的 receiptLineId 来源：`GET /api/v1/purchase-orders/{id}/receipts`（PurchaseReceipt.lines[].id）

**ProductBundleController** `/api/v1/product-bundles`（sal:read / sal:bundle）
- `GET ?keyword=&onlyEnabled=&page=&size=`；`GET /{id}`
- `POST {code(2-32), name, priceAmount(分,Long), enabled, items:[{componentSkuId, ratioQty≥1}]}`；`PUT /{id}` 同构
- `POST /{id}/disable`；`GET /{id}/availability?warehouseId=` → `{availableQty=min(组件可用÷配比), components[]}`（套装无库存行，INV-16）

**CreditController** `/api/v1/customers/{id}/credit`（注意：权限是 **mdm:read / mdm:write**，不是 sal:*）
- `GET` → `{customerId, creditLimit(分), creditDays, exposureAmount, availableCredit(-1=不设限), overdueAmount, snapshotDate}`
- `PUT {creditLimit(分,≥0), creditDays(≥0)}`；creditLimit=0 即"不设限"

**ReportAdvancedController** `/api/v1/reports`（全部 rpt:read，只读）
- `GET /operating?from&to&dimension?&warehouseId?` → items[{period, opening/inbound/outbound/closingQty, purchaseQty/Amount, salesQty/Amount}]
- `GET /inventory-turnover?from&to&deadDays=30&warehouseId?` → items[{skuCode, warehouseName, turnoverDays, idleDays, stale}]
- `GET /customer-contribution?from&to&limit=20` → `{items, summary{repurchaseRateBp…}}`
- `GET /aging?type=AR|AP&asOf` → `{items{bucket0..3}, summary}`；金额分口径（fenToYuan 展示）

**库存洞察（意外发现已存在）**：`GET /api/v1/inventory/alerts?warehouseId=&type=&expiringDays=&slowMovingDays=`、
`GET /api/v1/inventory/replenishment?warehouseId=`（V2-1，inv:read，纯查询幂等）。AlertType 只有 SAFETY/SLOW_MOVING/EXPIRING。

## 3. 取价优先级与补货公式（最终实现口径）

- 取价（`PricePlanApplicationService#resolvePrice`，类注释同款）：
  `AGREEMENT 协议价 > CUSTOMER 专属价 > CUSTOMER_LEVEL 等级价 > skus.retail_price_amount 标准售价`；
  同类型内 priority 降序 → planId 升序；明细 `min_qty>qty` 跳过；生效价 = price_amount × discount_bp ÷ 10000（long 四舍五入，禁 double）。
  冒烟实测：AGREEMENT(7777) 覆盖 CUSTOMER_LEVEL(8888@9000bp=7999) → 返回 AGREEMENT_PRICE ✓；无客户→STANDARD_PRICE ✓。
- 补货（`com.erp.inv.domain.ReplenishmentFormula` 纯函数 + 5 例单测全过）：
  在途>0 不建议；可用≥min 不建议；建议量=max−可用，≤0 不建议。
- **金额口径**：PRM 全部用"分"(BIGINT)与"万分比"(discount_bp)，与 sal 报价/出货/套装/信用一致；页面输入元、提交×100。

## 6. 踩的坑（新增 3 条）

1. **`jdbc.query(sql, rs -> …)` 单参 lambda 是 ResultSetExtractor**：拿到的是游标初始位，不 `while(rs.next())` 就报"查询结果指标位置不正确"；且 `query(sql, rse)` 不传 varargs 会静默编译过、运行期"参数缺失→syntax error at end of input"。两处都是编译绿、冒烟红。
2. **`(? IS NULL OR col = ?)` 在 PG 对无类型绑定必炸**（`could not determine data type of parameter $1`）——既有 `/inventory/alerts|replenishment` 不带 warehouseId 时 500 是**V2-1 存量 bug**，本次以 `?::bigint` 修复（inv 在我所有权内）。
3. Windows curl 发中文 JSON 走 GBK 字节 → Jackson "Invalid UTF-8 middle byte"：冒烟脚本一律 ASCII；前端 axios 是 UTF-8 不受影响。
（复用旧坑：tenant_id 可空、显式列清单不用 SimpleJdbcInsert、timestamptz 不直接 getObject(LocalDateTime)、迁移全 IF NOT EXISTS 可重放。）
