## 8. 实测踩过的坑（每一条都是红灯换来的）

### 8.1 纯开关的"重放信号"不能取自幂等键，要取自状态本身

第一版停用判重放用的是 `WHERE id = ? AND (disable_request_id IS NULL OR disable_request_id IS DISTINCT FROM ?)`，
即"这一行已经带着这个键 → 判为重放"。**`TC-MDM-033` 把它打死了**：
停用 → 别人用 PUT 重新启用 → 原键再来，此时接口返回 `enabled=true` 却自称成功。
一次真实的"再停一次"被幂等键藏掉了。
改成 `WHERE id = ? AND enabled`：0 行的唯一含义就是"没有可改的"，这才是正确的重放信号；
键仍然记（`uq_*_disable_request`），但只用来拦"同一个键打到两个不同资源"（`TC-MDM-035/041` → 409）。

### 8.2 无副作用的重放必须打标记，否则审计切面照写一条

`AuditAspect` 在 Controller **外层**，只看"是不是写请求"。停用走"已是停用态 → 直接返回"这条
无写入分支时，我一开始没打重放标记，于是 `audits(...,"DISABLE",id)` 拿到 2 而不是 1
（`TC-API-090/091/092` 三条首跑全红）。现在仓储返回 0 行 → 服务立刻打标记 → 切面跳过留痕。

### 8.3 `ON CONFLICT` 那套并发写法会让覆盖率跌破基线

第一版按 `InventoryTransferRepository` 的 `ON CONFLICT DO NOTHING RETURNING id` + 抢输后回查实现，
新增了一个返回 `Optional<Long>` 的平行 insert。首跑 `check` 后读 jacoco：
**行 86.47% < 基线 86.55%**（分支反而升到 65.43%）。原因是那几个"抢输后回查"分支
在单线程测试里根本无法确定性触发 —— 5 处永久不可覆盖的行把比例拉了下去。
改用 `PurchaseRequisitionApplicationService` 那派"先查后插 + 唯一索引兜底"后，
新增行只剩 `throw ex;` 这类与既有代码同形的兜底重抛，行覆盖率回到 86.86% > 基线（见 §4）。

**代价说清楚**：同键并发双击的创建请求，抢输的那个拿到 409 `SYS_DUPLICATE_REQUEST` 而不是首次结果。
数据正确性不受影响（唯一索引保证只有一行），`purchase_orders` 建单今天就是这个行为。

### 8.4 验收项"重放不重复推进单号序列"对 MDM 恒真，我加了正向对照

事实纠正：MDM 的 5 个创建流程**从来不占单号** —— `code` 由调用方给定，由 `uq_*_code` 唯一约束管，
SKU 连 code 都没有（靠 `uq_sku_variant`）。整个 `com/erp/mdm/**` 对
`DocumentNumberGenerator` / `document_sequences` / `numberGenerator` 的 grep 结果为空。
所以"不推进序列"这条断言对 MDM 是恒真的，不是一条会红的防线。
我没有删它（它能拦住"将来有人改成用序列生成 MDM 编码"的回归），但在 `TC-MDM-036` 里加了正向对照：
先证明 5 次 MDM 写入前后指纹不变，再**直接调一次** `numbers.next(PURCHASE_ORDER, 2026-10-24)`
证明同一个指纹在真的进位时会变。否则这块只是一个会绿的死代码。

### 8.5 给既有用例补幂等头：字面量 id 被循环/夹具复用，测试自己吃掉了被测行为

34 处补齐后首跑全量 `check`：`tests=951, failures=4`。

| 失败 | 根因 |
|---|---|
| `MasterDataApiIT.product_paging`（items 期望 2 得 1） | 循环里的同一行源码用了同一个字面量 id → 第二次成了真重放 |
| `AuditQueryIT.filterByAction`（CREATE 审计期望 2 得 1） | 夹具方法 `createProduct()` 被调用两次，同一行源码同一个 id |
| `MasterDataApiIT.supplier_crud` / `warehouse_listAndFilter`（期望 200 得 400） | `post("/api/v1/suppliers/" + id + "/disable")` 是**拼接路径**，第一版正则只认整串字面量，把它们漏了 → 现在缺头 = 400 |

改法：统一 `.header("X-Request-Id", UUID.randomUUID().toString())`（每次调用必然唯一），
并把拼接路径纳入匹配。6 个文件补 `import java.util.UUID;`。
★ 没有改动任何被测语义，只补请求头。

### 8.6 MockMvc 响应体默认按 ISO-8859-1 解码

`TC-MDM-027` 首跑断言 `name` 相等，拿到的是 `æ94¹å...` 形态的乱码 ——
`MockHttpServletResponse.getContentAsString()` 用响应的 characterEncoding（Spring 写 JSON 时不带 charset）。
测试里显式 `getContentAsString(StandardCharsets.UTF_8)`。
`jsonPath(...)` 匹配器与只取数字的路径不受影响，所以只有拿中文字符串做比对的用例会炸。

### 8.7 幂等插入不能丢掉"编码重复 → 409"的翻译

拆分出平行 insert 方法时，`uq_*_code` 的 catch 没跟过去，重复编码会从 409 退化成 500，
而 `MDM_CODE_DUPLICATED` 是契约写明的响应。现在编码翻译与幂等键翻译串在同一个 catch 里，
`TC-MDM-030` 专门钉住"幂等键不稀释编码唯一"。

### 8.8 只有 8 个端点能改，多一个就反向报错

`/skus/matrix`、`/skus/{id}/disable`、`/products/{id}/disable` 契约里**没有**声明 `RequestId`。
给它们加头，门禁会从"契约声明、实现不消费"翻成"实现消费、契约没声明"，
残留错误从 0 变 4。改完后我重数了一遍输出，不是"看起来差不多"。

### 11.3 一个必须说出来的发现：原有两条"看起来相关"的用例抓不到这个漂移

注入漂移的那一次，**26 条里只有 `TC-MDM-042` 变红**，`TC-API-090` 与 `TC-API-094` 全绿。
原因是这两条都按 `(resource_type, action, resource_id)` 过滤计数，而兜底过滤器的
`resource_id` 取自 **URI 末段的纯数字**：`/warehouses` 末段是 `warehouses`、
`/warehouses/42/disable` 末段是 `disable`，都不是数字 → 兜底行的 `resource_id` 是 **NULL**，
过滤条件根本匹配不上。

所以 `TC-MDM-042` 用的是**不筛维度的总行数差值** + 第二道网
`result='FAIL' AND error_code LIKE 'HTTP%'` 必须为 0。
这也回答了指挥第 2 条要求：首次调用恰好 1 行、重放 0 行新增 ——
断言方式是计数（`COUNT(*) FROM audit_logs`），全程没有对 `audit_logs` 做任何 DELETE/UPDATE
（append-only 触发器会拦，也不该绕）。
