## 3. 80/443 决策（回答“我没有删除，直接拒绝授权，可以吗？”）

**可以，而且应该保留。** 原因：

1. **80 正在给主页作品集提供服务**。删掉 80 规则，`http://8.163.96.61/` 立刻不可访问，主页打挂。
2. **443 是后续 `xuliu` / `lancang` HTTPS 的入口**，现在开着不碍事；没有对应 vhost 时，访问 443 不会返回任何业务内容。
3. **备案审的是“域名 → 解析到服务器 → 网站内容”**，不是“安全组有没有开 80”。只要 **新子域名不解析**、不提前对外提供新网站，80/443 开着不影响备案。
4. 我之前建议删 80/443，是基于“服务器上还没有任何网站”的假设；你这台有主页，前提不成立，**那条建议作废**。

**保留 80/443 后仍要守的三条：**

- `xuliu.zemworld.cn` / `lancang.zemworld.cn` 在备案确认前**不加 DNS A 记录**；
- 不提前加这两个子域名的 Nginx server 块对外（预览用 `curl -H 'Host: ...'` 或本机 hosts）；
- 18080 / 15435 / 8080 继续对公网关闭（已实测不可达，保持）。

> 如果备案审核期间阿里云明确要求“网站关闭”，只处理**新子域名对应的 site**，主页作品集不受影响；不要动 `zemworld.conf`。

## 6. 2C2G 运行与运维

### 6.1 资源预算

| 组成 | 预估 |
| --- | --- |
| OS + 宿主 Nginx + 基础进程 | 350~450MB |
| Docker daemon + 网络 | 80~120MB |
| PostgreSQL（shared_buffers 128MB） | 150~250MB |
| Spring Boot（Xmx512m + metaspace） | 600~900MB |
| Web Nginx | 20~40MB |
| **合计** | **约 1.2~1.7GB** |

- 2G swap 已加，`vm.swappiness=10`；不加 Redis/RabbitMQ/Prometheus。
- 监控：`free -m`、`docker stats --no-stream`、`dmesg -T | grep -i oom`；OOM 先降堆/停服务，不硬扛。
- 若仍 OOM：公网退回静态演示，真实云裳回本机 standalone；不升级服务器。

### 6.2 ★ 部署脚本与 2G override 的缺口（必须补）

`scripts/lib/deploy-common.sh` 只加载 `docker-compose.prod.yml`，**不认识 `docker-compose.2g.yml`**。
如果直接跑 `./scripts/deploy.sh --no-build`，会丢掉 `mem_limit` 与 PG 参数，2C2G 上风险变大。

二选一（建议 A）：

- **A. 给 `deploy-common.sh` 加一个可选 `COMPOSE_EXTRA_FILES`**（从 `.env` 读），`compose()` 拼上 `-f`；
  然后 `.env` 写 `COMPOSE_EXTRA_FILES=infra/deploy/docker-compose.2g.yml`。
- **B. 不用 deploy.sh**，统一手工：
  ```bash
  cd /opt/erp
  docker compose --env-file infra/deploy/.env \
    -f infra/deploy/docker-compose.prod.yml \
    -f infra/deploy/docker-compose.2g.yml \
    up -d --no-build
  ```
  回滚/重启也必须带两个 `-f`，不能只带 prod。

同时把 `infra/deploy/docker-compose.2g.yml` 提交进 Git，避免下次部署丢文件。

### 6.3 日常命令（服务器）

### 14.1 工作台「后端不可达」的根因与修复（13:19 上线 `prod-20261029-r2`）

- 现象：已登录的 `/dashboard` 上状态面板报「后端不可达 + 数据库异常」，但业务接口全通。
- 根因：`SystemStatusPanel.vue` 探的是 `/actuator/health`。该路径**在生产根本不存在** ——
  web 容器 nginx 只反代 `/api/` 与 `/readyz`（`/readyz` → `backend/actuator/health/readiness`），
  宿主 nginx 还额外把 `/actuator` 整段 404。所以面板在任何生产部署下都必红，是缺陷不是故障。
- 修复：改探 `/readyz`；`show-details=never` 拿不到 `components.db` 时按就绪组整体状态回退（就绪组本身含 db 指示器），
  不再谎报「异常」。文案同步为「/readyz 就绪探针」。
- 验证：线上产物 `DashboardView-*.js` 内 `actuator/health` 命中 0、`readyz` 命中 1；
  浏览器同源实测 `/readyz` 200 `{"status":"UP"}`、`/actuator/health` 404、`/api/v1/auth/login` 401。

### 14.2 本轮踩到的两个坑（要记住）

1. **`IMAGE_TAG` 是 backend 与 web 共用的**：只重建 web 会让 `compose up` 找不到 `erp-backend:<新tag>` 而**整次中止**，
   且 `readyz` 仍 UP（旧容器还在），极易误判成功。每次换 web 镜像必须同时 `docker tag` backend 到新 tag。
2. **覆盖层 Dockerfile 不能放在 `dist/` 里**：`vite build` 会清空 outDir，文件会被删掉，
   `docker build -f` 读到 2 字节空文件后报 `failed to read dockerfile`。已改放仓库外
   `D:\MajorCacheFolder\erp-web-overlay.Dockerfile`。
