## 2. 设计与关键决策

### 2.1 方案 (b)：业务表自带 request_id 列，而不是通用 `idempotency_keys` 表

三条理由，按分量排：

1. **重放必须返回资源的当前状态，而不是当时的响应快照。**
   通用表要兑现"返回同一个结果"就得缓存 `response_body`，于是：
   建好仓库 → `PUT` 改名 → 客户端重放原 `POST` → 缓存吐回**改名前**的 body，
   调用方据此以为改名没成功。方案 (b) 回查实体表，永远拿到当前值。
   这条不是假想缺陷，`TC-MDM-027` 就是把它钉成用例（改名后重放，断言返回新名字）。
2. **守卫与它保护的数据同生共死。** 守卫行与业务行分处两表时，"守卫写了、业务没写"
   这个缝隙需要额外的事后才可发现；同表同事务不存在这个缝。
3. **与既有实现同构。** `purchase_orders.request_id`（V2）、
   `purchase_orders.conversion_request_id`（V10）、`inventory_transfers.request_id`（V9）
   全是"业务表列 + 局部唯一索引"。指挥会话指定的参考写法也正是这条。

顺带说明为什么**不复用现成的休眠表 `idempotency_keys`**（V1 建、V2 加 `result_ref`，
全项目无任何 Java 代码读写它）：它的主键是**全局** `request_id`，
意味着"同一个键打到两个不同端点"会变成硬冲突。本项目前端每个请求生成一个新 UUID，
但把键的命名空间绑在全局上会让将来的批量导入极其脆弱。
方案 (a) 自己也是 `UNIQUE(resource_type, request_id)` —— 即按资源类型分namespace。
方案 (b) 天然按表分 namespace，语义等价，代码更少。`TC-MDM-038` 钉住这个语义。

### 2.2 为什么守卫必须是数据库唯一索引

契约门禁的判据是"读实现"，但幂等正确性的判据是"重启后还成不成立"。
进程内缓存承担幂等时：客户端重试恰好撞上发布/重启窗口 → 建出两行 →
而这件事在开发机上**永远看不到**（没人会在测试中途 `kill -9`）。

所以 V15 给 8 个端点各建一条**局部唯一索引**（`WHERE ... IS NOT NULL`），
并专门写 `TC-MDM-028`：绕过应用层、直接对仓储第二次 `insert` 同一个键，
断言它被 `uq_warehouse_create_request` 拦住并翻成 `SYS_DUPLICATE_REQUEST`。
"拦住它的是索引，不是 Java 里的 if" —— 这条用例就是重启语义的证明。

`IS NOT NULL` 谓词的作用：这三列对迁移前的存量行和无键的内部写入全是 NULL，
局部索引①只覆盖真正参与幂等的少量行，②把"NULL 不参与唯一性"写成声明而不是依赖 PG 默认行为
（`TC-MDM-029` 断言 8 条索引的存在与谓词，`TC-MDM-032` 断言无键写入彼此永不冲突）。

### 2.3 创建型：先按键回查 + 唯一索引兜底（照 pur，不是照 inv）

```
findByRequestId(key) 命中  → 打重放标记，返回已有那一行
未命中                    → 带着键 insert → 并发抢输时唯一索引拦住 → 409 SYS_DUPLICATE_REQUEST
```

我最初写的是 `inv` 那一派的 `ON CONFLICT DO NOTHING RETURNING id` + 抢输后回查
（它能做到"并发下也返回同一个资源"而不是报错），后来**主动改成了 pur 一派**，理由有三：

- 指挥会话指名照 `PurchaseRequisitionApplicationService.findByRequestId(...)` 的现成写法；
- `ON CONFLICT` 版本需要新增一个返回 `Optional<Long>` 的平行 insert，
  与既有 `long insert(...)` 并存 —— 两份几乎一样的 SQL，是未来的漂移源；
- 那一派的并发回查分支在单线程测试里无法确定性地触发，会留下 5 处永久不可覆盖的代码，
  而本泳道的覆盖率门限贴着基线（见 §4）。

**已知取舍**：同键并发双击的两个请求里，抢输的那个拿到 409 而不是首次结果。
数据正确性不受影响（唯一索引保证只有一行），客户端按契约把 409 当"重试已在飞行中"处理即可。
`purchase_orders` 建单今天就是这个行为。

### 2.4 纯开关：状态自身幂等 + 键只做归属

```
UPDATE ... SET enabled = FALSE, disable_request_id = ? WHERE id = ? AND enabled
```

`AND enabled` 是关键：**已经是停用态时更新 0 行**，于是重放自然没有任何副作用
（`updated_at` 不推后 —— 否则连续点击会让"最后一次改动"看起来刚发生，
而实际什么都没变，运维按"最近改动时间"排查时会被误导）。0 行由应用服务判为重放。

这一版是**改出来的**，不是第一版。第一版我用
`WHERE id = ? AND (disable_request_id IS NULL OR disable_request_id IS DISTINCT FROM ?)`
把"本行已带该键"当作重放信号 —— `TC-MDM-033` 把它打死了：
停用 → 别人重新启用 → 原键再来，那是一次**真实**的状态变更，
被我当成重放吞掉后接口回了 `enabled=true` 却自称成功。
幂等键不该把一次真实的"再停一次"藏起来，这是会漏进生产的那类 bug。

键仍然要记：`uq_*_disable_request` 拦住"同一个键打到两个不同资源"（`TC-MDM-035` → 409）。
那种情况若按状态返回"已停用"是错的 —— 第二个资源根本没被停过。

### 2.5 重放不留第二条审计：`com.erp.shared.idem.IdempotencyReplay`

`AuditAspect` 的既有契约是"**每个写请求恰好一条审计**"，它只看 HTTP 方法是不是写操作，
分不清"真的建了一行"和"重放拿回已有的那一行"。验收要求"重放不重复产生审计流水"，
两者必须握手。做法是 1 个字节宽的标记：

- 守卫命中时，应用服务调 `IdempotencyReplay.markCurrentRequest()`；
- 切面在 `proceed()` 之后读到标记 → **跳过留痕**，但仍然打一条 INFO 日志（可观测性没有黑洞）；
- 标记放在 **request attribute** 而不是 ThreadLocal：生命周期由容器管，
  ThreadLocal 要每个出口（异常/异步/线程池复用）都记得清理，
  漏一处就把"上次是重放"泄漏给下一个复用该线程的请求，
  表现为随机的"审计少了一条"且几乎无法复现。

blast radius 控制到最小：
- 架构规则"审计模块只依赖 shared 与 IAM 注解" —— 标记类放 `com.erp.shared.idem`，合法；
- 切面的新分支**只在标记存在时生效**，而标记只有 MDM 的 8 个守卫会打。
  `pur`/`inv` 等其它模块的行为**一个字节都没变**（它们今天的重放仍会留 2 条流水）；
- ★ 跳过留痕时**必须**照样置 `AuditSafetyNetFilter.AUDITED_ATTR`，
  否则兜底过滤器会以为"切面没跑"，补一条 `result=FAIL` 的审计 ——
  一次成功的重放被记成失败，那比重复更糟。

### 2.6 前端不需要改（已核实）

`frontend/web/src/api/client.ts:89` 与 `frontend/miniapp/src/api/client.ts:227` 的请求拦截器
都给 `post/put/patch/delete` 注入 `X-Request-Id`，取值 `crypto.randomUUID()`（36 字符，
落在契约的 `minLength 8 / maxLength 64` 内）。本泳道没有触碰这两个文件，
也没改动任何前端代码；`TC-API-093` 从后端侧钉住"缺头/空头一律 400"，
即前端拦截器一旦失效就会立刻暴露，而不是静默建出重复数据。

### 关于第 6 步（必要的一致性代价，不是范围扩张）

`@RequestHeader` 默认 required，因此**任何**不带头的调用都会 400。契约早就写着
`RequestId` 是 `required: true`，前端拦截器也一直在发 —— 是这 8 个实现一直缺席。
补齐实现后，既有 34 处不发头的测试请求必然 400。这属于"实现追上契约"的应有代价，
且全部落在**测试夹具**层（给请求补一个唯一键），没有改动任何被测语义。

★ 补的键**每次调用都必须唯一**。我第一版按 `@CaseId` + 出现序号生成字面量
（`tc-api-002-1` / `-2`），跑出来 3 条回归：同一行源码可以被 `for` 循环或夹具方法执行多次，
id 一复用，本来"两次普通写请求"的第二次就被判成了幂等重放 ——
`product_paging` 少一行、`AuditQueryIT.filterByAction` 少一条审计。
现在统一用 `UUID.randomUUID().toString()`：测试夹具要的只是"这是一个正常写请求"，
唯一性由 UUID 保证，不依赖源码行的出现次数。
另有一类调用 `post("/api/v1/warehouses/" + id + "/disable")` 是**拼接路径**，
第一版的正则只认整串字面量，把它们全漏了 → 那些请求现在缺头发 400。

证明同一个指纹在真的进位时**会变**。否则这条用例是一块只会绿的死代码。

## 5. 踩过的坑（都付过时间）

1. **`ON CONFLICT` 版与"先查后插"版不是一回事，选错会留不可覆盖的行**。
   见 §2.3：换回 pur 一派后代码更少、更贴指定风格，也更贴覆盖率门限。
2. **幂等插入必须保留"编码重复 → 409"的翻译**。
   第一版把 insert 拆成独立的 `insertIdempotent`，`uq_*_code` 的 catch 没跟过去，
   重复编码会从 409 退化成 500 —— 而 `MDM_CODE_DUPLICATED` 是契约里写明的响应。
   现在编码翻译与幂等键翻译在同一个 catch 里串起来。
3. **`WHERE ... IS DISTINCT FROM 键` 当重放信号是错的**（§2.4）：
   它把"停用后被重新启用、再用原键"这次真实变更吞成了重放，接口回 `enabled=true` 却自称成功。
   `AND enabled`（状态自身幂等）才是正确的信号源。
4. **跳过审计留痕时必须照样置 `AUDITED_ATTR`**（§2.5），否则兜底过滤器补一条 FAIL。
5. **MockMvc 响应体默认按 ISO-8859-1 解码**：`getContentAsString()` 把中文读成乱码，
   `TC-MDM-027` 首跑就挂在这里。测试里显式用 `getContentAsString(StandardCharsets.UTF_8)`。
   （`jsonPath(...)` 匹配器与只取数字的路径不受影响，所以只有拿中文字符串比对的用例会炸。）
6. **给既有用例补幂等头时，键必须"每次调用唯一"而不是"每行源码唯一"**（详见 §3 第 6 步）：
   循环与夹具方法会让同一行源码执行多次，字面量 id 一复用就把普通写请求变成了真重放。
   另外拼接路径（`post("/api/v1/warehouses/" + id + "/disable")`）不是整串字面量，
   按字面量匹配的正则会把这类调用整体漏掉 —— 漏掉的后果是那些请求现在拿到 400。
7. **`@NotBlank` 加在 header 参数上确实会拦空值**（Spring 6.1 的方法级校验 →
   `HandlerMethodValidationException` → 已有 handler 翻成 400），
   不需要给 Controller 补 `@Validated`。`TC-API-093` 同时钉住"缺头"与"空值头"两条路径。
8. **只有 8 个端点能改**。`/skus/{id}/disable`、`/products/{id}/disable`、`/skus/matrix`
   契约里**没有**声明 `RequestId`；多给任何一个加头，门禁就反向报错，
   错误数从 0 变 4。改完后我重新数了一遍，不是"看起来差不多"。

## 6. 回滚方式

改动是**纯追加**的，回滚成本按层递增：

1. **代码层**：`git revert` 本泳道的提交即可（实现、迁移、测试各为独立提交）。
2. **数据库层**（若已应用到某个库，需要单独降级脚本，Flyway 不会自动往下走）：
   ```sql
   DROP INDEX IF EXISTS uq_warehouse_create_request, uq_supplier_create_request,
        uq_customer_create_request, uq_product_create_request, uq_sku_create_request,
        uq_warehouse_disable_request, uq_supplier_disable_request, uq_customer_disable_request;
   ALTER TABLE warehouses DROP COLUMN IF EXISTS create_request_id, DROP COLUMN IF EXISTS disable_request_id;
   ALTER TABLE suppliers  DROP COLUMN IF EXISTS create_request_id, DROP COLUMN IF EXISTS disable_request_id;
   ALTER TABLE customers  DROP COLUMN IF EXISTS create_request_id, DROP COLUMN IF EXISTS disable_request_id;
   ALTER TABLE products   DROP COLUMN IF EXISTS create_request_id;
   ALTER TABLE skus       DROP COLUMN IF EXISTS create_request_id;
   ```
   这些列没有任何外键、没有默认值、不被既有代码读，删掉不伤存量数据。
3. **行为层的最小回滚**（保留列，只关掉行为）：把 8 个 Controller 方法签名里的
   `@RequestHeader("X-Request-Id") @NotBlank String requestId` 撤掉即可 ——
   契约门禁会退回 8 条错误，但线上行为立刻恢复成本泳道之前的样子。
   ★ 注意这会让**前端**不受影响（它一直在发头），但 `contract-check` 立刻红。

## 7. 遗交给指挥会话的三件事

1. **`3 个 {id}/disable` 该不该声明 `X-Request-Id`**（详见 `.plan/V2-C1-契约申请.md`）：
   门禁脚本自己的规范表把"纯开关"列为**不声明**（幂等来源写的是"状态本身幂等"），
   而契约在这 3 个端点上声明了它。本泳道按指挥会话定的方向补齐了实现，
   但这个矛盾是契约内部的，不是实现能解决的。
   ★ 若将来决定从契约删掉这 3 个声明，**必须同时**撤掉实现里的 `@RequestHeader`，
   否则门禁会反向报"实现消费、契约未声明"。
