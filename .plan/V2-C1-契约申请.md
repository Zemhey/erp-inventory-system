## 申请 1（需要决断）：3 个 `{id}/disable` 到底该不该声明 `X-Request-Id`

### 矛盾在哪

`scripts/contract-check.py` 文件头的规范表（第 20~25 行）自己写着：

| 端点类型 | 特征 | 幂等来源 | 是否声明 X-Request-Id |
|---|---|---|---|
| 纯开关 | 只改 enabled 标志 | 状态本身幂等 | **不声明** |

但契约在 `POST /warehouses/{id}/disable`、`POST /suppliers/{id}/disable`、
`POST /customers/{id}/disable` 上**声明了** `#/components/parameters/RequestId`。
而同一族的 `POST /skus/{id}/disable`、`POST /products/{id}/disable` **没有**声明。

也就是说：五个语义完全相同的纯开关端点，三个声明、两个不声明，
而声明的那三个恰好是本次 8 条门禁错误里的 3 条。

### 两条路，各自的代价

- **A. 保留声明（本泳道已按此实现）**
  代价：契约的规范表与实际声明不一致，得在表里补一句
  "开关一旦声明键，就必须按 `disable_request_id` 记住归属"。
  收益：能拦住"同一个键打到两个不同资源"这类客户端 bug（本泳道的 `TC-MDM-035` → 409），
  也能让"重放不留第二条审计"有确定的判定依据。
- **B. 从契约删掉这 3 个声明**（与规范表一致）
  ★ **必须同时**撤掉实现里的 `@RequestHeader`，否则门禁反向报错
  （"实现消费、契约未声明"），错误数从 0 变 3。
  涉及文件：`WarehouseController.disable` / `SupplierController.disable` / `CustomerController.disable`
  以及 `MdmIdempotencyIT` 的 `TC-API-090/091/092`、`TC-MDM-034/035`。
  `warehouses.disable_request_id` 那 3 列可以留在 V15 里不用，但更干净的做法是连列一起去掉。

本泳道**没有**赌哪一条对，而是按指令做了 A 并把它测穿了。请指挥会话定 B 还是 A；
如果要 B，我可以出一个独立的小改动（约 3 个方法签名 + 5 条用例）。

## 申请 2（信息同步）：验收项里的"重放不重复推进单号序列"对 MDM 是恒真的

任务书写的是：给 5 个创建型端点做幂等，并断言重放**不重复推进 `document_sequences`**。

实测事实：MDM 的 5 个创建流程**从来不占单号**。
`code` 由调用方给定，由 `uq_warehouse_code` / `uq_supplier_code` / `uq_customer_code` /
`uq_product_code` 唯一约束管；SKU 连 code 都没有，靠 `uq_sku_variant (product_id, color, size)`。
整个 `com/erp/mdm/**` 里 `DocumentNumberGenerator` / `document_sequences` / `numberGenerator`
的 grep 结果为空 —— 只有 pur/sal/rma/inv/set 那 12 个单据流在占号。

所以"不推进单号序列"这条断言对 MDM 恒真，不是一条会红的防线。
我没有把它删掉（它仍然能拦住"将来有人改成用序列生成 MDM 编码"的回归），
但在 `TC-MDM-036` 里加了**正向对照**：先证明 MDM 五次写入前后指纹不变，
再直接调一次 `numbers.next(PURCHASE_ORDER, 2026-10-24)` 证明**同一个指纹真的进位时会变**。
否则这条用例是一块只会绿的死代码。

★ 请指挥会话在验收时按这个理解读 `TC-MDM-036`：它证明的是"度量本身有感知力 + MDM 不动它"，
而不是"MDM 曾经动过、现在不动了"。

## 申请 3（跨模块，建议转给 V2-5 owner）：审计不变量被有意收窄

`AuditAspect` 的既有契约是"**每个写请求恰好一条审计**"
（`AuditSafetyNetFilter` 的 Javadoc 也这么写）。但任务验收项要求
"同一 requestId 重放**不重复产生审计流水**"，且特别叮嘱"别去删审计表"——
即要合法地少写，而不是写完再删。

落地的做法是 `com.erp.shared.idem.IdempotencyReplay`（一个 request attribute 标记）：
守卫命中重放时打标记，切面读到就跳过留痕（仍写 INFO 日志）。
于是这条不变量实际变成了：**每个非重放的写请求恰好一条审计**。

三点让 blast radius 可控：

1. 标记类在 `com.erp.shared.idem`，符合架构规则
   "审计模块只依赖 shared 与 IAM 注解"（`ArchitectureTest` L577 那条）。
2. 切面的新分支**只在标记存在时生效**，而标记只有 MDM 这 8 个守卫会打。
   `pur` / `inv` 等模块今天的重放仍然留 2 条流水 —— 它们的行为一个字节都没变。
3. 跳过留痕时照样置 `AUDITED_ATTR`，所以 `AuditSafetyNetFilter` 不会补一条 FAIL；
   INV-15 完备性门禁也不受影响（它要求"每个写接口至少 1 条"，首次请求就满足了）。

**要不要把同样的收窄推广到 pur/inv**，是 V2-5 的判断，不是本泳道该做的：
它能让"重试不进审计表"成为全项目一致的语义，代价是所有模块的重试都变得不可见
（安全视角下"有人重试了 50 次"本身可能是有意义的信号）。
本泳道倾向"保持现状，只有 MDM 显式打了标记才跳过"，因为它是可选加入的、不会意外生效。
