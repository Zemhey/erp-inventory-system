## 3. `scripts/schema-field-check.py` 设计

### 3.1 五条检查（三条是任务书要求，两条是必要的配套）

| # | 检查 | 对应债 |
|---|---|---|
| ① | 全树 `$ref` 必须可解引用（`paths` + `components`） | **M** |
| ② | 请求体 schema 字段 ⇔ `@RequestBody` record 组件的字段名、必填、边界 | **H**、**L** |
| ③ | 数值 / 长度边界：契约 `minimum/maximum/minLength/maxLength/minItems` **不得宽于**实现 `@Min/@Max/@Positive/@Size/@NotEmpty` | **L** |
| ④ | 响应 `data` 的字段树 ⇔ Controller 交出去的 Map 的 `put` 键（含嵌套与数组元素） | **H** |
| ⑤ | query 参数名双向核对（契约声明 ⇔ `@RequestParam`） | 2.7 |

判据取向：**以实现为事实源，两个方向都报**。
契约缺字段 / 边界宽于实现 → 红；契约多字段 / 边界严于实现 → 也红（「契约承诺了实现没有的东西」）。

### 3.2 响应侧形状提取（本脚本的技术核心）

响应体是 Controller 里现拼的 `Map<String,Object>`，没有 DTO 可读，所以实现了一个
**只为「长什么样」服务的迷你求值器**（`EvalCtx`），认得：

| 写法 | 例子 |
|---|---|
| 信封剥壳 | `ResponseEntity.ok(ApiResponses.ok(…))`、私有别名 `ok(Object)` |
| 分页 | `ApiResponses.page(new PageResult<>(items, …))`、`ApiResponses.page(svc.page(…))` |
| 就地构造 | `Map<String,Object> m = new LinkedHashMap<>(); m.put("id", …)` |
| 合并 | `m.putAll(toTotalsMap(t.totals()))` |
| 元素循环 | `List<Map<String,Object>> lines = …; lines.add(lm); m.put("lines", lines)` |
| 流映射 | `xs.stream().map(Ctrl::toMap).toList()`、`ReportController.items(List)` |
| 常量 Map | `Map.of("items", items)` |

**读不出来的子树必须嚷出来**：进「未比对缺口」清单并计数，既不算红也不算绿。
这是防「假绿」的开关 —— 静默跳过等于给门禁开后门。当前 21 条缺口清单
（分页 `items[]` 元素形状由 service 层决定、`NlCommandResult` 是 record 载荷）逐条打印在报告里。

### 3.3 防「永绿空校验器」的三道网

1. **事实源非空断言**：解析出的 Controller 处理器 < 20 个、或 record 数异常 → 直接失败，
   拒绝以「0 错误」冒充「通过」。
2. **`--selftest` 现场注入四类漂移**（在内存副本上改，不动磁盘文件）：
   - M：塞一个指向不存在 schema 的 `$ref`；
   - H：删掉一个当前对得上的字段；
   - H（反向）：给 schema 塞一个实现没有的字段；
   - L：把一个边界放宽到实现之外。
   每条都断言「门禁真的报了这条」，并反向断言基线对这几处是干净的（否则对照失效）。
   **注入靶子取自当前真实干净的 (schema, 字段) 对**：哪天覆盖塌了，selftest 会因为
   找不到靶子而失败，而不是「注入成功但断言了个寂寞」。
3. **修复前的红**：在 `78bbb27` 的旧契约副本上跑，必须当场报出 H/L/M 各至少一条（报告 §2）。

### 3.4 风格对齐 `contract-check.py`

- Windows GBK 控制台保护（`sys.stdout.reconfigure(encoding='utf-8', errors='replace')`）；
- 退出码 0 = 通过、1 = 失败，可被 CI 直接调；
- 中文输出、`✓`/`✗` 前缀、全绿才打印「✓ 字段级契约门禁通过」那一行。
