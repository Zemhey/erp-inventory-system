## 0. 一分钟交接

V2-1 把库存从"能查、能预占、能出入库"补成**能作业**：
仓间调拨、盘点、调整、冻结、五维结存、预警、补货建议。

设计上只有两个新机制：

1. **`inventory_balances.frozen_qty`**：冻结量既不进可用量，也不能被预占/出库/调拨扣减。
   为此 V1 的生成列 `available_qty` 必须重建为 `on_hand - reserved - frozen`。
2. **六张作业表**：调拨/盘点用"单据 + 明细"，调整/冻结用"流水式记录"。
   所有数量变动仍然只经过 `InventoryApplicationService`（ADR-0007），
   新增的 `InventoryOperationsApplicationService` 只做取号、幂等与状态推进。

五维/预警/补货是**纯只读查询**，不落"建议表"：补货建议的幂等由"不写任何表"直接保证；
"已下单未到货不重复建议"通过只读查询 `purchase_orders` 的未收数量实现
（只读跨域，不 import PUR 类，避免包依赖环）。

**基线**：main `a4c4149` 的后端基线为 `234 tests / 0 failures`，
行覆盖 **80.5%**（2983/3704）/ 分支 **58.7%**（708/1207），契约 39 路径 / 50 操作 / 40 schema。
本泳道验收不得低于这组数字。

## 2. 技术方案

### 2.1 模块与依赖

```
api:         InventoryOperationsController  (transfers/stocktakes/adjustments/freezes)
             InventoryInsightController     (balance-dimensions/alerts/replenishment)
application: InventoryOperationsApplicationService  —— 取号/幂等/状态推进/事务边界
             InventoryInsightApplicationService     —— 只读聚合与 ClockProvider 边界
             InventoryApplicationService            —— 库存数量唯一入口（新增 adjust/transferOut/In/freeze/unfreeze）
domain:      TransferStatus / StocktakeStatus / FreezeStatus / StockStatus / Ownership / AlertType
             InventoryTransfer / TransferLine / Stocktake / StocktakeLine /
             InventoryAdjustment / InventoryFreeze / InventoryAlert / ReplenishmentSuggestion
repository:  InventoryTransferRepository / StocktakeRepository /
             InventoryAdjustmentRepository / InventoryFreezeRepository /
             InventoryInsightRepository（只读）
```

**依赖方向**：`api → application → repository`，不新增反向依赖。
洞察仓储只读 `purchase_orders` 表判断"已下单未到货"，不 import `com.erp.pur.*`。

### 2.2 数据模型（`V9__inventory_operations.sql`）

| 表 | 关键约束 |
|---|---|
| `inventory_transfers` | `from <> to`；`COMPLETED ⇔ received_at 非空`；`request_id` / `receive_request_id` 部分唯一索引 |
| `transfer_lines` | `0 <= in_transit_qty <= qty`；`(transfer_id, sku_id, batch_no)` 唯一；批次日期快照 |
| `stocktakes` | `POSTED ⇔ posted_at 非空`；`request_id` / `post_request_id` 部分唯一 |
| `stocktake_lines` | `diff_qty` 生成列 `counted - book`；`(stocktake_id, sku_id, batch_no)` 唯一 |
| `inventory_adjustments` | `change_qty <> 0`；`length(btrim(reason)) > 0`；`request_id` 唯一 |
| `inventory_freezes` | `qty > 0`；`ACTIVE ⇔ released_at 为空`；`request_id` / `release_request_id` 唯一 |

余额改造顺序（同一事务）：

```sql
ALTER TABLE inventory_balances ADD COLUMN frozen_qty INTEGER NOT NULL DEFAULT 0 CHECK (frozen_qty >= 0);
ALTER TABLE inventory_balances DROP COLUMN available_qty;
ALTER TABLE inventory_balances ADD COLUMN available_qty INTEGER
    GENERATED ALWAYS AS (on_hand_qty - reserved_qty - frozen_qty) STORED;
ALTER TABLE inventory_balances ADD CONSTRAINT ck_frozen_reserved_le_onhand
    CHECK (reserved_qty + frozen_qty <= on_hand_qty);
```

同时收紧三个既有 SQL：

- `tryReserve`：`reserved_qty + ? <= on_hand_qty - frozen_qty`；
- `decreaseOnHand`：`reserved_qty + frozen_qty <= on_hand_qty - ?`；
- `freeze/releaseFrozen`：条件更新保证 `frozen + reserved <= on_hand`。

### 2.3 调拨：两段式与守恒（INV-7）

1. `POST /inventory/transfers`：取号 → 插单头（`IN_TRANSIT`）→ 逐行
   `decreaseOnHand` + `TRANSFER_OUT` 负流水 → 明细 `in_transit_qty = qty`。
2. `POST /inventory/transfers/{id}/receive`：条件更新 `IN_TRANSIT → COMPLETED` →
   逐行 `increaseOnHand`（目的仓，带原批次效期）+ `TRANSFER_IN` 正流水 →
   `in_transit_qty = 0`。

守恒式用查询实现，不在代码里写死：

```
ledgerNet(transferNo) + Σ in_transit_qty == 0
ledgerNet = Σ(TRANSFER_OUT) + Σ(TRANSFER_IN)
```

每次到货响应都带 `conservationDiff`；测试在"仅发运 / 已到货 / 多行多批次 / 交错到货"
四个时点断言它为 0。

### 2.4 盘点：快照 + 差异过账

- 建单：对每行读当前 `on_hand_qty` 存为 `book_qty`，实盘数存 `counted_qty`；
  `diff_qty` 由数据库生成列计算。
- 过账：状态条件更新 `DRAFT → POSTED`，随后只对 `diff != 0` 的行调用
  `inventory.adjust(diff)`，流水来源单号为盘点单号。
- `diff = 0` 的行不写流水；整单全 0 抛 `INV_STOCKTAKE_NO_DIFFERENCE`，
  状态保持 DRAFT（不留"过账了但什么都没调整"的空单）。
- 盘亏若会把实存压到预占/冻结以下，条件扣减失败 → 整单回滚（状态与流水一起退）。

### 2.5 调整与冻结

- 调整：原因 service 层与 Bean Validation 双重必填；`change_qty` 有符号且非 0；
  正数允许建余额行（期初建账），负数走条件扣减。
- 冻结：只改 `frozen_qty`，不写流水（INV-2 只约束实存）；
  `POST /freezes` 可选 `expiresAt`，到期由 `expireOverdueFreezes()` 用注入时钟判断；
  方法挂在既有 `ReservationExpiryScheduler` 上，复用同一个开关与调度线程。

### 2.6 五维 / 预警 / 补货

- **五维**：余额按状态拆成 AVAILABLE / RESERVED / FROZEN 至多三行；
  数量为 0 的状态不出行；`totals.byStatus` 与 `totals.onHandQty` 一并返回。
  权属当前只有 SELF；`CONSIGNMENT` 查询显式 400，不静默降级。
- **预警**：
  - 安全库存：`SUM(available_qty) < skus.min_level`（按 SKU+仓库）；
  - 临期：`expiry_date <= today + N`（`today` 来自 ClockProvider）；
  - 滞销：最后出库时间（无出库则取第一条流水）早于 `now - N`；
  - 排序按 `warehouses.priority DESC`，让高优先级仓先被看到。
- **补货**：可用量 < min 时建议补到 max；存在 `APPROVED/PARTIAL` 且
  `qty > received_qty` 的进货行时整条建议跳过。纯查询、不落表，天然幂等。

## 5. 已知坑与规避

| # | 坑 | 规避 |
|---|---|---|
| 1 | **部分唯一索引的 `ON CONFLICT` 必须带 `WHERE`**：`request_id` 唯一索引是部分索引，`ON CONFLICT (request_id)` 会报 "no unique or exclusion constraint matching" | 写 `ON CONFLICT (request_id) WHERE request_id IS NOT NULL DO NOTHING`（调拨/盘点） |
| 2 | **改生成列必须删列重建**：PostgreSQL 不能直接改生成表达式 | V9 先加 `frozen_qty`，再 `DROP COLUMN available_qty` 后重建；同迁移同事务 |
| 3 | **冻结让既有 SQL 的可用量口径改变**：只改生成列不够，`tryReserve`/`decreaseOnHand` 的条件也必须加 `- frozen_qty` | 三处 SQL 一起改；用 062/027 用例守 |
| 4 | **盘点过账的幂等键不能与调整流水共用**：同一次过账会拆成多条流水 | `scopedRequestId(base, ":L" + lineNo)`，并截断到 64 字符 |
| 5 | **补货的"已下单未到货"不能只按单据状态排除**：APPROVED 但已收满的单不应继续挡住建议 | 条件用 `pol.qty > pol.received_qty`，测试 084 覆盖 |
| 6 | **滞销判断的时钟**：`occurred_at` 是 timestamptz，注入时钟写入后读回可能带时区偏移 | 比较时用 `OffsetDateTime.toLocalDateTime()`，边界留 ≥1 天余量（89/100 天） |
| 7 | **测试库复用容器的 Flyway**：新迁移会在复用容器上顺序执行；若失败应用起不来 | 首次跑新用例先确认 `V9` 成功；失败时看 Flyway 报错而不是猜 SQL |
| 8 | **并行构建争抢**：多条泳道共用 Gradle 用户目录，构建可能排队数分钟 | 单次跑目标用例集；全量 check 放最后；不杀别人的 daemon |
| 9 | **前端 `TEMP/TMP`**：宿主默认 TEMP 下 esbuild 偶发 `Access is denied` | 构建前 `TEMP/TMP=frontend/web/.tmp` |
| 10 | **调拨流水唯一索引**：同一 `request_id` + `TRANSFER_OUT` + 同批次只能一条流水 | 调拨单内禁止重复 `(sku,batch)`；测试 032 守 |

### 7.5 已知限制与未决风险

1. **权属维度只有 SELF**：`Ownership.CONSIGNMENT` 已建模但查询显式拒绝（400）。
   当前没有寄售库存的数据来源（任务允许的加列清单里也没有 ownership 列），
   与其静默当成自有，不如拒绝；接入寄售时需补列与业务规则。
2. **补货阈值没有管理界面**：`skus.min_level/max_level` 与 `warehouses.priority`
   已落库并被查询使用，但本批未改 MDM 的 SKU/仓库接口与页面，运营暂时只能由 DBA 维护。
3. **调拨无取消/红冲**：只会 `IN_TRANSIT → COMPLETED`；取消需要新的补偿规则，未在本批范围。
4. **安全库存只对已有余额行的 (SKU, 仓库) 预警**：从未建过账的仓库不会提示，
   系统没有"SKU 在哪些仓铺货"的主数据，这是当前最合理的近似。
5. **构建环境的网络问题**：Gradle 插件仓库探测在本机偶发挂起，本次用 `--offline` 完成；
   若 CI/新机器缺少依赖，需先联网完成一次正常解析。
6. **基线 check 曾被打断**：首次基线运行期间 Gradle daemon 被外部清理误杀（指挥已告知），
   基线数字采用 main 批次报告（234 tests / 80.5 / 58.7）与本次全量实测对比。
